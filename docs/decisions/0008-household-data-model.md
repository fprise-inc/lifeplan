# 0008. 世帯のデータモデル

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。世帯ファイルの形式は「安定」の公開の約束で、変えるときは一方向の自動変換を必ず添える（0011）

## 背景

- 世帯ファイル（0011）の中身のうち、構成員・働き方・プラン・目標・資産・負債・保険・前提条件・上書き・値の状態は、計算部品・画面・ヒアリング・移行・AI接続口・書き出しのすべてが頼りにする。後から形を変えると、万一・年金・社会保険・税・取り崩しの計算と、承認画面・取り込みの作り直しになり、既存のプランの数字も変わる。
- 日本のFP実務では、次のことを表せないと業務に使えない。
  - 夫婦それぞれの働き方の移り変わり（正社員→育休→時短→退職→パート、定年→再雇用など）と、そこから決まる被保険者の種別（第1〜3号）。
  - 「現状」と「提案」の差を1件ずつON/OFFして見せること。見直しのたびに前回の現状と比べること。
  - 「この年に亡くなったら」を1年ずつずらす万一の計算。
  - NISAの枠（簿価で管理し、売却の翌年に復活）、ペアローン・連帯債務、団信、保険の契約者・被保険者・受取人の違いによる課税区分。
  - 分からない値・推定した値と、確定した値の区別。誰がどこから入れた値か。
- 顧客の氏名は持たない（0012）。暗号化と鍵は 0013、同意とAIに渡した記録は 0014、控えは 0009、ファイルの封筒・自己完結・拡張領域は 0011、IDの命名は 0004、時間の規約は 0003、金額と率は 0002 で定める。

## 決定

### 1. 共通の決まり

- **物には乱数のIDを振る**（0004の「世帯内の物のID」）。構成員・働き方の期間・口座・負債・保険契約・目標・イベント・差分・候補のすべて。IDは変えない・使い回さない。IDの書き方は UUID 第4版（0004）。この記録の例では読みやすさのため `"<構成員A>"` のように書く。物が自分のIDを持つ欄は `id`、他の物を指す欄は、指す先の名前（`member`・`object`・`candidate`）か役割の名前（`owner`・`policyholder`・`insured`）にする（0003・0004の例に合わせる）。
- 名義・当事者は、必ず**構成員ID**で指す（資産・負債・収入・保険の契約者・被保険者・受取人）。
- 時点は 0003 の「時点の型」で書く（絶対の年月、「構成員Xが○歳になった月」、「イベントYの年月＋n年」）。計算の前に絶対の年月へ解決し、解決結果は根拠の記録に残す。
- 金額は「通貨＋最小単位の整数」、率は10進の文字列（0002）。
- **入力値と計算結果（参照値）を分ける**（0004）。世帯ファイルの入力の区画には、計算結果を入れない。移行元のソフトが計算した値は、取り込みの記録に参照値としてだけ持つ。

### 2. 値の箱（値の状態・出どころ・承認の記録）

入力項目ID（0004）を持つすべての入力値は、次の「値の箱」で持つ。値だけを裸で書く省略形は作らない（読み手が1種類の形だけを扱えばよいように）。

```json
{
  "value": 4800000,
  "state": "confirmed",
  "origin": {"kind": "hearing", "ref": "<取り込みの記録>"},
  "approval": {"by": "fp", "at": "2027-03-02T10:15:00+09:00", "candidate": "<候補>"}
}
```

- `state`（値の状態）は4つ:
  - `confirmed`（確定）
  - `unknown`（わからない）: 計算には代わりの値 `substitute`（値の箱の入れ子。状態は `estimated`）を使う。画面で目立たせ、面談チェックリストに自動で載せる。
  - `notApplicable`（該当なし）: `value` を持たない。計算では「無い」として扱う。
  - `estimated`（推定）: `estimate: {method, basis}` を必須にする。`method` は `statistic`（統計の値）・`derived`（他の値からの逆算）・`officeDefault`（事務所のひな形）など。`basis` には統計名と年度、または逆算に使った値の入力項目IDを書く。
- `origin.kind`（出どころ）: `manual`（手入力）、`hearing`（ヒアリングシート）、`import`（移行）、`ai`（AIの案）、`auto`（自動で入った既定値）、`override`（上書き。下記7）。`ref` は取り込みの記録・候補などのID。`ai` のときは接続先の名前も持つ。
- `approval`: 外から来た値（ヒアリング・移行・AI）は、FPが承認した記録を必ず持つ。`by` は `fp` だけ（AIは承認できない）。手入力の値は `approval` を持たなくてよい。
- 各計算部品は、入出力の約束（0006）の中に「与えられたらこの値を使う」置き換え口を持つ（例: ねんきん定期便の見込額、ローンの返済額の直接入力、手取りの直接入力）。置き換え口に入った値も値の箱で持つ。
- **キャッシュフロー表のセルの手修正**は、プランごとに入力値と別の区画（`manualCells`）に、`{row, year, member?, object?, amount, reason, at}` で持つ（キーは `row`・`year`・`member`／`object` の組、`amount` は円の整数。形は0004と同じ）。根拠には「FPの手修正」と出す。

### 3. 構成員

```json
{
  "id": "<構成員A>",
  "kind": "self",
  "birth": {"birthYearMonth": "1981-04", "bornOnFirst": false},
  "sex": "female",
  "joins": null,
  "leaves": null,
  "expected": false
}
```

- `kind`（家族の種類）: `self`（本人）、`spouse`（配偶者）、`child`、`parent`、`grandparent`、`other`。続柄の文字（長女・義父など）は保存せず、関係から計算して表示する。
- 生年月日は「生年月＋1日生まれか」（0012）。性別は持つ（遺族年金の経過措置などの計算に使う）。
- **関係**は構成員の外に、辺の一覧として持つ: `{"type": "spouse", "a": "<構成員>", "b": "<構成員>", "marriage": "legal" | "deFacto", "from": 時点, "to": 時点}`、`{"type": "parentOf", "parent": "<構成員>", "child": "<構成員>"}`。子がどの親の子かはこれで表す。
- 世帯にいる期間は `joins` / `leaves`（時点。null は最初から・最後まで）。**まだいない家族**（出産予定・結婚予定）は `expected: true` と `joins` で表す。
- 親・祖父母には `{dependent, cohabiting, allowance, care}`（扶養・同居か別居か・仕送り・介護）を持たせる。
- **死亡は構成員の属性に持たない**。万一の想定の層（下記5）の「対象者と発生年月」としてだけ表す。
- 年ごとの役割（主たる生計維持者、扶養、第3号被保険者）は保存せず、計算で導く。
- 離婚・再婚・世帯の分割と統合はデータで表せるようにしておく（画面は次の版）。分割・統合では新しい世帯IDを振り、世帯の `lineage: [{"householdId": "…", "relation": "splitFrom" | "mergedFrom", "at": "…"}]` に系譜を残す。
- 表示期間の標準は、全構成員のうち最も長く表示が必要な人が100歳になるまで（プランの設定で変えられる）。

### 4. 人ごとの働き方の期間

構成員ごとに `employmentPeriods` の列を持つ。期間は重ならない（休業は期間を分けて表す）。

```json
{
  "id": "<期間>",
  "member": "<構成員A>",
  "from": {"at": "2027-04"},
  "to": {"event": "<退職のイベント>"},
  "type": "regular",
  "healthInsurance": {"kind": "kyokaikenpo", "insurer": "kyokaikenpo.13"},
  "pensionCategory": "employee1",
  "employer": {"size": 120, "weeklyHours": "40"},
  "salary": {"annual": {…値の箱…}, "bonus": {…}, "growth": {"curve": "wageStats.default"}},
  "retirementBenefit": "<退職給付>",
  "endsWith": "retirement"
}
```

- `type`: `regular`（正社員）、`contract`、`partTime`、`selfEmployed`、`civilServant`、`leave`（`leaveKind: maternity | childcare | sick | other`）、`unemployed`。法人役員は次の版で足す（値の追加として扱う）。
- `healthInsurance.kind`: `kyokaikenpo`（支部のIDつき）、`union`（健保組合）、`mutualAid`（共済）、`national`（国民健康保険）、`dependent`（家族の扶養）、`continuation`（任意継続）、`lateElderly`。健保組合・共済の料率は世帯ごとの入力（給与明細の保険料からの逆算も可）で、上書きの範囲②（下記7）に置く。
- `pensionCategory`: `employee1`〜`employee4`（厚生年金の種別）、`none`。**第1〜3号の被保険者の種別は入力させず、エンジンが各月について導く**（例: 夫が60歳で退職すると60歳未満の妻は第3号でなくなる）。
- 適用拡大の判定のため、勤務先の従業員数と週の所定労働時間を持つ。
- 典型的なつながり（正社員→育休→時短→退職→パート、60歳定年→再雇用→65歳以降パート）は、事務所のひな形（0011）から期間の列として作る。

### 5. 現状・プラン・差分・候補（プランの4層）

- **現状**（`currentVersions`）: 基準日（`asOf`）つきの版の列。見直しのたびに新しい版を積み、古い版は変えない（前回との比較用）。各版が、構成員・働き方の期間・収入・支出・口座・負債・保険契約・目標とイベント・上書き（範囲②④の世帯の範囲）を持つ。
- **プラン**（`plans`）: `{id, baseVersion（現状の版のID）, baseMonth（計算基準日。`"YYYY-MM"`。0003）, dataSet（使う制度・マスタのデータの組の版。0009）, assumptions（下記8）, proposals, contingencies, settings, customModules（使ったカスタムの指紋）}`。
- **提案**（`proposals`）: 複数持てる。1つの提案は差分の列で、差分は1件ずつON/OFFできる。前提条件の変更も差分の一種。
- **万一の想定**（`contingencies`）: `{id, kind: "death" | "disability" | "incapacity", member, occurs: 時点, grade?（障害等級。仮定としてだけ）}`。現状や提案の上に重ねる層。必要保障額の推移は、`occurs` を1年ずつずらした連続計算で出す（層の側には1件だけ持つ）。
- **候補**（`candidates`）: 外から来た案（ヒアリング・移行・AI）。差分と同じ形で受け、承認されるまで現状にもプランにも効かない。

**差分と候補の共通の形**

```json
{
  "id": "<差分>",
  "target": {"object": "<ローン>"},
  "item": "loan.prepayment.amount",
  "op": "set",
  "value": {…値の箱…},
  "before": {…差分を作った時点の値の箱…},
  "enabled": true,
  "origin": {"kind": "manual"},
  "note": null
}
```

- `target` は `{"object": 物のID}`、`{"member": 構成員ID}`、`{"plan": "assumptions"}` のいずれか。`item` は入力項目ID。
- `op`: `set`（値を変える）、`add`（物を足す。`value` に物の全体）、`remove`（物を外す）。
- 候補は、このほかに `{source: "hearing" | "import" | "ai", sourceRef, status: "pending" | "accepted" | "rejected" | "needsReview", confidence?}` を持つ。
- **要確認**: 現状を更新して、差分・候補の `target` が無くなったとき、または `before` が今の値と食い違うとき、その差分・候補を `needsReview` にして画面に出す（黙って当てはめない）。
- 「プランを複製して1つ変える」操作は、プランの複製として作る（差分の層と並ぶ入口。データの形は同じ）。

### 6. 目標の二重の表現

- **正本は目標の物**（`goals`）の1つだけにする: `{id, kind: "education" | "housing" | "retirement" | "other", priority: "need" | "want" | "wish", owner?, when: 時点, amount or 内訳, links}`。教育の目標は子・進路・学校（0010）を持つ。
- キャッシュフロー表の行は目標から**生成する見せ方**で、目標の物を保存し直さない。
- 表の側で、目標から生成された行を直したときは、その行が目標のどの項目に対応するかの対応表（行ID→入力項目ID）で**目標の値の変更に変換**して保存する。対応できない直し方（目標の一部の年だけを直すなど）は、手修正（上記2）として保存し、印を出す。
- これにより、目標カードと表のどちらで直しても、もう一方が追従する。

### 7. 上書きの4つの範囲と決まり方の順番

| 範囲 | 置き場所 | 例 |
|---|---|---|
| ① 事務所全体の標準 | 事務所データ（0011） | 前提条件の標準値、帳票の文言 |
| ② 世帯・構成員の事実 | 世帯ファイルの現状 | 健保組合の料率、国保の上書き、勤務先の退職金規程 |
| ③ プランの前提 | 世帯ファイルのプラン | 物価上昇率、運用利回り、年金の将来額の方式 |
| ④ 制度の値の上書き | 世帯ファイル（範囲は世帯かプランを選ぶ。既定はプラン） | 特定の控除額の仮定 |

- **計算時の決まり方の順番**: 公式（プランの `dataSet` の値）→ ② → ④（世帯の範囲）→ ③ → ④（プランの範囲）→ 万一の重ね。後のものが前のものに勝つ。
- ①は、プランを作るときに③へ写すためだけに使う。計算のときに①が直接効くことはない。
- 上書きの記録: `{id, scope: "household" | "plan", target: {param: 制度の値ID} または {object, item}, value, officialAtTime: {valueRef: "<値ID>@r<rev>", value}, dataSetAtTime, appliesFrom, appliesTo, jurisdiction, reason, by: "fp" | "ai"}`。公式が変わったら「当時の公式／今の公式／上書きした値」の3つを並べて見せる。
- 構成員の勤め先に保険者のID（協会けんぽの支部か健保組合か）、世帯に市町村コードを持たせる。住所そのものは持たない。

### 8. 前提条件は年ごとの列、標準値は写す

- 前提条件はプランごとに持ち、**すべて年ごとの列の型**（0006）で持つ（定数はその特別な場合）:
  ```json
  {"inflation": {"default": "0.015", "byYear": {"2030": "0.02", "2031": "0.02"}}}
  ```
- 前提の項目の例: 物価上昇率、賃金上昇率、資産クラスごとの利回り、教育費の上昇率、為替レート、年金の将来額の方式、期限つき特例の延長の仮定、`proposed` の制度をシナリオとして使うか（0007）、計算方式の設定（期首／期末、年齢の基準日など。0003）。
- 事務所の標準値は、**プランを作るときにプランへ写す**。写したことを `copiedFrom: {officeDefaultsDigest, at}` で残す。事務所の標準値を変えても作成済みのプランは変わらない。
- 移行したプランは、移行元の前提をそのまま写して持つ。

### 9. 資産の器

```json
{
  "id": "<口座>",
  "kind": "nisa",
  "owner": "<構成員A>",
  "marketValue": {…値の箱…},
  "costBasis": {…値の箱…},
  "asOf": "2027-03",
  "assetMix": [{"assetClass": "equity.global", "share": "0.8"}, {"assetClass": "bond.domestic", "share": "0.2"}],
  "withdrawalLockedUntil": null,
  "contributions": [{"from": 時点, "to": 時点, "monthly": 50000, "tranche": "tsumitate"}]
}
```

- `kind`: `deposit`、`taxable`（課税口座）、`nisa`、`juniorNisa`、`childNisa`、`legacyNisa`（旧NISA）、`ideco`、`corporateDc`、`zaikei`（財形）、`esop`（持株会）、`fxDeposit`、`insurance`（保険の積立部分は保険契約から導く）、`realEstate`。
- 時価と取得価額を分けて持つ（課税口座の譲渡益の税、NISAの枠の計算に使う）。
- **NISAの枠**: 1人1つのNISAの器に、`frame: {lifetimeUsedCost, growthUsedCost, asOfYear}`（現在消化している枠を簿価で）を持つ。年ごとの買付・売却はエンジンが簿価で計算し、**売却した簿価分の枠は翌年に復活**させる。枠の上限額は制度データ（`nisaIdeco` パック）から読む。旧NISA・ジュニアNISAは、非課税期間の終わりを判定するため `lots: [{vintageYear, costBasis, marketValue}]` を持つ。
- 引き出せない期間（iDeCo・企業型DCなど）は `withdrawalLockedUntil` か、制度から導く。
- 資産クラスは公式の一覧のIDで指す。期待リターンは資産クラス単位の前提値で、個別の商品の過去の成績は使わない。

**負債の共通の型**（住宅ローン・車・奨学金・その他）

```json
{
  "id": "<ローン>",
  "kind": "mortgage",
  "debtors": [{"member": "<構成員A>", "role": "primary", "share": "0.6"}, {"member": "<構成員B>", "role": "joint", "share": "0.4"}],
  "principal": 40000000,
  "balance": {…値の箱…},
  "balanceAsOf": "2027-03",
  "rateSchedule": [{"from": 時点, "type": "variable", "rate": "0.0075"}],
  "repayment": {"method": "equalPayment", "termMonths": 420, "bonusShare": "0", "variableRules": {"fiveYear": true, "cap125": true}},
  "prepayments": [{"at": 時点, "amount": 3000000, "mode": "shortenTerm"}],
  "creditLife": {"covered": ["<構成員A>"], "ratio": "1.0", "events": ["death", "cancer"]},
  "housing": {"residenceStartYear": 2027, "propertyType": "newCertified", "ownership": [{"member": "<構成員A>", "share": "0.6"}]}
}
```

- `role`: `primary`（主債務者）、`joint`（連帯債務）、`guarantor`（連帯保証）。ペアローンは2本の負債として持ち、`pairWith` で互いを指す。
- `housing` は住宅ローンだけが持つ拡張で、住宅ローン控除を人ごと・持分で按分する計算に使う。
- 返済は月単位で計算して年に集計する（0003）。

### 10. 保険契約の形と年次の数表

```json
{
  "id": "<保険契約>",
  "template": "insurance.wholeLife",
  "policyholder": "<構成員A>",
  "insured": "<構成員A>",
  "beneficiaries": [{"member": "<構成員B>", "share": "1.0"}],
  "contractDate": "2015-06",
  "currency": "JPY",
  "premium": {"amount": 18000, "frequency": "monthly", "payUntil": {"memberAge": {"member": "<構成員A>", "years": 65, "months": 0}}},
  "waiver": true,
  "renewals": [],
  "deductionCategory": {"type": "general", "regime": "new"},
  "coverages": [
    {"id": "<補償>", "role": "main", "benefit": "death", "amount": 10000000, "from": 時点, "to": 時点},
    {"id": "<補償>", "role": "rider", "benefit": "hospitalDaily", "amount": 10000, "from": 時点, "to": 時点}
  ],
  "schedule": {"source": {"productRef": "<商品集の数表>", "digest": "sha256:…"}, "rows": [
    {"coverage": "<補償>", "policyYear": 1, "premium": 216000, "deathBenefit": 10000000, "surrenderValue": 0, "annuity": 0, "survivalBenefit": 0}
  ]}
}
```

- 契約者・被保険者・受取人は構成員IDで持つ（構成員でない受取人は `{"external": "relationKind"}`）。この組み合わせで、死亡保険金（相続税の非課税枠／一時所得／贈与税）・満期金・解約返戻金・個人年金の課税区分を税の部品が判定する。
- `template` は保険の種類ごとの公式のひな形（定期・収入保障・終身・医療・がん・学資・個人年金・外貨建・変額）。
- **年次の数表**は主契約・特約（`coverage`）ごとの時系列。金額は契約の通貨の最小単位。数表を事務所の商品集から持ってきたときは、商品集のIDと指紋を `schedule.source` に写す（商品集を直しても既存の世帯は変わらない。0011）。
- 設計書の数表が無いときの簡易入力（解約返戻金を返戻率で、保険料を年齢ごとの行で）は、数表の行を生成する入力の型として持つ。

## 理由

- **値の箱を省略形なしで統一**: 公開する形式を読む人・AI・移行先が、状態と出どころの有無で分岐しなくて済む。容量の増加は世帯1つあたり小さい。
- **被保険者の種別・役割・続柄を保存しない**: 保存すると、働き方の期間や構成員を直したときに食い違いが残る。導ける情報は導く。
- **死亡を構成員の属性にしない**: 必要保障額の推移のように同じ世帯で「死亡の年」を何十通りも試すので、層として重ねる形にしないと計算できない。
- **差分と候補を同じ形にする**: ヒアリング・移行・AIの案を、提案と同じ承認画面・同じ取り込み処理で扱える。`before` を持つことで、現状が変わったときの食い違いを機械で見つけられる。
- **目標の正本を1つにする**: 2つの表現を別々に保存すると、どちらが正しいか決められなくなる。
- **前提を年ごとの列にする**: ストレステストや将来の確率的な計算（次の版）で作り直さずに済む。
- **標準値を写す**: 事務所の設定を変えたら過去のプランの数字が変わる、という事態を防ぐ。
- **NISAを簿価の枠で持つ**: 枠の復活は売却した簿価で決まるので、時価だけでは計算できない。
- **負債を共通の型にする**: 車・奨学金・住宅ローンの返済計算と、取り崩し・資金不足の判定を同じ部品で扱える。住宅ローンに固有の部分だけを拡張に分ける。

## 影響

- 後から変えると: 万一・年金・社会保険・税・取り崩しの計算、承認画面、ヒアリングと移行の取り込み、AI接続口の道具、書き出しがすべて作り直しになる。前提と上書きの扱いを変えると既存のプランの数字が変わる。
- 守るべき決まり:
  - 入力の区画に計算結果を入れない。導ける値（被保険者の種別・役割・続柄）を保存しない。
  - 外から来た値は候補を通し、FPの承認の記録なしに現状へ入れない。
  - 上書きの決まり方の順番は、エンジンの1か所（組み立て役）だけで実装する。計算部品が独自に上書きを探さない。
  - 名義・当事者は構成員IDで指す。氏名や続柄の文字を保存しない。
- テストで確かめること:
  - JSON Schema の検査（値の箱が必須の項目に裸の値が入っていないか）。
  - 被保険者の種別の導出（夫の退職・65歳到達で妻の第3号が切れる、など）の性質のテスト。
  - 決まり方の順番: 同じ項目に①〜④と万一の重ねを入れ、勝つ値が順番どおりか。
  - 差分の `before` と今の値の食い違い、`target` の消失で `needsReview` になるか。
  - 目標カードと表の行の往復（カードを直す→表、表を直す→カード）で値が一致するか。
  - NISAの枠: 売却した簿価分が翌年に復活し、枠を超えて買付しないか。
  - 事務所の標準値を変えても、作成済みのプランの計算結果が変わらないか。

- 退職給付（退職一時金・確定給付企業年金・企業型DC・iDeCo・小規模企業共済・公務員の制度）の共通の型の細部。差し込み口「退職給付の規程」（0006）の入出力と合わせて決める。
- 口座の `kind`・保険の `template`・資産クラスの正式な一覧。
- 「わからない」の代わりの値を、計算のたびに統計から入れ直すか、入力時に固定するか。
- 構成員でない受取人・債務者（世帯外の親族など）の表し方の細部。
- 現状の版を積むときに、前の版から何を引き継ぎ、何を空にするか。
