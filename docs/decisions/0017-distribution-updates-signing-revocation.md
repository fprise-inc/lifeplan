# 0017. 配布・更新・署名・取り下げ

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: アプリの識別子、署名の名義、配布元の設定の1か所化、更新の4経路、自動通信の相手を1つに限ること、データパックにプログラムを入れないこと、署名鍵の役割の分け方と「現用＋次期」の埋め込み、取り下げ・最低版の仕組みは β公開から変えない（骨格）。配信の URL の細部（`/v1/` の下の構成）は版を上げて変えられる

## 背景

ファイナンシアは、FPのPCで動くデスクトップアプリ（Windows・Mac）として配り、計算エンジン・制度データ・学費などを更新し続ける。配布済みのアプリに更新を届けられなくなること、偽の更新を受け入れること、誤りが見つかった値で提案書を作り続けさせることは、どれも後から直せない。そのため、最初の版から次を固定する。

- どの名前・どの名義で配るか
- 何を、どの経路で、どの鍵で署名して届けるか
- アプリがどこと通信するか
- 誤りが見つかったときに、配布済みのアプリへどう知らせ、止めるか

関連: 制度データの形式は 0007、控え・取り下げの単位・PDFの刻印は 0009、学費データは 0010、世帯ファイルの形式移行は 0011、識別と持たない情報は 0012、AI接続口（同梱の実行ファイル）は 0015、ライセンスとリポジトリは 0021、自動化と自動配信の範囲は 0022。

## 決定

### 1. 識別子と署名の名義

- アプリの識別子は **`com.fprise.lifeplan`**。製品名に依存させない。
  - Tauri の `identifier`、Mac のバンドルID、Windows のアプリの識別、データ・設定・作業フォルダの名前（例: `~/Library/Application Support/com.fprise.lifeplan/`、`%LOCALAPPDATA%\com.fprise.lifeplan\`）、OS の資格情報の保管庫の項目名に使う。
  - 識別子を変えると、更新が届かなくなり、データの置き場所が切れる。製品名を変えても識別子は変えない。
- 署名の名義は **FPRISE, INC.**。
  - Mac: Apple Developer Program（法人）の Developer ID で署名し、公証（notarization）する。hardened runtime を有効にする。同梱する実行ファイル（AI接続口 `lifeplan`。0015）も同じ名義で署名・公証する。
  - Windows: Authenticode で、発行元が FPRISE, INC. と表示される署名をする。方式（Azure Artifact Signing か、組織の証明書か）は未確定。
- 配り方: Windows は管理者権限の要らないユーザー単位のインストーラー（NSIS）と、企業向けの MSI。Mac は Intel・Apple シリコン両対応の dmg。アプリのストアには出さない。
- 「公式版」とは FPRISE, INC. の署名があるビルドのこと。フォークのビルドは「公式」の表示を出さない。

### 2. 配布元の設定を1か所にまとめる

- 次をリポジトリの1つのファイル（`config/distribution.toml`）にまとめ、ビルドのときに読み込む。Tauri の設定（`tauri.conf.json` の識別子・更新の公開鍵・配信先）は、このファイルから生成する。

  ```toml
  identifier   = "com.fprise.lifeplan"
  product_name = { ja = "ファイナンシア", en = "Financia" }
  publisher    = "FPRISE, INC."

  [endpoints]               # 自動通信の相手はこのホストだけ
  host = "updates.fprise.com"
  app      = "https://updates.fprise.com/v1/app/latest.json"
  packs    = "https://updates.fprise.com/v1/packs/index.json"
  notices  = "https://updates.fprise.com/v1/notices/notices.json"
  revocations = "https://updates.fprise.com/v1/revocations/revocations.json"

  [keys]                    # 公開鍵（それぞれ現用＋次期）
  app_update   = ["<現用>", "<次期>"]
  data         = ["<現用>", "<次期>"]
  auto_delivery = ["<現用>", "<次期>"]
  revocation   = ["<現用>", "<次期>"]
  ```

- フォークは、このファイルを書き換えるだけで、識別子・名前・配信先・鍵を自分のものにできる（フォーク向けの手順は SDK に置く。0019）。公式の制度データパックだけを受け取り続けることもできる（データの配信先と鍵を公式のままにする）。
- CI で、識別子・配信先のホスト名・公開鍵がこのファイル以外に直接書かれていないことを検査する。

### 3. 更新の4経路

| 経路 | 中身 | 署名する鍵 | 仕組み |
|---|---|---|---|
| アプリ本体 | 画面、計算エンジン、帳票の型、SDK、AI接続口 | アプリ更新用 | Tauri の updater（署名なしは受け付けない。古い版への戻しは禁止） |
| 制度データパック（分野ごと） | 税・社会保険・年金・NISA/iDeCo・住宅・教育の支援 | データ用、または自動配信用 | 目録（`index.json`）＋パック。0007 の形式 |
| マスタデータパック（提供元ごと） | 学費、投資信託の一覧、簡易生命表 | データ用 | 同上。提供元・許諾ごとに分ける（0010・0021） |
| お知らせ・取り下げ | 告知、取り下げの一覧、アプリの最低版 | お知らせはデータ用、取り下げ・最低版は取り下げ用 | 署名した JSON |

- **データパックにプログラムを入れない**。中身は宣言型の値と表だけ。0007 の「計算式」の種類の値も、決まった文法の宣言に限り、実行できるコードにはしない。計算方法が変わる改正は、アプリ本体の更新（計算部品の改訂）で届ける。
- パックは、必要な計算部品の約束の版（0006）を宣言する。足りなければアプリ本体の更新を促す。
- データパックの経路は、アプリの更新とは独立に受け取れる（フォークを含む）。
- 署名の確認とパックの読み込み・検査は、アプリの内部（Rust 側）で行う。画面側では行わない（0016）。
- インストーラーには最新のパックを同梱し、オフラインでも初回から全機能を使えるようにする。過去のパックはすべて手元に残す（控えの再現のため。0009）。
- 一度受け入れた版より古い版（アプリ・各パック・取り下げの一覧）は受け付けない。

### 4. 自動通信の相手は `updates.fprise.com` だけ

- アプリが自動で通信する相手は `updates.fprise.com`（配布元の設定の `host`）だけに固定する。通信は Rust 側の HTTP の部品だけが行い、許可したホスト以外への接続を部品の中で拒否する。画面は CSP で外と通信できない（0016）。
- 他のホストへの転送（リダイレクト）には従わない。配信元は、ファイルを `updates.fprise.com` そのものから返す。GitHub の配布用リポジトリは、手動でダウンロードする人のための写しとし、アプリからは読みに行かない。
  - 理由: 転送先に従うと、実際に通信する相手が「外部送信の一覧」に書いたものと食い違う。
- TLS を必須とし、証明書は OS の仕組みで確かめる。証明書の固定（pinning）はしない（中身の正しさは署名で守るので、固定による「更新が届かなくなる」危険のほうが大きい）。
- 送るのは、更新の判定に要る情報（アプリの版・OS・CPU の種類）だけ（CPU の種類は、どの配布物を渡すかの判定に要る）。世帯・FP・PC を識別する値、クッキーは送らない。配信元では版ごとの更新確認の件数だけを数え、IPアドレスは保存しない設定にする。
- 確認するのは、起動時と、起動中は1日1回、FPが「更新を確認」を押したとき。
- 利用状況の送信は既定で OFF（FPが ON にしたときだけ回数のカウンタを同じホストへ送る）。通信先と送る項目はすべて「外部送信の一覧」で公表する（0012 の5）。

### 5. 署名鍵の体系

| 鍵 | 署名するもの | 本数 | 権限の制限 |
|---|---|---|---|
| アプリ更新用 | アプリ本体の更新 | 現用＋次期 | — |
| データ用 | 人が承認した制度データパック・マスタデータパック、お知らせ、自動配信の許可表（0022） | 現用＋次期 | — |
| 自動配信用 | 決まった関門を通って自動で配る制度データの更新（範囲は 0022） | 現用＋次期 | **既にある値IDに、前の期間と同じ形の新しい適用期間を1つ足すことだけ**を受け付ける。新しい値ID・計算部品・既存の期間の値の書き換え・状態の変更・形の変更は受け付けない。許可表で対象にした値の種類だけで、変化率の上限を超えるものは受け付けない。配信の一時停止と巻き戻しができる |
| 取り下げ用 | 取り下げの一覧とアプリの最低版 | 現用＋次期 | オフラインで保管する |

- このほかに、OS のコード署名（Apple の Developer ID、Windows の Authenticode）がある。これは OS が管理する証明書で、上の鍵とは別に扱う。
- 署名の方式は Ed25519（アプリ本体は Tauri の updater の minisign 形式、データ・お知らせ・取り下げは切り離した署名）。署名には鍵のIDを入れ、アプリに埋め込んでいない鍵のIDは拒否する。
- 4種類とも、最初の版から**現用と次期の2本の公開鍵を埋め込む**。どちらかで正しく署名されていれば受け付ける。鍵を入れ替えるときは、次期の鍵で署名を始め、次の版のアプリで「次期を現用に、新しい次期を追加」とする。これにより、鍵を入れ替えても配布済みのアプリへ届け続けられる。
- 自動配信用の鍵の制限は、アプリが受け取ったときに検査する（手元のパックとの差を取り、既にある値IDに新しい期間の行が1つ足されただけで、既存の行が変わっておらず、形が前の期間と同じで、前の期間からの変化率が上限内かを確かめる。0022）。対象の値の種類と変化率の上限は、データ用の鍵で署名した「自動配信の許可表」（0022）に置く。自動配信用の鍵で許可表を変えることはできない。
- 漏れた鍵は、取り下げの一覧に鍵のIDを載せて無効にする。
- すべての鍵はオフラインに二重の控えを持つ（鍵を失うと、配布済みのアプリに更新を届けられなくなるため）。秘密鍵は公開・非公開のどのリポジトリにも、クラウドの開発環境にも置かない。

### 6. 段階配信の欄

- パックの目録（`index.json`）は、各データパックの「配信の目録」（0022）を並べたもの。各項目に、段階配信の欄（`rollout`）・一時停止の印（`paused`）・巻き戻しの元（`rollbackOf`）・アプリが理解しなければならない欄の一覧（`critical`）を最初から持たせる。欄の一覧・意味と運用は 0022 が正（各アプリはインストールのときに作った0〜99の乱数を手元にだけ持ち、`rollout` の割合と比べて適用するかを決める。乱数は送信しない）。
- 各項目は、そのパックを署名した鍵（データ用または自動配信用）で署名し、どちらの鍵かを `signer` に書く。取り下げにあたる誤りの修正は段階配信にしない。
- 理由: 段階の欄と巻き戻しの入口は、配った後のアプリには足せない。

### 7. 取り下げと最低版（最初の版から入れる）

- 取り下げの一覧（`revocations.json`）の形:

  ```json
  {
    "format": "fprise-lifeplan-revocations",
    "formatVersion": "1.0",
    "serial": 42,
    "issuedAt": "2027-03-01T00:00:00Z",
    "expiresAt": "2027-05-30T00:00:00Z",
    "minAppVersion": "1.2.0",
    "revoked": {
      "regulationValues": [{ "id": "incomeTax.basicDeduction", "packVersion": "2027.3.1" }],
      "componentRevisions": [{ "id": "pension.oldAge.basic", "revision": 14 }],
      "packs": [{ "id": "regulation.tax", "version": "2027.3.0" }],
      "appVersions": ["1.1.3"],
      "keys": []
    },
    "notice": "事実だけの短い説明"
  }
  ```

  - `serial`（通し番号）は増える一方。手元で見た最大の番号より小さい一覧は受け付けない（古い一覧を見せ続ける攻撃を防ぐ）。
  - `expiresAt`（有効期限）を過ぎた一覧は、最新とみなさない。
  - 取り下げの単位は、制度の値のID（パックの版つき）と計算部品の改訂（0009）。ほかにパックの版・アプリの版・鍵のIDを載せられる。`revision` は整数（0006）、パックのIDは `regulation.<分野>` などの形（0007）、`formatVersion` は `MAJOR.MINOR`（0001）。
- アプリの動き:

| 状況 | 動き |
|---|---|
| 取り下げられた値・計算を使うプラン | 赤い帯を出し、更新するまで新しい提案書の出力を止める。過去の控えの再印刷は止めない（FP向けの画面に注記。PDFには出さない。0009） |
| アプリが最低版より古い | 閲覧はできる。計算と PDF の出力は更新してから |
| 有効な取り下げの一覧を30日以上取れていない、または手元の一覧が期限切れ | 黄色い帯で「取り下げの確認ができていません」と出す。計算と出力は止めない（顧客先でオフラインのこともあるため） |
| パックの見直し期限を過ぎても新しい版がない | 黄色い帯。PDF の前提条件のページに「改定が反映されていない可能性」と注記 |

- **更新を遅らせる**: FPはアプリ本体の更新を最大14日遅らせられる。ただし、制度データパック、取り下げの知らせ、世帯ファイルの形式が変わる更新（0011）、最低版に指定された更新は遅らせられない。
- アプリ本体の更新は裏でダウンロードし、終了時か「今すぐ再起動」を押したときに当てる（Windows は既定の `passive`）。

## 理由

- **識別子を製品名から切り離す**: 製品名は変わりうるが、識別子が変わると更新とデータの置き場所が切れる。名前の変更をソフトの都合に影響させない。
- **配布元の設定を1か所に**: MIT で公開する以上、フォークが自分の識別子・鍵で配れることは避けられない。散らばっていると、フォークが公式の識別子や配信先を残したまま配り、公式版と混ざる危険がある。
- **自動通信を1つのホストに限る**: FPが「外部送信の一覧」を見て確かめられる状態を保つ。顧客データを扱うPCで、通信の相手が増えることはそれ自体が不安の種になる。
- **データパックにプログラムを入れない**: データの更新は頻度が高く、自動配信も含む。プログラムを入れられると、データの鍵が漏れたときに任意のコードを実行させられる。宣言型に限れば、最悪でも値の誤りに留まり、取り下げで止められる。
- **鍵を役割で分ける**: 頻繁に使う鍵（自動配信用）が漏れても、アプリ本体の更新や取り下げには使えないようにする。自動配信用の鍵の権限を受け取り側で制限するのは、配った後から制限を足せないため。
- **現用＋次期の2本**: 鍵の入れ替えの手段がないと、鍵が漏れたり失われたりしたときに、配布済みのアプリが更新を受け取れなくなる。
- **取り下げを最初の版から**: 取り下げの仕組みが無い版を一度配ると、その版には誤りを知らせる手段がない。有効期限と通し番号は、古い一覧を見せ続けて取り下げを隠す攻撃への対策（The Update Framework の考え方を、小さな運用で回せる範囲に絞ったもの）。

## 影響

- **後から変えると何が起きるか**: 識別子・署名の名義を変えると、更新が届かず、OS の警告の評価（Windows の SmartScreen など）が最初からになる。鍵の体系・埋め込んだ公開鍵・取り下げの仕組みは、配布済みのアプリに後から足せない。通信の相手を増やすと、外部送信の一覧と説明を書き直すことになる。
- **守るべき決まり**
  - 署名の確認を飛ばす設定・開発用の抜け道を、本番のビルドに入れない。
  - データパックの形式に、実行できるコード・外部への参照（URL を読みに行く指示など）を入れない。
  - 秘密鍵をリポジトリ・CI の公開ログ・クラウドの開発環境に置かない（CI の秘密情報の検出を最初のコミットから動かす。0021）。
  - 配信の URL の構成を変えるときは `/v1/` の版を上げ、古い構成も配布済みの版が使い終わるまで返し続ける。
- **テストで確かめること**
  - 署名なし・知らない鍵・改ざんしたアプリ更新とパックを拒否する。次期の鍵で署名したものは受け付ける。
  - 古い版のアプリ・パック・取り下げの一覧（通し番号が小さいもの）を拒否する。期限切れの一覧で黄色い帯が出る。
  - 自動配信用の鍵で署名したパックについて、新しい値・計算部品の追加・状態の変更・変化率の上限を超える変更を拒否し、既存の値の上限内の変更だけを受け付ける。
  - 取り下げた値を使うプランで、新しい PDF の出力が止まり、控えの再印刷は止まらない。最低版より古いアプリで計算と出力が止まり、閲覧はできる。
  - アプリが `updates.fprise.com` 以外へ接続しない（通信を記録する環境で起動・更新・パック受け取り・取り下げの確認を流して確かめる）。他のホストへの転送に従わない。
  - 送る情報に、世帯・FP・PC を識別する値が入っていない。
  - 識別子・ホスト名・公開鍵が配布元の設定のファイル以外に書かれていない。
  - Windows・Mac の両方で、インストール・更新・取り下げが動く。

## 試作での確認

- 配布・更新・署名は、試作ではまだ確かめていない。署名の申請（Apple・Windows）が済んだ後に、署名したビルドで確かめる。
- 関連して、署名していない試作のビルドでは、画面のデータの置き場の名前がプログラム名になった（署名して `.app` にすると識別子の名前になる見込み）。また、OS の資格情報の保管庫は、プログラムを作り直すと前の版が作った項目を読むときに確認ダイアログが出る可能性があり、署名を毎回同じにすれば出ない見込みである（どちらも推測。署名した版で確かめる）。
