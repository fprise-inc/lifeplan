# 0005. 計算エンジンの実行環境と二本立て

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。実行環境の上限の数値・並列の数は内部（測定に合わせて変えてよい）

## 背景

ファイナンシアの計算エンジンは、税・社会保険・年金・NISA/iDeCo・住宅・教育・保険・万一・キャッシュフローを計算する。次の条件を同時に満たす必要がある。

1. **同じ入力なら同じ結果**: 画面・AI接続口・コマンド・CI・PDFのどこで計算しても、Windows でも Mac でも、円単位で同じ結果になる。
2. **隔離**: FPやFPのAIが書いたカスタム計算部品を、顧客データのそばで動かす。部品がネットワーク・ファイル・時計・乱数・アプリ本体に触れられないようにする。
3. **速さ**: 面談中にスライダーを動かすと、その場で結果が変わる。目標は「100年分×提案5案×万一の想定4つ（20回の計算）」を0.1秒以内。

## 決定

### 1. 言語と構成

- 計算エンジンは TypeScript で書く、独立した純粋な部品。入力（JSON）を受け取り、出力（JSON）を返すだけ。
- アプリ本体（Rust）が担うのは、保存・暗号化・署名の確認・更新・PDF・AI接続口との連絡。金額の計算は Rust では行わない。
- エンジンのソースは esbuild で1つの JavaScript にまとめ、さらに quickjs-ng のバイトコードに変換してアプリに同梱する。読み込むバイトコードは、自分たちがビルドして署名つきで配ったものだけ（外から来たバイトコードは読み込まない）。
- カスタム計算部品は TypeScript のソースのまま読み込み、読み込むときに型を取り除く（0016・0019）。

### 2. 「正」の実行環境: Rust に組み込んだ quickjs-ng

- 計算結果の正は、アプリ本体に組み込んだ quickjs-ng（Rust のライブラリ rquickjs 経由）で計算したものとする。
- 保存・PDF・顧客に見せた版の控え・AI接続口・書き出し・不具合報告の再現に使う数字は、すべてこの実行環境の結果。
- カスタム計算部品は、この実行環境でしか動かさない。
- AI接続口とコマンド（同梱の小さなプログラム。0015）も、同じ Rust のライブラリで同じ実行環境を組み込む。
- quickjs-ng と rquickjs の版は固定する。版を上げるときは、一致テスト（下の6）と脱出テスト（0016）を通してから。バイトコードの形式は版ごとに変わるので、毎回のビルドで作り直す。

### 3. 実行環境の作り方（計算ごとに新しく作る）

1つの計算の要求ごとに、次の順で新しい実行環境（ランタイムとコンテキスト）を作り、終わったら捨てる。使い回さない。

1. 新しいランタイムを作り、メモリの上限・スタックの上限・割り込み（時間の上限）を設定する。
2. 標準の組み込みのうち、計算に要らないものを入れない・消す。
   - 入れないもの: `Date`、`std`・`os` モジュール、モジュールの読み込み機能（エンジンと承認済みのカスタム部品の、決まった相対の読み込みだけを本体が解決する）、`console`、タイマー。
   - 消すもの: `WebAssembly`、`SharedArrayBuffer`、`Atomics`、`WeakRef`、`FinalizationRegistry`、`eval`、`Function` コンストラクタ（実行時にコードを作れないようにする。承認したコードだけが動く）。
   - 残すもの: `queueMicrotask`（時計も入出力も持たないので無害）。
3. 時計と乱数は**エラー**にする。`Date` は存在しない（参照すると `ReferenceError`）。`Math.random` は呼ぶと例外を投げる関数に差し替える。基準日は入力で渡す（0003）。
4. 結果がエンジンやOSで変わる `Math` の関数（`pow`・`exp`・`log`・三角関数など。一覧は 0002）を、呼ぶと例外を投げる関数に差し替える。
5. 組み込みオブジェクトを凍結する（`Object`・`Array`・`Function`・`Math`・`JSON`・`Number`・`BigInt`・`String`・`Symbol`・`Error` 系と、それぞれの `prototype`）。凍結の前に、Hardened JavaScript（SES）と同じ方法で "override mistake" への対策をする: よく上書きされる名前（`constructor`・`toString`・`valueOf`・`toJSON`・`name` など）を、「子のオブジェクトへの代入は子に自分の値を作る」形の取得・設定関数に置き換えてから凍結する。
6. エンジンのバイトコードを読み込み、続けて承認済みのカスタム部品を読み込む（凍結の後なので、公式もカスタムも組み込みを書き換えられない）。
7. 入力のコピー（JSON として渡す）、制度データの読み取り関数、端数処理などの公式関数だけを渡して計算する。
8. 結果を JSON として受け取り、実行環境を捨てる。

### 4. 上限と、外から打ち切る手段

- 初期値（測定に合わせて変えてよい）:

| 上限 | 根拠の記録なし・要約 | 根拠の記録全部 |
|---|---|---|
| メモリ（実行環境1つ） | 64 MB | 256 MB |
| 時間（要求1つ） | 10 秒 | 30 秒 |
| スタック | 1 MB | 1 MB |

- 上限を超えたら、その要求はエラーにし、画面には「計算が上限を超えました」と部品のIDだけを出す。
- QuickJS の時間の上限は「ときどき割り込んで確かめる」仕組みで、重い組み込みの処理の途中では効かないことがある。そこで、計算はアプリ本体とは別の**計算プロセス**（アプリ自身を計算専用のモードで起動したもの）で動かし、期限を過ぎても戻らなければ本体がプロセスごと終了させる。プロセスはあらかじめ起動しておき（待機中のプロセスを置く）、終了させたら作り直す。
- 計算プロセスの中で実行環境が壊れても、本体（保存中のデータ）は巻き込まれない。

### 5. 二本立て: 画面側のエンジンは「表示の先出し」だけ

- 同じエンジンのまとめた JavaScript を、画面（Tauri の WebView。Mac は JavaScriptCore、Windows は V8）でも動かす。
- 画面側のエンジンを使うのは、**スライダーなどを動かしている間の表示の先出し**だけ。
  - 操作が止まったら（目安: 最後の入力から150ミリ秒）、本体の計算プロセスで計算し、結果で置き換える。
  - カスタム計算部品を含む案は、画面側で計算しない。本体の並列計算（下の7）で間に合わせる。
  - 画面側の結果は保存しない。PDF・控え・AI接続口・書き出しに渡さない。
  - 先出しの間は、数字が確定前であることを控えめに示す（見せ方は画面の設計で決める）。
- 画面側と本体の結果が食い違ったら、本体の結果を表示し、不具合として内部の記録に残す。記録するのはエンジンの版と結果のハッシュだけで、顧客の数字は残さない。
- 画面側の実行環境には、本体のような `Math` の差し替えや凍結をしない（画面の他の部品が使うため）。lint（0002）と一致テストで守る。画面の通信の遮断と保存機能の無効化は 0016。

### 6. 一致テスト（CI で必須）

- 同じ入力を次のエンジンで計算し、出力 JSON の SHA-256 が一致しなければ変更を取り込まない。
  - Node（V8）
  - Rust 組込みの quickjs-ng（Windows・macOS・Linux それぞれでビルドしたもの）
  - JavaScriptCore（Bun、または WebKit）
- 対象: 結果を固定するモデル世帯（すべて合成した架空の世帯）の全件 × 根拠の記録「なし・要約・全部」。
- 画面の中の実物（WKWebView・WebView2）での一致は、画面の自動テストで確かめる。
- 一致のために、出力は決まった形にする: キーの順番はエンジンが決めた順、数値は整数だけ（率は文字列）、`-0` を出さない。CI で出力に小数や `-0` がないことも確かめる。
- Node はテストを速く回すためだけに使い、隔離には使わない（Node の `vm` は抜け道があり、メモリの上限もない）。CI で扱うのは合成した世帯だけ。

### 7. 並列化と差分の再計算

- 本体の計算プロセスの中で、「案×想定」を単位に、複数の実行環境（それぞれ別のスレッド）に分けて同時に計算する。スレッド数は「論理コア数−1」（最低1、最大8）。
- スライダーを動かしたときは、変わった案だけを、全想定について計算し直す（5案すべてを計算し直さない）。
- 必要保障額の推移（死亡の時期を1年ずつずらした連続計算）は、年ごとに要求を分けて並列に計算し、要求ごとに時間の上限をかける。
- 並列に計算した結果は、順番に計算した結果と一致しなければならない（テストで確かめる）。

### 8. 顧客データを外に出さない

- エンジンにはログの出口（`console`）を渡さない。
- エンジンのエラーメッセージには、部品のID・制度の値のID・規則のID・入力項目IDだけを入れ、値は入れない。本体は、エラーを画面やファイルに出す前にもう一度この形に整える。
- 画面の中の保存機能（ブラウザの保存領域）に計算の入力・結果を置かない（0016）。

## 理由

- 小さな JavaScript 実行環境は、最初からネットワーク・ファイル・時計・乱数を持たないので、「隔離」と「同じ入力なら同じ結果」を1つの仕組みで満たせる。
- Rust 組込みの quickjs-ng は、WebAssembly 版より約2倍速く、メモリの上限に達したときもすぐ止まる（WebAssembly 版は止まるまで8〜13秒かかり、その間は時間の上限も効かなかった）。
- 内蔵の QuickJS は JIT を持たないので、画面側のエンジン（V8・JavaScriptCore）より8〜30倍遅く、20回の計算を0.1秒に収められない。一方、画面側のエンジンは速いが、隔離が弱く、カスタム部品を動かせない。そこで「正」は隔離できる本体側に置き、画面側は表示を早く出すことだけに使う。両者が同じ結果になることを一致テストで保証すれば、先出しの数字が後で変わることは起きない。
- 計算ごとに新しい実行環境を作るのは、ある計算での汚染（組み込みの書き換えなど）が次の計算に残らないようにするため。バイトコードからなら作り直しは数ミリ秒で、速さにほぼ影響しない。
- 凍結が要るのは、同じ実行環境の中で `Math.min` などを差し替えると、エラーにならずに結果だけが黙って変わるため。凍結を単純に行うと `x.constructor = ...` のような普通の代入が失敗する（JavaScript の古い仕様の落とし穴）ので、SES と同じ対策を入れる。
- 時計と乱数を固定値ではなくエラーにするのは、固定値だと「今日の日付で年齢を計算する」誤りを、もっともらしい数字のまま黙って通してしまうため。エラーなら書いた人（人でもAIでも）がすぐ気づく。
- 計算プロセスを分けるのは、時間の上限が効かない重い処理でも確実に打ち切るため（スレッドは安全に外から止められない）と、実行環境の不具合でアプリ本体が落ちて保存前のデータを失うのを防ぐため。

## 影響

- 後から変えると、全カスタム部品とAIの手順の作り直しになる。
- 守るべき決まり:
  - エンジンは純粋な関数のまま保つ。時計・乱数・入出力・グローバルな状態に頼るコードを入れない。
  - 画面側の結果を確定値として使わない。
  - 出力に浮動小数点の値を出さない。
- テストで確かめること:
  - 一致テスト（上の6）を毎回の変更で。
  - 脱出テスト（ネットワーク・ファイル・モジュール・ホストの内部・タイマー・時計・乱数・`eval`・`Function`・WebAssembly がすべて失敗すること、無限ループ・メモリの使い尽くし・深い再帰で本体が落ちないこと、失敗の後に新しい実行環境に前の状態が残らないこと、組み込みの書き換えが次の計算に影響しないこと）をリリースのたびに（0016）。
  - 凍結の後に、エンジンと代表的なカスタム部品が動くこと（override mistake の対策が効いていること）。
  - 計算プロセスを強制終了した後も、本体が動き続け、次の計算ができること。
  - 速さの回帰: 決まった機種（CI の実行環境と、開発用の Mac）で、20回の計算の中央値を毎回記録し、前回より大きく遅くなったら知らせる。

## 試作での確認

合成した14部品（給与・副収入・社会保険料・所得税・住民税・公的年金・遺族年金・障害年金・児童手当・教育費・住宅ローン・生活費・n年ごとの支出・資産）、1200か月の計算で測った。数値の表し方は 0002 の「工夫版」、根拠の記録なし、ミリ秒の中央値。

| 計算 | クラウド（Intel Xeon 2.1GHz 4コア、Linux） | Apple M5（10コア、macOS） |
|---|---|---|
| Rust組込み quickjs-ng、5案×4想定（20回）を順番に | 614 | 217 |
| 同、5案×4想定を5つの実行環境で同時に | 203 | 85 |
| 同、1案×4想定を4つの実行環境で同時に | 41 | 18.5 |
| 同、毎回新しい実行環境を作って5案×4想定 | 575 | 238 |
| WebAssembly の quickjs-ng、5案×4想定 | 1,266 | 571 |
| 画面側の代わり Node（V8）、5案×4想定 | 38 | 14.8 |
| 画面側の代わり Bun（JavaScriptCore）、5案×4想定 | 79 | 30.1 |
| Tauri の実物の画面（WKWebView）、5案×4想定 | — | 16 |

- 実行環境の作成とエンジンの読み込み（バイトコードから）: クラウド 3.3ミリ秒、Apple M5 1.3ミリ秒。
- 隔離（脱出テスト）: Rust組込みの quickjs-ng は全項目合格。無限ループは0.1秒の上限で止まり、32MBの上限でメモリを使い尽くす計算は31〜93ミリ秒で止まってホストは落ちなかった。Node の `vm` は `this.constructor.constructor` 経由でホストの `process` に届き、メモリの上限も設定できなかった（隔離に使えない）。
- 凍結しないと、同じ環境の中で `Math.min` を差し替えたとき、エラーにならず結果だけが変わった。単純な凍結では big.js が動かなくなり、SES と同じ override mistake の対策で直った。
- 一致: 全エンジン・全範囲・根拠の記録の全モードで、結果の SHA-256 がビット単位で一致した。Apple M5（arm64）とクラウド（Linux x64）でも全方式が一致した。Tauri の画面（WKWebView、CSP の下）と本体の quickjs-ng も一致した。
- メモリ: 5案×4想定で、根拠の記録なしは約3MB、全部は約88MB を使った。
- 画面の結果（約355KB）を本体へ送る時間は約3ミリ秒。

新しめの Mac なら、内蔵の quickjs-ng だけでも5つ同時に計算すれば0.1秒に入る。クラウドの4コアでは入らず、二本立てが要る。

## 未確定

- **遅いPC**: 2コアの Celeron・Pentium・古い Core i3 の Windows ノートでは、1案×4想定を並列にしても0.08〜0.2秒、画面側（V8）の5案×4想定でも0.08〜0.12秒と見込む（公開されたベンチマークの傾向からの推測で、実機では未測定）。β公開までに実機で測り、入らなければ、スライダーの間引き（操作中は一定の間隔でだけ計算する）や、先出しを変わった案だけにするなどの対策を決める。
- Windows の実機（WebView2 の中での速さ、MSVC でビルドした quickjs-ng の速さ）。
- 計算プロセスの起動にかかる時間（特に Windows）と、待機させるプロセスの数。測ってから、プロセスで分ける形を確定する（測った結果、プロセスでは重すぎる場合は、スレッド＋割り込みに戻し、重い組み込みの処理を部品に渡さない形で補う案を比べる）。
- 上限の最終値（メモリ・時間）。本物のエンジンで必要保障額の推移などの重い計算を測ってから決める。
- 凍結を「エンジンを読み込む前」に行う順番は、試作では「読み込んだ後」で確かめた。本番の順番で動くことを、エンジンの土台を作る11月に確かめる。
- 本物の部品（制度の細かい分岐が入る）での速さ。重さは「月ごと×部品ごとの処理の数」にほぼ比例するので、所得税・社会保険料の部品ができた段階で同じ計測をやり直す。
- 次の版でモンテカルロを入れるときの乱数は、決まった計算で作る疑似乱数を、種を入力として渡して使う（実行環境の乱数は使わない）。形式はそのときに決める。

## 追記

- 2026-10-08（JavaScriptCore の一致テスト）: Bun は、配布しない CI の道具としてなら使ってよい（0015 の「Bun は採らない」は配布物の話）。6 の JavaScriptCore での一致テストを、Bun で CI に足した。
- 2026-10-08（凍結の順番）: 「未確定」の凍結の順番は、本番の順番（組み込みを凍結してからエンジンを読み込む）で、エンジン（esbuild の出力・ビルドの時に作った検査器・`class extends Error`）が動くことを土台で確かめた。この項目は閉じる。
- 2026-10-08（lint の禁止の追加）: 計算エンジンの lint で、`Date`・`console`・`globalThis`・`Intl`・`eval`・`Function`・`localeCompare`・`toLocaleString` も禁止する（3 で実行環境から外す・消すものを、書いた時点で止めるため）。
- 2026-10-08（エラーの形）: 8 のエラーの形を `{"error": {"code": "E_…", "ids": [ … ]}}` とする。`ids` に入れるのは部品・制度の値・規則・入力項目のIDと、スキーマの誤りの場所（例 `/input/openingBalance:type`。値ではなく欄の場所）だけ。ホスト（Rust）が出すエラーの符号は `E_HOST_` で始める。
