# 0114. カスタム層の最小の仕組み（拡張の束・宣言型の入力欄・見せ方の差し込み口・提案書の拡張の章）と、合算BS を公式の拡張としてその上に移す（形式 0.54）

- 状態: 採用（一部未確定）（2026-11-03）
- 固定の強さ: 骨格は、拡張の束の形（`manifest.json` を持つ1つのフォルダ。宣言型の入力欄 `fields/`・計算部品・提案書の章を1つの束に入れられる。置き場所はカスタム層の `modules/<束の名前>/`）、束と値の名前の付け方（束の `id`・入力欄の値の置き場所・章の `id` はどれも `ext.<作成者>.<名前>`。作成者 `official` は提供元だけ）、入力欄の値は世帯ファイルの拡張領域 `ext` に置き定義を `extDefinitions` に写すこと、見せ方の差し込み口の考え方（エンジンの8つの差し込み口とは別。JSON の値だけを受け取り JSON の値だけを返す副作用の無い関数。計算の結果を変えない）と2つの ID（`view.balance`・`report.chapter`）、拡張の章を置く場所（「提案での変更点」の後・「プランの比較」の前）と帳票の入力の欄 `extensions`、有効にする道が2つ（公式の拡張は機能を有効にするコード〔0110〕と事務所の設定の印、FP の束は承認〔0016 の6〕）であること、2段に分けて作ること（β公開までは同梱の公式の拡張だけを動かす）、形式 0.54 の変換の段（`household.companyBs` を `ext.official.combinedBs` へ移し `meta` に記録する）。試験版は、マニフェストの欄・入力欄の宣言の欄（`extFields@1.0`）・2つの差し込み口の入出力の欄（約束の版 `1`）・`@lifeplan/sdk` の拡張の型（0001 の試験版の規則）。内部は、同梱の束の画面での描き方・作業の層の値の持ち方
- 前提にする記録: 0004（ID の書式）、0006（差し込み口・約束の版）、0009（帳票・控え）、0011 の4（拡張領域）、0016（画面の安全とカスタム層。3〜8 と追記）、0017（配布元の設定・更新の署名）、0019（SDK フォルダ）、0020（書き出し）、0027 の8（`customViews`）、0105 の6、0107（合算BS を暫定で公式の画面に置いた）、0110（機能を有効にするコード）

## 背景

- 合算BS は、カスタム層の仕組みを待たずに「公式の画面の中の、既定では使わない機能」として先に置いた（0107。暫定）。0107 ではカスタム層へ移すのは β公開の後としていた。
- 利用者の判断（2026-11-03）で、**最初の公開（β）の時点から、合算BS はカスタム層の上で動く形にする**。カスタム層の仕組みのうち、合算BS を動かすのに要る部分を β公開の前に作る。
- 0105 の6 は、見本に要る仕組みを7つ挙げていた: ①カスタム層のフォルダを読む、②計算部品の読み込み（マニフェスト・型を取り除く部品）、③承認と指紋、④隔離実行、⑤資産と負債のタブの差し込み口、⑥宣言型の入力欄 `fields/`、⑦提案書の任意の章。今動いているのは、①と③のうち設定（説明の文・名前・欄の見せ方）の分だけ（0016 の 2026-11-02 の追記）。
- このうち重いのは、②の型を取り除く部品（0016 の未確定）、④の隔離実行（見るものは欄を1つ変えるたびに作り直すので、計算の要求ごとに新しい環境を作る 0016 の7 の形を、画面の操作の速さで動かす確かめが要る）、③の計算部品の承認の画面（差分・読む項目・モデル世帯での見本）。
- β公開で固まるのは骨格（差し込み口の約束・束の形・`ext` の名前の付け方）。ここを β の前に決めきれば、FP の束を読む仕組みは後から足しても、合算BS と FP の束が同じ形の上に乗る。

## 決定

### 1. 2段に分けて作る

| 段 | いつ | 動かす束 | 動かし方 |
|---|---|---|---|
| 1 | β公開まで（この記録で作る） | **同梱の公式の拡張だけ**（提供元が作り、アプリの配布物に入れて配る束。今は合算BS の1つ） | アプリの作業の層の中で、アプリのコードとして呼ぶ |
| 2 | β公開の後 | FP の束（カスタム層の `modules/<束の名前>/`）と、別に配る公式の拡張（提供元の署名つきの束） | 承認と指紋（0016 の6）で固定し、隔離実行（0016 の7）の中で呼ぶ |

- 段1 で決めきるもの（骨格）: 束の形（2）、名前の付け方（3）、宣言型の入力欄の形と値の置き場所（4）、見せ方の差し込み口の約束（5）、提案書の拡張の章（6）、有効にする道（7）。段2 は、同じ形の束を読む道（読み込み・承認・隔離実行）を足すだけで、形は変えない。
- 段1 では、カスタム層の `modules/` に束を置いても読まない（何も起きない。承認待ちにも出さない）。FP がカスタム層で作れる物は、今までどおり設定（説明の文・名前・欄の見せ方）だけ。
- **同梱の公式の拡張を作業の層で呼ぶこと**: 0016 の1 の「カスタムの計算部品は画面の中では動かさない」は、アプリの外から来たコードについての決まり。同梱の公式の拡張は提供元のコードで、アプリの配布物の一部として、アプリの更新の署名（0017）で守られて届く（公式の画面のコードと同じ扱い）。段2 で外から読む束は、公式の拡張でも隔離実行の中でしか呼ばない（どこから来たかで分け、作成者で分けない）。
- **束を作る決まりは段1 から守る**: 同梱の束も、外から読む束と同じ決まり（0016 の5）で書く。読み込めるのは束のフォルダの中の相対パスと `@lifeplan/sdk` だけ、時計・乱数・`Math.pow` などを使わない、`import()` を使わない、副作用を持たない。段2 で同じ束を隔離実行の中で動かせるようにするため。テストが束のソースを読んでこれを確かめる。

### 2. 拡張の束の形

- 1つの束は1つのフォルダ。カスタム層では `modules/<束の名前>/`（0016 の3 の4種類の置き場所は変えない。計算部品のフォルダの中に、その部品が使う入力欄と章を一緒に入れられる形にした）。

  ```
  modules/<束の名前>/
    manifest.json        … 束の宣言（必須）
    index.ts             … 入口（manifest の entry。差し込み口に載せる関数を名前つきで出す）
    parts/*.ts           … 計算部品（任意。入口から相対パスで読む）
    fields/<名前>.json    … 宣言型の入力欄（0個以上。4）
    reports/<名前>.typ    … 提案書の拡張の章（0個以上。6）
    signature.json       … 提供元の署名（別に配る公式の拡張だけ。段2。8）
  ```

- **マニフェスト**（0016 の5 の `manifest.json` に、束の欄を足す。`manifestVersion` は `1.0` のまま。試験版）:

  ```json
  {
    "manifestVersion": "1.0",
    "id": "ext.official.combinedBs",
    "name": "合算BS（経営者個人と会社のバランスシート）",
    "version": "1.0.0",
    "author": "提供元",
    "license": "MIT",
    "kind": "component",
    "entry": "index.ts",
    "provides": [
      { "type": "extend", "extensionPoint": "view.balance", "contract": "1", "export": "balanceView", "label": "合算BS（会社と合わせる）" },
      { "type": "extend", "extensionPoint": "report.chapter", "contract": "1", "export": "chapter", "chapter": { "id": "ext.official.combinedBs", "label": "会社と合わせたバランスシート（合算BS）", "typst": "reports/chapter.typ" } }
    ],
    "reads": ["balance.now"],
    "fields": ["fields/company.json"],
    "activation": { "feature": "combinedBs", "households": "executive" },
    "description": "経営者個人（家計）と会社のバランスシートを並べ、間の貸し借りを相殺して1枚にする"
  }
  ```

  - `provides[].export` は、入口が出す関数の名前。差し込み口ごとに1つずつ。`label` は見るものの切り替えに出す名前。
  - `reads`: 差し込み口の関数に渡す値の名前（5）。束の入力欄の値は宣言しなくても渡す。書いていない値は渡さない（0016 の5 の `reads` と同じ考え方。入力項目の ID でなく、見せ方の差し込み口が渡せる値の名前を書く）。
  - `fields`: 宣言型の入力欄のファイル（束の中の相対パス）。
  - `activation.feature`: 機能を有効にするコード（0110）の機能の名前。**作成者 `official` の束だけが書ける**（FP の束が書けば承認できない）。`activation.households`: どの世帯で使うか（`all`〔既定〕・`executive`〔役員として働く人のいる世帯だけ。`employmentPeriods[].type` が `executive`〕）。
  - 知らない差し込み口・知らない約束の版・入口に無い `export`・`official` でない束の `activation.feature`・束の `id` の作成者と入力欄の値の置き場所の作成者が違う、のどれかがあれば読み込まない（段2 では承認できない）。

### 3. 名前の付け方

- 束の `id`、入力欄の値の置き場所（拡張領域のキー）、章の `id` は、どれも `ext.<作成者>.<名前>`（各段は 0004 の書式。英小文字で始まる英数字。0011 の4）。
- 作成者 `official` は提供元だけが使う（0011 の4 の予約）。同梱の束と、提供元の署名のある束（段2）だけが `official` を名乗れる。FP の束が `official` を名乗れば承認できない（公式の見本を写した束は、作成者を自分の名前に変える。7）。
- 1つの束の中では、入力欄の値の置き場所と章の `id` の作成者は、束の `id` の作成者と同じにする。
- 見るものの切り替えの鍵（画面の中だけ）は束の `id`。

### 4. 宣言型の入力欄（`fields/<名前>.json`・`extFields@1.0`）

- 入力欄はプログラムではなく、JSON の宣言だけで作る（0016 の4）。画面は宣言を読んで欄を描き、入れた文字を読んで値にし、世帯ファイルに書く。束の関数は欄の値を受け取るだけで、文字の読み方を持たない（万円の読み方・年月の書き方・範囲は画面が決まった形で行う）。
- 形（JSON Schema は SDK の `schemas/`。試験版）:

  ```json
  {
    "schema": "extFields@1.0",
    "key": "ext.official.combinedBs",
    "version": 1,
    "attachTo": "household",
    "label": "会社の数字（合算BS）",
    "form": {
      "title": "会社の数字を入れる",
      "note": "…",
      "groups": [{ "title": "基準日と毎月の固定の支出", "fields": ["asOf", "amount:monthlyFixed"] }]
    },
    "fields": [
      { "id": "asOf", "path": ["asOf"], "type": "month", "label": "基準日（試算表の月末）", "placeholder": "2026-09" },
      { "id": "amount:cash", "path": ["amounts", "cash"], "type": "yen", "label": "現預金" },
      { "id": "amount:retained", "path": ["amounts", "retained"], "type": "yen", "negative": true, "label": "剰余金（利益の積み上げ）", "help": "マイナス（▲）も入ります" },
      { "id": "stage", "path": ["stage"], "type": "choice", "label": "会社の段階", "options": [{ "value": "founding", "label": "創業期" }] },
      { "id": "useRestated", "path": ["useRestated"], "type": "check", "label": "直した額で並べる" }
    ]
  }
  ```

  - `key`: 値の置き場所（拡張領域のキー。3）。`version`: 値の形の版（整数。変えるときは束の中で読み替える）。`attachTo`: 今は `household` だけ（0011 の4 の `member`・物の種類は段2 で開く）。`label`: 元に戻すの知らせ・不明な拡張項目の表示に出す名前。
  - `form`: 欄の並び（まとまりの見出し・説明・欄の `id` の並び）。宣言に無い欄の `id` を並べたら読み込まない。
  - 欄の種類は4つ: `yen`（円の整数で持つ。画面では万円で入れて出す。`negative: true` のときだけマイナスも入る。上限は1兆円）、`month`（`YYYY-MM`）、`choice`（`options` の `value` のどれか。「選ばない」は欄を持たない）、`check`（真偽。付けていなければ欄を持たない）。どの種類も、空欄は値を持たない（値の対から消す）。
  - `path`: 値の対の中の場所（1〜2段。英小文字で始まる英数字）。同じ `path` を2つの欄で使えない。
  - 文字（`label`・`help`・`placeholder`・選択肢の名前・見出し・説明）は字のまま出す（0016 の 2026-11-01 の追記の3 と同じ決まり。HTML として読まない・制御文字と向きを変える字を受け付けない・長さの上限）。
  - **既定の値は書けない**（0016 の 2026-11-02 の追記の3。既定の値は事務所の既定値の画面）。
- **値の置き場所**: 世帯ファイルの拡張領域 `ext["<key>"]` に、`path` のとおりの対（JSON の対）で置く。何も入れていなければキーごと持たない。あわせて `extDefinitions["<key>"]` に定義を写す（0011 の4。`{ type: "object", label, version, attachTo, by: <束の id>, fields: [{ id, path, type, label }] }`）。束の無いアプリ・束を有効にしていないアプリでも、定義から「不明な拡張項目」として名前つきで見せられ、捨てない（0011 の4 の捨てない決まり）。
- **読むときの確かめ**: 世帯を開くとき、画面は宣言に合わない値（種類・範囲・選択肢の外・宣言に無い場所）を捨てて読む（今までの `readCombinedInput` と同じ考え方を、宣言から行う）。束を有効にしていないとき（コードが無い・切れたなど）も、値は読んで持ち、そのまま書き戻す（消さない）。
- 元に戻す・やり直す・自動保存・保存していない変更の確かめは、ほかの入力と同じ道を通る（0107 の4 で世帯の区画に置いた理由を、拡張領域の値でも満たす）。計算の要求には入れない。
- 段1 で画面が描くのは、見るもの（5）の中の入力欄だけ。入力の画面（入力項目のパネル）に束の欄を出す道は段2 で作る（入力のホームの「自由な項目を作る（準備中）」の入口。0016 の 2026-10-17 の追記）。

### 5. 見せ方の差し込み口（`view.balance`・`report.chapter`）

- 0006 の3 の8つはエンジンの中の差し込み口（計算の結果を作る）。ここで決めるのは**エンジンの外の、見せる値だけを作る差し込み口**で、計算の結果・キャッシュフロー表・家計のバランスシートを変えない。0006 の8つの一覧には足さない（`slot.` で始めず、`view.`・`report.` で始める）。
- どちらも、**JSON の値だけを受け取り、JSON の値だけを返す副作用の無い関数**（関数・日付・未定義の値を返さない）。受け取った値を書き換えても元は変わらない（写しを渡す）。文字は字のまま出す（HTML として読まない）。
- **渡す値**（どちらの差し込み口も同じ形。約束の版 `1`）:

  ```ts
  interface ExtInput {
    /** 束の入力欄の値（入力欄ごと。何も入れていなければ null） */
    values: Record<string, Record<string, unknown> | null>;
    /** reads に "balance.now" を書いたときだけ: 現状のプランの今の年の家計のバランスシート */
    balance?: { now: HouseholdNow };
  }
  interface HouseholdNow {
    at: BsAt;          // 年・項目（鍵・名前・分け方・額）・資産の合計・負債の合計・純資産・金融資産・資金の不足
    monthly: Yen;      // 生活費＋ローン返済の月額（家賃収入で返す不動産のローンは除く。0105 の3）
    guarantee: Yen;    // 会社の借入の連帯保証の額（今の額。0105）
  }
  ```

  - 渡すのは提示用の値と同じ粒度の数字と名前だけ（構成員の呼び方・FP のメモ・物の ID は渡さない）。`balance.now` の項目の鍵は分け方の部品（`bsGroups.ts`）の鍵。
  - 渡せる値の名前は、今は `balance.now` だけ。足すときは、この記録に追記して約束の版を上げずに足す（足すだけ）。
- **`view.balance`（約束の版 1）**: 資産と負債のタブの見るもの（0027 の8 の `customViews`）を1つ作る。返す値は `BsCustomViewModel` の形から、画面の側で決める物（鍵・欄の今の値）を除いたもの:
  - `label`・`lead`・`note`・`columns`（並べる図。列ごとに `name`・`sub`・`at`〔`BsAt` の形に任意の `netParts`〕）・`steps`・`scale`・`groups`（分け方の名前の置き換え）・`notices`・`sections`（表と文。`field` は入力欄の `id` で指す）・`form`（`open` と、欄ごとの差し込みの文 `hints`〔`placeholder`・`help`。世帯の数字を入れた案内の文など〕）・`empty`。
  - 画面は、返った値に、鍵（束の `id`）と入力欄（4 の宣言と今の値から作る）を足して描く。図は家計のバランスシートと同じ部品で、共通の縮尺。
- **`report.chapter`（約束の版 1）**: 提案書の拡張の章の材料を作る。返す値は JSON の対（束の Typst が読む）か `null`（材料が無い。章を載せない）。6 のとおり帳票の入力の `extensions["<章の id>"]` に入る。
- 2つの差し込み口の呼び出しは、作業の層（`app/src/workspace/extensions/`）だけが行う。提示層は返った値を描くだけ（0016 の2 は変えない）。

### 6. 提案書の拡張の章

- 束の章（`provides` の `report.chapter` の `chapter`: `id`・`label`・`typst`）は、提案書の章の一覧で「提案での変更点」の後、「プランの比較」の前に並ぶ（合算BS の章を置いていた所）。束が複数あれば束の `id` の順。FP が章を選び、材料があるとき（関数が `null` を返さないとき）だけ載る。
- **帳票の入力**（試験版 0.1.0 の中で）: 任意の欄 `extensions`（章の `id` → 関数が返した対）を足し、`chapters` に章の `id`（`ext.` で始まる）を書けるようにする。合算BS の前の欄 `combinedBs` と章の `id` `combinedBs` は外す（外にこの欄を読む帳票は無い）。
- **章の Typst**: `reports/<名前>.typ` が、関数 `chapter(ext-data, data)` を出す（`ext-data` は関数が返した対、`data` は帳票の入力の全体）。読めるのは、公式の帳票の部品 `@lifeplan/report-core:0.1.0`（同梱の部品。`chapter`・`section`・`note`・`data-table`・`bs-column`・`man-unit` など）と、束の `reports/` の中のファイルだけ（0016 の7。ネットワーク・時計は無い）。金額は計算し直さず、書式だけを当てる（`sdk/docs/reports.md` と同じ）。
- アプリが組む外枠の文書が、有効な束の章を読み込み、公式の帳票の `proposal(data, frame, ext: (...))` に渡す。公式の帳票は決めた場所で、選ばれて材料のある章だけを呼ぶ。独自帳票（0016 の7 の `reports/<帳票名>/main.typ`）から `proposal` を呼ぶときは `ext` を渡さなければ拡張の章は載らない。
- 刻印・透かし・必須の記載はアプリが外側で付ける（0009。拡張の章からは消せない）。

### 7. 有効にする道と、公式の拡張と FP の束の関係

- **公式の拡張**（作成者 `official`）: マニフェストの `activation.feature` の機能を有効にするコード（0110）が今使えて、事務所の設定の印（事務所データの `defaults.features.<機能>`）が付いていて、`activation.households` に合う世帯のときだけ、見るもの・章を出す。FP の承認の操作は要らない（提供元が確かめた計算で、コードを入れて印を付けることが FP の判断）。
  - **推奨の形（合算BS）**: 提供元が配る公式の拡張（署名つき）で、コードを入れた FP だけが有効にできる。段1 では同梱の束としてアプリと一緒に届く（署名はアプリの更新の署名。8）。
  - 公式の画面に残すのは、公式の拡張の入り切りの所だけ: 事務所の既定値の区画「法人経営者向けの機能」と印、コードの入れ口と期限・止めたの知らせ（0110 の3）、資産と負債のタブの「見られなくなった・データは消していない」の1文（`hiddenNote`）。区画は「公式の拡張を使う印」として、拡張の名前（マニフェストの `name`）を出す。
- **FP の束**（段2）: 承認（0016 の6）で有効になる。`activation.feature` は書けない。`activation.households` は書ける。印・コードは要らない。
- **0107 の 2026-11-02 の追記と矛盾させない**: コードで守るのは公式の拡張（`ext.official.*`）だけ。見せ方の差し込み口・宣言型の入力欄・拡張の章は FP の束にも同じ約束で開き（段2）、FP や FP の AI が似た物を作ることは止めない。SDK の見本（9）は公開のリポジトリに置く物で、写して作成者を自分の名前に変えれば、FP の束として承認して使える（コードは要らない）。公式の拡張は、作りの良さと説明の分かりやすさで選んでもらう。
  - 公式の拡張の値の置き場所（`ext.official.combinedBs`）は、FP の束からは読めない（ほかの束の値は渡さない。5 の `values` は自分の入力欄だけ）。FP が自分の束へ値を移したいときの手順は段2 で作る（未確定）。

### 8. 承認・指紋・署名・「カスタム計算あり」の印

- **同梱の公式の拡張**: 承認の対象にしない（0016 の6 の「アプリの画面の外で変わったもの」に当たらない）。中身はアプリの版で決まるので、指紋を控え・PDF の内部情報に別に残さない（アプリの版は控えに残っている。0009）。
- **FP の束（段2）**: 0016 の6 のとおり、束のフォルダの全ファイルの指紋で固定し、保留・承認の画面（前の版との差分・使う差し込み口・`reads`・ライセンス）を通す。見せ方の部品は計算の結果を変えないので、「モデル世帯での公式との計算の差」の代わりに、モデル世帯で作った見るもの・章の見本を承認の画面に出す。宣言型の入力欄だけの変更（`fields/`）も承認の対象（0016 の6 の4種類）。
- **提供元の署名（別に配る公式の拡張。段2）**: 形だけ決めておく。`signature.json` に `{ "kid": <鍵の名前>, "digest": "sha256:<束の指紋>", "sig": <Ed25519 の署名の base64url> }`。署名するのは「前置き `lifeplan-extension/1` と NUL ＋ 指紋の文字列のバイト列」。公開鍵は配布元の設定 `config/distribution.toml` の `[keys]` の `official_extension`（機能を有効にするコードの鍵とは別の鍵。0017 の5 の「鍵を役割で分ける」）。署名の合う束だけが `official` を名乗れる。署名があっても、束は取り込んだら保留に置く（0016 の6。公式の拡張なら承認の画面に「提供元の署名あり」と出す）。
- **「カスタム計算あり」の印**（0016 の8・2026-11-03 の追記）: 公式の拡張には付けない（公式の計算で、プランの計算も変えない）。FP の束の見せ方の部品にも、案の一覧の印・計算のお知らせの1行は付けない（プランの計算を変えないため）。代わりに、FP 向けの画面の見るものの切り替えと提案書の章の一覧の名前の横に、小さく「事務所の拡張」と出す（提示層・提案書には出さない。段2）。FP の束がエンジンの差し込み口の計算部品を持つときは、その部品について 0016 の8 と 2026-11-03 の追記のとおり。

### 9. 合算BS を公式の拡張に移す（段1 で行うこと）

- 束の正本は `sdk/examples/extensions/combined-bs/`（SDK の見本と同じファイル。アプリはここを同梱の公式の拡張として読み込む）。中身は 0107 の2 のまま: 入力欄 `fields/company.json`（0107 の2 の会社の入力の欄すべて）、計算 `parts/combinedBs.ts`（前の `report/src/combinedBs.ts`。入出力は同じ）、見るもの `parts/view.ts`（前の `combinedView.ts` の値を作る所）、章の材料 `parts/chapter.ts`（前の `report/src/build.ts` の `combinedBsOf`）、章 `reports/chapter.typ`（前の `report-core/pages/combined.typ`）。
- 利用者から見て、見た目・計算・提案書の章・お知らせ・コードでの有効化の振る舞いは前と同じ（0107・0110 の決定のまま。前と同じテストが通ること）。計算エンジンの結果と家計のバランスシートは変えない。
- `@lifeplan/sdk` のうち拡張の型と小さな関数（`BsAt`・`HouseholdNow`・2つの差し込み口の入出力・`man` など）の正本は `report/src/sdk.ts`（リリースのビルドが SDK フォルダの `types/` に写す。0019 の2）。束はこれを `@lifeplan/sdk` という名前で読む（リポジトリの中では、アプリと帳票の部品の設定がこの名前をこのファイルにつなぐ）。
- AI 向けの説明: `sdk/docs/extensions.md`（束の形・入力欄・2つの差し込み口・拡張の章・作る決まり・合算BS の見本の読み方）を足し、`sdk/README.md` から辿れるようにする（0019 の2 の `docs/` に足す）。
- **世帯ファイルの形式 0.54**（0011 の5。MINOR）:
  - 変換の段（`0.53` → `0.54`）: `household.companyBs` があれば、中身をそのまま `ext["ext.official.combinedBs"]` に移し、`extDefinitions["ext.official.combinedBs"]` に定義（4）を写し、`meta.extTransfers` に `{ "from": "household.companyBs", "to": "ext.official.combinedBs", "formatVersion": "0.54" }` を1行足す（0011 の4 の「引き継いだことを `meta` に記録」）。`household.companyBs` は消す。移す先にすでに値があれば移す先を残し、元の値は記録の行の `value` に写して残す（捨てない）。会社の数字の無い世帯は版だけを書き換える。

## 理由

- **段を分ける**: β公開の前に要るのは「合算BS が β の時点の骨格の上で動くこと」で、FP の束を読むこと自体ではない。束の形・差し込み口・名前・値の置き場所・章の置き場所を今決めて、同梱の公式の拡張をその上で動かせば、β の後に読み込み・承認・隔離実行を足しても、合算BS も FP の束も作り直さずに済む。隔離実行まで β の前に作ると、型を取り除く部品の選定・見るものを操作の速さで作り直す確かめ・承認の画面がそろうまで、β の準備と試しの版が止まる。
- **同梱の束は作業の層で呼ぶ**: 同梱の束は、アプリの他のコードと同じ道（アプリの更新の署名）で届き、同じ人が書いて同じテストを通る。隔離は「アプリの外から来たコード」から顧客データを守るための仕組みで、同梱の束を隔離に入れても守れる物が増えない。どこから来たかで分ければ、段2 で別に配る公式の拡張は自然に隔離の中に入る。
- **束の署名を段1 で付けない**: アプリの外を通らない物に署名を付けても確かめる意味が無い。リポジトリに秘密鍵を置かない決まり（0110 の1・0017 の5）のもとでは、束を直すたびに提供元の署名を待つことになり、開発が止まる。形だけを決めておけば、別に配る段で道を足せる。
- **見せ方の差し込み口をエンジンの差し込み口と分ける**: エンジンの差し込み口は計算の結果を変え、根拠の記録・二本立て（0005）・モデル世帯での差の確かめが要る。見せる値だけを作る部品は計算の結果を変えないので、同じ重さの約束を課すと作りにくくなる。名前の頭で分けておけば、0006 の8つの一覧（骨格）を変えずに足せる。
- **入力欄を宣言だけにして、文字の読み方を画面が持つ**: 0016 の4（画面系は宣言型だけ）。束の関数が文字を読むと、同じ「万円」の欄でも束ごとに読み方が違い、全角・▲・範囲の扱いがずれる。画面が決まった形で読めば、どの束の欄も同じに入れられ、宣言から値を確かめて捨てることもできる。
- **値を拡張領域に移す**: 0107 では元に戻す・自動保存の道を通すために世帯の区画に置いた。拡張の値を作業の層で同じ道に通す仕組みを作ったので、0011 の4 の約束どおり拡張領域に置ける。世帯の区画のままだと、FP の束の値と公式の拡張の値が別の場所に分かれ、捨てない決まり・書き出し（0020）・不明な拡張項目の見せ方を2通り持つことになる。
- **公式の拡張はコードと印で有効にする**: 0110 で決めた「提供元がコードを渡した FP だけが使う」をそのまま保ち、FP の束の承認と混ぜない。コードは提供元の判断、承認は FP の判断で、守る物が違う。

## 代案（採らなかったもの）

- **β の前に隔離実行まで作る**: 上の理由。形を β で決めきれば、後から足しても壊れない。
- **0107 のまま公式の画面に置き、β の後に移す**: 利用者の判断で採らない。β の後に移すと、試しの版の世帯ファイルの形と帳票の入力をもう一度変えることになる。
- **0006 の差し込み口に9つ目を足す**: 0006 の8つは骨格で、エンジンの中の約束。見せ方の部品にエンジンの差し込み口の決まり（根拠の記録・科目の枝）は合わない。
- **束ごとに入力欄の読み方を関数で書く**: 0016 の4 を崩す。上の理由。
- **合算BS の値を世帯の区画（`household.companyBs`）のままにする**: 上の理由。
- **公式の拡張も FP の承認で有効にする（コードを使わない）**: 0110 の決定を覆すので採らない。
