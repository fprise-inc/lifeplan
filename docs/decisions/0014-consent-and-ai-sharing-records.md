# 0014. 同意の記録とAIに渡した記録

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。記録の形（項目と、追記だけで書き換えないこと）は骨格。画面の見せ方と説明文は試験版

## 背景

FPは個人情報を扱う事業者として、顧客から「何のために使うか」の確認を取り、外部のAIに顧客の情報を渡す場合はその説明と同意が求められる場面がある。顧客から開示を求められたときや、問題が起きたときに、FPが「いつ、何に同意をもらい、いつ、どの情報を、どこに渡したか」を示せなければ説明責任を果たせない。

ファイナンシアは世帯データを外部のAIに渡す手段（AI接続口。0015）を持つので、渡した事実を世帯ごとに残す仕組みを最初から持つ。記録の形を後から変えると、それまでの記録と比べられなくなり、過去の分は取り戻せない。

関連: 世帯ファイルの区画は 0011、ヒアリングシートの同意欄は 0018、AI接続口の許可・期限・取り消しは 0015、鍵と改ざん検出は 0013、書き出しは 0020。

## 決定

### 1. 置き場所

- **同意の記録**と**AIに渡した記録**は、どちらも世帯ファイルの区画として持つ（区画名は `consents` と `aiShares`。0011）。世帯ファイルと一緒に暗号化され、書き出し・引き継ぎ・完全削除の対象になる。
- AIへの許可の「今の状態」（有効な共有、期限）は、アプリ本体のメモリの中だけで判定する（0015）。共有の開始・期限・取り消しは、事務所データの「AIへの許可の台帳」（0011）にも書く。この記録は世帯ごとの「何が起きたか」の履歴で、台帳と同じく許可の判定には使わない。
- どちらの記録も**追記だけ**で、既存の行を書き換えない・消さない。撤回や訂正は、新しい行として足す（訂正の行は、訂正する行のIDと理由を持つ）。例外は世帯の完全削除（0013）で、このときは世帯ファイルごと消える。

### 2. 同意の記録の形

1件ごとに次を持つ。

| 項目 | 中身 |
|---|---|
| `id` | 記録の乱数ID |
| `kind` | 種類: `purpose`（利用目的の確認）／`externalAi`（外部AIへの提供）／`familyInfo`（家族の情報の扱い） |
| `decision` | `given`（同意した）／`refused`（同意しなかった）／`withdrawn`（撤回した） |
| `obtainedOn` | 同意を得た（撤回を受けた）日付（`YYYY-MM-DD`） |
| `method` | 取得方法: `hearingSheet`（ヒアリングシートの同意欄）／`paper`（紙の書面）／`inPerson`（面談で口頭）／`email`／`other` |
| `hearingRef` | ヒアリングシートで得た場合: 依頼の番号とシートの版 |
| `explanationRef` | 説明に使った文面の指紋（下の4） |
| `externalAi` | `kind` が `externalAi` のとき: 提供先のAIの会社、所在国、FPが確かめた「学習に使われない設定」の有無 |
| `members` | `familyInfo` のとき: 対象の構成員のID（任意） |
| `supersedes` | 訂正のとき: 訂正する記録の `id` と理由 |
| `recordedAt` | 記録した日時（時差つきの ISO 8601） |
| `origin` | `thisOffice`（この事務所で取った）／`previousOffice`（引き継ぎで受け取った。下の5） |

- 種類ごとの「今の状態」は、その種類の最新の行で決まる（`given` の後に `withdrawn` があれば撤回済み）。
- ヒアリングシートの同意欄は、取り込みをFPが承認したときに同意の記録になる。欄が空欄なら記録を作らない（「同意しなかった」とは扱わない）。「いいえ」に印があれば `refused` を作る。
- `externalAi` は、提供先のAIの会社ごとに1件ずつ持つ。

### 3. AIに渡した記録の形

1件ごとに次を持つ。

| 項目 | 中身 |
|---|---|
| `id` | 記録の乱数ID |
| `kind` | `household`（世帯の情報を渡した）／`headings`（移行の見出しと並びだけを渡した。値は含まない） |
| `shareId` | AI接続口の共有のID（0015） |
| `grantedAt`・`expiresAt` | 渡し始めた日時と期限 |
| `endedAt`・`endReason` | 終わった日時と理由: `revoked`（取り消し）／`expired`（期限切れ）／`appClosed`（アプリの終了）／`consentWithdrawn`（同意の撤回による自動の取り消し） |
| `scope` | `reduced`（縮約版。既定）／`custom`（FPが項目を足した） |
| `fields` | 渡した入力項目IDの一覧（0004）。自由記述・メモを含めた場合はその項目も載る |
| `householdRevision` | 渡した時点の世帯の改訂のID（0011） |
| `destinationDeclared` | FPが申告した接続先（例: 使うAIのアプリの名前） |
| `consentAtGrant` | 渡した時点の `externalAi` の同意の状態と、参照した同意の記録の `id`。同意が無いまま渡した場合は `none` と、警告を見せたこと |
| `reads` | 読まれた記録の列: 日時、道具（MCPのツール）の名前、返した項目の一覧、返した中身の指紋（SHA-256）、観測できた呼び出し元（接続口のプロセスの親の実行ファイルのパスなど） |
| `proposals` | AIから届いた案（「外から来た案」に入ったもの）の候補のIDと日時 |
| `importRef` | `headings` のとき: 取り込みの記録のID |

- 渡した中身そのものは保存せず、**項目の一覧と指紋**だけを持つ（中身は同じ世帯ファイルにあり、改訂のIDから当時の値をたどれる）。
- `reads` は、同じ共有の中で、同じ道具・同じ指紋の読み取りが続いた場合、1行にまとめて回数と最初・最後の日時を持つ（記録が際限なく増えないように）。
- 呼び出し元の名前は確かめられない（0015）。`destinationDeclared` はFPの申告、`reads` の呼び出し元は観測できた範囲の参考情報であり、どちらも認証ではないことを画面に書く。

### 4. 説明文の版

- 同意を得るときに見せた説明文（ヒアリングシートの同意欄の文、アプリの初回の説明の文）は、FPが事務所の設定で書き換えられる。
- 同意の記録には説明文の指紋を持たせ、その版の文面そのものを世帯ファイルに1回だけ写して持つ（世帯ファイルは自己完結。0011）。後から「何を説明して同意をもらったか」を示せる。

### 5. 引き継ぎで受け取った記録

- 他のFPから引き継ぎで受け取った世帯（0020）では、前の事務所の同意の記録とAIに渡した記録を `origin: previousOffice` として読み取り専用で残す。
- 引き継ぎを受けた事務所での「今の状態」は「同意の記録なし」から始める。同意は事務所ごとに取り直すものなので、前の事務所の同意をこの事務所の同意として扱わない。

### 6. アプリの動き

- **AIに渡す前の確認**: FPが「この世帯をAIに渡す」を押したとき、`externalAi` の同意が `given` でなければ警告する。FPは理由を確かめたうえで続けられる（判断はFP）。続けた場合は `consentAtGrant` に記録する。
- **撤回したとき**: `externalAi` の撤回を記録すると、その世帯の有効な共有をすぐに取り消し（`endReason: consentWithdrawn`）、「送った内容はAIの会社の側に残る」ことを画面に出す。
- **見る画面**: 世帯ごとに「同意とAIの記録」を一覧で見られる。共有中は目立つ表示を出す。
- **出力**: 同意とAIの記録は、全データの書き出しと顧客本人への開示の書き出しに含める（0020）。不具合報告用の書き出しには含めない。提案書PDFと、顧客に見せる画面（提示の層）には出さない。

## 理由

- **世帯ファイルに置く理由**: 記録は世帯ごとに求められ、世帯と一緒に引き継ぎ・書き出し・削除されるべきものだから。事務所データに置くと、世帯を削除しても記録が残り、引き継ぎで記録が欠ける。
- **追記だけにする理由**: 後から書き換えられる記録は、説明責任の根拠にならない。世帯ファイル全体が暗号と改ざん検出で守られている（0013）ので、追記だけの決まりと合わせて、記録の信頼性を保てる。
- **中身ではなく項目と指紋を持つ理由**: 渡した中身を丸ごと写すと、同じ情報が世帯ファイルの中で増え続ける。項目の一覧と指紋があれば「何を渡したか」を示すには足り、指紋で中身の同一性も確かめられる。
- **空欄を「同意しなかった」にしない理由**: 記入漏れと拒否を区別できなくなり、FPの判断を誤らせるため。
- **同意が無くても止めない理由**: 同意の取り方（口頭・書面・他の手段）や、渡してよいかの最終判断はFPの責任であり、ソフトが業務を止めるべきではない。そのかわり、同意なしで渡した事実を必ず残す。

## 影響

- **後から変えると**: 項目を後から足すことはできるが、それまでの記録には値が無い（取り戻せない）。種類（`kind`）の意味や、追記だけの決まりを変えると、過去の記録の読み方が変わり、説明の根拠として使えなくなる。
- **守るべき決まり**
  - 同意とAIの記録を書き換える・消す機能を作らない（完全削除を除く）。
  - AIに世帯の情報を渡す経路は、必ずこの記録を残す1か所の処理を通す（縮約と文章の包み方を行う Rust の側の処理と同じ場所。0015）。記録を残さずに渡す経路を作らない。
  - 移行の見出しをAIに渡す場合も `kind: headings` で残す。
- **テストで確かめること**
  - 共有の開始・読み取り・取り消し・期限切れ・アプリの終了・同意の撤回のそれぞれで、正しい行が足される。
  - 同意が無い世帯を渡すと警告が出て、続けた場合に `consentAtGrant: none` が残る。
  - 同意を撤回すると、その世帯の共有が即座に止まる。
  - ヒアリングシートの空欄からは同意の記録が作られない。
  - 記録の既存の行を書き換えようとする処理がない（データの層の単体テストで、既存の行の変更を拒否する）。
  - 引き継ぎで取り込んだ世帯の記録が `previousOffice` になり、今の状態が「記録なし」から始まる。
  - 不具合報告用の書き出しに、記録が含まれない。

## 試作での確認

- AI接続口の試作（捨てる前提）で、許可・期限・取り消し・縮約版・文章の包み方・別のユーザーからの接続の扱いが計画どおりに動くことを確かめた（詳細は 0015）。
- 同じ試作で、同じユーザーで動くプログラムは、FPが今渡している世帯の縮約版を読めてしまうこと（防げない範囲）を確かめた。このため、FPに「いつ・どの接続口が読んだか」を見せることを勧める結果になり、この記録の `reads` に反映した。
- 記録の残し方そのものは試作の範囲外で、まだ動かしていない。

## 未確定（11月以降に決めること）

- 顧客本人への開示用に、同意とAIの記録を人が読める一覧（PDFなど）でも出すか（0020 の未確定と合わせて決める）。

- 2026-10-08（全体の整合）: 区画名（`consents`・`aiShares`）と、許可の「今の状態」と台帳の分担を 0011・0015 にそろえて明記した。

- 2026-10-19（アプリへの組み込み。骨格は変えない）:
  1. **同意が無い世帯は渡せない**: 6 の「同意が `given` でなければ警告し、FPの判断で続けられる」を、この版のアプリでは最も保守的に「同意が `given` の世帯だけを渡せる（続ける道を出さない）」にした（共有の台帳の `require_consent`）。共有中に同意の状態が `given` でなくなった世帯は、接続口の一覧に出さず、読ませず、その場で `consentWithdrawn` で閉じる。警告して続けられる形に戻すかは、FPの業務の確認の後に決める（未確定）。
  2. **同意の記録に足した項目**: `scope`（渡してよい範囲。この版は `reduced` だけ）と `fpConfirmed`（FPが説明して同意（撤回）を確かめたことを画面で確かめた）。説明文は初版の固定の文（事務所の設定での書き換えは後の版）で、指紋と文面を区画 `consentExplanations`（指紋 → 文面）に1回だけ写す。
  3. **画面から書かない**: `consents`・`consentExplanations`・`aiShares`・`candidates` はアプリ本体だけが書き、画面から届いた本文にこれらの区画が入っていても使わない。保存の前に、前に保存した記録から追記だけかを確かめる（`crates/ai-share` の `HouseholdBook`）。
  4. **前の起動の共有**: 世帯を開いたとき、終わりの記録が無い共有（アプリが落ちたなど）は「アプリの終了」で閉じる（終わりの日時は期限か今の早いほう）。
  5. **呼び出し元の見せ方**: 画面には実行ファイルのファイル名だけを出す（パスは世帯ファイルの記録にだけ残す。0016 の1）。

- 2026-10-19（事務所での共有。0023 の6）: 同意の記録に、書いた人 `recordedBy`（メンバーの内部IDと表示名。任意）を足した。AIの候補の判断にも `decidedByMember` を足した（`decidedBy` は今までどおり `fp`）。どちらも事務所で共有しているときだけ書き、共有していないときは書かない。追記だけの決まりは変わらない（判断の欄は1回だけ埋める）。

- 2026-11-05（Web のヒアリング。0125）: Web のヒアリングの最初の画面の次に、シートと同じ同意の3つ（利用目的・家族の情報・外部AIへの提供〔任意〕）を出す。答えは Excel と同じ受け皿で取り込み、同意の記録の下書きの方法は今までどおり `hearingSheet`（ヒアリングの同意欄）。どの依頼かは依頼番号（`hearingRef.requestId`）で分かる（Web の依頼の記録にも同じ依頼番号がある）。

- 2026-11-06（Web のヒアリングのお客さまの画面。0138）: ヒアリングの同意欄の外部 AI への提供の文を「（任意）担当の FP が、AI を使ってお答えを整理することがあります（お名前は渡しません）。このことに同意します」にした（利用者の判断。何が・誰のために使われるかが分からなかったため）。Web の画面とシート（`basic` 版2・`full` 版2〜4）で同じ文。同意の種類 `externalAi`・選択肢・同意の記録の下書き（方法 `hearingSheet`）は変えない。説明文の版（4）の文面のひな形は、規約と合わせて作るときにこの文にそろえる。
- 2026-11-07（書類の読み取り。0151）: AI に書類を読ませる2つの道は、この記録の外部AIへの提供の同意で決める。AI接続口の道具（`propose_inputs`）は今の共有の仕組みのまま（同意が `given` の世帯だけ）で、届いたことは `aiShares` の `proposals` に候補の ID と日時だけが残る（答えの中身は残さない）。ウェブのチャット AI の答えを貼り付ける入口は、同意が `given` の世帯（と見本の世帯）だけで使え、渡した記録は読み取りの記録（`documents` の `via: "paste"`・AI の名乗り・日時）に残る。説明文（4）は変えていない。書類（名前を伏せたもの）を渡すことを説明文に足すかは 0151 の未確定。
