# 0011. 世帯ファイルの封筒・自己完結・事務所データ・拡張領域・一方向の形式移行

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。世帯ファイルの形式は「安定」の公開の約束（βで作ったファイルも正式版で読める。変えるときは一方向の自動変換を必ず添える）

## 背景

- 1世帯＝1ファイルで、常に暗号化して保存する（暗号と鍵の3段は 0013）。ファイルはFPのPC内のほか、クラウドの同期フォルダに置かれることを前提にする。2台のPCで同じファイルを触ると、片方の変更が消えうる。
- 世帯ファイルは、他のFPへの引き継ぎ・バックアップからの復元・別のPCでの利用・全データの書き出し（0020）で、作ったPCの外へ出る。共有データ（制度データ・学費・保険の商品集・カスタム項目の定義）を参照だけで持つと、出た先で中身を説明できない。
- FPは、事務所全体で使うデータ（鍵置き場・保険の商品集・ひな形・前提の標準値・AIへの許可の台帳など）も持つ。どれを世帯ファイルに、どれを事務所データに置くかを決めないと、引き継ぎ・削除・バックアップの扱いが崩れる。
- FPやFPのAIは、公式に無い項目（独自の入力欄・ヒアリングの独自の質問）を足したい。公式の項目とぶつからず、カスタム層が無いPCでも捨てられない置き場が要る。
- 配布したアプリの版が上がると、世帯ファイルの形式も変わりうる。βで作ったファイルを正式版で読めなくすると、FPの業務が止まる。
- 保存の途中でアプリが落ちたり電源が切れたりしても、世帯ファイルが壊れてはならない。

## 決定

### 1. 封筒（ファイルの外側）

ファイルは「識別の印＋封筒の見出し（平文）＋暗号文」の3つでできる。

```
[4バイト] 識別の印 "LPHF"
[1バイト] 容器の版（0x01）
[4バイト] 見出しの長さ（ビッグエンディアン）
[見出し]   UTF-8 の JSON（正規化した形）
[残り]     暗号文（認証タグを含む）
```

見出しのJSON:

```json
{
  "format": "lifeplan.household",
  "formatVersion": "1.0",
  "householdId": "3f2b8c1e-9a4d-4e7b-8c21-5d0f6a9b7e10",
  "parentRevision": "sha256:…",
  "generation": 42,
  "deviceId": "a71c…（UUID）",
  "keyId": "0d4e…（UUID）",
  "cipher": "aes-256-gcm",
  "nonce": "…",
  "compression": "zstd"
}
```

- `format`（形式名）: 世帯ファイルは `lifeplan.household`。控えのPDF（0009）は同じ封筒で `lifeplan.snapshotPdf`。製品名に依存しない名前にする。
- `formatVersion`（形式の版）: 本文の形式の版。書き方は `MAJOR.MINOR`（0001の `household-file@1.0`）。本文の形が変わるたびに、どちらかを必ず上げる（下記5）。
- `householdId`（世帯の内部ID）: 変わらない乱数のID（UUID。0004・0012）。鍵置き場から世帯の鍵を探すために平文で持つ。
- `parentRevision`（親の改訂のID）: **この保存の元になったファイル全体のバイト列の指紋**（SHA-256）。ファイル自身の改訂のIDは、そのファイル全体の指紋として読む側が計算する（自分の指紋を自分の中に書けないため）。新規作成のときは `null`。
- `generation`（世代番号）: 保存のたびに1つ増える数。
- `deviceId`（PCのID）: アプリを入れたときに作る乱数のID（0012）。機器の製造番号などは使わない。
- `keyId`（鍵のID）: 鍵置き場の中の、この世帯を暗号化した世帯の鍵の鍵ID（0013）。親鍵の鍵IDではない。
- `cipher`（暗号の方式）と `nonce`: 方式の名前と、保存のたびに新しく作る乱数（0013）。
- **改ざん検出**: 認証つき暗号の認証の対象に、**見出しのJSON全体**を含める。見出しの1文字でも書き換えると開けない。これにより、別の世帯の欄への差し替えや、古い世代を新しい世代と偽る差し込みを検出する。
- 見出しには、顧客を推測できる情報（基準日・保存日時・顧客番号など）を書かない。保存日時は本文の中に持つ。

### 2. 本文の区画

暗号を外した本文は JSON で、形式は JSON Schema で公開する（0020の全データ書き出しは、この本文をそのまま出す）。

| 区画 | 中身 | 決める記録 |
|---|---|---|
| `meta` | 形式名・形式の版（封筒と同じ値の写し）、保存日時、保存したアプリの版、表示用の顧客番号、系譜 | 本記録・0012 |
| `currentVersions` | 現状の版の列。構成員と関係も各版の中に持つ（構成員のIDは版をまたいで変えない） | 0008 |
| `plans` | プラン（前提・提案・万一・データの組の版・キャッシュフロー表の手修正） | 0008 |
| `candidates` | 外から来た案 | 0008 |
| `snapshots` | 控え | 0009 |
| `imports` | 取り込みの記録（移行・ヒアリング） | 0018 ほか |
| `consents` / `aiShares` | 同意の記録、AIに渡した記録 | 0014 |
| `embedded` | 使った共有データの写し（下記3） | 本記録 |
| `extDefinitions` / `ext` | 拡張領域（下記4） | 本記録 |

- 本文の各物（構成員・口座・負債など）も、自分の `ext` を持てる。
- **取り込みの記録**（`imports`）の1件は、`{id, kind: "migration" | "hearing", at, approvedBy: "fp", ...}` に次を持つ。
  - 移行: 元ファイルの指紋、移行元のソフトと帳票の版、使った読み取り規則の版、伏せ字の後の抽出結果、移行メモ（対応先のない項目）、移行元が計算した参照値（形は0004）、互換の計算方式、AIに見出しを渡したかどうか。元のファイルそのものは持たない。
  - ヒアリング: 依頼の記録（依頼番号・シートIDと版・配置の指紋・書き出した日時）と、伏せ字の後の元の回答（0018）。

### 3. 自己完結（使った共有データを写して持つ）

- 世帯ファイルは、計算と説明に使った共有データを**参照だけでなく写して持つ**。`embedded` に置くもの:
  - `regulation`: 各プランの最後の計算で実際に読んだ制度の値の行（`<値ID>@r<rev>` と行の全体。出典を含む）。
  - `tuition`: 教育の目標が使った学費の行（0010）。
  - `insuranceProducts`: 保険契約が使った商品集の数表（商品集のIDと指紋つき。0008）。
  - `templates`: プランの作成に使った事務所のひな形・前提の標準値の指紋（中身はプランに写してあるので指紋だけ）。
- 控え（0009）は、これとは別に自分の写しを持つ（控えは変えないため）。
- 写しは計算のたびに入れ替える（使わなくなった行は消す）。控えの写しは消さない。
- 共有データの元（パック・商品集）を直しても、世帯ファイルの写しは変わらない。新しい版があるときは差分を見せ、FPが選んだときだけ入れ替える（0009の作業中のプランと同じ）。
- 共有データの元が無いPC（引き継ぎ先など）で開いたとき: 作業中のプランの `dataSet` の版がそのPCにあればそれを使う。無ければ写しで表示・説明はでき、計算し直しに写しに無い値が要るときは、手元の新しい版へ更新するよう案内する（黙って別の版で計算しない）。
- **カスタムの計算部品は既定では写さない**。書き出しのときに「使ったカスタムの写しを同梱する」を選べる。部品が無いPCで開いたら「モジュールが無いため計算できません」と出す（黙って公式に戻さない）。

### 4. 拡張領域

- 世帯ファイルとヒアリングシートの形式に、名前空間つきの拡張領域を予約する。キーは `ext.<作成者>.<項目キー>`（各段の書き方は0004の命名規則。英小文字で始まる英数字）。公式の項目のキーは `ext.` で始まらないので、ぶつからない。作成者 `official` は予約する（公式が拡張の形で試す項目に使う）。
- 独自項目の定義を、値と一緒に世帯ファイルに写して持つ:
  ```json
  "extDefinitions": {
    "ext.exampleOffice.carCount": {"type": "integer", "unit": "台", "label": "車の台数", "description": "…", "version": 1, "attachTo": "household"}
  }
  ```
- `attachTo` は `household`、`member`、または物の種類（`account`・`liability` など）。
- 拡張の値は計算部品に、マニフェストで宣言したときだけ渡す（0016）。
- **捨てない決まり**: アプリは、定義を知らない拡張項目も「不明な拡張項目」として表示・保存・書き出しする。読み込んで保存し直したときに、拡張領域を1つも失わない。
- 公式が同じ意味の項目を後から足したときは、形式の移行（下記5）の中で、FPが選んだ拡張項目を公式の項目へ引き継ぐ。引き継いだことは `meta` に記録する。

### 5. 一方向の形式移行

- アプリは、**過去のすべての形式の版**の世帯ファイルを読める。読み込み時に、古い版から今の版まで、版が上がった順に1段ずつ変換する（各段は入力と出力が決まった純粋な関数）。MINOR だけが上がった段も、変換の関数を置く（中身が「何もしない」でも置き、全段がそろっていることをCIで確かめる）。
- 保存は常に今の版で行う。変換前のファイルは、下記7の「直前の世代」として残る。
- **新しい形式の版のファイルを、古いアプリでは保存させない**。
  - MAJOR が新しいファイル: 開かない。「新しい版のアプリで保存されたファイルです。アプリを更新してください」と出す。
  - MINOR だけが新しいファイル: 閲覧だけできる（0001の定義どおり、知らない任意の欄を無視しても正しく読める）。保存・控えの作成・PDFの出力はさせない（保存し直すと、知らない欄を失うため）。
- 世帯ファイルの形式が変わる更新は、FPが遅らせられない（0017）。片方のPCだけが新しい形式で保存し、もう片方で開けなくなるのを防ぐ。形式の版を上げる変更は、まとめて行い、回数を少なくする。
- β公開のときの形式を、安定の最初の版にする。β公開より前の開発中の形式は読めなくてよい。
- **βで作った世帯ファイルは、正式版とその後のすべての版で読める**。
- 控えの中身（0009）は、入れ物の形だけを変換し、計算に使った値・出力は変えない。
- **過去の全形式のサンプルを永久に保存する**: 形式の版ごとに、架空の世帯のサンプルを `tests/fixtures/household-format/<版>/`（例: `1.0/`） に置き（暗号化したファイルと、試験用の鍵と、暗号を外した本文）、消さない。CIで毎回、すべての版のサンプルを開いて今の版へ変換し、JSON Schema の検査・計算・結果の固定値との照合を行う。

### 6. 事務所データの区分

世帯ファイルとは別に、事務所全体のデータを持つ。**世帯についての情報は世帯ファイルに、事務所全体の情報は事務所データに**置き、世帯ファイルは事務所データを参照だけで頼らない（必要なものは写す）。

| 中身 | 扱い |
|---|---|
| 鍵置き場 | 事務所の親鍵で暗号化した、世帯ごとの鍵の一覧（0013） |
| 保険の商品集 | 事務所の中で貯める数表。世帯が使うときはIDと指紋つきで世帯ファイルに写す |
| 事務所のひな形 | ひな形の世帯、よく使う進路パターン、働き方のつながり、よく使う一時的支出。公式の架空のモデル世帯を出発点に配る |
| 前提条件の標準値、事務所名・ロゴ・帳票の設定 | プランを作るときに写すためだけに使う（0008） |
| 顧客番号の採番 | PCごとの接頭辞で、2台のPCでの番号の衝突を防ぐ |
| AIへの許可の台帳 | 共有の開始・期限・取り消しの記録。親鍵による改ざん検出つき。許可の判定には使わない（判定はアプリ本体のメモリの中の状態だけで行い、起動時に台帳に残る有効な共有はすべて閉じる。0014・0015） |
| カスタムの承認の台帳と、承認した中身の保存庫 | カスタム層の中には置かない。親鍵による改ざん検出つき（0016） |

- カスタム層（設定・計算部品・帳票・入力欄）は事務所データともデータフォルダとも**別の場所**に置く（0016・0019）。
- 事務所データも暗号化して保存し、毎日自動でバックアップする（暗号化のまま、30世代）。
- 鍵置き場のバックアップは、アプリが決めた場所に日ごとの世代で最大30日分だけ持ち、OSや同期サービスのバックアップの対象から外す（0013）。

### 7. 保存の手順と直前の世代

- 保存は**一時ファイルに書いて差し替える**:
  1. 同じフォルダに一時ファイル（`<ファイル名>.tmp-<乱数>`）を作り、全体を書く。
  2. 一時ファイルをディスクへ同期する。
  3. 今のファイルを `<ファイル名>.prev` へ名前を変える（前の `.prev` は置き換わる）。
  4. 一時ファイルを今のファイルの名前へ変える。
  5. フォルダをディスクへ同期する（できるOSのとき）。
- **直前の世代**（`.prev`）を1つ残す。これとは別に毎日の自動バックアップ（30世代）がある。
- 起動時の片付け: 今のファイルが無く、完全な一時ファイルか `.prev` があれば、新しいほうを今のファイルに戻す。残った一時ファイルは、開けることを確かめてから片付ける。
- **2台のPCでの分岐の検出**: 保存の前に、今のファイルの指紋が、開いたときのファイルの指紋（＝これから書く `parentRevision`）と同じかを確かめる。違えば、別のPCか別の画面が先に保存している。同期サービスが作る「競合したコピー」も、見出しの `householdId` と `parentRevision` で同じ世帯の分岐と判定する。分岐を見つけたら、両方の違いを見せてどちらを残すかFPに選ばせ、選ばなかったほうも消さずに別のファイルとして残す。
- 世帯ファイルの保存場所は、カスタム層・SDK・AIの作業フォルダの中と、それらを含むフォルダを選べない（0016）。

## 理由

- **見出しを平文で持ち、全体を認証の対象にする**: 鍵を探すために世帯IDと鍵のIDは暗号の外に要る。外に出す以上、書き換えを検出できなければならない。
- **改訂のIDをファイル全体の指紋にする**: 乱数のIDだと、ファイルの中身とIDが食い違っても気づけない。指紋なら、同期サービスがどのファイルを作っても、中身から親子関係を確かめられる。暗号文の指紋なので中身は漏れない。
- **新しい版のファイルを古いアプリで保存させない**: 古いアプリが知らない項目を落として保存すると、データが消える。MINOR の追加は読むだけなら害がないので閲覧は許すが、保存は許さない。形式が変わる更新は遅らせられない決まりと組み合わせれば実害は小さい。
- **共有データを写す**: 引き継ぎ・復元・書き出しの先でも、使った値と出典を説明できる。制度データを更新しても、過去のプランの数字が勝手に変わらない。
- **拡張の定義を写し、知らない拡張を捨てない**: カスタム層はPCごとにあるので、定義が無いPCで開いて保存しただけで独自項目が消えると、FPのデータが失われる。
- **一時ファイルからの差し替え**: 試作で、直接の上書きは途中で落ちると前の世代も新しい世代も読めなくなることを確かめた。
- **過去の全形式のサンプルを永久に残す**: 形式の変換は、古い版ほど試されなくなる。サンプルを消さずに毎回流せば、何年前の版のファイルでも開けることを機械で保証できる。

## 影響

- 後から変えると: 配布済みの世帯ファイルが読めなくなる。書き出し・引き継ぎ・カスタム項目が壊れる。
- 守るべき決まり:
  - 形式の版を上げる変更には、必ず1段分の変換の関数と、その版のサンプルを添える。
  - サンプルを消さない。変換の関数も消さない（古い版から今の版までの全段を残す）。
  - 見出しに顧客を推測できる情報を書かない。
  - 世帯ファイルは事務所データ・カスタム層を参照だけで頼らない。
  - 拡張領域を読んで保存し直したときに、失わない。
- テストで確かめること:
  - すべての形式の版のサンプルが、今の版へ変換でき、検査・計算・固定値との照合を通ること（CI、毎回）。
  - MAJOR が新しいファイルを古いアプリが開かないこと。MINOR だけが新しいファイルを閲覧はでき、保存・控え・PDFの出力ができないこと。
  - 見出しの各欄の1文字の書き換え、別の世帯の見出しへの差し替え、古い世代の差し込みを検出すること。
  - 保存の各段階（一時ファイルの途中・差し替えの直前・直後）で強制終了しても、前の世代か新しい世代の完全な形で残ること。
  - 同じ親から2つの保存が作られたとき、分岐として検出し、どちらも失わないこと。
  - 知らない拡張項目を含むファイルを開いて保存し直しても、拡張項目がそのまま残ること。
  - 共有データの元が無い環境で開いても、写しから値と出典を表示できること。

## 試作での確認

- 3段の鍵（親鍵はOSの資格情報の保管庫、世帯の鍵は鍵置き場、世帯ファイルは世帯の鍵）で作った世帯ファイルについて、1ビットの改ざん・別の世帯の鍵・違う親鍵では開けないことを確かめた。試作では世帯IDと世代番号を認証の対象に入れ、別の世帯の欄への差し替えと古い世代の差し込みを防いだ（本記録では見出し全体に広げる）。
- 一時ファイルに書いて差し替える保存で、書き込みの途中・差し替えの直前に強制終了しても前の世代のまま読め、差し替えの直後なら新しい世代が完全な形で読めた。比較として直接上書きでは、前の世代も新しい世代も読めなくなった。
- 1MBの世帯ファイルの暗号化・復号は、それぞれ約8ミリ秒（Apple シリコンのMac）。
- Windows 向けはコンパイルだけ確かめた。Windows の実機での途中終了の試験は未実施。
