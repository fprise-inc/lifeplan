# 0183. AI接続口の「数字の根拠」と「対応範囲の一覧」（explain_value・search_coverage・get_coverage）

- 状態: 採用（一部未確定）（2026-11-09）
- 固定の強さ: 道具の名前と入出力は試験版（0015 と同じ。予告して変えることがある）。作り（根拠は画面の根拠のパネルと同じ関数を接続口が同梱して同じ固めた実行環境で動かす・対応範囲の一覧は `docs/coverage/` の YAML を正本にしてビルドで確かめて同梱する・どちらも単体の群）は内部。一覧の中身はいつでも直す
- 前提にする記録: 0005（計算の実行環境）、0006 の7（根拠の記録「全部」と根拠の表示）、0014（AIに渡した記録）、0015（AI接続口）、0016（提示層は内部情報を受け取らない）、0087（要望・不具合を送る）、0151（書類の読み取りの道具）

## 背景

- FP がファイナンシアを使っていて「この数字はどんな計算？」「〇〇は入っている？」と思ったとき、自分の AI（AI接続口をつないだ物）に聞いても、AI は推測で答えるしかなかった。
  - 画面には「数字の根拠」（表の数字を押すと右に出る内訳・式・使った制度の値と出典。0006 の7）があるが、接続口の `calculate` は根拠の記録なし（`trace: "none"`）で計算し、表の数字しか返さない。
  - ソフトが何をどう計算しているか（入っている・近似している・まだ入っていない）は、計算の部品のコメントと設計記録に散らばっていて、FP に見せてよい形の一覧が無い。設計記録は社内向けの判断の経緯が多く、そのまま AI に渡す物ではない。
- 利用者の判断（2026-11-09）: 2つの道具を足す。1つの数字の根拠を返す道具と、ソフトの作りを調べる道具。どちらも推測でなく根拠のある答えを返すため。

## 決定

### 1. 数字の根拠を返す道具 `explain_value`（単体の群。`share_id` のときは世帯を扱う群）

- 入力: 世帯は `calculate` と同じく、見本の世帯（`sample_household_id`）・FP が渡した世帯（`share_id`）・AI が組み立てた入力（`input`）のどれか1つ。プラン・万一の想定は `changes`（JSON Patch の `replace`・`add`・`remove`）、ストレステストは `stress_test` で当てる（`calculate` と同じ部品で選び・当てる）。
- 指す数字: `row` と `year`。`row` は画面のキャッシュフロー表の行の鍵（`taxSi`・`pension:self`・`education`・`financial` など。画面の表の行の決まり `rowDefs` と同じ）か、`calculate` の `table` の行ID（`cf.` で始まる。人ごとの行は `member`、物ごとの行は `object` も）。`cf.` の行は、その行のマスを含む画面の行に読み替える。`row` を省くと、その世帯で根拠を出せる行の一覧と表の年の範囲を返す。合計の行（収入合計・支出合計・年間収支）は画面と同じく根拠を出さず、内訳の行ごとに聞くよう返す。
- 返すもの: `evidence` は画面の根拠のパネルと同じ中身（見出し・合計・その年の家族の年齢・計算式ごとの内訳・式の説明・使った制度の値〔名前・値・出典の場所・制度データの版・適用の始まり〕・注記）。`ids` に、式の説明と同じ並びの計算式ID と、使った制度の値と同じ並びの制度の値ID を添える（制度の値ID は `get_regulation_value` で値・適用期間・出典を引ける）。世帯の物の ID は返さない（行を選ぶために受け取るだけ）。
- 大きさ: 1つのマスの根拠だけを返す。`depth`（内側の計算を何段までたどって制度の値を集めるか。0〜3、既定3）と `max_params`（制度の値を何件まで。1〜24、既定24）で小さくできる（既定は画面と同じ）。答えが 64KB を超えたら、小さくして呼び直すよう返す。
- 計算: 根拠の記録「全部」（`trace: "full"`）で、アプリ本体の根拠の計算と同じ上限（`Limits::FULL_TRACE`）と同じ options（表示の形にしない・検査済みのパックの指紋）で計算する。計算の要求は `calculate` と同じ入力（画面が計算の前に当てる「計算に入れない行を外す」「事務所の推定の値」は、`calculate` と同じく当てない。未確定）。→ 2026-11-10 に当てると決めた（0184。下の追記）。
- 世帯を扱う群の決まり（0015 の2）を守る: `share_id` の世帯は必ずアプリ本体に頼み（許可の判定・復号・縮約・包み方・記録はアプリ本体だけ）、接続口は縮約版の `input` をそのまま計算に使う。読んだ道具の名前 `explain_value` で「AIに渡した記録」に残る。期限切れ・取り消し・アプリが起動していないときは、ほかの道具と同じ答え。`client_text` の扱いも同じ（根拠には世帯の文章の項目が入らない。縮約版の文章は計算の入力に入らない）。

### 2. 画面と接続口で根拠の文をずらさない: 画面の関数をそのまま同梱する

- 根拠の組み立ては、画面の関数（`app/src/workspace/evidence.ts` の `buildEvidence`）を、接続口がそのまま動かす。接続口の側に読み方を書き直さない。
  - 画面の側: `buildEvidence` を `evidenceDetail`（根拠の中身と、その元の計算式ID・制度の値ID。集め方の細かさ `depth`・`maxParams` を受ける）と、その中身だけを返す `buildEvidence` に分けた。画面は今までどおり `buildEvidence` を既定の細かさで呼ぶ（提示層には ID を渡さない。0016 の2）。
  - 接続口の入口: `app/src/connector/explain.ts`（行の選び方と返す形だけを決め、根拠は `evidenceDetail` に任せる）。lint で、作業の層のうち `evidence`・`present` だけを読めるようにし、画面の部品（preact）・本体の命令・画面の大枠を読めなくした。表の行の決まりが読む `resultRows.ts` から、画面の hook（`useRefResult`）を `useRefResult.ts` に移した。
  - まとめる: `app/scripts/build-explain.ts`（`npm run build:explain`。`prepare-assets` からも呼ぶ。中身が変わっていなければ作り直さない）が、1つの JS（`crates/lifeplan/dist/explain.js`。iife・グローバル `FinanciaExplain`）にまとめる。npm のパッケージが1つでも入ったら・動的な import があったら止める。
  - 動かす: 接続口（`crates/lifeplan/build.rs`）がこの JS を埋め込み、計算と同じ固めた新しい実行環境（engine-host の `Sandbox`。時計・乱数・環境で変わる数学の関数は使えない）で読み込み、`Sandbox::call_function`（engine-host に足した。グローバルの物の関数を3つの文字の引数で呼ぶ）で呼ぶ。計算と根拠の読み方は別の実行環境（計算の後に捨て、読み方用に新しく作る）。
- テスト: 画面の側（`app/test/connector-explain.test.ts`）で、モデル世帯6つ × 根拠を出せるすべての行 × 3つの年で、接続口の入口の答えが `buildEvidence` と同じことを確かめ、決まった問い（9件）の答えを見本（`crates/lifeplan/tests/fixtures/explain-value/expected.json`）に書く（`LIFEPLAN_UPDATE_FIXTURES=1` で作り直す）。接続口の側（`crates/lifeplan/tests/mcp_connector.rs` の `explain_value_matches_the_screen`）で、本物の接続口を起動して同じ問いを MCP で呼び、見本と1文字も違わないことを確かめる。Node と quickjs-ng で同じ関数が同じ答えを返すことになる。

### 3. 対応範囲の一覧（`docs/coverage/`）

- 正本は `docs/coverage/<分野>.yaml`（1分野1ファイル）。形は `docs/coverage/coverage.schema.json`。項目ごとに:
  - `id`（`<分野>.<名前>`）・`title`・`status`（`included`＝入っている／`approximated`＝近似している／`notYet`＝まだ入っていない）・`summary`（「〇〇は入っていますか」への1〜2文の答え）
  - `how`（どう計算するか。入っている・近似している）、`approximation` と `reason`（どう近似しているか・理由。近似している）、`reason`（まだ入れていない理由。まだ入っていない）、`instead`（代わりにできること）
  - `keywords`（探す言葉）・`items`（関係する入力項目ID）・`fields`（画面の入力項目・欄の呼び方）・`rules`（根拠の制度・法令の名前）・`regulation`（使う制度の値ID）・`rows`（金額が入る表の行ID）・`components`（中身を決めている計算の部品と、書いたときの部品の `revision`）・`related`（関係する項目）
- FP に見せてよい形にする: 設計記録をそのまま同梱しない。文は FP が読んで分かる言葉で、画面の呼び方に合わせる。設計記録の名前と番号・内部の決定の番号・作業の印は書かない（検査が止める）。内部の英語の ID は決まった欄にだけ書く。実在の会社の名前を書かない（国・公的機関・法令の名前はよい）。
- 確かめて1つにする: `engine/scripts/coverage.ts`（読む・形〔JSON Schema〕・参照〔入力項目ID・制度の値ID・表の行ID・部品が登録簿にあること、関係する項目が一覧にあること、鍵が重ならないこと〕・書かない言葉を確かめる）と `engine/scripts/build-coverage.ts`（engine の `npm run build` の最後に流す）が、`engine/dist/coverage.json` を作る。同梱する形には、入力項目ID・制度の値ID・表の行ID・部品に登録簿の名前を添え、部品の `revision` は入れない（照合はテストだけで使う）。版は中身の指紋（sha256 の先頭12桁）で、道具の答えに `coverageVersion` として添える。
- 最初の版（2026-11-09）: 14 分野（計算の基本の決まり・収入と支出・税・社会保険・公的年金・給付・手当・子ども・教育・住まい・住宅ローン・収益不動産・保険・万一の想定・必要保障額・介護・親・相続・贈与・貯蓄・運用）の 141 項目（入っている 85・近似 40・まだ 16）。計算の部品の先頭のコメントと処理・根拠の表示の式の説明・計算の知らせの文・入力項目と登録簿・推定の見直しの一覧（`docs/estimates-review.md`）・設計記録の未確定から書いた。全部を網羅した一覧ではない（目次の答えにそう書く）。

### 4. 一覧と計算の作りをずらさない仕組み

- 項目の `components` に、その項目の中身を決めている計算の部品と、書いた（見直した）ときの部品の `revision` を書く。engine のテスト（`engine/test/coverage.test.ts`）が、今の部品の `revision`（公式部品の定義）と比べ、1つでも違えば**落ちる**（どの項目のどの部品が何から何に変わったかを出す）。部品を直して `revision` を上げた人は、その部品を書いた項目の説明が今の計算と合っているかを見直し、数を今の `revision` にする。
  - 警告ではなく失敗にした理由: 警告は読まれずに残りやすく、一覧が古いまま AI に「入っている」と答えさせるほうが害が大きい。部品の `revision` は計算の中身を変えたときに上げる物（0006）なので、見直しの回数は部品の直しの回数と同じで済む。
  - `plan.cashflow` のように多くの話題にまたがる部品は、その項目の中身を本当に決めている物でなければ書かない（見直しの空振りを増やさない）。
- 参照の検査（登録簿に無い入力項目ID・制度の値ID・表の行ID・部品）は、engine のビルドとテストの両方で止める（入力項目や制度の値を消した・名前を変えたときに気づく）。
- CI: `docs/coverage/` の変更で engine（検査・テスト・ビルド）と host（接続口のテスト）を流す（`.github/scripts/ci-changes.sh`。`docs/` のほかの変更は今までどおり何も流さない）。

### 5. ソフトの作りを調べる道具 `search_coverage`・`get_coverage`（単体の群）

- 顧客の情報を含まないので、アプリが起動していなくても、同意なしで使える。
- `search_coverage`: `query`（言葉や問い）と、任意の `status`・`area`・`limit`（1〜20、既定5）。日本語の問いを形態素に分けずに読むため、問いと項目の文の「2文字の並び」の重なりで点を付け（ひらがなだけの並びは言い回しなので数えない。名前・探す言葉の重みを大きく）、名前・探す言葉が問いの中にそのまま入っていれば点を足す。いちばん近い項目の4分の1に満たない物は出さない。返すのは鍵・名前・分野・状態・短い答え・点。
- `get_coverage`: `id` で項目の中身を全部（関係する入力項目は ID と名前、制度の値ID は `get_regulation_value` に、表の行は `explain_value` につなげる）。`id` を省くと分野ごとの目次（鍵・名前・状態と状態ごとの数）。
- 「まだ入っていない」と答えるとき（まだ入っていない項目が当たった・何も当たらなかった・まだ入っていない項目を開いた）は、`feedback` に、FP がアプリの上の帯の FP のメニュー（カバンのアイコン）の「ファイナンシアへ」→「要望・不具合を送る」から送れること（お知らせの一覧の下にも同じ入口がある）と、この接続口からは送れないことを返す。接続口から要望を送る道具は作らない（送るのは FP がアプリで行う。0015 の追記の3段目）。
- 何も当たらなかったときは、言い方を変えるか目次を見るよう返し、「入っていると推測で答えないで」と書く。

### 6. サーバーの説明（INSTRUCTIONS）

- 「この数字はどんな計算？」には推測で答えず `explain_value` で根拠を取り出す（画面の「数字の根拠」と同じ中身）、「〇〇は入っている？」には推測で答えず、まず `search_coverage` で探して `get_coverage` で中身を読んでから答える、一覧に無い話題は入っていると推測しない、まだ入っていない物は FP がアプリの「要望・不具合を送る」から送れると伝える（接続口からは送らない）、を足した。単体で使える道具の一覧にも足した。

### 7. ビルドと CI

- 接続口のビルドには、`engine/dist`（エンジン・制度データ・対応範囲の一覧）に加えて `crates/lifeplan/dist/explain.js` が要る（無ければ build.rs が作り方を出して止まる）。CI に、エンジンのビルドの後に数字の根拠の読み方をまとめるジョブ `ai-explain` を足し、接続口をビルドするジョブ（host・bench）がその成果物を使う。画面の根拠の関数が読むファイル（`app/src`・`app/scripts`・`report/`・`hearing/`）の変更でも host を流す。

## 理由

- 画面の関数をそのまま同梱すれば、画面と接続口で根拠の文・内訳の分け方・制度の値の選び方がずれない（直すのは1か所）。計算と同じ固めた実行環境で動かすので、接続口に新しい実行の仕組みを足さない（0005）。
- 一覧を構造化した YAML にすれば、参照（入力項目・制度の値・部品）を機械で確かめられ、部品の直しと結びつけて見直しを促せる。分野ごとのファイルに分けると、直すときの重なりが減る。
- 制度データ（0007）と同じく「YAML が正本・ビルドで確かめて JSON で配る」形にすると、接続口に YAML を読む部品を足さずに済む。

## 代案（採らなかったもの）

- **根拠の読み方を Rust で書き直す**: 画面の表の行の決まり（車・物件・ローンの分け方など）と式の説明の表を二重に持つことになり、ずれる。
- **根拠の読み方を計算エンジンのまとめた JS に入れる**: 表示のための部品（行の名前・式の説明）が計算の正（0005）に入り、エンジンの中身の指紋が画面の文の直しで変わる。
- **設計記録をそのまま同梱する**: 社内向けの判断の経緯が多く、FP への答えに向かない。決まった欄が無いので、部品の直しと結びつけられない。
- **一覧を自由な文（Markdown）で書く**: 参照の検査も、部品の `revision` との照合もできない。
- **部品の `revision` のずれを警告だけにする**: 読まれずに残る（4）。
- **接続口から要望を送る道具**: PC の外へ出る物を増やす操作は AI からはさせない（0015 の追記の3段目）。

## 未確定

- **事務所の行の名前**: 画面は事務所で直した表の行の名前で根拠の見出しを出すが、接続口は公式の名前（接続口は事務所の設定を読まない）。渡された世帯のときに、アプリ本体から事務所の行の名前を受け取るか。
- ~~**画面が計算の前に当てる物**: 画面は「計算に入れない」にした収入・負債・夢を外し、事務所の推定の値を足してから計算する。接続口の `calculate`・`explain_value` は世帯の入力のまま計算する（渡された世帯の縮約版も）。渡された世帯の計算を画面と同じにするには、アプリ本体が計算の要求の形にしてから渡すか、接続口が同じ処理を持つか（読み方と同じく画面の関数を同梱できる）。~~（2026-11-10 に決めた: 接続口が画面の関数を同梱して当てる。0184）
- **表の外の数字の根拠**: 必要保障額の推移・相続税の目安・万一の想定の画面の表は、`explain_value` の対象にしていない（キャッシュフロー表の数字だけ）。
- **revision の上がらない変更**: 制度データの値・推定の目安・画面の側の計算（月々の目安など）が変わっても、一覧の見直しは促されない。制度データの版や推定の見直しの一覧と結びつけるか。
- **一覧の中身の原本照合**: 根拠の法令の条文の番号の一部は、計算の部品のコメントに無く、一般の知識で書いた（原本で確かめる）。画面の欄の呼び方の一部（万一の想定の画面・退職金の受け取りの並び）は、画面で確かめきれていない。
- **探し方の精度**: 形態素に分けない簡単な読み方。言い換えの辞書（入力の「探して開く」の辞書。0045）と共有するか、項目の `keywords` を増やすかは、FP の問いを見て決める。
- **一覧の英語版**、一覧を画面（アプリの中のヘルプ）にも出すか。
- **一覧を書いているときに見つけた、計算の知らせの文と部品の食い違い**（直すかは別の回で確かめる）: ① 70歳以上の高額療養費の知らせは「上限なしで数えています」だが、部品は70歳未満の区分と3割の負担で上限をかけている。② 相続時精算課税の知らせは「相続のときの加算は入れていません」だが、相続税の目安の部品は精算課税の贈与を課税価格に足している。

## 追記
