# 0009. 作業中のプランと控え・取り下げ・PDFの刻印とTypst

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: 作業中のプランと控えの区別、控えの中身、取り下げの単位、刻印の中身、帳票の外側でアプリが付ける仕組みは β公開から変えない（骨格）。帳票の部品（Typstのパッケージ）の入出力は「試験版」（過去の版をアプリ内に残す）

## 背景

- FPは、顧客に見せた提案書について、後から「あのとき何を前提に、どの制度の値で、どう計算したか」を説明できる必要がある。一方で、制度データとアプリは更新され続けるので、同じ入力でも計算し直すと数字が変わる。
- 誤った制度の値や計算が配布された後に見つかったとき、その誤りを使っているプランだけを止めたい。止める単位が粗いと、関係のないプランまで止まる。
- 提案書のPDFには、宛名（顧客の氏名）が入る。顧客の氏名は保存しない（0012）。
- 顧客に渡すPDFには提供元（FPライズ）の表記を入れない。一方で、どの制度データ・基準日で計算したかはPDFから分かるようにしたい。
- FPは独自の帳票を作ったり、計算部品を差し替えたりできる（0016）。独自の計算を使ったことは顧客が見るPDFには表示せず、FP向けの画面・保存データ・PDFの印刷されない内部情報にだけ記録する。必須の記載（試算である旨など）と刻印は、FPがページを減らしても独自帳票に替えても消えてはならない。
- PDFは Windows と Mac で同じものにしたい。

## 決定

### 1. 作業中のプラン

- 作業中のプランは、使う制度・マスタの**データの組の版**（`dataSet`。どのパックのどの版を組にしたものか。目録の形は 0007・0017）を1つ持つ（0008）。
- 新しいデータの組が届いても、作業中のプランは自動では切り替わらない。アプリは新旧で計算し、「制度改正で○○が±○円変わります」と差分を見せ、FPが「更新」を押したときに `dataSet` を進める。
- カスタムの計算部品・設定を変えたときも同じく、差分を見せてから再計算する。
- 根拠の記録（0006）は、作業中のプランでは保存しない。必要なときに計算し直す（容量のため）。

### 2. 控え（顧客に見せた版）

- PDFを出力したとき、または「控えとして保存」を押したときに、控えを作る。控えは世帯ファイルの `snapshots` 区画に置き、**作った後は変えない**。
- 控えの中身:

```json
{
  "id": "<控え>",
  "createdAt": "2027-04-12T14:03:00+09:00",
  "plan": "<プラン>",
  "baseMonth": "2027-04",
  "inputs": {…その時点の現状の版とプランの全体の写し…},
  "dataSet": {"id": "…", "packs": {"regulation.tax": "2027.3.0", "regulation.pension": "2027.2.1", "master.education.tuition": "2027.5.0"}},
  "usedValues": [{"ref": "incomeTax.basicDeduction@r4", "value": […]}],
  "components": [{"id": "pension.oldAge.basic", "contract": "2.1", "revision": 14, "hash": "sha256:…"}],
  "customModules": [{"id": "…", "digest": "sha256:…"}],
  "report": {"packages": [{"name": "@lifeplan/report-core", "version": "1.2.0"}], "typst": "0.x.y", "fonts": [{"file": "BIZUDGothic-Regular.ttf", "digest": "sha256:…"}], "customTemplate": {"digest": "sha256:…"} },
  "appVersion": "1.0.3",
  "outputs": {…キャッシュフロー表と主な結果…},
  "evidence": {…根拠の記録（全部）…},
  "pdf": {"file": "<控えのPDFのファイル名>", "digest": "sha256:…", "keyId": "…"},
  "digest": "sha256:…"
}
```

- `usedValues` は、実際に読んだ制度の値の**IDと値そのもの**（0007の `<値ID>@r<rev>`）。パックが手元に無い環境でも控えを説明できるようにする。
- `components` は、使った計算部品のIDと約束の版・実装の改訂・指紋（0006の見出しと同じ形）。
- `digest` は控えの中身（`digest` 以外）の指紋。アプリは開くたびに確かめ、食い違えば「控えが変更されています」と出す。
- 控えは消せるが、書き換えはできない（直したいときは新しい控えを作る）。

### 3. 控えのPDFは宛名なしで別ファイル

- 控えのPDFは、**宛名欄を空にした版**で作る。宛名は印刷・出力の画面でその場で入力し、出力するPDFにだけ重ね、保存しない。
- 控えのPDFは世帯ファイルの中に入れず、**別の暗号化ファイル**として世帯ファイルと同じ場所に置く。暗号は同じ世帯の鍵（0013）、封筒は世帯ファイルと同じ形（0011。形式名だけ `lifeplan.snapshotPdf`）。世帯ファイルには指紋（`pdf.digest`）だけを持つ。
- **再印刷は、保存したPDFに宛名を重ねて作る**（帳票を組み直さない）。宛名を重ねる位置は、表紙の部品が宣言する宛名欄の位置を控えに記録しておく。
- 世帯の完全削除（0013）では、控えのPDFのファイルも消す。

### 4. 取り下げの単位

- 取り下げの単位は次の2つ:
  - 制度の値の1行: `<制度の値ID>@r<rev>`（0007）。
  - 計算部品の実装の改訂: `<計算部品ID>@<revision>`（0006）。ロジックの誤りのとき。
- 取り下げの一覧の配り方・署名・有効期限は 0017 で定める。一覧の中では、制度の値は `{id, packVersion}`（その値IDの行のうち、そのパックの版で入った行。0007）、計算部品は `{id, revision}` で書く。アプリはこれを上の2つの書き方に読み替えて照合する。
- アプリは、取り下げの一覧が届いたら、作業中のプランについては `dataSet` と使う部品の改訂から、控えについては `usedValues` と `components` から、影響のあるものだけを特定する。
- 影響のある作業中のプラン: 赤い帯を出し、更新するまで**新しい提案書の出力を止める**。
- 影響のある控え: **再印刷は止めない**。FP向けの画面に「取り下げ済みの値・計算を含む」と注記する。この注記はPDFには出さない。

### 5. 刻印

- PDFの**各ページのフッター**に、次の2つを刻印する:
  - 制度データの版（データの組の版を表す短い文字列）
  - 計算基準日
  - 例: `制度データ 2027.03-b ／ 計算基準日 2027-04`（書式の細部は未確定。計算基準日は月までで、0003 の `baseMonth`）
- 刻印に**製品名・提供元の名前は入れない**。
- 刻印は、帳票（Typst）の中身ではなく**アプリが帳票の外側で付ける**。帳票の作者（公式・FP・FPのAI）は刻印の位置に描けず、刻印を消せない。
- β版の期間は、画面とPDFに「β版・試算」の透かしを、刻印と同じ仕組みで付ける。

### 6. 必須の記載

- 次の記載は、刻印と同じく**アプリが帳票の外側で必ず付ける**: 試算である旨、公的データの出典名、「前提条件や計算方法の一部は担当FPが設定しています」の一般的な文、該当する場合は制度の見直し前の計算である旨、反映していない改正がある旨。
- 公式の「前提条件と注意書き」のページを使っていれば、そのページの決まった欄に入れる。独自帳票でそのページが無いときは、アプリが「注意書き」のページを最後に足す。
- FPは文言を足すこと、体裁（文字の大きさの範囲内など）を変えることはできるが、消すことはできない。
- 出力の後に、アプリがPDFから文字を抜き出し、刻印と必須の記載が入っていることを確かめる。入っていなければ出力しない。

### 7. カスタム計算の記録

- カスタムの計算部品・エンジン一式を使ったことは、**顧客が見る紙面には出さない**。記録する場所は次の3つだけ:
  - FP向けの画面（「カスタム計算あり」の印）
  - 控え（`customModules` の指紋）
  - PDFの印刷されない内部情報（XMPのメタデータ）
- PDFの内部情報に入れる項目: 控えのID、データの組の版、計算基準日、カスタムを使ったかどうかと、その指紋の一覧。顧客の情報・世帯の内部ID・FPのメモは入れない。
- PDFの作成ソフトの欄（Producer・Creator）は空にする。内部情報の名前空間は製品名・社名を含まない名前（例: `urn:x-lifeplan:proposal:1`）にする。
- これらもアプリが帳票の外側で付ける。帳票の部品は、カスタムを使ったかどうかの情報を受け取らない（0016の「提示層は内部情報を受け取らない」）。

### 8. Typst と同梱フォント

- PDFは Typst をアプリ（Rust側）に**ライブラリとして組み込んで**作る。外部のコマンドは呼ばない。
- Typst の版はアプリの版ごとに固定する。上げるときは、事前に公式の帳票とFPの独自帳票（手元にあるもの）をすべて試し、失敗するものがあれば知らせる（0016）。
- フォントは **BIZ UDゴシック**（SIL OFL 1.1）を同梱し、ライセンス文も同梱する。**OSに入っているフォントは探さない・使わない**（Windows と Mac で同じPDFにするため）。帳票が同梱以外のフォントを指定したら、エラーにする。
- グラフは画面と同じ描画部品で作ったもの（ベクター）を帳票に渡す。
- Typst の実行には、時間とメモリの上限を付ける。読めるのは帳票のフォルダと渡された値だけ（0016）。

### 9. 帳票の部品のパッケージの形

- 公式の帳票の部品は、版つきの Typst パッケージとして出す。名前の空間は製品名に依存しない `@lifeplan/`（例: `@lifeplan/report-core:1.2.0`）。
- パッケージの中身: `typst.toml`（名前・版・入口・必要な Typst の版）、ページの部品（表紙、前提条件と注意書き、世帯サマリー、ライフイベント表、キャッシュフロー表、教育費、住宅ローン、老後と年金、万一、保障内容一覧、変更点の一覧）、共通の部品（表・見出し・グラフの枠）。
- 帳票に渡す値は、1つのJSON（**帳票の入力**）にまとめる。形は JSON Schema で定め、版を付ける。中身は提示に必要な値だけで、FP用のメモ・他の顧客・カスタム計算の印・内部ID・宛名は入れない。宛名は3のとおり後から重ねる。
- 表紙の部品は、宛名欄の位置（ページ番号・座標・大きさ）を宣言する。
- 帳票の外側の帯（刻印の帯）の高さは、アプリが決めて帳票に渡す。帳票はその内側にだけ描く。
- 公式のパッケージの過去の版はアプリ内に残す。FPの独自帳票は、使う公式パッケージの版を宣言する。

## 理由

- **作業中と控えを分ける**: 作業中のプランは更新に追従させたいが、顧客に見せたものは再現できなければならない。両方を1つで満たそうとすると、どちらかが崩れる。
- **使った値そのものを控えに写す**: パックの版だけを持つと、パックが失われた環境や、取り下げで値が差し替わった後に説明できない。
- **宛名なしのPDFを別ファイルに**: 氏名を保存しないためには、宛名入りのPDFを残せない。世帯ファイルに入れると、ファイルが大きくなり、同期・保存のたびにPDFを書き直すことになる。
- **再印刷は保存したPDFに宛名を重ねる**: 組み直すと、Typst・フォント・帳票の部品の版が変わったときに中身が変わりうる。保存したPDFを使えば、顧客に見せたものと同じものが出る。古い Typst をアプリに残し続ける必要もない。
- **取り下げを値の1行と部品の改訂の単位にする**: 根拠の記録からどちらも特定できるので、影響のあるプランだけを止められる。分野やパックの単位では粗すぎる。
- **刻印と必須の記載をアプリが外側で付ける**: 帳票は公式もFPの独自のものも差し替えられるので、帳票の中で付ける形では消されうる。出力後の文字の抜き出しで確かめれば、帳票の作りに関係なく保証できる。
- **OSのフォントを使わない**: OSごとにフォントが違うと、同じ入力から違うPDFになり、CIでの確かめもできない。

## 影響

- 後から変えると: 過去の提案書を再現できなくなる。取り下げの照合ができなくなる。FPの独自帳票が動かなくなる。
- 守るべき決まり:
  - 控えは作った後に変えない。控えの形式を変えるときも、中身の値は変換しない（形式の移行は入れ物だけ。0011）。
  - 宛名を保存しない（世帯ファイル・控え・PDFのファイル・ログのどこにも）。
  - 帳票の入力に内部情報を入れない。
  - 刻印・必須の記載・内部情報は、帳票の外側の1か所の処理で付ける。
- テストで確かめること:
  - 控えから、同じ版の部品と `usedValues` で計算し直すと `outputs` と一致すること。
  - 控えの `digest` の改ざんを検出すること。
  - 取り下げの一覧を与えたとき、影響のあるプラン・控えだけが特定されること。作業中のプランの出力が止まり、控えの再印刷は止まらないこと。
  - 刻印の帯に描こうとする帳票・必須の記載のページを消そうとする帳票でも、出力されたPDFに刻印と必須の記載が入ること。
  - PDFの文字を抜き出して、数字がエンジンの出力と一致すること（代表的なプランで、CI）。
  - Windows と Mac で、同じ入力から同じPDF（バイト単位、または文字と配置の単位）ができること。
  - 帳票の入力・PDFの内部情報・Producer の欄に、製品名・社名・宛名・FPのメモが入っていないこと。
