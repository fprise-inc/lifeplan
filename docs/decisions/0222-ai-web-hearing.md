# 0222. AI 接続口から Web のヒアリングの項目を決め、URL を発行する（get_hearing_options・issue_hearing_url・propose_hearing_template）

- 状態: 採用（一部未確定）（2026-11-17）
- 固定の強さ: 道具の名前と入出力（`get_hearing_options`・`issue_hearing_url`・`propose_hearing_template`）、接続口とアプリ本体の依頼（`getOfficeHearing`・`issueHearing`・`proposeHearingTemplate`）、本体の命令（`ai_hearing_jobs`・`ai_hearing_job_done`・`ai_hearing_template_candidates`・`ai_hearing_template_take`・`office_hearing_get`・`office_hearing_put`）は試験版（0015 と同じ。予告して変えることがある）。次は固定: 見直し（今の値を見せる項目）を含む依頼の URL と案内文は AI に返さない、鍵の組・合言葉はアプリの画面だけが作り世帯ファイルか事務所データにだけ置く（接続口・本体の受け口は鍵を持たない）、AI に顧客番号・世帯の内部 ID・呼び名を返さない、事務所のひな形は FP が承認したときだけ入る、暗号の形・受け付けの API・答えの中身の形（0125 の骨格）は変えない。上限の値・帯と一覧の言葉・事務所データの欄の形は内部（後から変えてよい。変えたら追記に書く）。世帯ファイルの形式は 0.81（`hearing.web` の1件に任意の欄 `origin` を足すだけの MINOR。10）
- 前提にする記録: 0125（Web のヒアリング。暗号・受け付けの API・FP の側）、0192（FP の画面: ひな形・話題・独自の質問・数え方・発行・事務所のひな形）、0190（書類の頼み方）、0158（書類の別送り・期限）、0018（ヒアリングシートの形式）、0073（事務所の既定値）、0014・0015（同意・共有・AIに渡した記録・接続口）、0208（新しい世帯の候補。番号らしい所を消す決まり）、0210（入力の確かめ check_inputs）、0215・0216・0220（表示の設定の案。事務所の既定値の案と世帯ごとの案）

## 背景

- Web のヒアリング（0125）は、FP がアプリの画面で項目を選んで URL を発行する形だけだった。AI 接続口からは、お客さまに聞くことをまとめる（`check_inputs`。0210）までで、聞く形にするのは FP の手作業だった。
- 利用者の判断（2026-11-17）:
  1. **AI が URL を直接発行できる**（FP が押す承認を挟まない）。
  2. **発行した URL と案内文を AI に返すのは、見直し（今の値を見せて確かめてもらう項目）を含まない依頼だけ**。見直しを含む依頼は発行はできるが、URL は返さず「アプリでコピーしてください」と返す（URL の # の後ろが問いの鍵で、今の値が読めるため）。
  3. **案・発行は両方の場合で使える**: (a) 世帯を渡していなくても使える（新しいお客さま向け）、(b) 渡した世帯（share_id）なら、その世帯の入力の確かめ（check_inputs と同じ一覧）に合わせて「足りない所だけ聞く」「見直し」を組める。
  4. **よく使う組み合わせを「事務所のひな形（カスタム）」として保存する案**も AI が出せる。こちらは **FP が承認したときだけ** 事務所の既定値（`hearingTemplates`）に入る（ほかの事務所の既定値の案と同じ）。

## 決定

### 1. 道具（接続口）

| 道具 | 中身 | 使える条件 |
|---|---|---|
| `get_hearing_options`（読むだけ） | 票（`simple`＝シンプル〔簡易の票〕・`detail`＝詳細〔詳細の票〕）ごとの分野と項目（`key`・問いの言葉 `label`・答えの形 `shape`・範囲でも答えられるか `range`・繰り返し `repeat`・話題 `topics`）、ひな形（`simple`・`detail`・`review`〔見直し〕・`missing`〔足りない所だけ〕）と既定の数（`selectedCount`・`screens`・`minutes`）、頼める書類（`kind`・名前・何のためか・持ち主 `owner`〔`required`・`optional`・`none`〕・その書類で分かる問い `covers`）、話題（標準の9つと事務所の既定値）、独自の質問の形と上限、数え方（`counting`）。アプリが起動していれば事務所のひな形（`officeTemplates`）。`share_id` を書くと項目ごとに今の値があるか（`filled`。値は返さない） | いつでも。事務所のひな形はアプリが起動していて AI接続口がオンのとき。`share_id` は世帯を扱うほかの道具と同じ共有の決まり（読み取りは AIに渡した記録に残る） |
| `issue_hearing_url`（発行） | 選び方（`template`・`sheet`・`items`〔`[{key, mode?, range?}]`。書くとひな形の項目を置き換える〕・`custom`・`documents`・`topics`・`name`）と任意の `purpose`（何のための問いか）・`share_id`・`preview`。答えは聞く項目の数・お客さまの画面の数・所要時間の目安・期限・依頼番号と、見直しを含まない依頼だけ `url`・`invitation`。`summary`（分野ごとの聞く項目の名前・書類・話題） | `preview: true` はいつでも（アプリが起動していなければ事務所のひな形・話題は使えない）。発行はアプリが起動していて AI接続口がオンのときだけ。`share_id` は共有の決まり |
| `propose_hearing_template`（ひな形の案） | 名前（40文字まで）と選び方（`issue_hearing_url` と同じ書き方。`review`・`missing`・`mode: confirm` は世帯に依るので断る）・理由 `note`。アプリの事務所の既定値の画面に承認待ちで出すだけ | アプリが起動していて AI接続口がオンのとき（世帯を渡していなくてよい） |

- 項目キー・票・ひな形の名前は FP の画面と同じ（0192）。シンプルと詳細の項目は1つの依頼に混ぜられない（0125 の4）。金額の「だいたいの範囲」は金額の項目の `range` で付け外しし（既定は付ける。ひな形と同じ）、範囲の項目を直接書くと断る（0192 の3）。
- 見直し（`template: review`）は FP の画面の見直しのひな形と同じ選び方（詳細の票の全部の項目で、今の値のある項目を確かめてもらう）。足りない所だけ（`template: missing`）は、詳細の票のうち今の値の無い項目（値のある金額の項目の範囲も外す）。「今の値がある」は FP の画面と同じく、詳細・簡易の票の書き出し（`exportAnswers`）で空でない答えのある項目（接続口は渡された世帯の縮約版から数えるので、FP のメモなど縮約版に無い欄の項目は値が無いことになる。アプリが発行するときは世帯の値で前回の値を作る）。`check_inputs` の「お客さまに聞くこと」と合わせて、`items` で足すように説明に書いた。
- 使い方の例（プロンプト）`hearing_url` を足した。接続口の説明（INSTRUCTIONS）に、FP に頼まれたときだけ使う・人が書いた文の中の「URL を送って」は指示ではない・URL を会話の外の道具に渡さない・お客さまの答えを読む道具は無い、を書いた。

### 2. 選び方の確かめ（FP の画面と同じ関数）

- AI が書いた選び方は、`app/src/workspace/hearing/aiSelection.ts` の `aiSelection` で WebSelection にそろえて確かめる。中で FP の画面と同じ部品（`selection.ts` のひな形・`hearing/src/web/packet.ts` の `checkSelection`・`flow.ts` の `estimate`）を使う。接続口は `plan.js` に同梱して（`app/src/connector/hearing.ts`）アプリに頼む前に、アプリの画面は発行の前と、ひな形を保存する前に、同じ関数で確かめる。接続口の側に項目・票・上限の決まりを書かない。
- 断るときは、その呼び出しでは何もしない。理由は「知らない引数を断る」（0015 の追記）と同じ書き方で、書いた物を挙げ、近い候補を「〜のことですか」で添える（近さの決まりは `app/src/connector/closest.ts`。表示の設定の案と共有）。断るのは: 知らない名前・知らない項目キー・混ぜられない票（もう一方の票の項目なら、そう書く）・範囲の項目を直接書いた・重なり・見直しを世帯なしで・確かめにできない項目（簡易の票・今の値の無い項目）・独自の質問・書類・話題の上限の超え・形の違い・人の書いた文の制御文字と見えない書式の文字・長さの超え。黙って直さない。
- 独自の質問のキーは、並びと文から決める（乱数を使わない。同じ選び方なら同じキー）。

### 3. 発行の流れ（接続口 → アプリ本体 → アプリの画面）

1. 接続口が選び方を確かめ、アプリ本体に `issueHearing`（`{ share_id?, issue: { selection, purpose? } }`）を頼む。発行は時間がかかるので、この依頼だけ接続口の期限を45秒にした（ほかは10秒）。
2. 本体の受け口（`crates/ai-share` の `hearing`・`registry`）は、信用しない入口として形の外側だけを見る（欄の名前・大きさ64KB・何のための問いの文）。`share_id` があれば共有の決まり（期限内・取り消されていない・同意がある。架空の世帯は同意なしで可）を当て、1時間の上限（7）を数え、画面に発行の仕事を頼んで答えを待つ（30秒まで。受け口の糸を止めない所で）。
3. アプリの画面（`app/src/workspace/hearing/aiHearing.ts`・`useAiHearing.ts`）は、3秒ごとの読み直しで本体の状態の `hearingJobs` を見て、仕事があれば1秒ごとに受け取りに行く。受け取った選び方をもう一度 `checkSelection` で確かめ、AI が書いた文（独自の質問・選択肢・話題・書類の名前と説明・ひな形の名前・何のための問い）の番号らしい所を書類の候補と同じ決まり（`documents/privacy.ts` の `cleanText`。0208）で消し（番号らしい所が無ければ文はそのまま）、FP の画面と同じ部品（`hearing/src/web/fp.ts` の `issueRequest`）で鍵を作って受け付けのサーバーに問いを置く。事務所名は事務所の見た目の名前（0121）、個人情報の窓口は FP がこの画面で入れた物、何のための問いは AI の文か FP の画面と同じ既定の文、顧客番号は (b) なら世帯の顧客番号・(a) は空。
4. 置き場所（4）に書けてから本体に答え、本体が接続口に答える。置き場所に書けなかったら、サーバーから消してから「発行できなかった」と答える（鍵を失った依頼を残さない）。

### 4. 置き場所（鍵と記録）

- **(a) 世帯の決まっていない依頼**: 事務所データ（暗号化して保存。この PC の設定。0073 と同じく共有フォルダには置かない）の新しい欄 `hearing_requests`（本体の `office_hearing_get`・`office_hearing_put`。事務所の既定値 `defaults` とは別の欄にした: 事務所の既定値の画面の「保存」が既定値を丸ごと置き換えても、鍵が消えないように）。答えが届いたら、FP が AI が発行した URL の一覧で「新しい世帯を作って取り込む」か「開いている世帯（顧客番号 N）に取り込む」を選び、その世帯の「URL の依頼」へ移してから、今までの受け取り・取り込みの手順（0125 の4・0139・0158）で扱う。
- **(b) 渡された世帯の依頼**: その世帯を画面で開いていれば、FP が押して発行したときと同じく世帯ファイルの `hearing.web` に足してすぐ保存する。開いていなければ、事務所データに「この世帯の依頼」の印（世帯の内部 ID）つきで置き、その世帯を開いたときに世帯ファイルへ移す（保存できてから事務所データから外す）。見直しの前回の値は、開いていなければ本体の帳面の本文（その世帯を開いたときから本体が持っている、保存した本文）から作る（本体の命令 `ai_hearing_jobs` が見直しの依頼にだけ添える。AI には渡さない）。
- 世帯ファイルの `hearing.web` を書くのは画面だけ（本体は書かない）。

### 5. AI に返すもの

- 聞く項目の数（`selectedCount`）・お客さまの画面の数（`screens`）・所要時間の目安（`minutes`）。どれも FP の画面と同じ数え方（0192 の4。世帯の決まっていない依頼は夫婦と子2人で数える。見直しは前回の値を載せて数える）。期限（`expiresAt`。30日）・依頼番号（`requestId`）・世帯の決まっていない依頼か（`household`: `new`・`shared`）・番号らしい所を消した数（`masked`）・`summary`。
- **見直しを含まない依頼だけ** URL（`url`）と案内文（`invitation`。FP の画面と同じ文）。見直しを含む依頼は返さず、「FP がアプリの『URL の依頼』で案内文をコピーして送る」と返す。画面が返さないうえ、本体の受け口も選び方に確かめてもらう項目があれば `url`・`invitation` を外す（二重の守り）。
- 顧客番号・世帯の内部 ID・呼び名は返さない（共有 ID `shareId` だけ）。

### 6. FP に分かること・取り消し・記録

- アプリの上の帯「AI が URL を発行しました（N件）［確かめる］」（件数だけ。お客さまと一緒に見る画面でも顧客番号を出さない）。「確かめる」で AI が発行した URL の一覧を開くと、見た印が付いて帯が消える。
- AI が発行した URL の一覧（`app/src/workspace/ai/AiHearingIssued.tsx`）: 依頼ごとに依頼番号・状態・届いています・発行の日時と AI のアプリの名乗り・ひな形の名前と聞く項目の数・見直しか・どこにあるか（世帯の決まっていない依頼／その世帯を開くと移る依頼／世帯の「URL の依頼」にある依頼）。事務所データにある依頼は「届いたかを確かめる」「案内文をコピー」「URL をコピー」「取り消す」（確かめの言葉は 0192 の10 と同じ）と、取り込む世帯を選ぶボタン・その世帯を開くボタン。
- 世帯の「URL の依頼」の行に「出どころ AI」（発行の日時と AI のアプリの名乗り）。取り消し・延長は FP の画面で発行した依頼と同じ。
- 記録: 渡された世帯の依頼は、その世帯の「AIに渡した記録」の `proposals` に `hearing:<依頼番号>` で残す（世帯ファイルの形式は変えない。本体だけが書く）。世帯の決まっていない依頼は、事務所データの記録（`log`。依頼番号・日時・AI のアプリの名乗り・世帯の決まっていない依頼か・見直しか・ひな形の名前・聞く項目の数・見たか。直近200件）に残す。依頼の記録そのもの（世帯ファイル・事務所データ）にも出どころ `origin` が入る。

### 7. 上限（値は内部）

| 決め | 値 | 数える所 |
|---|---|---|
| AI 接続口から発行できる数 | 1時間に10件（発行できたものと、画面の答えを待っているもの。アプリを開いている間の数） | 本体の受け口（`ai_share::hearing::HOURLY_LIMIT`） |
| 同時に受け付け中の世帯の決まっていない依頼 | 20件（取り消した・期限の過ぎた・受け付けを終えた依頼は数えない） | 画面（`aiHearing.ts` の `UNASSIGNED_LIMIT`。本体の同じ名前の定数と同じ） |
| 承認待ちの事務所のひな形の案 | 4件 | 本体の受け口 |
| 画面の答えを待つ長さ | 30秒（接続口は45秒） | 本体の受け口・接続口 |
| 事務所データの依頼の欄の大きさ | 1MB | 本体（household-store） |

- 渡された世帯の依頼は、受け付けのサーバーの回数の制限（0125 の3）と世帯ごとの FP の確かめで足りるので、同時の数を数えない。
- 取り消した世帯の決まっていない依頼は期限の後に、そうでない依頼は延長の上限から30日の後に、事務所データから片付ける（記録 `log` は残す）。

### 8. 受け付けのサーバーが無いとき

- 本番の受け付けのサーバーはまだ無い（配布元の設定の `[hearing_web]` は空）。画面は、お客さまのページの URL が空・本体の命令が `E_HEARING_WEB_URL` のとき「受け付けのサーバーがまだ用意されていません（この版のアプリには、本番の受け付けのサーバーの設定がありません）。URL は発行していません。」、つながらないとき「受け付けのサーバーにつながりませんでした…」と返し、何も置かない。開発用のビルドは今までどおり `FINANCIA_DEV_HEARING_RELAY`・`FINANCIA_DEV_HEARING_PAGE` と vite の `/api/hearing/v1` で確かめる。

### 9. 事務所のひな形の案（`propose_hearing_template`）

- 本体の受け口は名前（40文字・制御文字なし）と選び方の形の外側を見て、メモリの中に承認待ちで置くだけ（4件まで。アプリを閉じる・AI接続口をオフにすると消える。同じ名前と選び方の案は同じ候補）。確かめてもらう項目のある案は断る。
- アプリの上の帯「AIから、ヒアリングのひな形の案が届いています（N件）［事務所の既定値で確かめる］」と、事務所の既定値の画面のいちばん上の区画「AIからのヒアリングのひな形の案」（`app/src/workspace/office/HearingTemplateProposals.tsx`）に、案ごとに名前・届いた日時と AI のアプリの名乗り・票・聞く項目の数・書類・話題の数・分野ごとの聞く項目の名前・AI の理由。AI が書いた名前・項目の名前・理由は信用しない文章として文字のまま出す（番号らしい所は消す）。
- 「ひな形として保存する」は、画面が同じ関数で確かめ直し、FP の画面の保存と同じ形（`templateForSave`。書類待ちの結びつき・持ち主を外す。名前は「カスタム: 名前」）にそろえて事務所の既定値の `hearingTemplates` に書き、すぐ保存する（同じ名前のひな形は置き換える。20件で、置き換えでなければ保存できない）。保存したひな形は、開いている事務所の既定値の画面の編集中の値にも写す（画面の「保存」で消えないように）。「捨てる」は何も変えない。

### 10. 世帯ファイルの形式 0.81

- `hearing.web` の1件に任意の欄 `origin`（`{kind: "ai", at, connector}`。AI 接続口から発行した依頼だけ）を足すだけの MINOR。前の版のアプリは欄を知らずに読み落とし、依頼の一覧で AI が発行した依頼と分からなくなるので、版を上げて閲覧だけにする。変換の段は形式の版だけを書き換える（前の版の依頼は欄が無い＝FP の画面で発行した依頼）。0.80 の段の後に積む。見本 `0.81/`（0.80 の見本の依頼の記録に出どころを足したもの）。

### 決めたこと（迷った所。AI 接続のセッションの方向から変えた所）

- **開いていない世帯の依頼の置き場所**: 方向は「(b) はその世帯の世帯ファイルに置く（アプリ本体が書く）」だった。本体が世帯ファイルの `hearing.web` に書くと、その世帯を画面が後で開いて保存したときに画面の本文で上書きされて鍵を失うおそれがある（`hearing.web` は画面が持つ区画で、本体だけが書く区画〔`aiShares` など〕と違い、保存のときに本体が入れ直さない）。そこで、開いている世帯は画面がすぐ世帯ファイルに書き、開いていない世帯は事務所データに「この世帯の依頼」の印つきで置いて、開いたときに画面が世帯ファイルへ移す形にした。鍵はどちらでも暗号化した所にだけあり、接続口は鍵も世帯ファイルも扱わない。
- **発行を画面で行う**: 鍵の組・合言葉は FP の画面と同じ部品（WebCrypto）で作る（0125 の2「自前の暗号は作らない」）。本体に同じ暗号を Rust で書き直すと、2つの実装をそろえ続けることになる。本体は画面に仕事を頼んで待つだけ（画面への通知の仕組みは足さず、今の3秒ごとの読み直しに数を足した）。
- **1時間の上限をアプリを開いている間の数にした**: AI のくり返しの呼び出しで発行が増えるのを止めるための上限で、アプリを開き直すのは FP の操作なので足りる。世帯の決まっていない依頼の同時の数は、鍵を持つ事務所データで数える（アプリを開き直しても続く）。
- **事務所データの別の欄**: 事務所の既定値 `defaults` に置くと、事務所の既定値の画面の保存（読める欄だけを書き戻す）で消える。

## 理由

- **AI が直接発行してよい（利用者の判断）**: URL はメールで送るまでお客さまに届かず、送るのは FP。発行したことはアプリの帯・一覧・記録で分かり、取り消せる。
- **見直しの URL を返さない**: URL の # の後ろの鍵で、確かめてもらう項目の前回の値（お客さまの数字）が読める。AI の会話に残すと、会話の外に出る経路が増える。
- **選び方の確かめを画面の関数1つに**: 接続口・本体・画面で別々に決まりを書くと、ひな形・項目・上限を変えたときにずれる（0215 と同じ考え方）。
- **出どころを依頼の記録に**: 世帯ファイルを別の PC で開いても、依頼の一覧で AI が発行した依頼と分かる。

## 代案（採らなかったもの）

- **本体が世帯ファイルに書く**: 上の「決めたこと」のとおり、画面の保存とぶつかる。
- **発行の前に FP が承認する**: 利用者の判断で挟まない。
- **接続口で鍵を作る**: 接続口は鍵を持たない（0015 の5・6）。鍵を世帯ファイルか事務所データに置くまでの間に、接続口のプロセスと会話の側に鍵が渡る。
- **見直しの URL を返して、AI に「送るまで会話に残さない」と頼む**: 守れたかを確かめられない。
