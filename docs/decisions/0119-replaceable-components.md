# 0119. カスタム層で差し替えを許すエンジンの部品の一覧と、差し替えの約束（入力と出力の形・約束の版と改訂・公式の計算との違いの見せ方）

- 状態: 採用（一部未確定）（2026-11-04）
- 固定の強さ: 骨格は、分け方の決まり（1 の初めの3つと「迷ったら許さない」）、一覧で許した部品を β公開の後に一覧から外さないこと（足すのはよい）、差し替えの約束（3 の1〜3。同じ ID・同じ入出力のスキーマ・同じ MAJOR で公式以下の MINOR・計算式ID は `ext.<作成者>.`・黙って公式に戻さない）、公式の計算と違うことを FP 向けの画面・根拠・見出し・控えに必ず残すこと（4 の1〜4）。試験版は、許した8つの部品の入出力の約束（0006 の試験版の規則。β公開の後は3か月前に予告して変える）とマニフェストの `basedOn`。内部は、理由の文・テストの作り・テスト専用の `probes`。提案書の印刷される面での示し方（4 の5）は未確定（利用者に確かめる）
- 前提にする記録: 0001（公開の約束の版と試験版の規則）、0004（ID の書式）、0006（部品表・差し替え・差し込み口・2つの版・根拠の記録）、0009（控え・刻印と必須の記載）、0016（カスタム層・承認・「カスタム計算あり」の印）、0019（SDK フォルダ）、0111（事務所の推定の値）、0114（拡張の束と2段の作り方）

## 背景

- 0006 の3 で、差し替え（公式部品の置き換え）ができるのは `replaceable: true` を付けた公式部品だけと決め、その一覧は未確定にしていた（候補: 退職金規程・必要保障額の考え方・生活費の段階。0006・0016 の未確定）。
- β公開から、外の FP が拡張を作り始める。FP が作った束を読み込む仕組み（読み込み・承認・隔離実行）は β公開の後に作る（0114 の段2）が、**どの部品を差し替えてよいか**と**差し替えるときの約束**は、作られた拡張がそのまま依存する形になる。後から一覧から外したり、約束の形を変えたりすると、作られた拡張が動かなくなる。そこで β公開の前に固める。
- これまでは、差し替えの仕組みのテストのために、雇用保険料・健康保険料・厚生年金保険料の3つの部品（どれも法律で決まる計算）に `replaceable: true` を付けていた。FP の束はまだ読み込まないので、製品で差し替えが使われたことは無い。

## 決定

### 1. 差し替えを許す部品

**分け方の決まり**

- 許すのは、計算の結果が次のどれかで決まる部品だけ。
  1. **推定・目安**（estimate）: 統計や経験則の数字で、確かな答えが無い所（教育費の平均、評価額の下がり方、整理資金の目安など）。
  2. **FP の考え方**（method）: 数え方・段階の付け方が FP ごとに違ってよい所（必要保障額の数え方、生活費の段階）。
  3. **事務所・勤め先の決まり**（rule）: 法律ではなく私的な決まりで決まる所（FP 自身の料金表、勤め先の退職金規程）。
- 許さないのは、次のどれかに当たる部品。
  1. **法律・制度で決まる計算**（law）: 税・社会保険・公的年金・公的な給付と支援・非課税の器の決まり。差し替えると、制度の正しさを公式が保証できず、制度改正の追従（0017）からも外れる。
  2. **契約・FP が入れた値をそのとおりに並べる部品**（input）: ローンの返済・保険契約・積立の予定・家賃と購入・何年かごとの支出など。替える「考え方」が無く、違う結果にしたいなら入力を変える。行を足したいなら差し込み口 `slot.expense.flow`（0006 の3）で足す。
  3. **集める・組み立てる・判定する部品**（assembly）: キャッシュフロー表・お金の動きの集計・万一の判定など。替えると表の作りそのものが変わり、ほかの部品の約束（科目の木・根拠の記録・二本立て）が守れない。
- **迷ったら許さない**。一覧に足すのは、後から足すだけで済む（今ある差し替えは壊れない）。一覧から外すと、作られた差し替えが動かなくなる。
- 部品の中に法律の計算が少し入っていても、主な中身が許す3つなら許す（退職給付の中の公務員の退職手当の支給率など）。差し替えた計算は 4 のとおり必ず公式と違うと示すので、法律の計算と取り違えない。逆に、主な中身が法律の計算なら、目安が少し入っていても許さない（介護の費用・不動産所得など）。目安の値だけを変えたいときは、事務所の推定の値（0111）で変えられる。
- **値だけを変えたいときは差し替えを使わない**: 推定の元の値は事務所の推定の値（0111）、物価・利回り・昇給などは前提（年ごとの列。0006 の6）、世帯ごとの値は入力で変える。差し替えは「計算の仕方」を変えるときだけに使う。

### 3. 差し替えの約束

1. **入力と出力の形**
   - 部品の ID は差し替える公式部品と同じ（`ext.` で始めない。差し替えであることは見出しの `origin` で分かる）。
   - 入力・出力のスキーマ（マニフェストの `input`・`output` のキー）は公式部品と同じにする。形を変えた入出力は名乗れない。出力は製品でも常にスキーマで検査する（0006 の5）。
   - 呼べる差し込み口は、公式部品が呼ぶものの内だけ（今の8つは、どれも差し込み口を呼ばない）。
   - `replaceable` は公式部品だけが書く。差し替えの部品が書けば拒む。
   - 読める入力項目・制度の値・呼べる部品は、差し替えの部品自身のマニフェストの `reads`・`params`・`requires` に書いたものだけ（0006 の1）。公式部品と同じでなくてよい（読まない項目を減らしてよい・ほかの公式部品を呼んでよい）。依存が循環すれば組み立てで止める。
   - 1つの公式部品に有効な差し替えは1つだけ（0016 の5）。
2. **約束の版と改訂**
   - 差し替えの宣言（マニフェストの `provides`）は約束の版の MAJOR に対して書く: `{ "type": "replace", "target": "<部品ID>", "contract": "<MAJOR>", "basedOn": <公式の改訂> }`。部品の `contract` は公式と同じ MAJOR で、MINOR は公式以下（公式より新しい約束は名乗れない）。MINOR が公式より古い差し替えは使える（MINOR で足した欄を使う側は、欄が無いときの扱いを持つ。0006 の4）。
   - **公式の MAJOR が上がったら**、その差し替えを使う案の計算を止め、FP に「差し替えを直す／公式に戻す」を選んでもらう。黙って公式に戻さない（0006 の4 のまま）。
   - **公式の改訂（`revision`）が上がったら**（制度改正・不具合の直し）、差し替えはそのまま使い、FP 向けの画面に「差し替えている公式の部品が新しくなった」と知らせ、「公式の計算と比べる」を開けるようにする（段2）。`basedOn` は、差し替えを作ったときに見た公式部品の改訂で、この知らせに使う（無ければ承認したときの公式の改訂）。
   - 差し替えの部品の `revision` は、その部品自身の改訂（1から）。見出しには差し替えの約束の版・改訂・指紋が残る（0006 の7）。
   - 許した8つの部品の入出力の約束は公開の約束（試験版）。β公開の後に変えるときは、3か月前に予告し、SDK の版ごとの変更点（`changes/`）に差と移行の手順を書く（0001・0006 の影響）。テストが8つの約束の版を書き留め、変えたらテストと SDK の文書を直すようにする。
3. **計算式ID**: 差し替えの部品が出すお金の動きと年ごとの行の計算式ID は `ext.<作成者>.` で始める（0006 の7 の決まりを、差し替えにも確かめるようにした）。公式部品が返した行をそのまま返すことはできない（計算式ID が公式のままなので拒む）。差し込み口に足す部品（追加）も同じ。

### 4. 公式の計算との違いの見せ方

差し替えた計算で作った結果には、公式の計算と違うことを必ず残す。

1. **根拠の表示**: 数字をクリックしたときの根拠（0006 の7）で、計算式ID が `ext.` で始まる行は「事務所の計算」と出し、束の名前を添える（段2 の画面）。計算式ID の決まり（3 の3）で、公式の計算式と取り違えることが仕組みの上で起きない。
2. **結果の見出し**: 組み立てた部品表に、差し替えた部品が `origin: "replacement"` と指紋で残る（0006 の2・7。今もそうなっている）。画面・控え・PDF の内部情報は、これを読んで差し替えの有無を決める（ほかの所に別の印を持たない）。
3. **FP 向けの画面**: 0016 の8 と 2026-11-03 の追記のとおり、案の一覧の名前の横の小さな印と、結果のタブの計算のお知らせの1行（「この案は事務所の計算を使っています: 必要保障額の推移（束の名前）」のように、差し替えた公式部品の名前と束の名前）。その行から「公式の計算と比べる」を開き、同じ案を公式の計算で計算した結果と並べる。改訂が上がったときの知らせ（3 の2）も同じ行に出す。
4. **控え・PDF の内部情報**: 差し替えた部品の ID・束の `id` と版・指紋を残す（0016 の8・0009）。
5. **提案書の印刷される面**（未確定・利用者に確かめる）: 0016 の8 では、「カスタム計算あり」の印は顧客の見る提案書と提示層に出さないと決めている（2026-11-03 の追記で、顧客には関係の無い FP 向けの知らせとした）。差し替えた計算は数字そのものを変えるので、印とは別に、提案書の前提の注記に「必要保障額は担当の FP の計算方法で計算しています（ソフトの標準の計算とは異なります）」のような1行を、差し替えた部品ごとにアプリが帳票の外側で付ける（必須の記載。0009。独自帳票からも消せない）案がある。0016 の8 の決定に関わるので、この記録では作らず、利用者の判断を待つ。FP の束の読み込みは β公開の後なので、決めるのはそれまででよい。

### 5. 差し込み口との関係

- 差し込み口 `slot.protection.method`・`slot.retirement.rules`（0006 の3。正式公開で開く予定。行を出さない）は、必要保障額の考え方・退職金規程を足すための口として設計した。この記録で、同じことは `protection.need`・`retirement.benefit` の差し替えでできるようにした（入出力の形が公式部品の約束として既にある）。2つの差し込み口の約束の中身（0006 の未確定。12月）は、差し替えと重ならない形（例: 公式の考え方と並べて見せる別の考え方を足す）にするか、開かずに差し替えに一本化するかを、そのとき決める。
- `slot.expense.flow`（支出の行を足す）は今までどおり。

### 6. コードで確かめること

- 公式部品のマニフェストの `replaceable: true` を、1 の8つに付け、雇用保険料・健康保険料・厚生年金保険料の3つから外した（`engine/src/components/*/index.ts`）。
- 登録簿 `registry/components.yaml` に、許した部品だけ `replaceable: true` の欄を書く（`npm run gen` がマニフェストから作り、CI の `registry:check` が食い違いを止める）。
- 組み立て役（`engine/src/registry/assemble.ts`）: 許さない部品の差し替えを `E_NOT_REPLACEABLE` で、3 の1・2 に合わない差し替えを `E_COMPONENT_DEFINITION`（`id`・`input`・`output`・`slots`・`replaceable`）と `E_CONTRACT_MISMATCH` で拒む。
- 部品の呼び出し（`engine/src/registry/ctx.ts`）: 差し替え・追加の部品の計算式ID が `ext.<作成者>.` で始まらなければ `E_FORMULA_ID`（テストの部品の `test.` は通す）。
- テスト `engine/test/replaceable.test.ts`: 公式部品のすべてを1・2 の分け方の表で持ち、(1) 表が公式部品と過不足なく一致する、(2) マニフェストの `replaceable` と登録簿の欄が表の「許す」と同じ、(3) 許さない部品の差し替えはすべて拒む、(4) この記録の1・2 の表と SDK の `docs/extension-points.md` の表が同じ、(5) 3 の約束、(6) 許した8つを公式と同じ計算の差し替えにして同時に使っても、モデル世帯の表・年ごとの行・要約・必要保障額が公式と同じで、見出しに差し替えが残る、(7) 許した8つの約束の版を書き留める、を確かめる。
- テスト専用の `probes`（`RunOptions`）: 区間・構成員ごとの依存・凍結など、エンジンの仕組みを差し替えを許さない公式部品で確かめるテストは、差し替えの決まりを通さずに定義を置き換える `probes` を使う。製品の入口（`runJson`・`runBatchJson`・セッション）は渡さない。
- 部品の書き方の約束（`COMPONENT_API_VERSION`）を 1.3 → 1.4 にした（差し替えの決まりを足した。公式部品の書き方は変わらない）。世帯ファイルの形式の版は変えない（世帯ファイルに差し替えの欄は無い。束の指紋を残す欄は段2 で足す）。

## 理由

- **法律の計算を許さない**: 制度の正しさは公式が制度データと答え合わせ（L2）で保証している。差し替えを許すと、同じ「所得税」の数字でも事務所ごとに違う計算になり、制度改正の追従から外れる。FP が税・社会保険の計算を変えたい場面は、制度の誤りの報告として公式を直すのが正しい。
- **入力を並べる部品・組み立ての部品を許さない**: 並べる部品には替える考え方が無く、違う結果は入力で作れる。組み立ての部品を替えると、科目の木・根拠の記録・二本立て（0005）の一致の前提が崩れ、差し替え1つで表全体が信用できなくなる。足したい行は差し込み口で足せる。
- **迷ったら許さない**: 約束を開いた部品は、β公開の後は試験版の規則（3か月前の予告）でしか変えられない。開く数が多いほど公式部品の直しが重くなる。後から足すのは壊さないので、使われ方を見て足す。給与（`income.salary`）を今は開かないのも、多くの制度の部品が読む中心の部品で、約束を縛ると制度の部品の直しが止まりやすいため（昇給の考え方は前提と事務所の推定の値で変えられる）。
- **同じ入出力の形にする**: 差し替えは「呼ぶ側の公式部品から見て同じ形」でなければ、部品表を通した呼び出し（0006 の2）で呼ぶ側が壊れる。スキーマのキーを同じにすれば、出力の検査が公式の検査器のままで足りる（0006 の5）。
- **MINOR を公式以下にする**: 公式に無い欄を名乗る差し替えは、使う側が読まない欄を持つだけで意味が無く、公式が後でその MINOR を別の意味で使うと食い違う。
- **計算式ID を `ext.` で始める**: 根拠の表示は計算式ID で計算の説明を引く。公式の計算式ID のまま違う計算をすると、根拠に公式の式が出て、違う計算であることが隠れる。
- **違いの見せ方を見出しの部品表に一本化する**: 画面・控え・PDF が別々に印を持つと食い違う。見出しは計算ごとに必ず付き（0006 の7）、根拠の記録の細かさに依らない。

## 影響

- 計算の結果は変わらない（マニフェストの印と、外から来た部品への確かめを足しただけ。公式部品の計算は同じ。見本の世帯の結果は同じ）。
- 公式部品の中身の指紋（`build-info.json`）は、`replaceable` を付け外しした11の部品で変わる（改訂は上げない。計算は同じ）。
- 雇用保険料・健康保険料・厚生年金保険料は差し替えられなくなった。FP の束はまだ読み込まないので、製品で困る人はいない。
- 守るべき決まり:
  - 公式部品を足したら、1・2 のどちらかの表と `engine/test/replaceable.test.ts` と SDK の `docs/extension-points.md` に入れる。
  - 許した8つの部品の入出力の約束を変えるときは、MAJOR と MINOR の区別を守り、SDK の変更点に書く（β公開の後は3か月前に予告）。
  - 許した部品の中に法律の計算を足さない（足すなら別の部品に分けて呼ぶ）。
