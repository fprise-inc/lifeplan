# 0023. 事務所での共有（メンバーごとの鍵・誰が直したか・開いている人・分岐）

- 状態: 採用（一部未確定）（2026-10-19）
- 固定の強さ: β公開から変えない（骨格）。共有フォルダの中のファイルの形（名簿と親鍵の包み・世帯の鍵の札・世帯の札・開いている印・参加の申請）、世帯ファイルの本文に足した「誰が直したか」の欄（形式の版 0.2）は骨格。画面の文言・開いている印の時間の値（更新の間隔・無効になるまでの時間）・指紋の見せ方は後から変えてよい

## 背景

- 複数のFPがいる事務所（想定は2〜5人）では、同じ顧客の世帯を、担当の交代・休みの代わり・確認のために、それぞれのPCで開きたい。
- 提供元はサーバーを持たない（0012）。顧客データはFPのPCと、FPが選んだ共有フォルダ（同期サービスの同期フォルダや社内のファイルサーバー）にだけ置き、常に暗号化する（0013）。
- これまでの鍵の3段（0013 の2）は1台のPC（と、復元キーで設定した2台目）を前提にしていた。全員が同じ復元キー（＝親鍵そのもの）を持つ形にすると、1人が辞めたときに鍵を取り上げられない。誰が持っているかも分からない。
- 共有フォルダは、同期の遅れ・衝突（「〜のコンフリクトコピー」のようなファイル）・版の履歴がある。2人が同じ世帯を同時に直すと、片方の変更が消えうる（0011 の7 の分岐の検出はあるが、誰が開いているかは見えない）。
- 事務所の中では「この変更は誰がしたか」「このメモ・同意の記録・AIの候補の判断は誰が書いたか」が要る（引き継ぎ・確認・顧客への説明）。
- 世帯ファイルの形式は β公開から「安定」と約束する（0011）。鍵と世帯ファイルの形に関わる部分は、配った後から足すと古いファイル・古いアプリで扱えなくなるので、今回で形を固める。
- 1人で使うFPには何も増やさない（共有は事務所の設定でオンにしたときだけ）。

関連: 封筒と事務所データは 0011、識別と持たない情報は 0012、鍵と完全削除は 0013、同意とAIの記録は 0014、画面の安全と保存先の制限は 0016、書き出しは 0020。

## 決定

### 1. 共有はオプトイン。1人のときは今までどおり

- 事務所の設定に「事務所で共有する」を置く。既定はオフ。オフの間は、データフォルダ（PCの中。0013）だけを使い、ファイルの形も動きも今までと同じ（世帯ファイルの形式の版だけは上がる。下の6）。
- オンにするのは次の2つのどちらか:
  - **始める**（最初の1人）: 共有フォルダを選び、表示名を入れる。その中に事務所のフォルダ（`lifeplan-office/`）を作り、このPCの世帯を移す（下の8）。
  - **参加する**（2人目から）: 同じ共有フォルダを選び、表示名を入れて参加の申請を置く。既存のメンバーが承認すると使える（下の3）。
- 共有を始めると、事務所は新しい事務所ID・新しい親鍵で作る。PCの中の事務所（今までの親鍵と復元キー）は残し、世帯は共有の事務所へ移す。共有の事務所の復元キーは新しいものになるので、保管を必須にする（0013 の3 の「同期フォルダを選ぶときは必須」と同じ）。

### 2. メンバーごとの鍵と、親鍵の包み

```
各メンバーのPC
  OSの資格情報の保管庫
    ├─ メンバーの秘密鍵（X25519。PCごと・事務所ごと）
    └─ 事務所の親鍵の写し（起動を速くするため。名簿から取り出したもの）
共有フォルダ（lifeplan-office/）
  members.lpmb … 名簿と、親鍵をメンバーごとの公開鍵で包んだもの
    └─ 事務所の親鍵（32バイト）
         ├─ keys/<親鍵の鍵ID>/<世帯ID>.lphk … 世帯の鍵の札（親鍵から導いた鍵で暗号化）
         │    └─ 世帯の鍵 → households/<世帯ID>.lphf（今までと同じ封筒）
         ├─ cards/<世帯ID>.lpcd … 世帯の札（一覧に出す顧客番号・要約・最後に直した人）
         └─ presence/<世帯ID>.<メンバーID>.lpop … 開いている印
```

- **メンバーの鍵の組**: 各メンバーのPCが、参加のときに X25519 の鍵の組を作る。秘密鍵はOSの資格情報の保管庫（サービス名はアプリの識別子、アカウント名は `<事務所ID>.member`。開発用のビルドは 0013 と同じく別のサービス名）に置き、PCの外へ出さない。公開鍵だけを共有フォルダに置く。
- **親鍵の包み**: 事務所の親鍵を、メンバーごとに「使い捨ての鍵の組＋相手の公開鍵」の鍵交換（X25519）から HKDF-SHA256 で導いた鍵で、AES-256-GCM で包む。改ざん検出の対象に「名簿の包みであること・事務所ID・親鍵の鍵ID・メンバーID」を入れる（別のメンバーの欄・別の時代の欄と入れ替えても開かない）。
- **名簿**（`members.lpmb`。容器は 0011 の1 と同じ形で、識別の印は `LPMB`）:
  - 見出し（平文）: 形式名 `lifeplan.officeMembers`・形式の版・事務所ID・親鍵の鍵ID・確かめ値（0013 の2 と同じ形）・ナンス・**包みの一覧**（メンバーID・使い捨ての公開鍵・ナンス・包んだ親鍵）。
  - 本文（親鍵から導いた鍵 `lifeplan/office-members/v1` で暗号化。見出し全体を改ざん検出の対象にする）: メンバーの一覧（メンバーID・表示名・公開鍵・指紋・参加日・承認した人・**役割**）、外したメンバーの一覧（表示名・外した日・外した人）、前の親鍵の一覧（鍵ID・鍵・退いた日。下の4）、最後に直した日時と人。
  - **役割**は今は `member`（すべての操作ができる）だけを書く。閲覧だけ等の細かい権限は作らないが、欄だけを予約する。知らない役割のメンバーは、読む側が閲覧だけとして扱う（将来の版が足しても、古いアプリが権限を広く取り違えない）。
- **世帯の鍵の札**（`keys/<親鍵の鍵ID>/<世帯ID>.lphk`。識別の印 `LPHK`）: 見出しに世帯ID・親鍵の鍵ID・事務所ID、本文に「今の世帯の鍵（鍵ID・鍵）」と「前の世帯の鍵の一覧」。親鍵から導いた鍵 `lifeplan/household-keys/v1` で暗号化し、見出し全体を改ざん検出の対象にする（別の世帯の札への差し替えは開かない）。
  - 1つのファイルにまとめた鍵置き場（0013 の2）にしないのは、共有フォルダでは2人が同時に別の世帯を作ると、まとめた1つのファイルが同期の衝突を起こし、片方の世帯の鍵が消えうるため。世帯ごとの札なら、別の世帯の作成どうしはぶつからない。
  - 札のファイル名から世帯IDと世帯の数は外から見えるが、世帯ファイルの名前（`<世帯ID>.lphf`）で既に見えている範囲で、増える情報は無い。
  - PCの中の事務所（共有オフ）は今までどおり1つの鍵置き場を使う（形も変えない）。
- **世帯の札**（`cards/<世帯ID>.lpcd`。識別の印 `LPCD`）: 一覧のための顧客番号・構成の要約・作った日時・最後に保存した日時・最後に直した人・世代番号。親鍵から導いた鍵 `lifeplan/household-card/v1` で暗号化する。一覧を出すたびに世帯ファイルを全部開かないため。保存のたびに、保存した人が書き直す（世帯ごとのファイルなので、別の世帯の保存どうしはぶつからない）。
- **事務所の確かめ用の番号**: 親鍵から導いた8文字（`lifeplan/office-code/v1`）を、全員の事務所の設定に出す。参加した人は、承認した人の画面と同じかを確かめるよう勧める（共有フォルダに書ける第三者が、名簿ごと偽物に差し替えて新しいメンバーに偽の親鍵を渡す攻撃に気づくため）。
- **PCが名簿を受け入れる条件**: 自分の包みを自分の秘密鍵で開けて、出てきた親鍵で本文が開け、本文のメンバーの一覧に自分（同じ公開鍵）が入っていること。さらに、手元の親鍵と違う親鍵の名簿は、本文の「前の親鍵の一覧」に手元の親鍵が入っているときだけ受け入れる（入れ替え。下の4）。手元の親鍵を知らない者は、名簿を偽物に差し替えられない。

### 3. 参加（申請と承認）

1. 新しいメンバーのアプリが、鍵の組を作り、`requests/<メンバーID>.json`（平文。形式名 `lifeplan.joinRequest`・事務所ID・メンバーID・表示名・公開鍵・申請した日時）を置く。画面に**自分の指紋**を出す。
2. 既存のメンバーのアプリの事務所の設定に、申請（表示名・申請した日時）が出る。**承認する人の画面には、申請のファイルの指紋を出さない**。
3. 承認する人は、新しいメンバーに口頭・電話・対面などファイルとは別の経路で指紋を読み上げてもらい、**指紋の16文字を入力する**。アプリは申請のファイルを読み直して公開鍵から指紋を計算し、入力と一致したときだけ承認する。一致しなければ承認しない（打ち間違いと区別せず「指紋が違います」と出す）。
4. 承認すると、親鍵をその公開鍵で包んで名簿に足し、申請のファイルを消す。
5. 新しいメンバーのアプリは、名簿に自分の包みが入ったことを見つけると、親鍵を取り出して保管庫に入れ、共有の事務所を使い始める。このPCの中の世帯を共有フォルダへ移すかを聞く（移すのはFPが選んだときだけ）。

- **指紋**: 「メンバーの公開鍵であること」の印と公開鍵をつないだものの SHA-256 の先頭10バイトを、復元キーと同じ文字の並び（数字と英大文字の32文字。I・L・O・U を使わない）で16文字にし、4文字ずつ区切って見せる（例: `7K2M-QX9P-…`）。80ビットあるので、他人が同じ指紋の鍵を作ることは現実的にできない。
- **なりすましへの対策**: 共有フォルダに書ける第三者（共有の設定の誤り、同期サービスのアカウントの乗っ取りなど）が、実在のメンバーの表示名で申請を置いても、承認する人が本人から聞いた指紋と一致しないので承認できない。承認する人の画面に申請の指紋を出さないのは、画面の値を写して確かめた気になることを防ぐため。
- 申請は「断る」で消せる。申請した側も取り下げられる。

### 4. 外す（親鍵の入れ替え）

- 外すときは、確認（外す人の表示名の入力）のうえで、**事務所の親鍵を新しくし、残りのメンバーにだけ包み直す**。
  1. 新しい親鍵と鍵IDを作る。
  2. すべての世帯の鍵の札を、**世帯の鍵も新しくして**（今の鍵を「前の世帯の鍵」に回す）、新しい親鍵の時代のフォルダ `keys/<新しい鍵ID>/` に書く。
  3. 名簿を書き直す（新しい親鍵の確かめ値・残りのメンバーの包み・外したメンバーの記録・前の親鍵の一覧に古い親鍵を足す）。名簿を書いた時点で入れ替えが成り立つ（途中で止まっても、古い時代のフォルダと名簿はそのまま使える。作りかけの新しい時代のフォルダは次の入れ替えで使わない）。
  4. 自分の保管庫の親鍵の写しを入れ替え、世帯の札を新しい親鍵で書き直す。
- **世帯の鍵も入れ替える理由**: 外した人は、それまでの親鍵で世帯の鍵の札をすべて開けたので、世帯の鍵を写し取っている可能性がある。包み直すだけでは、外した後に保存した改訂も、写し取った世帯の鍵で開けてしまう。世帯の鍵を新しくすれば、**外した後に保存した改訂は、外した人には開けない**。
- 世帯ファイルは、入れ替えのときには暗号化し直さず、**次に保存したときから新しい世帯の鍵で暗号化する**（前の世帯の鍵は、今の改訂・直前の世代・バックアップを読むためにだけ札に残す）。今の改訂の中身は外した人がもともと見られたものなので、すぐに暗号化し直しても守れる範囲は増えない。一斉に書き直すと、他の人が開いている世帯との分岐を大量に作る。
- **前の親鍵の一覧**: 入れ替えの直後は、同期の遅れで、まだ入れ替えを知らないメンバーのPCが古い時代のフォルダに世帯の鍵の札を書くことがある。今のメンバーは前の親鍵でそれを開き、世帯の鍵を新しくして今の時代へ移す（「迷子の札の引き取り」）。前の親鍵は退いてから30日で名簿から消し、古い時代のフォルダも30日で片付ける（鍵置き場の世代を30日で入れ替える 0013 の4 と同じ長さ）。
- **外した人の手元の写しは消せない**: 外した人のPCに既に同期された世帯ファイル・世帯の鍵の札・バックアップ、外した人が書き出したファイルは、アプリからは消せない。外した時点までの中身は、外した人が読めるままである。画面に正直に出す:「○○さんを外すと、これから保存する内容は○○さんには読めなくなります。○○さんのPCに既に同期された写しや、○○さんが書き出したファイルは、このアプリからは消せません。共有フォルダの共有の設定からも○○さんを外してください」。
- **共有フォルダの共有からも外す**: 外した人が共有フォルダに書けるままだと、外した直後の同期の遅れの間に、古い親鍵で偽の入れ替えを置くことができる（下の「残る危険」）。外す画面で、共有の設定から外すことを必ず案内する。
- 外された人のアプリは、名簿に自分の包みが無いことを見つけると「この事務所の共有から外されました」と出し、共有の事務所を使わない。
- 自分自身は外せない（最後の1人も外せない）。自分のPCを手放すときは、他のメンバーに外してもらう。

### 5. 復元キーとの関係

- 共有の事務所の復元キーは、**共有の事務所の親鍵そのもの**（形は 0013 の3 と同じ72文字）。親鍵を持つ全メンバーが表示できる。
- 保管は事務所の代表（1人か2人）が行うことを勧め、画面に「事務所の復元キーを保管した」の記録（いつ・誰が）を出す。**外す（親鍵の入れ替え）たびに復元キーは変わる**ので、入れ替えの後は新しい復元キーの保管を必須にし、古い控えは破棄するよう案内する（古い控えでは古い時代の写しだけが開ける）。
- **メンバーがPCをなくしたとき・買い替えたとき**: 新しいPCで「参加する」から申請し、他のメンバーが承認する。なくしたPCのメンバーは外す（親鍵の入れ替え）。なくしたPCのディスクが暗号化されていても、外すことを勧める。
- **全員のPCが使えなくなったとき**（1人の事務所で共有を使っていた場合を含む）: 新しいPCで復元キーを入れると、親鍵で名簿を開き、自分の新しい鍵の組を名簿に足せる（復元キーを持つことが事務所の全権を持つことになる理由。画面と説明書に書く）。
- PCの中の事務所の復元キー（共有を始める前のもの）は、PCの中の事務所にだけ効く。共有の事務所とは別のもの。

### 6. 誰が直したか（世帯ファイルの形式の版 0.2）

本文の形を次のとおり足し、形式の版を `0.1` から `0.2` に上げる（足すだけなので MINOR。0011 の5）。0.1 のファイルは、読み込みのときに一方向に変換する（`meta.revisions` と `meta.editors` を空で足すだけ）。0.1 のアプリは 0.2 のファイルを閲覧だけで開く（保存させない）。

| 場所 | 欄 | 中身 |
|---|---|---|
| `meta.savedBy` | `{memberId, name}` | この改訂を保存したメンバー。共有オフのときは書かない |
| `meta.revisions` | `[{fromGeneration, toGeneration, memberId, from, to, count}]` | 改訂の履歴。同じメンバーが30分以内に続けて保存した改訂は1行にまとめる（自動保存で行が際限なく増えないように）。共有オフのときの `memberId` は `null`。最大500行（古い行から消す） |
| `meta.editors` | `{<メンバーID>: {name}}` | このファイルに出てくるメンバーの表示名（名簿が無いPC・引き継ぎ先でも、誰が書いたかを表示できるように写して持つ。0011 の3 の自己完結） |
| `household.memoBy` | `[メンバーID または null]` | FP用のメモの行ごとの書いた人（`memo` と同じ並び）。変わらない行は前の書いた人を残し、新しい行・直した行は直した人にする |
| `consents[].recordedBy` | `{memberId, name}` | 同意の記録を書いた人（0014 の2 に足す。任意） |
| `candidates[].decidedByMember` | `{memberId, name}` | AIの候補を判断した人（`decidedBy` は今までどおり `fp`。AIは判断できない。0008 の2） |

- **表示名は FP 自身の名前**で、顧客の識別子ではない。0012 の「氏名の欄を作らない」は顧客と家族の氏名についての決まりで、FP（事務所のメンバー）の名前はこれに当たらない。ただし、表示名の欄には「顧客のお名前は入れないでください」と出し、長さを20文字までに限る。メンバーIDは乱数のID（UUID 第4版）で、人や機器の情報を含めない（0012 の1）。
- 封筒の見出し（平文）には、誰が直したかを書かない（0011 の1 の「見出しに書かない」と同じく、平文の情報を増やさない）。
- 記録は世帯の鍵の改ざん検出の内側にあるが、メンバーどうしの間では名乗りの証明ではない（メンバーは誰でも世帯の鍵を持つので、他人の名前で書ける）。事務所の中の協力のための記録と位置づけ、画面にもそう書く。署名で証明する形は将来の余地とする（下の「代案」）。

### 7. 開いている人の表示と同時編集

- **開いている印**（`presence/<世帯ID>.<メンバーID>.lpop`。識別の印 `LPOP`）: メンバーID・表示名・開いた日時・最後に印を新しくした日時・PCのID。親鍵から導いた鍵 `lifeplan/presence/v1` で暗号化する（誰がどの世帯を開いているかも、事務所の外には見せない）。
- 世帯を開くと印を置き、開いている間は**1分ごと**に新しくする。別の世帯に移る・アプリを閉じると消す。**5分**新しくならない印（アプリが落ちた・PCが眠った）は無効として扱い、見つけた人が片付けてよい。PCの時計がずれていても、未来の時刻の印は5分を超えたら無効にする。
- 他の人が開いている世帯を開くと「○○さんが開いています（○分前から）」と出す。閲覧はそのままでき、**自動保存は止めた状態で開く**。「編集を始める」を押すと自動保存を始める（同時に直すと分岐になることを、そのボタンの横に書く）。
- 世帯の一覧に、最後に直した人と時刻、開いている人の印を出す。
- 印は同期サービスの遅れの分だけ遅れて届く（数秒〜数分）。印は「気づくための目安」で、同時編集を止める鍵（ロック）ではない。止める形を採らないのは、同期フォルダでは確実なロックが作れず、落ちたPCの印が残ると誰も編集できなくなるため。
- **分岐の検出**: 今までどおり、保存の前に今のファイルの指紋が親の改訂の指紋と同じかを確かめる（0011 の7）。違えば上書きせず、こちらの内容をPCの中の `conflicts/` に暗号化のまま残して、分岐を選ぶ画面を出す:
  - **相手の内容を残す**: 相手の改訂を開き直す。こちらの内容は `conflicts/` に残る。
  - **こちらの内容で上書きする**: 相手の改訂も `conflicts/` に残してから、こちらの内容を、今の改訂を親として保存する。
  - **両方を残す**: 相手の改訂を開き、こちらにだけあったプラン（同じIDで中身が違うものは別のIDの写し）を、プランとして足す。こちらの現状（入力）の違いは `conflicts/` の写しに残る（現状どうしを自動で混ぜない。混ぜた結果の数字をFPが確かめずに使うことになるため）。
  - 画面には、相手の名前と保存した日時（相手の改訂の `meta.savedBy` から）を出す。
- **同期サービスの衝突ファイル**: 同期サービスが作る別名のファイル（`<世帯ID> (… のコンフリクトコピー …).lphf` のように、名前が世帯IDで始まり `.lphf` を含むもの）は、見出しの世帯IDと指紋で同じ世帯の分岐と判定する（0011 の7）。一覧に「同期の衝突の写しがあります」と出し、「写しを今の内容にする」（今の内容は `conflicts/` に残す）か「写しを片付ける」（`conflicts/` に移す）を選ばせる。
- **入れ替えを知らないPCの保存**: 外した直後の同期の遅れの間に、入れ替えをまだ知らないPCが古い世帯の鍵で保存した改訂は、外した人にも読める。アプリは保存の前に名簿が変わっていないかを確かめ（名簿のファイルの指紋）、変わっていれば読み直してから保存して、この時間を同期の遅れの分だけにする。

### 8. 保存先（共有フォルダ）と移し方

- 共有フォルダは事務所の設定の「共有フォルダを選ぶ」で、**本体が OS のフォルダのダイアログを出して**選ばせる。画面からパスを受け取らず、画面にパスを返さない（0016 の1。0020 の追記の書き出しの出口と同じやり方）。画面に出すのは「設定済みかどうか」と「同期フォルダの中かどうか」だけ。
- 選べない場所（本体が止める）: データフォルダ（アプリのデータの場所）、カスタム層・SDK・AIの作業フォルダ（0016・0019・0020 の6）と、それらを含むフォルダ・それらの中のフォルダ。
- 選んだフォルダの中に `lifeplan-office/` を作り、その中だけを使う（FPの他のファイルと混ぜない）。参加のときは、`lifeplan-office/` そのものか、それを含むフォルダのどちらを選んでもよい。
- **PCの中から共有フォルダへの移し方**: 世帯ごとに、PCの中の鍵で開き、共有の事務所の新しい世帯の鍵で暗号化し直して共有フォルダに書き、書いたものが開けることを確かめてから、PCの中の世帯ファイル（直前の世代を含む）とその鍵を消す。世帯の内部IDと顧客番号はそのまま引き継ぐ。PCの中のバックアップの写しは、鍵が消えるので30日で読めなくなる（0013 の5 と同じ）。
- 共有フォルダの中の世帯ファイルの保存の手順（一時ファイルに書いて差し替える。0011 の7）は今までと同じ。一時ファイルを同期サービスが途中で拾う可能性は 0011 の未確定のまま。

### 9. 同期サービスの版の履歴と完全削除

- 同期サービスは、共有フォルダの中のファイル（世帯ファイル・世帯の鍵の札・名簿）の古い版を、サービスの側の履歴に残す。どれも暗号化したままの写しである。
- **完全削除**（0013 の5）は、共有の事務所では次を行う: 世帯ファイル・直前の世代・世帯の札・開いている印・すべての時代のフォルダの世帯の鍵の札を共有フォルダから消し、削除したPCのアプリが管理するバックアップの写しを消し、削除の記録を残す。他のメンバーのPCのアプリが管理するバックアップの写しは、世帯の鍵が無くなるので、最長30日で読めなくなる。
- 同期サービスの版の履歴に残った世帯の鍵の札は、古い親鍵（＝古い復元キー）を持つ人なら開ける。履歴から消すのはサービスの側の操作になる。画面で「同期サービスの版の履歴に暗号化された写しが残ります。読めなくするには、版の履歴から消すか、事務所の親鍵を入れ替えてください」と案内する（「すべて消えます」とは書かない）。
- 親鍵の入れ替え（外すときと同じ操作）をすれば、履歴に残った名簿・札は今の親鍵では開けない（古い親鍵の控えを破棄していれば、誰にも開けない）。

## 理由

- **メンバーごとの鍵の組で親鍵を包む**: 全員に同じ復元キーを配る形は、人が辞めたときに取り上げられず、誰が持っているかも分からない。メンバーごとに包めば、外す人の包みを除いて親鍵を入れ替えるだけで、外した人を締め出せる。秘密鍵は各PCの保管庫から出ないので、共有フォルダが漏れても鍵は漏れない。
- **X25519＋HKDF＋AES-256-GCM**: 公開鍵で包む標準的な組み合わせで、Rust の広く使われた実装（RustCrypto・dalek）がある。今の暗号の部品（0013 の1）と同じ AES-256-GCM・HKDF-SHA256 を使い、増やす部品を鍵交換だけにした。
- **指紋の入力を必須にする**: 共有フォルダは、同期サービスの共有の設定ひとつで第三者が書ける場所になる。申請を置くだけで参加できると、名前を名乗るだけで顧客データを読める。ファイルと別の経路で確かめた値を入力させれば、共有フォルダに書けるだけの者は参加できない。
- **世帯ごとの札**: 同期フォルダは、同じファイルを2台で書くと衝突する。事務所の全体を1つのファイルにまとめると、関係のない操作どうしが衝突する。世帯ごと・メンバーごとのファイルに分ければ、衝突は「同じ世帯を同時に直した」ときだけになり、それは分岐として扱える。
- **時代ごとのフォルダ**: 入れ替えを、名簿を書いた一瞬で切り替えられる。途中で止まっても、古い時代のフォルダと名簿で全員が使い続けられる。
- **次の保存から新しい世帯の鍵**: 守れる範囲（外した後の改訂）は一斉に暗号化し直すのと同じで、分岐を作らない。
- **開いている印をロックにしない**: 同期フォルダの上では、2台が同時に「空いている」と判断することを防げない。残ったロックで仕事が止まる害のほうが大きい。分岐の検出が最後の守りになる。
- **誰が直したかを本文に持つ**: 引き継ぎ先・書き出し・名簿が無いPCでも、誰が書いたかを示せる（自己完結。0011 の3）。見出しは平文なので書かない。

## 代案（採らなかったもの）

- **全員が同じ復元キー（親鍵）を持つ**: 一番簡単だが、外すことができない。
- **外すときに包み直すだけ（世帯の鍵は変えない）**: 外した人が写し取った世帯の鍵で、外した後の改訂も読める。
- **外すときに全世帯を一斉に暗号化し直す**: 守れる範囲は同じで、他の人が開いている世帯との分岐を大量に作る。途中で止まったときの扱いも難しい。
- **共有フォルダでも1つの鍵置き場ファイル**: 2人が同時に世帯を作ると衝突し、片方の世帯の鍵を失いうる。
- **開いている印でロックする**: 上の「理由」のとおり。
- **編集者の署名（Ed25519）**: 「誰が直したか」を暗号で証明できるが、鍵の組をもう1つ持ち、検証の失敗の扱い（外した人の過去の署名など）を決める必要がある。2〜5人の事務所の中の協力の記録としては過剰と判断した。名簿のメンバーには公開鍵があるので、署名の欄は後から足せる（足すときは本文の MINOR を上げる）。
- **承認する人の画面に申請の指紋を出して見比べる**: 一般的なやり方だが、画面どうしを見比べずに承認されやすい。入力させるほうが確実で、16文字なら手間も小さい。
- **提供元のサーバーで名簿を管理する**: サーバーを持たない決まり（0012）に反する。

## 残る危険（画面と説明書に書く）

- 外した人の手元の写し・書き出したファイルは消せない（上の4）。
- 外した直後の同期の遅れの間は、(1) 入れ替えを知らないPCの保存が古い世帯の鍵で行われうる、(2) 外した人が共有フォルダに書けるなら、古い親鍵で偽の入れ替えを置きうる。共有の設定から外すことを案内し、アプリは保存の前に名簿を確かめる。
- 共有フォルダに書ける第三者は、ファイルを消す・壊すことはできる（読めない・書き換えを見破られるだけ）。毎日のバックアップ（0011 の6）と同期サービスの版の履歴で戻す。
- メンバーの秘密鍵は同じPC・同じユーザーで動く悪いプログラムからは守りきれない（0013 の6 と同じ）。

## 影響

- **後から変えると**: 名簿・世帯の鍵の札・世帯の札・開いている印の形を変えると、事務所の全員のアプリを同時に更新しないと読めなくなる（世帯ファイルの形式の更新は遅らせられない 0011 の5・0017 と同じ扱いになる）。本文の「誰が直したか」の欄を変えると、過去の記録と比べられなくなる。
- **守るべき決まり**
  - メンバーの秘密鍵・親鍵を、共有フォルダ・ログ・画面に出さない（復元キーの表示だけは 0013 の3 のとおり）。
  - 承認は、入力された指紋と、申請のファイルの公開鍵から本体が計算した指紋が一致したときだけ。承認する人の画面に申請の指紋を出さない。
  - 外すときは親鍵と世帯の鍵の両方を入れ替える。外した人の手元の写しは消せないことを画面に出す。
  - 名簿は、手元の親鍵を「前の親鍵の一覧」に含むときだけ、新しい親鍵のものを受け入れる。
  - 共有フォルダのパスを画面に渡さない・画面から受け取らない。データフォルダ・カスタム層・SDK・AIの作業フォルダの中と、それらを含む場所は選ばせない。
  - 共有オフの事務所の動きとファイルの形を変えない。
  - 形式の版を上げる変更には、1段の変換と見本を添える（0011 の5）。
- **テストで確かめること**
  - 2人分の鍵の組（2つのデータフォルダ＋同じ共有フォルダ）で、同じ世帯を開ける・直せる。誰が直したかが残る。
  - 外した人は、外した後に保存した改訂を開けない（手元の古い親鍵・古い世帯の鍵の札があっても）。残ったメンバーは開ける。
  - 指紋を入力しない・違う指紋では承認できない。申請のファイルを承認の直前に差し替えても、入力した指紋と合わなければ承認しない。
  - 名簿を、手元の親鍵を知らない者が作った偽物に差し替えても受け入れない。
  - 開いている印が5分で無効になる。未来の時刻の印も無効になる。
  - 同じ親から2つの保存が作られたとき分岐として検出し、どちらも失わない。同期サービスの衝突ファイルを同じ世帯の分岐と判定する。
  - 0.1 の世帯ファイルが 0.2 へ変換でき、見本がそろっている。
  - 命令の引数にパスが無く、返す値にパス・鍵が入らない。
  - 共有オフでは、ファイルの形と動きが今までどおり。

## 最初の実装での確認（2026-10-19）

- 形式（名簿・世帯の鍵の札・世帯の札・開いている印・参加の申請、本文の 0.2）と、共有の始め方・参加・承認・外す・PCの中からの移し方・一覧・開いている印・分岐を選ぶ画面の最小の形を作った。
- 2つの PC を「2つのデータフォルダ＋同じ共有フォルダ（テスト用の一時フォルダ）＋メモリの保管庫」で模したテストで、上の「テストで確かめること」を確かめた。OS の資格情報の保管庫には触れていない。
- 同期サービスそのもの（遅れ・衝突ファイルの名前の付け方の実物）では試していない。
