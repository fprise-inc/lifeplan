# 0200. AI接続口で、場所だけ違う「動かす項目」も選べるようにする（場所 at・合成の対策 lever）

- 状態: 採用（一部未確定）（2026-11-11）
- 固定の強さ: 書き方（`list_plan_items` の `at`・`lever`・`place`、`calculate`・`explain_value`・`compare` の `plan_changes` と `propose_scenario` の `changes` の `at`・`lever`）は試験版（0015 と同じ。予告して変えることがある）。候補の変更の場所（世帯ファイルの `candidates[].diffs[].at`・`lever`。形式 0.75）は骨格。作り（候補の当てはめを1か所にする・選び方を画面の関数で作る）は内部
- 前提にする記録: 0015（AI接続口。プランの候補）、0035（並びの要素の ID）、0036（プランの差分の当て先と合成の対策）、0183・0184（画面の関数を同梱する）、0195（プランの動かす項目）、0198（比べる道具）

## 背景

- 0195 で、`list_plan_items` と `calculate`・`explain_value` の `plan_changes` を、プランの候補（`propose_scenario`）と同じ「対象・入力項目ID・値」の書き方で作った。ただ、同じ対象・同じ入力項目ID で場所だけが違う項目は、この書き方では1つに決まらないので一覧に出さなかった（見本の世帯 55 件で 2,510 件、平均約 46 件）。資産運用の「毎月の積立額」と「積立をやめる年齢」（どちらも前提を対象に `account.contributions`）、取り崩しの3項目（`assumptions.investment`）、黒字の貯まり方、生活費の段階ごとの割合、教育の段階ごとの欄、住宅ローンの金利の段階、年金の加入月数、相続税の目安の欄、定年後の予定の定年（働く最後の年齢と同じ `employment.to`）などで、FP が AI に頼みたい項目が多い。
- 利用者の判断（2026-11-11）: 次の段で作る（場所か動かす項目のキーを書き方に足し、`propose_scenario` も一緒に変える）。

## 決定

### 1. 書き方に「場所」を足す: 入力の欄の場所 `at` か、合成の対策の名前 `lever`（どちらか1つ）

- 変更1件は `{target, item, value}` に、要るときだけ次のどちらか1つを足す（両方を書いた変更は当てない・受けない）。
  - `at`: 入力の欄の場所。プランの差分の当て先の `at`（0036 の2）と同じ道（文字の並び）で、並びの要素は ID、欄は名前、欄の値そのものなら `[]`。例: 教育の段階の学費 `["stages", "<段の ID>", "annualOverride"]`、生活費の段階の割合 `["<段の ID>", "ratio"]`、標準報酬月額の健康保険の分 `["health"]`。
  - `lever`: 合成の対策の名前。プランの差分の向き先 `lever`（0036 の3。世帯ファイルの差分にこの名前で書く）と同じ。例: `investMonthly`（毎月の積立額）・`investStopAge`（積立をやめる年齢）・`drawdownStart`・`drawdownAmount`・`drawdownRate`（取り崩し）・`surplusRatio`（黒字のうち貯まる割合）・`loanRate`（ローンの金利の段をそろえて動かす）・`mainEndAge`（定年後の予定の定年）・`pensionClaimAge`（入力の欄の年金の受け取り開始）。
- どちらも無い変更は今までどおり（対象・入力項目ID だけで当てはめ、1つに決まらなければ当てない）。今までの書き方で選べた項目は、そのまま同じ項目・同じ答えになる（見本の答えの前の6件は1文字も変わらない）。
- 当てはめ（`app/src/workspace/plans/candidates.ts` の `matchItems`）: 場所を添えた変更は、動かす項目の読み替え（`resolveKey`）が、`at` なら同じ場所の当て先、`lever` なら同じ合成の対策になる項目だけを探す。対象の合わせ方・対策の固定の項目を先に探す順・同じ値の欄を1つに数えるのは今までと同じ。
- 見本の世帯 55 件のどの項目も、当て先（向き先・入力項目ID・場所）か合成の対策（名前・物）が一覧の中で重ならないことを確かめた。どの項目も、対象・入力項目ID・場所で1つに決まる（一覧の `unlisted` は 0）。

### 2. `list_plan_items` が場所と人が読める区別を添える

- 項目ごとの選び方は画面の関数（`candidateRefOf`）で作る: 対象・入力項目ID だけで1つに決まり、プランの候補にも出せるならそれだけ（今までと同じ形。`at`・`lever` を付けない）。決まらないときと、前提を対象にする前提条件でない入力項目（相続の遺したい額・相続税の目安の欄など。今までの書き方ではプランの候補に出せなかった）のときは、場所を添えてその項目自身に1つに決まる選び方にする。
- 場所を添えた項目には `place`（人が読める区別。まとまり・欄の区切り・物の名前を「›」でつなぐ。例「子ども・教育 › 第2子 › 大学（18歳から）」「働き方と収入 › ご本人 › ご本人の定年後の予定」「資産運用」）を添える。欄の区切りの名前は、動かす項目に足した `section`（入力の欄の区切りの見出し）から作る。AI は `at`・`lever` をそのまま渡し、FP には `place` と `label` で伝える。
- 大きさ: 既定（対策・資産運用・貯まり方・よく使う項目）は見本の世帯で平均約 6.5 件・約 2.6KB → 約 4.9KB（資産運用・貯まり方の項目が加わる）。`fields: true` は平均約 13KB → 約 25KB（多い世帯で約 110KB）。`group` で絞る使い方を案内する（未確定）。
- `proposable`: 場所を添えた変更は、前提を対象にして前提条件でない入力項目も指せる（3）ので true。ただし、場所 `at` に世帯のデータに書かれていない要素の ID（ID を持たない並びの要素に、親の物の ID と場所から決めて振る ID。資産配分の割合・取得の時期ごとの残高・借り換えの欄。見本の世帯で 504 件中 71 件）があれば false（渡された世帯では親の ID が共有の仮の ID なので、アプリ本体が元の ID に戻せない。計算はできる。未確定）。

### 3. `propose_scenario` と `crates/ai-share` の取り決め

- `propose_scenario` の `changes` の1件に任意の `at`（文字の並び）・`lever`（文字）を足した。アプリ本体の確かめ（`proposal.rs`）:
  - `at` と `lever` の両方は受けない。`at` は16段まで・1段1〜100文字、`lever` は英数字の1〜64文字。
  - `at` の中の乱数 ID の形の段は、値の中の ID と同じく共有の仮の ID から元の ID に戻す（知らない ID は受けない）。名前の段はそのまま。
  - 場所を添えた変更は、対象を前提（`assumptions`）にして前提条件でない入力項目を指せる（資産運用の積立・相続税の目安の欄など、世帯で1つの欄・対策）。場所の無い変更の決まり（前提を対象にできるのは前提条件の入力項目だけ・前提条件の入力項目は前提を対象に）は今までどおり。変えられる入力項目（縮約版の許可リスト・文章の項目を除く）も今までどおり。
- 承認待ちの候補の変更（`ProposedDiff`）と世帯ファイルの候補（`candidates[].diffs[]`）に任意の `at`・`lever` を足した。場所の無い候補には欄を書かない（前の版の候補と同じ形で、読み書きしても1文字も変わらない）。

### 4. 画面の「AIからの候補」

- 届いた候補の変更（`AiProposedDiff`）の `at`・`lever` を、接続口の計算と同じ当てはめ（1）に渡す。場所を添えた候補は、その項目に当たる。表の「変える項目」に、場所の区別（`place`）を小さく添える（同じ名前の欄が子ごと・段ごとに並ぶため）。
- 前の版の候補（場所が無い）は今までどおり当てはめる。

### 5. 世帯ファイルの形式 0.75

- 候補の変更に任意の欄を足したので、世帯ファイルの形式の版を 0.75 に上げた（足すだけの MINOR。変換の段は版だけを書き換える。見本 `0.75/` は 0.74 の見本に、場所を添えない候補と添えた候補を足した物）。前の版のアプリは欄を知らずに読み落とし、場所の無い候補として別の項目（定年後の予定の定年の候補を働く最後の年齢に、など）に当てるか、書き戻して落とすので、版を上げて閲覧だけにする。

### 6. 接続口・比べる道具

- 接続口の `PlanChange`（`calculate`・`explain_value`・`compare` の `plan_changes`）と `propose_scenario` の変更に `at`・`lever` を足し、そのまま画面の関数（`plan.js` の `applyPlan`）とアプリ本体に運ぶ（接続口に当てはめ方を書かない。0183・0184・0195 と同じ）。答えの `planChanges` の変更ごとに、渡した `at`・`lever` と `place` を添える。
- 比べる道具（0198）は `plan_changes` を同じ部品で当てるので、通りの `plan_changes` でも同じ書き方が使える。

## 理由

- **場所 `at`・合成の対策 `lever` にした（動かす項目のキーにしなかった）**: 画面のプランは差分を「向き先・入力項目ID・場所」（当て先）か「合成の対策の名前」で持つ（0036）。これは世帯ファイルに書く形で、AI の候補を承認したプランの差分も同じ形になる。動かす項目のキー（`inv:stop`・`field:edu/<ID>/stage/3/annual` など）は画面の内部の名前で、並びの番号を含み（足す・外す・並べ替えで別の要素に当たる。0035 の5 で当て先に改めた理由）、物の ID を文字の中に含む（共有の仮の ID に戻すには文字を組み替えることになる）。0036 の未確定（AI接続口の道具の入出力に `at` を足す時期）にもそのまま答えられる。
- **書き方を1つに保つ**: 場所は要るときだけ足す。今までの書き方で選べる項目は今までと同じ形で一覧に出るので、前の書き方の AI のアプリ・候補はそのまま動く。
- **選び方を画面の関数で作る**: 一覧の選び方（`candidateRefOf`）は当てはめ（`matchItems`）で確かめてから返すので、一覧の書き方で当てると必ずその項目に当たる。接続口・画面の候補・比べる道具が同じ関数で当てる。
- **形式の版を上げた**: 候補は世帯ファイルに残る。前の版のアプリが場所を読み落とすと、別の項目に当てて FP が気づかずに保存するおそれがある（世帯ファイルの形式の版の決まり。0011）。

## 代案（採らなかったもの）

- **動かす項目のキーを書き方に足す**: 上の理由。0195 の代案でも採らなかった。
- **`target` に向き先 `lever` を書く（`{lever: "investStopAge"}`）**: 差分の形にはより近いが、`target` が文字から物に変わり、前の書き方と形が分かれる。合成の対策の物（構成員・物）を別に書く欄も要る。
- **場所を `at` 1つにまとめる（合成の対策も `["lever:…"]` のような文字で）**: 入力の欄の道と名前がぶつかるおそれがあり、読み手が形を見分けにくい。
- **場所の無い候補でも、1つに決まらなければいちばん近い項目に当てる**: 別の項目に当たるおそれがある（今までどおり当てない）。

## 未確定

- **ID を持たない並びの要素の場所**: 資産配分の割合・取得の時期ごとの残高・借り換えの欄は、要素の ID を世帯のデータに書かず、親の物の ID と場所から決めて振る。渡された世帯では親の ID が共有の仮の ID なので、`at` の中の ID を元に戻せず、プランの候補には出せない（`proposable: false`。計算はできる）。これらの並びも保存するときに ID を書くか（世帯ファイルの形と計算の入力の形が変わる）、アプリ本体が仮の ID から振り直した ID を戻すか。
- **一覧の大きさ**: `fields: true` で多い世帯は約 110KB。まとまりごとに引く使い方で足りるか、`at`・`place` を短くするか。
- **足す・外す（`add`・`remove`）**: 物や並びの要素を足す・外す候補は、まだ書き方が無い（0036 の未確定のうち `add`・`remove` は残る）。
