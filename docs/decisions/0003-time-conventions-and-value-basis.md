# 0003. 時間の規約と値を選ぶ基準

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。時点の型・計算方式の設定の書き方は、世帯ファイルの形式（公開の約束・安定）の一部

## 背景

ライフプランの制度は、時間の扱いがばらばらである。

- 住民税は前年の所得に対して、6月から翌年5月に払う。年金は偶数月に前2か月分が振り込まれる。私立校の入学金は入学前の1〜3月に払う。
- 年齢の切り替えも制度ごとに違う。「年齢に達する日」は誕生日の前日（年齢計算に関する法律）、後期高齢者医療は誕生日当日、年金の支給は達した月の翌月から、児童手当や遺族基礎年金の「子」は18歳に達した後の最初の3月31日まで、学年は4月2日で区切る。
- どの時点の制度の値を使うかも違う。所得税は「その年分」、住民税は「前年の所得」、社会保険料は「○月分」、国民年金保険料は「年度」、住宅ローン控除は「入居した年」の制度が続く。

これらを部品ごとにばらばらに書くと、同じ世帯でも部品によって年がずれ、移行元のソフトの表との照合もできない。最初に共通の規約を決める。

## 決定

### 1. 時間の単位と表し方

- 計算の最小単位は「月」。日付は持たない（生年月日も「生年月＋1日生まれか」で持つ。0012）。
- 年月の書き方: データでは `"YYYY-MM"` の文字列（例: `"2031-04"`）。エンジンの中では月の通し番号の整数（`年×12＋(月−1)`）で持ち、比較・足し算を整数で行う。
- キャッシュフロー表は暦年（1月〜12月）単位。年度単位の表は作らない。
- 表の残高は年末（期末）の残高。表に出す年齢は「その年の12月31日時点の満年齢」。

### 2. お金の動きは「支払月」で持ち、表は支払月で年に集める

- 各計算部品は、年額ではなく「月ごとのお金の動きの列」を返す。1件の形（JSON Schema で定義。0006）:

```json
{
  "row": "cf.taxSi.residentTax",
  "ym": "2032-06",
  "amount": 15800,
  "accrualYear": 2031,
  "member": "（構成員のID）",
  "object": "（世帯内の物のID。あれば）"
}
```

- `ym` は**お金が実際に動いた月**（支払月）。`accrualYear` は「その年分」として帰属する年（住民税なら所得の年、年金なら支給対象の月の年）。
- キャッシュフロー表は、既定では `ym` の年で集計する（お金が動いた年に載る）。移行元のソフトとの照合のために、`accrualYear` で集計する載せ方も選べる（計算方式の設定 `aggregation: "cash" | "accrual"`。既定 `"cash"`）。
- 支払月の既定の例（各部品で宣言する）:
  - 住民税: 給与所得者は特別徴収で6月〜翌年5月の12回、それ以外は普通徴収で6・8・10月・翌年1月の4回。
  - 公的年金: 偶数月に前2か月分。
  - 確定申告による還付・納付: 翌年（既定は3月）。
  - 賞与: 働き方の期間で決めた支給月。
  - 私立校の入学金: 入学前の指定の月（既定は入学年の1〜3月のうち学費データの値。0010）。
  - 住宅ローン: 毎月（ボーナス返済は指定の月）。

### 3. 運用益

- 資産の器（口座・資産の種類）ごとに、年に1回計算する。
- 既定の式: 運用益＝期首残高×年利＋その年の収支の合計×年利×1/2（期中の収支は年の半ばに動いたとみなす）。丸めは規約 `conv.investment.return`（円未満切り捨て。0002）。
- 計算方式の設定で `investmentTiming: "midYear" | "beginning" | "end"` を選べる（期中の収支を期首に動いたとみなす／期末に動いたとみなす）。既定は `"midYear"`。
- 年利はプランの前提条件の「年ごとの列」（0006）から、その年の値を使う。
- 資金不足の判定は、年末の残高で行う。

### 4. 年齢による切り替えは、規則を宣言して使う

- 部品と制度の値は、年齢による切り替えのたびに、次のどれを使うかを属性 `ageSwitch` で宣言する。部品の中で年齢から月を自分で計算しない。

| `ageSwitch` | 切り替わる月 | 例 |
|---|---|---|
| `reachMonth` | 年齢に達する日（誕生日の前日）の属する月 | 介護保険の第1号被保険者（65歳）、70歳での厚生年金の資格喪失 |
| `monthAfterReach` | 達する日の属する月の翌月 | 年金の支給開始、70歳以上の医療の自己負担 |
| `birthdayMonth` | 誕生日当日の属する月 | 後期高齢者医療（75歳） |
| `firstMarch31AfterReach` | 達する日以後の最初の3月31日の属する月（その月まで該当） | 児童手当の対象、遺族基礎年金の「子」 |
| `schoolYear` | 4月2日〜翌年4月1日生まれを同じ学年とし、学年の始まり（4月） | 小学校の入学、学校の学年 |

- 月への解決のしかた（生年月 `birthYearMonth` と `bornOnFirst` から計算する）:
  - 達する日は誕生日の前日なので、1日生まれの人だけ、達する日が誕生月の前の月になる。それ以外は誕生月。
  - 誕生日当日は常に誕生月。
  - 学年は、4月1日生まれ（誕生月が4月で `bornOnFirst` が真）だけ前の学年に入る。
- 該当期間の終わり（「○歳に達した月まで」など）も同じ規則で解決する。期間は「始まりの月を含み、終わりの月を含む」で表す。
- `reachMonth` と `monthAfterReach` の違いのように、規則の名前で区別できない制度が出てきたら、規則を足す（既存の規則の意味は変えない）。

### 5. 計算基準日と初年度

- プランには計算基準日 `baseMonth`（`"YYYY-MM"`）が必須。基準日は「その月の初め」を表す。
- 現在の残高（預金・ローン残高など）は、計算基準日の時点の値として入力する。
- 初年度は、計算基準日の月以降のお金の動きだけを計上する（年額で入力した値も月ごとに分けた後で、基準日より前の月を落とすので、自然に按分される）。
- 初年度の運用益は、上の式の年利に「残りの月数÷12」を掛けて按分する（`mulRatio`、丸めは `conv.investment.return`）。
- 計算基準日は計算の入力として渡す。エンジンは「今日の日付」を見ない（時計を持たない。0005）。

### 6. 時点の型と名前つきイベント

- 入力の中で「いつ」を書く欄は、次の「時点」の型で書く。

| 形 | 例 | 意味 |
|---|---|---|
| 絶対 | `{"at": "2031-04"}` | その年月 |
| 年齢 | `{"memberAge": {"member": "<ID>", "years": 65, "months": 0}}` | 構成員がその年齢（月まで）に達する月。既定の規則は `reachMonth`。`"ageSwitch"` で他の規則を指定できる |
| イベントから | `{"event": "<イベントID>", "offset": {"years": 5, "months": 0}}` | 名前つきイベントの年月から n年m月後（負も可） |

- 退職・年金の受給開始（基礎と厚生を別々に）・進学・住宅の取得などは、名前つきイベントとして持つ。

```json
{ "id": "（世帯内の物のID）", "kind": "retirement", "member": "（構成員のID）",
  "at": {"memberAge": {"member": "（構成員のID）", "years": 60, "months": 0}} }
```

- 他の入力（退職金の受け取り、再雇用の働き方の期間の始まりなど）はイベントを指せる。スライダーでイベントを動かすと、指している入力が一緒に動く。
- 計算の前に、すべての時点を絶対の年月へ解決する。参照が循環していたらエラーにする。解決した結果（どの時点が何年何月になったか）は根拠の記録（0006）に残す。
- 進学の年月のように生年月と学年から決まるものは、学年の規則で計算した名前つきイベントとして自動で作る（子と学校の扱いは 0008・0010）。

### 7. 計算方式の設定

- プランの前提条件の一部として `calcConventions` を持つ。

```json
{
  "aggregation": "cash",
  "investmentTiming": "midYear",
  "compatibility": null
}
```

- `compatibility` は、他のソフトから移行したプランを旧ソフトの計算方式（期首・期末、年齢の数え方など）に合わせる「互換モード」の指定。移行したプランだけが使え、新しく作ったプランでは `null` に固定する。互換モードで変えられる項目の一覧は、他のソフトからの移行を扱う記録（まだ無い。β公開までに新しい番号で作る）で決める。
- 計算方式の設定を変えるのは前提条件の変更なので、提案の差分の一種として記録する。

### 8. 名目と現在価値

- 内部の計算と保存は、すべて名目値。
- 現在価値は表示のときだけ、計算基準日の年を基準に、前提条件の物価上昇率の累積で割って出す（`ratePow`・`rateDiv`、丸めは表示の規約）。現在価値の数字は保存しない。

### 9. 値を選ぶ基準（`basis`）

- 制度の値は、「どの時点の値を使うか」を属性 `basis` で必ず宣言する（制度データの形式は 0007）。
- 部品は、制度の値を `ctx.param(id, ...)` だけで読む（0006）。引く日（どの期間の値を使うか）は、`basis` と「いま計算している月」からエンジンが1か所で決める。部品が任意の日付を渡して値を引くことはできない。

| `basis` | 引く値 | 例 |
|---|---|---|
| `{"type": "incomeYear"}` | 計算している月の暦年の「その年分」の値 | 所得税の控除額・税率 |
| `{"type": "priorYearIncome", "switchMonth": 6}` | 判定に使う所得の年と、値の年度を、切り替え月で決める。計算月が切り替え月以降なら「前年の所得・今年の年度の値」、前なら「前々年の所得・前年の年度の値」 | 住民税（6月）、保育料（9月）、高校就学支援金（7月） |
| `{"type": "month"}` | その月の値（「○月分」） | 健康保険・厚生年金の料率、年金の月額 |
| `{"type": "fiscalYear", "startMonth": 4}` | 計算している月の属する年度の値 | 国民年金保険料、国保の料率 |
| `{"type": "anchor", "anchor": "moveIn"}` | 対象の物のその出来事の年月の値を、効果が続く間ずっと使う | 住宅ローン控除（入居年）。`anchor` は `moveIn`（入居）・`contract`（契約）・`acquisition`（取得）・`enrollment`（入学）・`benefitStart`（受給開始）のいずれか |
| `{"type": "birthDate"}` | 対象の構成員の生年月（と1日生まれか）で区分を選ぶ | 特別支給の老齢厚生年金の開始年齢、経過措置の表 |

- 引数のない型は文字列だけで書いてよい（`basis: incomeYear` は `{"type": "incomeYear"}` と同じ）。引数のある型を文字列で書いたときは既定値を使う（`fiscalYear` は `startMonth: 4`、`priorYearIncome` は `switchMonth: 6`）。`anchor` は引数を省略できない。
- `basis` ごとに、エンジンの中で別の型（例: `Param<"incomeYear">`）にする。年分の値を月の鍵で引くような取り違えを型で防ぐ。
- 「値が適用される期間」と「その値をいつ知ったか（データの版）」の2本の時間軸のうち、ここで決めるのは前者の引き方だけ。どの版のデータを使うかはプランが固定する（0007・0009）。

## 理由

- 月を最小単位にするのは、制度の切り替え・支払いの大半が月単位で、日単位で持つ必要がある入力（生年月日など）を持たない方針（0012）とも合うため。
- 支払月と帰属の年を両方持つのは、FPが見たいのは「お金が実際に動く年」の資金繰りで、移行元のソフトとの照合には「その年分」の載せ方が要るため。両方を1件の中に持てば、集計の切り替えだけで済む。
- 年齢の切り替えを規則で宣言させるのは、部品ごとに誕生日の前日の扱いを書くと必ず誰か（人でもAIでも）が間違えるため。規則を1か所で実装し、テストを集中させる。
- 生年月と1日生まれかの2つで、上の5つの規則はすべて正確に月へ解決できる（達する日が前月になるのは1日生まれだけ、学年の境目は4月1日生まれだけ）。
- 運用益を年1回・期中の収支は年央とするのは、国内のFPの実務と既存のソフトの多くが年単位で計算しており、月複利にすると年率から月率への変換（べき根）が要って結果の一致を保ちにくいため（0002）。
- `basis` を属性にして引き方を1か所に集めるのは、住民税の「前年所得」や保育料の「9月切り替え」のような取り違えが、制度の値の書き間違いと見分けにくい誤りになるため。`priorYearIncome` に切り替え月を持たせ、`anchor` を一般化したのは、同じ仕組みが住民税・保育料・就学支援金や、住宅ローン控除・生命保険料控除（契約日で新旧が決まる）・旧NISA（購入年）・学費（入学年度）に繰り返し現れるため。

## 影響

- 後から変えると、全部品と移行の照合の作り直しになる。制度データの `basis` を書き換えると、制度データ全体の書き直しになる。
- 守るべき決まり:
  - 部品は「今日」「年齢から月の計算」「制度の値を任意の日付で引く」を自分で書かない。
  - 新しい年齢の切り替え方・値の選び方が要るときは、既存の規則の意味を変えずに規則を足し、この記録に追記する。
- テストで確かめること:
  - 年齢の規則: 1日生まれ・2日生まれ・4月1日生まれ・4月2日生まれ・3月31日を含む月など、境目の世帯で、各規則が正しい月に解決すること。
  - 支払月: 住民税・年金・確定申告の還付が、指定の月に載ること。`aggregation` を切り替えると載る年だけが変わり、合計が変わらないこと。
  - 時点の解決: 循環参照がエラーになること。イベントを動かすと、指している入力が一緒に動くこと。
  - 性質のテスト: 期首残高＋収入−支出＋運用益＝期末残高が、毎年・器ごとに成り立つこと。
  - `basis`: 切り替え月の前後で、引く値の年度と判定に使う所得の年が変わること。

## 未確定

- 日単位の計算が要る給付（傷病手当金・出産手当金の日額と日数、育児休業給付の180日の区切りなど）の扱い。月単位で近似し、近似のしかたを根拠の記録に書く方針だが、「その月の暦の日数」を使うか「30日換算」かは、給付の部品を作る12月に決める（暦は時計と違い決まった計算なので、エンジンで使ってよい）。
- 年の途中で制度が変わる「年分」の値（年の途中から効く減税など）の書き方。月ごとの値の列として持つか、年分の値に特例の部品を足すかを、11月の所得税の部品で決める。
- 運用益の丸め（`conv.investment.return` を円未満切り捨てにしたこと）が、互換モードで旧ソフトに合わせる必要があるか。移行の照合を作る1〜3月に確かめる。
- 互換モードで変えられる項目の一覧（他のソフトからの移行を扱う記録で決める。その記録はまだ無く、β公開までに新しい番号で作る）。

## 追記

- 2026-10-08（最初の年より前に帰属するお金の動き）: `aggregation: "accrual"` で、表の最初の年より前の年に帰属するお金の動き（計算基準月以後に払うもの。前年の所得に対する住民税など）は、表の最初の年に載せる。
- 2026-10-08（運用益の丸め）: 3 の運用益は、（期首残高×2＋その年の収支）×年利×月数÷12÷2（`midYear` の場合）を分数のまま計算し、`conv.investment.return` で1回だけ丸める（項ごとに丸めない）。
- 2026-10-08（税・社会保険料の支払月の既定）: 2 の支払月の既定を、税・社会保険料について決めた。（a）健康保険料・介護保険料・子ども・子育て支援金・厚生年金保険料: 「○月分」を翌月の給与から控除する（翌月徴収）。期間の最後の月の分は最後の給与から控除する（月末に辞めると前月分と当月分の2か月分）。`accrualYear` は「○月分」の年。（b）賞与の保険料・雇用保険料: その支払いから控除する（支払いの月）。（c）所得税: 給与所得者は年末調整で年税額を精算するとみなし、年税額をその年の給与・賞与の支払いの月に支払額の割合で分ける（端数は最後の支払いの月）。`accrualYear` はその年分。（d）住民税: その年度の6月に給与を受けていれば特別徴収で6月〜翌年5月の12回（年税額の12分の1。端数は最初の月）、給与が無くなった後の残りは最後の給与の月にまとめる（一括徴収）。6月に給与が無ければ普通徴収で6月・8月・10月・翌年1月の4回（端数は最初の納期）。`accrualYear` は所得の年（年度の前の年）。（e）賞与の支給月: 働き方の期間で指定が無ければ6月と12月で、年額を等分する（端数は最後の支給月）。
