# 0012. 識別と持たない情報

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）

## 背景

ファイナンシアは、FPが顧客の世帯の家計・資産・年金・保険を扱うソフトである。扱う情報の大半は個人情報になるが、計算に本当に必要な情報はその一部にすぎない。持たない情報は漏れようがなく、後から「持たない」ことにはできない（一度でも保存の欄を作ると、既存のファイル・バックアップ・書き出しに残り続ける）。

そこで、最初の版から次を固定する。

- 世帯と構成員をどう識別するか
- どの情報を持ち、どの情報を持たないか
- 提供元（FPライズ／FPRISE, INC.）が顧客データを受け取る経路を一切作らないこと

関連: ID体系全体は 0004、世帯ファイルの封筒は 0011、暗号化は 0013、同意とAIの記録は 0014、書き出しは 0020、AI接続口は 0015、配布と自動通信は 0017。

## 決定

### 1. 世帯の識別は「内部ID」と「表示用の顧客番号」の2本立て

- **世帯の内部ID**: 世帯を作ったときに1回だけ振る、変わらない乱数のID。
  - 乱数だけで作り、作成日時・PC・FP・顧客の情報を含めない（例: UUID の第4版。文字列の書式は 0004 に従う）。
  - 世帯ファイルの封筒（0011）、鍵置き場（0013）、取り込みの記録、AIに渡した記録（0014）は、すべてこのIDで世帯を指す。
  - 画面には原則として出さない（問い合わせや照合で必要なときだけ、FP向けの詳細画面で見られる）。
  - 世帯の分割・統合では新しい内部IDを振り、元の内部IDを系譜として残す。
- **表示用の顧客番号**: FPが顧客を見分けるための短い番号（例: `A0042`）。
  - 既定の採番は「PCごとの接頭辞＋連番」。接頭辞はPCごとに事務所データで決め、2台のPCで同時に作っても番号がぶつからないようにする。
  - FPはいつでも変えてよい。変えても内部IDは変わらない。
  - 事務所の中で同じ番号が既にあれば警告する（禁止はしない。重複してもデータは内部IDで区別される）。
  - 顧客番号と顧客の氏名の対応表は、ファイナンシアの外でFPが管理する（ファイナンシアは持たない）。
- **構成員のID**: 世帯の中で構成員ごとに振る、変わらない乱数のID。資産・負債・保険・収入の名義は必ずこのIDで指す（構成員モデルは 0008）。
- **PCのID**: インストールしたときに作る乱数のID。機器の製造番号・MACアドレス・OSのユーザー名など、機器や人から導ける値は使わない。封筒の「どのPCで保存したか」の判別と、顧客番号の接頭辞の初期値にだけ使う。
- 画面での家族の表示は「本人(45)・配偶者(43)・長女(12)」のように、続柄と年齢で行う。

### 2. 氏名の欄はどこにも作らない

- データモデル（JSON Schema）、世帯ファイル、事務所データ、ヒアリングシート、画面の入力欄のどこにも、氏名・フリガナの項目を作らない。
- 提案書PDFの宛名は、印刷・PDF出力のときにだけ入力させ、保存しない。顧客に見せた版の控えのPDFは宛名を空にした版で保存し、再印刷のときにその場で宛名を重ねる（0009）。
- ヒアリングシートには「お名前は書かないでください」と明記する（0018）。
- 他のソフトからの移行では、氏名・住所・電話番号・番号類を読み取りの最初の段階で伏せ字にし（「本人」「配偶者」「第1子」などに置き換える）、伏せ字にした後のものだけを保存する。伏せ字のためにFPが入力した家族の名前は、メモリの上だけで使い、保存しない。移行元のPDFそのものは保存しない。
- メモ欄・自由記述に「様」「さん」「氏」などの敬称や、氏名らしい語があれば、保存の前に注意を出す（保存は止めない。FPが判断する）。
- 拡張領域（0011）で独自項目を定義するとき、項目のキーや表示名が持たない情報（下の3の一覧）を思わせる場合は警告し、FPの確認を求める。
- FP向けの説明では、「名前を持たなくても、FPにとっては個人情報のまま（FPは顧客番号と名前の対応を知っている）」ことをはっきり書く。名前を持たない効果は、漏れたときの被害と特定のしやすさを小さくすることであって、個人情報でなくなることではない。

### 3. 持つ情報と持たない情報

**持つもの（計算に必要なため）**

| 項目 | 持ち方 | 使う計算 |
|---|---|---|
| 生年月日 | 「生年月」＋「1日生まれかどうか」（例: `{"birthYearMonth": "1981-04", "bornOnFirst": false}`） | 年齢、年齢到達の月、学年 |
| 性別 | 制度の計算上の性別（`female`／`male`） | 遺族年金の経過措置、寡婦加算、平均余命 |
| 市町村 | 市町村コードだけ | 地域の値（国保・住民税などの標準値の選択） |
| 勤め先 | 保険者の区分（協会けんぽの支部か健保組合など）と退職給付の規程 | 社会保険料、退職給付 |
| 学校 | 学校コード（0010） | 学費 |

- **生年月日を日付で持たない理由**: 制度の年齢到達は「誕生日の前日」に達する扱いが多く、1日生まれの人だけが前の月に到達する。学年も4月1日生まれだけが前の学年に入る。年金・社会保険・学年の計算は「生年月」と「1日生まれかどうか」で正しく出せるので、日まで持つ必要がない。表に出す年齢は「その年の12月31日時点の満年齢」（0003）。
- **性別を持つ理由**: 遺族年金の経過措置などの制度が、法律上の性別で計算を分けているため。画面の表示名は「（制度の計算上の）性別」とする。値の種類は、制度の計算が区別する2つだけにする。

**持たないもの（聞かない・保存しない）**

| 種類 | 具体例 | 代わりにどうするか |
|---|---|---|
| 実在の健康状態 | 病歴、障害の有無・等級、要介護度の実際、通院歴 | 障害・就業不能・介護は「該当した場合」の仮定のシナリオとしてだけ扱う |
| 番号類 | 個人番号（マイナンバー）、基礎年金番号、健康保険の記号・番号、運転免許証・旅券の番号、保険の証券番号 | 計算には使わないので持たない。保険契約は世帯内の乱数IDで識別する |
| 口座・カード | 銀行・証券口座の番号、クレジットカード番号 | 残高と口座・資産の種類（NISA・iDeCo など）だけを持つ |
| 書類の画像 | 源泉徴収票・ねんきん定期便・保険証券などの写真やスキャン、移行元の帳票の切り抜き画像 | 数値を転記してもらう。画像は受け取らず、保存もしない |
| 連絡先 | 住所、電話番号、メールアドレス | 住所は市町村コードだけ。連絡はFPがファイナンシアの外で行う |
| 勤め先の名前 | 会社名・所属 | 保険者の区分と退職給付の規程だけを持つ |

- 勤め先の名前は、もとの一覧にはない項目だが、計算に使わず、個人の特定に強く結び付くので持たない。
- ヒアリングシートには「これらは聞きません」と明記する（0018）。
- 家族の障害に関わる税の扱い（障害者控除など）は、実在の状態を持たずに表す方法を後の版で設計する（未確定を参照）。

### 4. 提供元はどの経路でも顧客データを受け取らない

提供元のサーバー・メール・フォームのどこにも、顧客の世帯データが届く経路を作らない。経路ごとに次のように守る。

| 経路 | 決め |
|---|---|
| ヒアリング | シート（Excel／PDF）のやりとりはFPと顧客の間だけで行う。提供元のサーバーを通るWebフォームは作らない（0018） |
| 移行 | 読み取りはFPのPCの中で行う。見出しの対応付けにAIを使う場合も、FP自身のAIに、値を伏せた見出しと並びだけを渡す。提供元の中継は作らない |
| AI接続口 | FPのPCの中だけで動き、ネットワークの口を開けない。データが向かう先は、FPが選んだAIの会社だけ（0015） |
| 自動の通信 | アプリが自動で通信する先は更新の配信元（`updates.fprise.com`）だけ（0017）。何を・いつ送るかは下の「外部送信の一覧」に載せたものだけで、世帯の情報・世帯ID・PCのID・顧客番号は、どの通信でも送らない。配信元ではIPアドレスを保存しない |
| 利用状況 | 自動送信は既定でOFF。FPがONにしたときだけ、機能ごとの使用回数のカウンタを送る。世帯の内容・IDは含めない。送る項目はすべて公開の「外部送信の一覧」に載せる |
| 不具合報告 | 受け付けるのは、FPのPCで匿名化した書き出し（0020）だけ。生の世帯ファイルは受け付けず、届いた場合は開かずに削除する |
| 問い合わせ | 世帯ファイルや画面の写しを添付しないよう案内する。届いた場合の扱いは不具合報告と同じ |
| β | 参加の条件に「架空の世帯か、匿名化の書き出しで加工した世帯で試す」を入れる |

- 自動のクラッシュ報告や、第三者の分析・計測の部品（SDK）は組み込まない。
- アプリのログ・エラーメッセージに顧客データを書かない。画面（WebView）の保存機能にも置かない（0016）。

### 5. 外部送信の一覧

アプリが自動で外へ送るものは、この一覧に載せたものだけにする。相手はどれも配信元（配布元の設定 `config/distribution.toml` の `[endpoints]` の `host`）で、https・ほかのホストへの転送に従わない・クッキーを持たない・証明書は OS の仕組みで確かめる（0017 の4）。通信は本体（Rust）の HTTP の部品だけが行う。新しく足すときは、先にこの一覧を直す（`app/` の `npm run check:distribution` が、本体が読む配信先の欄〔`[endpoints]` の名前〕がこの一覧に無いと止める）。

| 送るもの | 相手（配布元の設定の欄） | いつ | 送る中身 | 送らないもの | 止め方 | 状態 |
|---|---|---|---|---|---|---|
| 取り下げの一覧と、コードを止めるだけの一覧の取得（0117 の3 (3)・追記 2026-11-04 の2。今は機能を有効にするコードの取り下げ〔0110 の7・追記 2026-11-04〕を当てるためだけ。2つを続けて取る） | 配信元（`revocations`・`feature_code_revocations`） | 機能を有効にするコードが入っている PC だけ。起動して少しあと（5秒後）・動いている間は1日1回（取れなければ1時間後にもう一度）・コードを入れたとき（入れ口・AIからの候補）・FP が「今すぐ確かめる」を押したとき | 一覧の取得の依頼（`GET`）だけ。クエリを付けず、User-Agent は決まった文字だけ | コード・名前・世帯の情報・PC を見分ける値・アプリの版・OS | コードを外せば取りに行かない（コードを入れていない PC は一度も取りに行かない。確かめを切る設定は作らない。0110 の7） | 入れた |
| 更新の確認（0017 の4） | 配信元（`app_catalog`・`app`・`packs`・`notices`。取り下げの一覧は上の行） | 起動時・起動中は1日1回・FP が「更新を確認」を押したとき | どの配布物を渡すかの判定に要るアプリの版・OS・CPU の種類（いずれも個人を識別しない） | 世帯・FP・PC を識別する値・顧客番号 | （更新の仕組みを入れる回で決める） | まだ入れていない |
| 利用状況（4 の表） | 配信元（欄はまだ無い） | FP が ON にしたときだけ（既定は OFF） | 機能ごとの使用回数のカウンタ | 世帯の内容・ID | OFF にする | まだ入れていない |

- 要望・不具合のフォームは、FP が押したときに既定のブラウザで開くもので、アプリの自動の通信ではない（0087。この一覧には入れない。URL に入れるのは受付番号・アプリの版・OS だけ）。
- 「まだ入れていない」ものは、入れる回に送る中身を確かめて「入れた」にする。それまで、アプリが自動で通信するのは「入れた」の行だけ。
- 取り下げの一覧（`revocations`）は、2026-11-04 に機能を有効にするコード専用の止めた一覧をこれに一本化した（0110 の追記）。同じ日に、コードを止めるだけの手軽な鍵で署名する小さな一覧（`feature_code_revocations`。`/v1/revocations/feature-codes.json`）を別に足した（0117 の追記 2026-11-04 の2）。相手（配信元）・送る中身（取得の依頼だけ）・いつ（コードが入っている PC だけ）は同じで、依頼が2つになる。アプリ本体の更新のつなぎ（0117 の未確定）を入れる回に、コードを入れていない PC も取りに行くかと、その回の「いつ」をこの行で決め直す。

## 理由

- 名前・番号類・健康状態・画像は、漏れたときの被害が大きい一方、ライフプランの計算には使わない。持たなければ、暗号化（0013）が破られた場合でも被害が小さくなる。
- 生年月日を「生年月＋1日生まれか」にすると、計算の正しさを落とさずに、特定のしやすさを下げられる。
- 内部IDを乱数にするのは、IDから作成時期や事務所が推測されないようにするため。表示用の番号を別に持つことで、FPは慣れた顧客番号で運用でき、番号を変えてもデータのつながりは切れない。
- 提供元が顧客データを受け取らないことを、規約で約束するだけでなく「受け取る経路が存在しない」という作りで保証する。経路が無ければ、提供元の側の漏えいや誤った取り扱いも起こりえない。

## 影響

- **後から変えると**: 氏名などの欄を後から足すと、「持たない」ことを前提にした説明・同意・漏えい時の判断がすべて崩れる。逆に、生年月日を日付で持つように変えると、全世帯ファイルの移し替えと、年齢・学年の計算の作り直しが要る。
- **守るべき決まり**
  - データモデルに上の「持たないもの」に当たる項目を足さない。拡張領域の公式キーにも足さない。
  - 新しい通信先・新しい送信項目を足すときは、この記録を改め、「外部送信の一覧」（5）を更新する。
  - ログ・エラー・クラッシュ時の出力に、世帯の値・メモ・自由記述を入れない。
- **テストで確かめること**
  - JSON Schema の検査: 項目名・説明文に禁止語（`name`、`kana`、`address`、`phone`、`myNumber`、`pensionNumber`、`accountNumber`、氏名、住所、電話、口座番号 など）を含む項目がないことをCIで確かめる。
  - 通信の検査: 画面の自動テストで主な流れ（世帯の作成→入力→PDF→保存→更新の確認）を通し、外への通信が更新の配信元だけで、送った中身が「外部送信の一覧」（5）の「送る中身」だけであることを確かめる（止めた一覧の取得は取得の依頼だけ、更新の確認はアプリの版・OS・CPUの種類だけ）。
  - 一覧と実装の突き合わせ: 本体が読む配信先の欄（配布元の設定の `[endpoints]` の名前）が「外部送信の一覧」にあることを、`npm run check:distribution`（CI）で確かめる。
  - 移行の伏せ字: 架空の氏名・住所・電話番号を入れた帳票を取り込み、保存された世帯ファイル（復号した中身）にそれらの文字列が残らないことを確かめる。
  - ログの検査: 架空の世帯で全機能を動かし、ログに世帯の値・メモが出ないことを確かめる。

## 試作での確認

- 鍵の置き場所の試作で、暗号化した世帯ファイル・鍵置き場に氏名の文字や鍵の生の値が入っていないことを確かめた。
- AI接続口の試作で、AIに渡す縮約版から名前・生年月日・住所・電話・FPのメモ・顧客の自由記述が外れ、年齢・収入・支出・資産・ローンが残ることを確かめた（詳細は 0015）。
