# 0248. 世帯をまとめて AI に渡す・顧客のフォローの要約（summarize_shared_households）

- 状態: 採用（一部未確定）（2026-11-23）
- 固定の強さ: 渡す理由の判定は1件ずつと同じ関数（0226）・期限と申告と記録は1件ずつと同じ・見本は渡さない・顧客番号とお名前と面談の履歴の文は AI に渡さない・AI は連絡を送らないは骨格。上限の値（50件）・命令 `ai_share_bulk_check`・`ai_share_bulk_start`・`ai_share_bulk_stop` の形・画面の言葉は内部。道具 `summarize_shared_households` の名前と入出力・プロンプト `follow_up_clients` は試験版（0015 の2）
- 前提にする記録: 0015（AI接続口。5 の世帯を渡す・8 の記録）、0014（同意と AI に渡した記録）、0012（持たない情報）、0033（区分と見本の棚）、0226（AI接続を使える条件）、0184 の追記（渡すのは保存した世帯）、0182（面談の履歴）、0072（次回確かめるの印）、0009（控え）

## 背景

- FP は顧問契約のお客さま全員を見て、フォローが要る人（面談から長くたった・資産が尽きる年が近い・確かめることが残っている）に連絡したい。今は世帯を1件ずつ開いて「この世帯をAIに渡す」を押すしかなく、AI も世帯の数だけ `get_shared_household`・`calculate` を呼ぶ。
- 利用者の判断（2026-11-23）: 世帯の一覧（区分 A 顧問契約・B 単発相談・C 見込み客〔0033〕や番号の絞り込み）で選んだ世帯を、まとめて AI に渡せるようにする。AI には1世帯1行の要約の道具を用意し、フォローの要る世帯を理由つきで並べ、連絡の文の下書きを作れるようにする。ファイナンシアはお名前・メールアドレスを持たない（0012）ので、宛先は FP が自分の台帳で入れる。
- この記録では、メモと面談の履歴の文は渡さない（FP が印を付けたときだけ渡す形は次の記録で決める。今の縮約版の決まりは変えない）。

## 決定

### 1. まとめて渡す（画面と本体）

- 入口は世帯の一覧の顧客の世帯の側で、絞り込み（「区分」「番号で探す」）の結果に対する操作として、一覧の上に「選んだ世帯をまとめてAIに渡す」を置く。一覧の行の部品には触らない（行の作り直しの作業と重ねないため）。見本の棚には出さない。
- 押すと、絞り込みの結果の世帯が選ぶ欄として並ぶ（初めはすべて選ぶ。一覧が上限を超えるときは選ばずに始める）。選ぶたびに本体が確かめ（`ai_share_bulk_check`。共有は作らない・世帯ファイルに書かない）、「渡せる世帯」「もう共有中の世帯」「渡せない世帯」（理由ごとの件数と顧客番号）を出す。
- 渡す（`ai_share_bulk_start`）: 選んだ世帯それぞれに、1件ずつと同じ共有を作る。期限（15分〜8時間）・接続先の申告（0014 の `destinationDeclared`）・縮約版・AIに渡した記録（0014）・取り消し・同意の撤回で止まることは、1件ずつと同じ。渡せない世帯は渡さず、理由を返す。もう共有中の世帯は新しい共有を作らない（期限はそのまま）。
- 渡す理由の判定は、1件ずつと同じ `ai_share::ai_use`（同意がある・事務所のプライバシーポリシーを確かめていて「同意しない」と答えていない・架空の世帯。0226）。共有を作るのも1件ずつと同じ `ShareRegistry::grant`（中でもう一度同じ判定をする）。
- 渡せない理由（見本の行は番号を持たないので、見本の名前で「見本「名前」」と出す。0247）: `refused`（「同意しない」と答えた）・`withdrawn`（撤回した）・`noBasis`（同意の答えが無く、事務所のプライバシーポリシーも確かめていない）・`sample`（見本）・`notSaved`（保存していない）・`readOnly`（閲覧だけで開く世帯。AIに渡した記録を世帯ファイルに残せないため。1件ずつの共有はこの確かめをしていない）・`openByOthers`（ほかのメンバー〔ほかの PC〕が今開いている世帯。下の「追記」）・`unreadable`（開けない）・`unknown`（一覧に無い）。
- 渡した後は、AI に見える仮名（「共有中の世帯A」など）と顧客番号の対応を画面に出す。AI の答えは仮名で並び、顧客番号は AI に渡さない（0015 の5）ので、FP はこの対応（と共有中の帯）で結びつける。
- まとめて取り消す（`ai_share_bulk_stop`）: 一覧の上の「この一覧の共有をまとめて取り消す」で、絞り込みの結果の世帯の共有をすべて取り消す（即時）。
- 命令が受け取るのは世帯の内部ID の並び・期限・申告だけ（パス・鍵は受け取らない・返さない。0016 の1）。

### 2. 上限は 50件（共有中の世帯と合わせて）

- 1回に選べるのは 50件まで。共有中の世帯と合わせて 50件を超えるときは、1件も渡さずに断る（`E_AI_BULK_LIMIT`）。確かめは、選んだ数が 50件までならいつでもでき、渡せる数と共有中の数を返す（画面が先に上限の文を出す）。
- 理由:
  1. 顧客のフォローの要約は、1回の呼び出しで世帯ごとにアプリに読み（記録が残る）、接続口の中で計算する。50件なら接続口の計算（CPU の数の半分で並べる）が数秒〜十数秒で終わり、答えも1行約300字×50件で AI の会話に収まる。
  2. 渡すときに、開いていない世帯を復号して帳面を作り、AIに渡した記録を世帯ファイルに書く。50件なら一度に書くファイルの数が限られ、画面の保存を長く待たせない。
  3. 1人の FP が持つ顧問契約のお客さまは数十件が多く、区分で絞り込めば多くの事務所で1回に収まる。収まらないときは番号で分けて渡せる。
  4. 渡す前の確かめの一覧を FP が目で確かめられる数にする（取り消しで止まるのは今後の読み取りだけで、送った内容は AI の会社の側に残る。0015 の5）。
- 要約の道具も、1回に読むのは 50件まで（共有が 50件を超えることは、1件ずつ渡した世帯と合わせても上限で起きない）。

### 3. 画面で開いていない世帯の開き方

- 画面で開いていない世帯は、保存の部品の `Store::open_unmarked` で開き、本体の帳面（`HouseholdBook`）を作ってから渡す。開いた印（前回開いた世帯・事務所の共有の「開いている」〔0023 の7〕）は変えない。帳面を作るのは、AIに渡した記録・読まれた記録を世帯ファイルに書き戻すため（0014 の3。記録を残さずに渡す経路を作らない。0015 の8）。
- この起動で開いた世帯（画面で開いている世帯を含む）は、持っている帳面をそのまま使う（保存の状態を作り直さない。画面の保存と衝突の確かめを崩さない）。
- 確かめ（`ai_share_bulk_check`）では帳面を作らず、世帯ファイルにも書かない。

### 4. 保存していない変更・見本

- 渡すのは保存した世帯のまま（0184 の追記と同じ）。開いている世帯に保存していない入力の変更があり、その世帯を選んでいれば、「開いている世帯（A0001）は、保存した内容を渡します。いまの入力の変更は、保存するまでAIの計算に入りません。」と添える。渡した後は、今までどおり共有中の帯で「保存するとAIにも反映されます」が出る。
- 見本の世帯（見本の棚）は渡さない。顧客の一覧に入らないうえ、本体も世帯の一覧の番号の中身で見本と分かれば `sample` として断る（画面で見本を開いていても同じ。見本が直せて保存されるようになっても、まとめて渡す対象に入れない）。

### 5. 顧客のフォローの要約の道具（summarize_shared_households）

- 世帯を扱う群の、読むだけの道具。`share_ids`（50件まで）を書くとその世帯、省くといま渡されている世帯すべて（仮名の順に50件まで。超えたら `truncated`）。
- 1行の項目: `shareId`・`alias`・`basis`・`category`（区分の記号 `code` と事務所の区分の名前 `name`）・`lastMeetingOn`（前回の面談の日。面談の履歴〔0182〕のいちばん新しい日付だけ）・`meetings`（面談の記録の数）・`lastSnapshotMonth`（最後の控えの年月）・`nextReviewMonth`（その1年後。画面の面談の準備の「次の面談の目安」〔`FpTools.tsx` の `reviewTiming`〕と同じ考え方）・`reviewDue`（今月が目安の月を過ぎたか）・`recheckMarks`（「次回確かめる」の印〔0072〕の数）・`depletion`（資産が尽きる年と本人の年齢）・`minimum`（金融資産がいちばん少ない年と額）・`notices`（計算のお知らせの件数）・`ok`。
- 主な数字は `calculate` と同じ道（プランの変更なし → 画面と同じ計算の前の処理〔0184〕→ 計算 → `keyFigures`〔0194〕）で数える。年金の見込みは計算しない（速さのため）。
- 読めない世帯（期限切れ・取り消し後・渡していない共有 ID）はその行だけ `ok: false` と `error`（`EXPIRED`・`REVOKED`・`NOT_SHARED` など）、計算できない世帯は `ok: false` と `calcError` を返し、ほかの行は返す（全体は止めない）。
- 要約の材料（`FollowupFacts`）は、本体の帳面が本文から日付・数・区分の記号だけを読んで作る（読み方は画面と同じ: 面談の履歴は形の合う日の記録で同じ ID は1件、印は形の合う行で同じ行の ID は1つ、控えは作った日時の年月）。面談の中身・FP のメモ・印の見出し・顧客番号は持たない。区分の記号は世帯の一覧の番号の中身から（世帯を開いたとき・区分を変えたときに入れる）。区分の名前は事務所の区分の設定から（名前は事務所が決めた短い言葉で、お客さまの文ではない。20字まで）。
- 読むたびに、世帯ごとの「AIに渡した記録」に道具の名前 `summarize_shared_households` で残す。項目は縮約版の項目に `followup.category`・`followup.lastMeetingOn`・`followup.meetings`・`followup.lastSnapshotMonth`・`followup.recheckMarks` を足し、中身の指紋にも要約の材料を入れる。計算に使う事務所の推定の値は、今までどおり記録の中身に入れない（0184）。

### 6. アプリとの取り決め

- 依頼 `getShareFollowup`（`shareId`・`tool`）を足した。返事は計算に使う読み取り（`getShare` の `forCalc`）と同じ形に、要約の材料 `followup` を添えたもの。接続口とアプリは同じ版でしかつながらないので、`IPC_VERSION` は 1 のまま（0015 の追記 2026-11-07 と同じ扱い）。

### 7. プロンプト「顧客のフォロー」（follow_up_clients）

- 引数は `category`（見る区分）・`focus`（フォローが要るとみる目安）・`purpose`（連絡の文の用途。既定は面談のお誘い）。進め方: 要約を取る → 区分に合う行から目安に当たる世帯を急ぐ順に理由つきで仮名で並べる（`ok: false` の行は別に並べ、推測で埋めない）→ 理由を確かめたい世帯だけ `calculate`・`check_inputs` で見る → 連絡の文の下書き（宛名は空ける。数字は丸め、試算であることを添える）。
- AI に伝えること: ファイナンシアはお名前・メールアドレスを持たず、AI には顧客番号も渡していない。宛先は FP がアプリの「顧客番号 → 仮名」の対応と自分の台帳で入れる。AI からメールを送らない・宛先を探さない。

### 8. ほかのメンバーが開いている世帯（2026-11-23 の追記）

- 確かめたこと: 事務所で共有しているとき、ほかのメンバーが開いている世帯に、こちらが開いた印を付けずに開いて（`open_unmarked`）AIに渡した記録を書き戻すと、相手の次の保存は分岐（`E_STORE_CONFLICT`。相手の内容は相手の PC に別のファイルで残る）になる。1件ずつの共有でも、渡した後に別の世帯を開いてから相手がその世帯を開いたとき、同じことが起きていた。
- 決めたこと（記録を事務所データの台帳だけに残す形は、台帳がまだ無いので採らない）:
  1. 渡すときに断る: まとめて渡すときは理由 `openByOthers`（「ほかの人（ほかのPC）が開いている世帯（AIに渡した記録を書くと、相手の保存が分岐になるため。閉じてから渡してください）」）、1件ずつのときは `E_AI_OPEN_BY_OTHERS`（「ほかの人（ほかのPC）がこの世帯を開いている間は、AIに渡せません（AIに渡した記録を書くと、相手の保存が分岐になるため）。閉じてから渡してください」）。
  2. 渡した後にほかのメンバーが開いたら、裏の見回り・取り消し・まとめて渡すときの書き戻しは、その世帯を書かずに待ち、相手が閉じた後の見回りで書く（記録はその間メモリの中にある）。
  3. 画面がいま開いていない世帯（この起動で前に開いた世帯・まとめて渡すときに画面に出さずに開いた世帯）は、書き戻す前に世帯ファイルを開いた印を付けずに読み直し、帳面を作り直してから記録を足す（間に相手が保存していても分岐にしない。作り直すのは、帳面だけの変化〔同意の記録・候補の判断〕が書いた後のときだけ）。
- 残ること: 同意の記録・候補の判断・アプリの終了のときの書き戻しは、今までどおりすぐ書く（相手が開いていれば分岐になりうる）。相手が開いたままアプリを閉じると、待っていた読み取りの記録も書く。画面がいま開いている世帯は、画面の保存と同じく分岐の確かめ（0011 の7）に任せる。

## 理由

- 1件ずつと同じ関数・同じ共有で作ることで、渡せるかの判定・記録・取り消しの決まりが、まとめて渡すときだけずれることを防ぐ。
- 要約の道具を1つにすると、AI が世帯の数だけ読み取りと計算を繰り返さずに済み、記録も世帯ごとに1行の読み取りになる。
- 顧客番号を渡さず仮名で並べるのは、顧客番号が FP の台帳と結びつく識別子だから（0015 の5・0012）。面談の日付と数は、フォローの要否を決めるのに要り、お客さまの文を含まない。
