# 0001. 記録の書き方と固定の時期

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。ただし「書き方の細部」（見出しの言い回し、テンプレートの補足）は理由を残せばいつでも直してよい

## 背景

ファイナンシア（Financia）は、FP（ファイナンシャルプランナー）が自分のAIを使って計算部品・帳票・入力項目を作り変えられるライフプランソフトである。提供元はFPライズ（FPRISE, INC.）。開発の大部分をAIが行い、利用者の側でもFPのAIがこのリポジトリのソースと記録を読んで作り変えを行う。

そのため、技術の決定は「人が覚えている」のではなく、AIが毎回読んで迷わない形で、リポジトリの中に残しておく必要がある。また、このリポジトリはβ公開（2027年2月予定）で誰でも見られるようになり、外部のFP・FPのAI・フォークが記録を頼りに作り変えを始める。β公開の後に骨格を変えると、配布済みのファイル・作り変え・AIの手順がまとめて壊れる。

この記録では、設計記録（ADR）の書き方と、「いつまで変えてよく、いつから変えないか」を決める。

## 決定

### 1. 置き場所とファイル名

- 置き場所は `docs/decisions/`。
- ファイル名は `NNNN-短い英語のスラッグ.md`（例: `0002-money-rate-rounding.md`）。
  - `NNNN` は4桁の通し番号。0001 から順に振る。
  - 番号は使い回さない。取りやめた記録も消さずに「廃止」として残す（番号が欠けると、他の記録からの参照が切れるため）。
  - スラッグは英小文字・数字・ハイフンだけ。スラッグは後から変えない（リンクが切れるため）。
- 索引として `docs/decisions/README.md` を置く（目的・一覧・未確定の要点）。ただし、状態と固定の強さの正は各ファイル冒頭の行で、索引はそれを写した案内にすぎない。食い違ったら各ファイルが正で、CIで索引の一覧と各ファイル冒頭の行が一致することを確かめる（二重管理で食い違うのを避ける。冒頭の行から機械で一覧を作る形に移ってよい）。

### 2. 各記録の形

```
# NNNN. タイトル
- 状態: 採用（YYYY-MM-DD）
- 固定の強さ: （下の4の区分のどれか）
## 背景
## 決定
## 理由
## 影響
## 試作での確認        ← あれば
## 未確定              ← あれば
## 追記                ← 採用後に足したこと（日付つき）
```

- 「決定」は箇条書きで、型・フィールド名・規則・数値など、実装する人（AI）がそのまま書ける具体さで書く。
- 「影響」には、後から変えると何が起きるか、守るべき決まり、テストで確かめることを書く。
- 「未確定」には、決めきれないことと、いつ・何を見て決めるかを書く。
- 日本語で書く。ID・型名・ファイル名・コードは英字のまま書く。
- 他の記録は番号で参照する（例: 「金額の型は 0002」）。

### 3. 状態

| 状態 | 意味 |
|---|---|
| 提案（YYYY-MM-DD） | 書いたが、まだ採用していない。実装の根拠にしない |
| 採用（YYYY-MM-DD） | 実装の根拠にする |
| 採用（一部未確定）（YYYY-MM-DD） | 「決定」に書いたことは採用。「未確定」に書いたことはまだ決めていない |
| 置き換え（YYYY-MM-DD、NNNN による） | 新しい記録 NNNN に置き換えた。本文は残す |
| 廃止（YYYY-MM-DD） | 取りやめた。置き換える記録はない。本文と理由を残す |

### 4. 固定の強さ

| 区分 | 意味 | 変え方 |
|---|---|---|
| 骨格 | 仕組みの考え方。β公開から変えない | β公開前は、新しい記録で理由を残せば変えてよい。β公開後は変えない（例外は下の6） |
| 安定（公開の約束） | 外部が頼りにする形式。版を付けて守る | 下の5の表の規則に従う |
| 試験版（公開の約束） | 外部が頼りにするが、まだ変わりうる形式 | 3か月前に予告して変えることがある（下の5） |
| 内部 | 外から見えない実装の決め | 理由を残せばいつでも変えてよい |

1つの記録の中に区分の違う決定が混じるときは、冒頭の「固定の強さ」にまとめて書いたうえで、決定ごとに区分を添える。

### 5. 公開の約束と、その変え方

外部の人（FP・FPのAI・フォーク）が頼りにする形式を「公開の約束」と呼び、約束ごとに版を付ける。

- 版の書き方は `MAJOR.MINOR`（例: `household-file@1.0`）。
  - MAJOR: 互換を壊す変更（必須の欄の追加、欄の削除・改名、意味の変更）で上げる。
  - MINOR: 互換を保つ変更（任意の欄の追加、選択肢の追加で古い読み手が無視しても正しく動くもの）で上げる。
- β公開の時点の区分と変え方:

| 公開の約束 | β公開時の区分 | 変え方の規則 |
|---|---|---|
| 世帯ファイルの形式 | 安定 | 古い形式は新しい形式へ一方向に自動で変換する。変換を必ず添える。βで作った世帯ファイルは正式版でも読める |
| 制度データ・マスタデータの形式 | 安定 | 互換を壊す変更は年1回まで、1年前に予告する |
| ヒアリングシート（Excel）の形式・シート定義 | 安定 | 過去の版のシートも取り込める状態を保つ |
| 計算部品の入出力の約束（拡張モジュールの書き方） | 試験版 | 3か月前に予告して変えることがある。予告には、AI向けの移行手順と、できる限り自動の変換を添える。正式公開の1年後をめどに安定にし、以後は古い約束を12か月動かし続け、互換を壊す変更は年1回までとする |
| AI接続口の道具の名前と入出力 | 試験版 | 同上 |
| 帳票の部品（Typst のパッケージ） | 試験版 | 過去の版をアプリ内に残し、古い版を使う独自帳票も動かし続ける |
| 移行の読み取り規則・用語辞書の書き方 | 試験版 | 過去の版の書き方をアプリ内で読み続ける |

- 予告と変更点は、リリースノート、アプリ内のお知らせ、SDKフォルダの「版ごとの変更点」（0019）に載せる。
- 公開の約束を変えるときは、必ず新しい記録（またはその約束を決めた記録の「追記」）を書き、旧版から新版への対応を書く。
- 「試験版」から「安定」へ上げるときも記録を書く。

### 6. β公開の後に骨格を変えなければならないとき

- 骨格は変えないのが原則。例外は、(a) 安全上の欠陥（顧客データが漏れうる、改ざんを検出できない等）、(b) 法令に合わなくなったこと、の2つだけ。
- 例外のときも、新しい記録で理由を書き、配布済みの世帯ファイル・制度データ・作り変えが読めなくならない移行（一方向の自動変換、古い形式の読み取りの維持）を必ず付ける。

### 7. β公開までの進め方

- 骨格の記録（0001〜0022）は2026年11月末までに「採用」にする。未確定の点は「採用（一部未確定）」で残してよいが、β公開までにすべて決めるか、「骨格ではない」と区分を変える。
- β公開までは、骨格も新しい記録で理由を残せば変えてよい。古い記録は「置き換え」にして残す。
- 試作で確かめてから確定すると決めたもの（計算エンジンの実行環境、AI接続口、画面の安全設定、鍵の置き場所、自動化）は、試作の数字を記録の「試作での確認」に書いてから確定する。

### 8. 書き換えのしかた

- 「採用」になった記録の「決定」は書き換えない。変えるときは新しい記録を作り、古い記録の状態を「置き換え（日付、NNNN による）」にし、本文の先頭に「→ NNNN に置き換え」の1行を足す。
- 「未確定」に書いていたことを決めたときは、同じ記録の「追記」に日付つきで書いてよい（既にある決定を覆さない場合に限る。覆すなら新しい記録）。
- 誤字・言い回し・リンクの修正は、そのまま直してよい（意味を変えない場合に限る）。

### 9. 書くことと書かないこと

- 書くのは技術の決定だけ。
- 書かないもの: 事業上の情報（集客・費用・人員・運用の時間）、個人名、実在の顧客データ、非公開リポジトリの中身（原本の写し、他社の帳票、テスト用の非公開サンプルの中身）、署名鍵・APIキー・トークン。
- 非公開のテスト用サンプルを使うテストがあることは書いてよいが、その中身や出どころは書かない。

### 10. 開発するAIの読み方

- 開発するAI（とFPのAI）は、作業の前に関係する記録を読む。どの記録が関係するかは、リポジトリ直下の `AGENTS.md`（0019）から案内する。
- 記録に反する変更をするときは、先に新しい記録（状態「提案」）を書き、採用されてから実装する。
- コードの中で決まりの根拠を示すときは、記録の番号をコメントに書く（例: `// 0002: 丸めは規則IDつき関数だけ`）。

## 理由

- 番号を使い回さず記録を消さないのは、「なぜそうなっているか」を後から追えるようにするため。AIは古い会話の記憶を持たないので、記録が唯一の手がかりになる。
- 骨格をβ公開から固定するのは、β公開の時点から外部のFPが作り変えを始め、世帯ファイル・ヒアリングシートが配られ始めるため。それ以前に変えても影響は開発の中に閉じる。
- 公開の約束に安定と試験版を分けるのは、データの形式（世帯ファイル・制度データ・ヒアリングシート）は配った後に読めなくなると顧客の記録を失うので最初から固く守り、計算部品・AI接続口・帳票・移行の書き方は実際に使われてからでないと良い形が分からないため。
- 版を `MAJOR.MINOR` にするのは、作り変えの側が「どの版の約束に合わせて書いたか」を宣言し、アプリが互換を機械で判定できるようにするため（0006）。

## 影響

- 新しい技術の決定は、必ず記録を足してから実装する。記録のない決まりは、AIが知らずに破る。
- β公開の後は、骨格を変える変更案は原則として受け付けない。CIで次を確かめる:
  - `docs/decisions/` のファイル名が `NNNN-slug.md` の形で、番号が重複していないこと
  - 各ファイルの見出しの直後（3行目・4行目）に「状態」「固定の強さ」があること
  - 索引（`docs/decisions/README.md`）の一覧の状態・固定の強さが、各ファイル冒頭の行と一致すること
  - 「置き換え」の記録が指す番号が存在すること
- 公開の約束（形式）の版は、スキーマやSDKに機械で読める形で埋め込み、記録の版と一致することをCIで確かめる。

## 未確定

- 公開の約束の版の初期値: 安定の約束（世帯ファイル・制度データ・マスタデータ・ヒアリングシートの形式）の最初の版を、β公開の時点で `1.0` にするか、β期間は `0.x` にするか。`1.0` にする案が有力。11月に決める（0001・0007・0011 で同じ未確定。決めたら3つの記録の「追記」に同じ内容を書く）。
- 記録を英語でも用意するか（海外のフォークやAIのため）。当面は日本語だけ。
