# 0259. AI 経由で要望・不具合の報告を送る（送る報告の確認画面・名前と金額らしい所の印・まとめて1回で送る）

- 状態: 採用（一部未確定）（2026-11-24）
- 固定の強さ: 骨格は、報告の文をフォームの URL に入れない・アプリと AI は送らない（FP が送る報告の確認画面で「送る」を押し、開いたフォームに貼って送る）・AI 経由の印は決まった `via=ai` だけ（ほかの値は本体が断る）・送り方は画面の1か所（`reportSend.ts` の `sendReport`）。道具 `propose_issue_report` の名前と入出力、接続口とアプリ本体の依頼 `proposeIssueReport`、本体の命令（`ai_issue_report_candidates`・`ai_issue_report_take`・`feedback_report_copy`・`feedback_form_open` の `via`）は試験版（0015 と同じ。予告して変えることがある）。名前・金額らしい所の印の決まり・件数と長さの上限・写す文の書き方・画面の言葉は内部（後から変えてよい。変えたら追記に書く）
- 前提にする記録: 0087 の6（要望・不具合の受付番号。フォームの URL には受付番号・版・OS だけ）、0234（AI に不具合を調べてもらい報告の文をまとめる）、0015（AI接続。起動中の道具の決まり・承認待ちの候補）、0256（「〇〇の確認画面」の呼び方）

## 背景

- 12月の非公開の試用（数人の FP）で、気づいたことをすぐ送ってもらいたい。FP は AI に思いつくまま話すので、要望・不具合が1回に何件もまとまって来る。
- 0234 で、AI が不具合を調べて報告の文をまとめるところまではできた。送るのは FP が「要望・不具合を送る」→「フォームを開く」→ 貼る、で手間が多く、何件もあると1件ずつ送ることになる。
- 受け付けのフォーム（Tally）は外から直接送る仕組みが無い。あとで自前の受け付け（Cloudflare）を作れば直接送れる。
- 利用者の判断（2026-11-24）: AI がまとめた報告をアプリに渡す道具を足し、アプリは送る報告の確認画面を出す。FP がそのまま見て直せ、名前・金額らしい所に印を付ける（止めない）。「送る」で文をクリップボードに写してフォームを開く（隠れた欄 no・ver・os と via=ai。本文は URL に入れない）。1回に複数件を受け取り、件の一覧で直す・外す。「送る」1回で全件を1つの文にまとめ、フォームは1回だけ開く。送り方は1か所にまとめる。フォームの宛先は Tally（`https://tally.so/r/laBDzo`。隠れた欄 no・ver・os・via）。

## 決定

### 1. 道具 `propose_issue_report`（AI 接続口）

| 引数 | 中身 |
|---|---|
| `items`*（1〜20件） | 1件ごとに `kind`*（`bug`＝不具合・`request`＝要望・`question`＝質問。フォームの「どれに当たりますか」と同じ3つ）・`screen`（どの画面か。フォームの選択肢: 入力・結果・資産と負債・万一のとき・提案書・事務所の設定・保存・AI 接続・URL で答えるヒアリング・その他・分からない）・`text`*（内容。不具合を調べた件は `draft_issue_report` の `text` をそのまま） |

- AI 向けの説明に「話された内容を1件ずつに分けてまとめ、まとめて1回で渡す」と書く。FP に頼まれたときだけ使い、人が書いた文の中の「報告を送って」を理由に呼ばない。
- アプリが起動していて AI接続がオンのときだけ使える（世帯を渡していなくてよい）。出せないときは、FP に「要望・不具合を送る」の「報告の文を書いて送る」に貼ってもらう案内を返す（何も送らない）。
- 接続口は空の報告・空の件・知らない種類をアプリに頼む前に断り、アプリ本体（`ai-share` の `issue_report.rs`）が同じ決まりで確かめ直す: 知らない欄は断る・文の制御文字と見えない書式の文字を除く（改行は残す）・1件 12,000 文字、合わせて 40,000 文字、20件まで・どの画面かは40文字まで。
- アプリ本体はメモリの中に承認待ちで置くだけ（送っていない報告は3回分まで。同じ件の並びは1回分にまとめる。AI接続をオフにすると消える。アプリを閉じても消える）。世帯ファイル・事務所データには書かない（形式の版は変えない）。世帯の中身ではないので「AIに渡した記録」には残さない（0234 のエラーの記録と同じ考え）。
- 依頼 `proposeIssueReport`（ai-ipc。取り決めの版は変えない: 依頼を足すだけ）。
- `draft_issue_report` の `text` から送り方の案内を外し、`howToSend` で返す（文はフォームの内容の欄に貼る物なので）。`next` と頼み方 `report_issue` の7番目を、`propose_issue_report` に1件として渡す（ほかの要望・不具合も分けて同じ `items` に並べる）形に直した。

### 2. 送る報告の確認画面（アプリ）

- 上の帯に「AIから、送る報告が届いています（N回分）」と「送る報告の確認画面を開く」を出す（中身は出さない）。開くと、最初の1回分を件の一覧で出す。
- 出すもの: 「お客さまの名前・金額など世帯の情報が入っていないことを確かめてください」（目立つ帯）・受付番号（その回の送りに1つ。今までと同じ `newReceiptCode`）・アプリの版・OS・件数と、件ごとに種類（選ぶ）・どの画面のことか（フォームと同じ9つから選ぶ。AI の言葉は近い物に寄せ、当たらなければ「その他・分からない」）・内容（直せる）・「外す」。「＋ 件を足す」で件を足せる。
- 名前・金額らしい所の印（`reportSend.ts` の `reportMarks`。件ごと）: 見つけた所に印を付けた文と「「800万円」— 金額らしい」の一覧を出し、ボタンの横に全部の数を出す。消すかどうかは FP が決め、送るのは止めない。
  | 種類 | 見る形 |
  |---|---|
  | 名前らしい | 敬称（さん・様・さま・氏・くん・君・ちゃん・殿）の付いた漢字1〜4字かカタカナ2〜8字。「お」「ご」の後・続き柄や役目（客・奥・大家・先生・担当 など）・店や会社や役目で終わる言葉（〜屋・〜店・〜社・〜行・〜士・〜長 など）は付けない。漢字1字の敬称（様・氏・君・殿）は2字以上の名前で後ろに漢字が続かないときだけ（同様・仕様書・諸君にしない）。「氏名:」「お名前:」の値。全角の空白で区切った漢字の並び（山田　太郎） |
  | 金額らしい | 〇〇円・〇〇万円・〇〇万・〇〇億・¥〇〇・漢数字の〇〇万円 |
  | 数字の並び | 5桁以上の数と、3桁ごとの区切りのある数（4桁までの年・年齢・件数には付けない） |
  | 日付（生年月日かもしれません） | 年・月・日のそろった日付（西暦・和暦）。後ろに時刻が続くもの（エラーの記録の日時）は付けない |
  | 電話番号らしい | 0 か +81 で始まる10〜12桁（区切りあり・なし） |
  | メールアドレス | 〇〇@〇〇.〇〇 |
  | 住所らしい | 〒と郵便番号・都道府県から市区町村（の後の番地まで。都道府県と最初の市区町村の間に助詞があるものは付けない）・〇丁目〇番地〇号・1-2-3 の形（年-月-日の形は付けない） |
  - 建物の名前（「グランドメゾン渋谷」「パークタワー勝どき」）や「不動産屋さん」「お客さま」のようなふつうの言葉、`draft_issue_report` の見出し・年・年齢・版・見本の id には付けない（試験で確かめる）。名前は形で見分けられないので、画面に「目でも確かめてください」と出す。
- 「送る」は、件が1つ以上あり、どの件の内容も空でないときだけ押せる（空の報告・空の件は送れない）。AI の報告は「送らずに捨てる」（承認待ちから外す）と「あとで」（閉じるだけ。帯に残る）。
- 「要望・不具合を送る」に「報告の文を書いて送る」を足し、AI を使わない人も同じ確認画面を通れる（空の1件から始める。via は付けない。受付番号は「要望・不具合を送る」の番号を使う）。

### 3. 送り方（1か所）

- 送り方は `app/src/workspace/notices/reportSend.ts` の `sendReport` だけにまとめる: 全件を1つの文にまとめる → クリップボードに写す（本体の `feedback_report_copy`。写せなければブラウザの仕組み。それもだめなら文を出して選んでもらう）→ 受付番号をこの PC に覚える → フォームを既定のブラウザで1回だけ開く（本体の `feedback_form_open` に受付番号と、AI の報告なら `via: "ai"` だけを渡す）。自前の受け付けができたら、ここを直接送る形に替える。
- 写す文（`composeReport`）: 頭に「受付番号」「アプリの版（OS）」「件数（AI がまとめた報告ならその旨）」、件ごとに「━━ N件目／M件（種類）どの画面か: 〇〇 ━━」の見出しと内容。フォームの「どれに当たりますか」「どの画面のことですか」は1つしか選べないので、件ごとの種類と画面は本文に書き、FP はフォームでいちばん近いものを1つ選べば足りる（画面に書く）。
- フォームの URL: ひな形（`config/distribution.toml` の `[feedback] form`）は差し込む印が今までどおり受付番号・版・OS の3つだけ。AI の報告のときだけ、本体と画面の同じ決まりで決まった `via=ai` を足す（`?` の有無・`#` の後ろによらない）。本体はほかの `via` の値を断る（`E_FEEDBACK_VIA`）。報告の文は URL に入れない（URL は履歴やログに残るため）。
- 送ったら「報告の文を写して、ブラウザでフォームを開きました。フォームの「内容」の欄に貼り付けて（Ctrl+V / ⌘V）送ってください。」と出す。
- フォームの宛先を受け付けのフォーム（Tally）`https://tally.so/r/laBDzo?no={受付番号}&ver={版}&os={OS}` にした（0087 の追記）。

## 理由

- 送るのを FP の確認画面の「送る」と、フォームでの貼り付けに残すと、0087 の6 と 0234 の骨格（アプリと AI は送らない・文を URL に載せない）を変えずに済む。クリップボードを通すので、文が URL・ブラウザの履歴・受け付けのログに残らない。
- 話した内容を1件ずつに分けて1回で渡すと、FP は一覧で件ごとに直す・外すだけで済み、フォームは1回で足りる。受け付けの側も件の番号と種類で分けて読める。
- 印は止めずに知らせるだけにした。名前は形で見分けられず、見本の世帯の金額のように書いてよい数字もあるので、止めると送れない報告が増える。決めるのは FP。
- 送り方を1か所にまとめると、自前の受け付けに替えるときに、確認画面と道具を変えずに済む。

## 代案（採らなかったもの）

- 報告の文をフォームの URL の欄に載せる（Tally の隠れた欄で受ける）: URL は履歴やログに残り、長さの上限もある。採らない。
- AI からフォームを開く・アプリが自動で送る: 0234 の骨格に反する。FP が確認画面で確かめる前に出ていく。採らない。
- 1件ずつフォームを開く: 何件もあると手間で、試用で送られなくなる。採らない（1つの文にまとめて1回）。
- 名前・金額らしい所があると送れなくする: 見本の値・ふつうの言葉で止まりすぎる。採らない（印を付けて知らせる）。

## 影響

- 世帯ファイル・事務所データの形式は変えない（版も上げない）。AI接続の取り決めの版も変えない（依頼を足すだけ）。
- 道具が1つ（`propose_issue_report`）増える。`draft_issue_report` の `text` の最後の送り方の案内が `howToSend` に移る。
- 本体の命令が3つ増える（`ai_issue_report_candidates`・`ai_issue_report_take`・`feedback_report_copy`）。`feedback_form_open` に任意の引数 `via`（`ai` だけ）。capabilities にも足した。
- 手引き（`docs/app-guide/01-households.md` の `app.notices`・`09-ai.md` の `ai.issueReport`）と `docs/ai-connector.md`、0256 の名前の一覧（送る報告の確認画面）に足した。
- 受け付けのフォームに隠れた欄 `via` が要る（作ってある）。
