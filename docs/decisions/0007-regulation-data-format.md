# 0007. 制度データの形式

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。形式は「安定」の公開の約束として扱い、互換を壊す変更は年1回まで、1年前に予告する

## 背景

- 税率・控除額・保険料率・年金額などの制度の値を、金額そのものとして返す公式のAPIはない。値はPDF・Excel・HTMLから読み取り、検証したうえでデータとして配る。
- 「いつの値を使うか」の基準が制度ごとに違う（所得税は年分、住民税は前年所得に対する年度分、社会保険料は○月分、年金は年度、住宅ローン控除は居住開始年、年金の一部は生年月日で固定）。この違いを形式で吸収しないと、後から全データの書き直しになる。
- 施行日と、値が適用される期間は一致しない。例: 2026年の基礎控除の改正は施行日が2026-12-01だが、2026年分の所得全体に適用され、源泉徴収への反映は2027-01-01から。
- 期限つきの特例、経過措置（生年月日による区分など）、物価や賃金に連動する値、まだ案の段階の改正が混在する。
- 配ったデータは、過去に作った提案書の再現（0009）と、改正前後の差の説明に使う。そのため「値が適用される期間」と「その値をいつ知ったか」の両方を後から引ける必要がある。
- データパックはインターネット経由で配布済みのアプリに届く。プログラムを含められる形式にすると、配信経路が乗っ取られたときに任意のコードが顧客データのそばで動く。

## 決定

### 1. パックの単位と正本

- 制度データは**分野ごとのパック**に分ける（パックのIDは `regulation.<分野>`）: `tax`（所得税・住民税）、`socialInsurance`（健康保険・介護・雇用・子ども子育て支援金など）、`pension`（公的年金）、`nisaIdeco`、`housing`（住宅ローン控除・住宅取得等資金の贈与など）、`educationSupport`（就学支援金・修学支援・児童手当など）。分野を足すのは形式の変更ではない。
- マスタデータ（学費 0010、投資信託の一覧、簡易生命表、賃金統計の昇給カーブなど）は、**提供元・利用条件ごと**に別のパックにする。形式の骨格（パックの目録・出典・版・署名）は制度データと共通にする。
- 正本はリポジトリ内の **YAML**。置き場所は `data/regulation/<分野>/` で、**制度の値ID 1つにつき1ファイル**（`data/regulation/tax/incomeTax.basicDeduction.yaml`）。変更案・差分の確認・取り下げがすべて値IDの単位で行えるようにするため。
- 各分野のフォルダに `pack.yaml`（パックの名札）を置く。
- 配る形は、YAMLを**正規化したJSON**に変換したもの（変換はCIで行い、YAMLの解釈の揺れを配布物に持ち込まない）。アプリは配布物のYAMLを読まない。

### 2. YAMLの書き方の制限

- YAML 1.2 のうち、JSONに1対1で写せる範囲だけを使う。アンカー・エイリアス・マージキー・タグは禁止（CIで拒否）。
- 金額は「通貨の最小単位の整数」（0002）。率は10進の**文字列**（`"0.0985"`）。日付は**引用符つきの文字列**（`"2026-01-01"`）。年月は `"2026-04"`。
- 形式は JSON Schema（0006）で定め、CIと読み込み時の両方で検査する。

### 3. パックの名札（`pack.yaml`）

```yaml
packId: regulation.tax
formatVersion: "1.0"        # 制度データの形式の版（この記録の対象）。「大.小」
version: "2027.3.0"         # パックの版。「年.通し番号.訂正番号」。単調に増える
features: []                # このパックが使う「無視できない」形式の機能（下記）
title: 所得税・住民税
requires:                   # 必要な計算部品の「約束の版」（0006）。フォークでも判定できる
  incomeTax.calc: ">=1 <3"
license:
  values: CC0-1.0           # 提供元の整理部分
  sources: 出典ごとの条件（各値の sources に記載）
```

- **パックの版**（`version`）は「年.通し番号.訂正番号」。新しい値・新しい期間の行を足す版は通し番号を上げ、既存の行の訂正（下記8の `supersededIn`）だけを含む版は訂正番号を上げる。どちらも単調に増え、古い版に戻らない（0017）。
- `formatVersion` の書き方は `MAJOR.MINOR`（0001）。「大」は互換を壊す変更で上がる（年1回まで、1年前に予告）。「小」は互換を保つ追加（任意の欄、条件のキー、値の種類、連動の種類の追加）で上がる。アプリは大が同じパックだけを読む。
- 条件のキー・値の種類・連動の種類のように、**読み落とすと誤った値を選びうる機能**を使うパックは、その機能の名前を `features` に並べる。アプリは、`features` に知らない名前があるパックを使わずに保留し、「アプリの更新が必要」と知らせる（配信の目録の `critical` と同じ考え方。0022）。`features` に載らない追加の欄は、古いアプリが無視してよい。
- 署名・配信の目録・鍵は 0017 で定める。パックは「名札＋値の集合＋署名」を1つの配布単位にし、署名の確認はアプリの本体側（画面ではない側）で行う。

### 4. 値の定義（1ファイルの中身）

```yaml
id: incomeTax.basicDeduction        # 制度の値ID（0004の命名規則）
title: 基礎控除
unit: JPY                           # JPY / rate / months / count / yearMonth / rounding（kind: rounding の値だけ）など
kind: bracketTable                  # 値の種類（下記）
basis: {type: incomeYear}           # 値を選ぶ基準の型（0003の表から1つ）
ageSwitch: null                     # 年齢による切り替えの規則（0003）。使う値だけ
rounding: null                      # 端数処理の規則ID（0002）。値の種類が式・連動のとき
linkage: none                       # 連動の種類（下記）
entries:
  - rev: 4                          # この値IDの中での改訂番号。使い回さない
    appliesFrom: "2026-01-01"       # 適用開始（含む）
    appliesTo: "2027-12-31"         # 適用終了（含む）。null は「次の行の適用開始の前日まで（次が無ければ終わりなし）」
    enforcedOn: "2026-12-01"        # 施行日。適用開始とは別に必ず持つ
    milestones:                     # 施行日・適用開始以外の日付（任意）
      - {kind: withholdingFrom, date: "2027-01-01"}
    status: enacted                 # proposed（案）/ enacted（決定済み）
    jurisdiction: national
    conditions: []                  # 経過措置などの条件（下記）
    value:
      - {upTo: 4890000,  amount: 1040000}
      - {upTo: 6550000,  amount: 670000}
      - {upTo: null,     amount: 0}
    sources:
      - type: web
        url: "https://www.nta.go.jp/..."
        retrievedAt: "2026-10-03"
        sha256: "…"                 # 原本の指紋
        locator: "表1"
        quote: "…"                  # 短い引用（原本に実在するかを機械で確かめる）
      - type: law
        lawNumber: "令和8年法律第○号"
        egovRevisionId: "…"
    recordedIn: "2026.1.0"          # この行が初めて入ったパックの版（知った時点）
    supersededIn: null              # この行が訂正・置き換えられたパックの版
    approval: {method: reviewed, keyId: "…", recordId: "…"}
```

（値は説明用の例）

- **値の種類**（`kind`）は次の7つに限る: `constant`（定数）、`bracketTable`（段階表）、`gradeTable`（等級表。標準報酬月額表など）、`formula`（決まった型の式）、`indexed`（基準額×改定率）、`rounding`（制度の端数処理。単位は `unit: rounding`、中身は0002の「方式」と「単位」。例: `incomeTax.taxAmount.rounding` の値 `{mode: DOWN, unit: 100}`）、`componentSwitch`（計算部品の切り替え表。下記7）。種類を足すことは形式の小の版の変更として扱い、`features` に載せる。
- **`formula` は自由な式を書かない**。「`収入×率＋加算額`」「`基準額×改定率`」のような**名前つきの式の型**をエンジン側に用意し、データは型のIDと係数だけを持つ（`{template: linear, rate: "0.3", add: 80000}`）。条件分岐・繰り返し・任意の関数呼び出しは書けない。
- **適用期間**は常に日付で書き、`basis` に従って解釈する（`incomeYear` なら1月1日〜12月31日に、`fiscalYear` なら年度の始まりの月に揃っていることをCIで確かめる）。同じ値IDで、同じ条件・管轄の行の適用期間が重なること・途中に空白があることはCIで拒否する。
- `appliesTo: null` は「次の行の適用開始の前日まで」を表す。毎年の改定のように**新しい期間の値を足すときは、新しい行を足すだけ**で、前の行を書き換えない（自動配信用の鍵が「既存の期間の値の書き換え」を受け付けない決まり（0022）と両立させるため）。期限が法令で決まっているものだけ `appliesTo` に日付を書く。
- **期限つきの特例**は、期限の後に何が適用されるかを必ず別の行として書く（本則に戻る行、または「制度なし」を表す `value: notApplicable`）。データの中に空白期間を作らない。期限後に「延長されたと仮定する」かはプランの前提の選択で、データには書かない。

### 5. 値の状態

- データに書く状態は `proposed`（案。大綱・閣議決定・審議会の案など）と `enacted`（決定済み。法律の成立、政令・告示、料率の認可・公表など）の2つだけ。
- 画面・根拠の記録に出す4つの状態は、計算する日付から**導く**: 案／成立・未施行（`enacted` かつ施行日より前）／施行中／期限切れ（適用終了を過ぎた）。日付が来ただけで古くなる情報をデータに書かないため。
- `proposed` の行は、プランで「シナリオとして使う」を選んだときだけ使う。関係する案はまとめて選べるよう `scenarioId`（例: `taxReform.2027.outline`）を付ける。
- 将来の推計値（物価・賃金の仮定から作る値）はパックに入れない。連動の規則だけを入れ、計算のときにプランの前提で出す。「推計」は計算結果の側の印にする。

### 6. 管轄・経過措置の条件

- **管轄**（`jurisdiction`）は `national`、または `{level, code}`。`level` は `prefecture`（都道府県コード）、`municipality`（全国地方公共団体コード）、`insurer`（保険者。例: 協会けんぽの支部 `kyokaikenpo.13`）、`wideAreaUnion`（後期高齢者医療広域連合）。
- 市町村ごと・健保組合ごとの個別の値は制度データに持たない（全国の標準値と、世帯ごとの入力・逆算で扱う。0008の上書き）。管轄の欄は、協会けんぽの支部のように公式に一覧化された単位のために使う。
- **条件**（`conditions`）は、決まったキーに対する範囲・一致の組み合わせ（ANDだけ）で書く。キーは形式で列挙したものに限る: `birthDate`（生年月日の範囲）、`sex`、`entitlementDate`（受給権の発生日）、`residenceStartYear`（居住開始年）、`contractDate`、`giftDate` など。キーを足すのは形式の小の版の変更（互換を壊さない追加）として扱い、新しいキーを使うパックは `features` に載せる。
  ```yaml
  conditions:
    - {key: birthDate, from: null, to: "1956-04-01"}   # 昭和31年4月1日以前生まれ
  ```
- 同じ期間に条件違いの行が複数あるときは、**互いに重ならず、すべての場合を覆う**ことをCIで確かめる。経過措置の根拠（附則の条項）は `sources` の `law` に書く。

### 7. 連動の種類と、新しい仕組みの切り替え

- `linkage` は次の4つ:
  - `none`: 改正で決まった分だけ変わる。将来も最後の値が続く（税の控除額と区分）。
  - `scheduled`: 法律で決まった日程の値を、将来の行として `enacted` で持つ（標準報酬月額の上限の段階的な引き上げなど）。
  - `indexed`: `基準額×改定率`。改定率の系列（`indexSeries`。新規裁定・既裁定などを条件で分ける）と、名目額の下限などの規則の型を指定する。改定率の将来の値は持たず、プランの前提（物価・賃金・スライド調整）から計算する（年金額、国民年金保険料、在職老齢年金の基準額、年金生活者支援給付金）。
  - `cpiLinked`: 法律で物価に連動すると決まった額（基礎控除の物価連動など）。連動の式の型と、端数処理の規則ID（0002）を指定する。
- 連動の計算に `Math.pow`・`exp`・`log` を使わない（`ratePow` などの掛け算の繰り返しと決まった丸めで行う。0002・0005）。
- **新しい仕組みの制度**は、値の差し替えではなく計算部品の切り替えで表す。`kind: componentSwitch` の値が「どの日からどの計算部品IDを使うか」を持つ（0006の「同じ系統の別ID＋有効期間」）。
  ```yaml
  id: switch.survivorPension.employee
  kind: componentSwitch
  entries:
    - {rev: 1, appliesFrom: "1986-04-01", appliesTo: "2028-03-31", value: {component: survivorPension.employee.v1}, status: enacted, …}
    - {rev: 2, appliesFrom: "2028-04-01", appliesTo: null,         value: {component: survivorPension.employee.v2}, status: enacted, …}
  ```
- 切り替え表が指す部品がアプリに無いとき、またはアプリがその部品を「未対応」と宣言しているときは、直前の部品で計算し、結果に「反映していない改正」の印を付ける（黙って旧制度で計算しない）。

### 8. 2本の時間軸

- **適用の時間軸**: `appliesFrom` / `appliesTo`（＋施行日）。
- **知った時点の時間軸**: `recordedIn`（その行が初めて入ったパックの版）と `supersededIn`（訂正・置き換えられた版）。
- 行は消さない。値の訂正は、古い行に `supersededIn` を書き、新しい `rev` の行を足す。これにより、最新のパック1つから「パックの版Xの時点で知っていた値」を再現できる。
- アプリは受け取った過去のパックもすべて手元に残す（控えの再現と、取り下げの照合のため）。
- 値の1行を指す書き方は `<制度の値ID>@r<rev>`（例: `incomeTax.basicDeduction@r4`）。根拠の記録と控え（0009）はこの書き方を使う。
- 取り下げの一覧（0017）は値を `{id, packVersion}` で指す。これは「その値IDの行のうち、`recordedIn` がそのパックの版の行」を意味する。アプリはこの対応で `@r<rev>` に読み替えて照合する。
- 巻き戻し（0022）は行を消さず、配信の目録の側でそのパックの版の適用を外す形で行う。外した後は、その値は連動の規則による推計に戻る。

### 9. 出典と承認の記録

- 各行に出典を1つ以上必須にする。`web`（URL・取得日・原本の指紋・ページや表の位置・短い引用）、`law`（法令番号・e-Gov の改正ID）、`document`（公式のExcel・PDFの表題・発行元・公表日・指紋）。
- 原本の写しは非公開のリポジトリに置き、公開側には出典の情報（URL・取得日・指紋・短い引用）だけを置く（0021）。
- `approval` には、人の確認を経たか（`reviewed`）、自動の関門を通ったか（`automated`）と、署名に使った鍵のID、配信の記録のIDを書く。個人名は書かない。

### 10. プログラムを入れない

- パックの中身は**宣言型の値と表だけ**。スクリプト・式の文字列・正規表現・外部の参照先（取りに行くURL）を持てない。
- 文字列の欄（題名・引用・注記）は、アプリが表示するときに常に平文として扱う（HTMLやマークダウンとして解釈しない）。
- 読み込み時に JSON Schema で検査する。形式の大の版が違うパック、`features` に知らない名前があるパックは使わない（3の規則）。

## 理由

- **値IDごとの1ファイル**: 改正の変更案・取り下げ・差分の確認が値IDの単位で行われるので、差分がそのまま読める。分野ごとの1ファイルにすると変更案の衝突が増える。
- **正本YAML・配布JSON**: 人とAIが読み書きしやすいのはYAML。一方でYAMLは処理系によって解釈が揺れる（日付・真偽値の自動変換、数の精度）ので、アプリには機械で正規化したJSONだけを渡す。
- **状態を2値で持ち、残りは日付から導く**: 「施行中」をデータに書くと、施行日が来ても更新されないパックが古い状態を言い続ける。
- **式の型だけを許す**: 式の言語を入れると、それは事実上のプログラムになり、隔離・検証・取り下げの単位が崩れる。新しい型が要るときはエンジンの更新で足す（計算方法が変わる改正は計算部品の改訂で扱うのと同じ考え方）。
- **行を消さない2本の時間軸**: 過去の提案書の再現、改正前後の差の説明、回帰テストに欠かせない。後から足すと全データの移し替えになる。
- **プログラムを入れない**: 配信経路が乗っ取られても、届くのは値と表だけになる。自動配信用の鍵で「既にある値IDに、前の期間と同じ形の新しい適用期間を足すことだけを受け付ける」検査（0017・0022）も、値と行の単位がはっきりしているから機械で行える。

## 影響

- 後から変えると: 全データの移し替えと、全計算部品の値の読み方の作り直しになる。過去の控えの照合も壊れる。
- 守るべき決まり:
  - 制度の値IDと `rev` は使い回さない。廃止した値IDも欠番として残す（0004）。
  - 行を消さない。訂正は `supersededIn` と新しい `rev` で行う。
  - 計算部品は制度の値を `ctx.param` だけで読み（0003・0006）、エンジンは読んだ値を `<値ID>@r<rev>` で根拠の記録に残す。
  - パックにプログラムを入れない。
- テストで確かめること（CI）:
  - JSON Schema の検査、YAMLの禁止機能の検出。
  - 同じ条件・管轄の行の、適用期間の重なりと空白。条件違いの行の排他と網羅。
  - `basis` と適用期間の揃い（年分なら暦年、年度なら4月〜3月など）。
  - 出典の必須項目、引用文が原本に実在すること（非公開側の原本で確かめる）。
  - 前の版のパックとの比較: 消えた行がないこと、`supersededIn` のない行の値が変わっていないこと。
  - 最新のパックだけから、過去のパックの版の時点の値を再現できること。
  - 大の版が違うパック・`features` に知らない名前があるパックを、アプリが使わずに保留すること。`features` に載らない知らない欄は無視して読めること。

## 試作での確認

- 内蔵の実行環境（QuickJS）と画面側のエンジンで、率を10進の文字列から読む方式なら、OSやCPUが違ってもビット単位で同じ結果になった。浮動小数点では円単位でずれた（最大923円）。率を文字列で持つ決定の裏付け。
- `Math.pow`・`exp`・`log` はエンジンやOSで最後の桁がずれた。連動の計算でこれらを使わない決まりの裏付け。

## 追記

- 2026-10-08（全体の整合）: パックのIDは `regulation.<分野>`（マスタデータは `master.<…>`。例 `master.education.tuition`）に統一した（0017 の取り下げの一覧の例を直し、ここの未確定を閉じた）。`basis` の例を 0003 の型の名前 `incomeYear` に直した。端数処理の値の欄名を 0002 と同じ `mode` にし、単位の一覧に `rounding` を足した。自動配信用の鍵で受け付ける範囲の書き方を 0022 にそろえた。版の初期値の未確定を 0001・0011 と同じ書き方で足した。

- 2026-10-08（版の初期値）: 公開の約束の版の初期値を決めた。β公開までは `0.x`（最初は `0.1`）とし、β公開のときに安定の約束（世帯ファイル・制度データ・マスタデータ・ヒアリングシートの形式）を `1.0` にする。試験版の約束（計算部品の入出力など）の版の付け方は変えない。0001・0007・0011 に同じ内容を書いた。「未確定」の該当の項目はこれで閉じる。土台の制度データの `formatVersion: "1.0"` は `"0.1"` に直した。
- 2026-10-08（requires の書き方）: パックの `requires` と計算部品の `requires`（0006）を、範囲の書き方（例 `">=1 <2"`）にそろえる。数だけの `"1"` は `">=1 <2"` の省略形として認める。文法は「空白区切りの AND、演算子は `>=` `>` `<=` `<` `=`、数は約束の版の MAJOR。演算子のない数 `N` は `>=N <N+1` と同じ」。
- 2026-10-08（架空のデータの印）: 架空の見本データは、パックの名札に `fictional: true`、出典に `type: fictional`（`note` に「架空」と書く）を付け、値IDは予約の接頭辞 `test.`（0004）で始める。「架空のパックには `test.` の値だけ、製品のパックには `test.` の値を置かない」と「`fictional` の出典は架空のパックだけ」を、制度データの道具（CI）で強制する。
- 2026-10-08（生年月日の条件）: 条件 `birthDate` の境目が月の途中にあり、構成員の「生年月＋1日生まれか」（0012）でどちらの行か決まらないときは、黙ってどちらかを選ばず、エラー `E_PARAM_AMBIGUOUS` にする。
- 2026-10-08（取り下げの指し方）: 値の1行を指す書き方を、計算部品と同じ `<制度の値ID>@<rev の整数>`（例 `incomeTax.basicDeduction@4`）に改めた（0009 の追記）。8 の `@r<rev>` はこの書き方に読み替える。
- 2026-10-08（値IDの命名）: `regulation.tax` と `regulation.socialInsurance` の値IDを `<制度>.<対象>.<中身>` で付けた。制度の段は `incomeTax`（所得税。復興特別所得税・防衛特別所得税を含む）・`residentTax`（住民税）・`forestEnvironmentTax`（森林環境税）・`socialInsurance`（健康保険・介護保険・子ども・子育て支援金・厚生年金。対象の段で `health`・`care`・`childSupport`・`pension` に分ける）・`employmentInsurance`（雇用保険）。所得税と住民税で同じ種類の値は、制度の段だけを変えた同じ名前にする（例 `incomeTax.basicDeduction` と `residentTax.basicDeduction`）。端数処理は `.rounding`、上限は `…Limit`（`incomeLimit`・`totalLimit` など）、年齢は `…Age`、本人の所得の段ごとの表は `.tier1`〜。保険者ごとの値は保険者の名前を対象の段に入れる（`socialInsurance.health.kyokaikenpo.rate`）。協会けんぽの支部の管轄は `{level: insurer, code: kyokaikenpo.<都道府県コード2桁>}`。年齢の値は `unit: years`（単位に足した）で、切り替えの規則を `ageSwitch` に書く。
- 2026-10-08（等級表の形）: `kind: gradeTable` の値は、行の配列 `{grade, amount, from, below}`。報酬月額が `from` 以上 `below` 未満なら等級 `grade`・額 `amount`。`grade` は1から1ずつ、最初の `from` は0、各行の `from` は前の行の `below` と同じ、最後の行だけ `below` が null、`amount` は昇順。これを道具（CI）で確かめる。健康保険と厚生年金は別の値ID（`socialInsurance.health.standardMonthlyRemuneration`・`socialInsurance.pension.standardMonthlyRemuneration`）にし、`basis: month` で持つ。
- 2026-10-08（延長の仮定）: 期限の後の値が分からない制度（適用終了がある行の後に、同じ条件・管轄の行が無い）は、計算を止めずに最後の行の値が続くとみなす（延長の仮定）。この仮定を使った結果は、見出しの `notices` に `{code: "N_PARAM_EXTENDED", ids: [<値ID>@<rev>, <最初の年>, <最後の年>]}` を出す。引く日が最初の行より前のときは値が無いので、これまでどおり `E_PARAM_NO_VALUE` で止める。それまで `E_PARAM_NO_VALUE` で止まっていた 2028年以後の給与所得控除などは、この仮定で計算する。値の有無だけを見たいとき（改定率のように前提で延ばす値）は、部品が延長の仮定を使わずに確かめる。
- 2026-10-08（国民年金・国民健康保険・後期高齢者医療の既定の値）: 国民年金の保険料は全国一律の値として制度データに持つ。国民健康保険と後期高齢者医療の保険料は市町村（広域連合）ごとに違うので、市町村ごとの値を持たない方針（6）のまま、「全国の標準的な値（3年ごとに見直す）」を制度データに持って既定にし、世帯の入力（決定通知書の年額、または料率）があればそれで置き換える（0008 の追記）。既定の値を使ったときは見出しの `notices` に `N_DEFAULT_USED` で出す。全国の標準的な値が制度データに無いときは計算せず、`N_INPUT_REQUIRED` で入力を求める。
- 2026-10-08（指定都市の配分・超過課税）: 指定都市の住民税の税率の配分（市8%・道府県2%）と、市町村・都道府県の超過課税は扱わない（全国一律の標準税率で計算する）。扱わないことを見出しの `notices` に `N_NOT_SUPPORTED` で出す。住宅借入金等特別控除などの税額控除は、住宅の部品の作業で作る。
- 2026-10-08（原本で確かめられない値）: 原本（公的な一次資料）で確かめられなかった値は、推測で埋めずに、検索の要約などの出典を付けて `approval: {method: "pendingReview"}` で入れてよい。原本と照らし合わせるまでは製品として配らない（`pendingReview` の扱いはこれまでどおり）。
