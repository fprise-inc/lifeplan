# 0241. 画面の日付の書き方を2つの形にそろえる（一覧は「2026/11/21 01:54」・文の中は「2026年11月21日」。書き方は `app/src/dates.ts` の1か所で決める）

- 状態: 採用（一部未確定）（2026-11-22）
- 固定の強さ: 内部（画面に出す日付・日時の書き方だけ）。世帯ファイルの形・保存する値の形（ISO 8601 の文字）・計算・ファイル名・紙に出す文書（提案書・持ち帰り用のレポート）の日付の形は変えない。日付を出す所の目印（`data-web-expires`・`data-web-sent-at`・`data-meeting-row` など）も変えない。確かめの一覧の「○○ に確認しました」の文は AI接続口の入力の確かめにも出るので、そこだけ AI に渡る文の日付の書き方が変わる
- 前提にする記録: 0009 の2（控え。作った時刻を時差つきの文字で残す）、0087（お知らせの一覧）、0125・0158・0191・0192（Web のヒアリングの依頼・届いた書類）、0182（面談の履歴）、0016（層の分け方。お客さまの画面・提示層は作業の層を読まない）、0234（エラーの記録）

## 背景

- 画面の日付の書き方が、画面ごとの組み立てで5通りあった。

  | 画面 | 前の書き方 |
  |---|---|
  | 控えの一覧 | 2026年11月20日 14:05 |
  | 面談の履歴・お知らせの一覧 | 2026年11月9日 |
  | 世帯の一覧・保存まわり・AI の画面 | 2026/10/18 14:03 |
  | 届いた書類 | 11/20 14:05（年なし） |
  | 発行した URL・プランの一覧 | 2026/11/5（桁をそろえない） |

  ほかに、お客さまが送った日時「11月6日 22:15」（年なし）、エラーの記録「2026-11-20 14:05」、機能を有効にするコードの期限・確かめの一覧の「2026-11-20」（保存する値の形のまま）もあった。
- 同じ表の中で年の有る無し・桁が違うと、縦に並べて比較しにくい。年をまたぐと、年なしの日付はいつのことか分からなくなる。
- 日付の文字を作る所が 40 か所ほどに散っていて、`toLocaleDateString`・手書きの組み立て・文字の切り出し（`slice(0, 10)`）が混ざっていた。

## 決定

### 1. 形は2つ（利用者の判断）

| 使う所 | 日だけ | 日時 |
|---|---|---|
| 一覧（表の欄・一覧の行に並ぶ日時・選ぶ欄の選択肢） | 2026/11/21 | 2026/11/21 01:54 |
| 文の中（説明の文・お知らせの文・見出し・ボタン・添え書き） | 2026年11月21日 | 2026年11月21日 01:54 |

- 一覧は月・日・時・分を2桁にそろえる（「2026/01/05 09:03」）。文の中の年月日はゼロ埋めしない（「2026年1月5日」）。
- 文の中の時刻は2桁（「2026年1月5日 09:03」）。前から年月日の漢字に時刻を添えていた所（控え・お客さまが送った日時・お客さまのページ）がどれも2桁だったので、多い方に寄せた。
- 秒は出さない。「今日なら時刻だけ」のような出し分けはしない。年は必ず書く。
- どちらの形にするかは、日付の置かれ方で決める。
  - 表の欄、一覧の1行の頭や添え書き（「発行 2026/11/01・期限 2026/12/01」「2026/11/06 に取り込み」）、選ぶ欄の選択肢は、一覧の形。
  - 行の下の説明・お知らせ・確かめの文・見出し（「2026年11月9日の面談」）・ボタン（「延長（2026年12月25日まで）」）・添え書き（title）は、文の中の形。
- 1つの行・1つの文の中では、形を混ぜない。

### 2. 書き方は `app/src/dates.ts` の1か所で決め、画面はそれを呼ぶ

- 関数は、形（`list`〜／`prose`〜）と、日だけか日時か（〜`Date`／〜`DateTime`）と、読み方（下の3）の組み合わせの8つ。
- 置き場所は `app/src/` の直下。お客さまの画面（`hearingForm/`）と提示層は作業の層（`workspace/`）を読めない決まり（0016・0125）なので、どの層からも読める所に置く。ほかの部品を読まない（日付の文字を作るだけ）。
- 画面ごとの組み立て（`shortDate`・`snapshotDateText`・`meetingDateText`・お知らせの `dateText`・`localTime`・`day`・`dayTime` など）は外した。AI の画面の `dateTimeText`（一覧の形）は、中身を共通の関数に替えて残し、文の中の形の `dateTimeProse` を足した（空のときに「—」を出す所を変えないため）。

### 3. 読み方は2つ。指す日・時刻は変えない

- **端末の時刻で読む**（`listDate`・`listDateTime`・`proseDate`・`proseDateTime`）: 時刻つきの文字と Date は、端末の時刻に直して出す。前から端末の時刻で出していた所（世帯の一覧・保存まわり・AI・エラーの記録・発行した URL・届いた書類・お客さまのページ）に使う。
- **書いてある数字のまま読む**（〜`Written`）: 時差を直さない。前から文字の数字をそのまま出していた所（控え・明細の取り込みの記録〔作った所の時刻を時差つきで残した文字〕、プランの一覧、日だけの文字〔面談の日・お知らせの日・期限・確かめた日〕、文字を切り出していた所）に使う。
- **日だけの文字**（「2026-11-21」）は、どちらの読み方でも書いてある日のまま。日時として読むと UTC の0時になり、時差が負の端末で前の日にずれるため。日時の関数に渡しても、日だけを出す（無い時刻を作らない）。
- 読めない文字は、渡した文字のまま返す（`bad` を渡せばその文字）。前の出し方を変えない: 世帯の一覧・保存まわりは空、お客さまが送った日時は「不明」、AI の画面は空のとき「—」・読めないときは元の文字。`toLocaleDateString` で「Invalid Date」と出ていた所だけは、元の文字が出るようになる。
- この変更で、どの呼び出し側も**書き方だけが変わり、指す日・時刻は変わらない**（下の「守るもの」）。

### 4. 変えない物

- 保存する値の形・計算・ファイル名に入れる日付。
- 年月だけ・年だけの表示（「2027年10月」）、年月の入力欄（「2012-04」）、年齢・和暦の添え書き、グラフの軸、「○分前から」「残り○分」のような今からの時間。
- 紙に出す文書: 提案書の作成日（「2026年11月21日」）、持ち帰り用のレポートの作成日・面談の日（「2026年11月21日」）。どちらも文の中の形にすでに合っている。お客さまに送る案内文の期限（「2026年12月5日」）も同じ形のまま（共通の関数に替えただけ）。
- 上の帯の「自動で保存しています（14:05 に保存）」は時刻だけ（日付を書いていないので、そのまま。未確定）。
- AI接続口が AI に返す文の中の期限（Web のヒアリングの発行の答え。「期限 2026-12-05」）は、画面に出す文ではないのでそのまま。

## 理由

- 一覧は縦に並べて比較するので、桁のそろう数字の形が読みやすい。文の中は、数字とスラッシュが文に埋もれないよう、年月日の漢字の形が読みやすい。
- 形を1か所で決めれば、次に形を見直すときも、新しい画面を足すときも、迷う所が無い。
- 読み方を2つに分けて残したのは、指す日・時刻を変えないため。控えは「作った所の時刻」を残す物（0009 の2）で、端末の時刻に直すと、別の時差の端末で開いたときに作った時刻と違って見える。

## 代案（採らなかったもの）

- 全部を1つの形（スラッシュだけ・漢字だけ）にする案: スラッシュだけだと文の中で読みにくく、漢字だけだと表の桁がそろわない。
- 一覧では今年の年を省く・今日は時刻だけにする案: 短くなるが、年をまたぐと分からなくなり、同じ列に形が2つ並ぶ。
- `Intl.DateTimeFormat`（`toLocaleDateString`）に任せる案: 端末・実行環境で出し方が変わりうる（AI接続口にまとめる JS の実行環境には `Intl` が無い）。形を自分で組み立てる。
- 作業の層（`workspace/`）に置く案: お客さまの画面から読めず、そこだけ別の組み立てが残る。

## 守るもの（テスト）

- `app/test/dates.test.ts`: 1桁の月・日・時・分、年の変わり目（12月31日 23:59 と 1月1日 0:00）、うるう日、深夜0時台、日だけの文字を日時の関数に渡しても前の日にずれないこと（UTC の文字・時差なしの文字・時差つきの文字）、読めない文字・空・null・undefined の出し方。端末の時差を UTC・日本・米国西海岸・UTC+14 に切り替えて確かめる（`TZ=UTC`・`TZ=Asia/Tokyo` で流しても通る）。
- 同じテストで、外した前の組み立てを写して残し、**前の書き方と新しい書き方が同じ日・同じ時刻を指す**ことを、境目の日時と4つの時差で確かめる（文字の中の数字の並びが同じ。年を書いていなかった所は月日と時刻が同じ）。

## 影響

- 画面: 上の「直した所」。年なしだった日付に年が付き、桁がそろう。
- AI接続口: 入力の確かめ（確かめの一覧と同じ関数）の「○○ に確認しました」の日付が「2026年11月22日」の形になる。ほかの答えは変わらない。
- お客さまのページ: 配るファイルの中身が変わるので、次に配るときに指紋（`fingerprints.json`）が変わる。
- 世帯ファイル・事務所データ・計算結果・提案書・持ち帰り用のレポート: 変わらない。

## 未確定

- 上の帯の「自動で保存しています（14:05 に保存）」を、時刻だけのままにするか、日付も書くか（今は時刻だけ。帯の幅が限られるので、そのままにしている）。
- UTC の数字のまま出している所を、端末の時刻に直すか: **プランの一覧の「作った日」**（プランを作った時刻は UTC の文字で残していて、その数字をそのまま出している。日本の端末では9時間前の時刻に見える）、AI からのコードの候補の届いた日時（「（UTC）」と添えている）、書類の読み取りの「同じファイルを前にも読んでいます（…）」（記録の文字の日の部分をそのまま出す）。この記録では指す日・時刻を変えない決まりにしたので、直していない（直すなら、その所の関数を端末の時刻で読む方に替えるだけ）。
- AI接続口が AI に返す文の中の日付（Web のヒアリングの発行の答えの期限）を、文の中の形にそろえるか。
- 表の欄の中の括弧（「保存した（2026/11/08）」「プランとして保存（2026/11/21 14:05）」）は、欄の中なので一覧の形にした。文の形に寄せるかは、使ってみてから決める。
