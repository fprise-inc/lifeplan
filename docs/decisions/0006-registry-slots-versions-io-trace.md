# 0006. 部品表・差し込み口・版・入出力と根拠の記録

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: 仕組み（部品表を通した呼び出し、8つの差し込み口の設計、2つの版、JSON Schema、根拠の記録）は β公開から変えない（骨格）。計算部品の入出力の約束と差し込み口の約束は公開の約束（試験版）

## 背景

ファイナンシアでは、FPが自分のAIで計算部品を作り、公式の部品を差し替えたり、決まった場所に計算を足したりできる。同時に、公式の部品は制度改正や不具合修正で更新され続ける。

この2つを両立させるには、(a) 部品同士がどう呼び合うか、(b) どこに計算を足せるか、(c) 「差し替えた部品が、更新後の公式と組み合わせても正しく動くか」をどう判定するか、(d) 入出力の形をどう決めて検査するか、を最初に決めておく必要がある。

また、どの数字もクリックすると、計算式・使った制度の値・出典・適用年度が出せること（根拠の表示）を約束する。そのための記録の形と、作る時機も決める。

## 決定

### 1. 計算部品の形

- 計算部品は、マニフェストと計算の関数を持つモジュール。例:

```ts
export default defineComponent({
  id: "pension.oldAge.basic",          // 計算部品ID（0004）
  contract: "2.1",                     // 入出力の約束の版（下の4）
  revision: 14,                        // 実装の改訂（下の4）
  requires: { "pension.contributionHistory": "1" },  // 使う部品と約束の版（MAJOR）
  params: ["pension.basic.fullAmount", "pension.basic.deferralRate"], // 読む制度の値ID
  reads: ["member.birth", "pension.statement.basicAmount"],           // 読む入力項目ID
  replaceable: true,                   // 公式部品だけが持つ。差し替えを許すか
  input: "schemas/pension.oldAge.basic.input.json",
  output: "schemas/pension.oldAge.basic.output.json",
  compute(input, ctx) {
    const hist = ctx.call("pension.contributionHistory", { member: input.member });
    const full = ctx.param("pension.basic.fullAmount");
    // ... 金額の計算は ctx の関数で（0002）
    return { flows: [/* 支払月ごとのお金の動き（0003） */] };
  },
});
```

- 部品が外の世界に触れる手段は `ctx` だけ:
  - `ctx.call(id, input)` … 他の部品を部品表を通して呼ぶ
  - `ctx.param(id)` … 制度の値を読む（引く時点は `basis` でエンジンが決める。0003）
  - `ctx.money`・`ctx.rate` … 金額・率の関数（端数処理を含む。0002）
  - `ctx.time` … 時点の解決・年齢の規則（0003）
  - `ctx.trace` … 根拠の記録への補足（計算式IDの指定など。下の7）
- マニフェストの `params`・`reads` に書いていない制度の値・入力項目は渡さない（読むと実行時エラー）。カスタム部品のマニフェストのその他の項目（作者・ライセンス・承認と指紋）は 0016。

### 2. 部品表（レジストリ）を通して呼ぶ

- 部品同士の直接の呼び出し（他の部品のファイルを import して関数を呼ぶこと）を禁止する。
  - lint: 部品のフォルダをまたぐ import を `no-restricted-imports` で禁止する（共通の型・公式SDKの関数は例外）。
  - 実行環境: カスタム部品が読み込めるのは、自分のフォルダの中の相対の読み込みと公式SDKだけ（0016）。
- 計算のはじめに、組み立て役が部品表を作る: 計算部品IDごとに、使う実装を1つだけ決める（公式、または承認済みの差し替え）。
- `ctx.call` は部品表を引くので、ある部品を差し替えると、他の公式部品から呼ばれるときも差し替え後が使われる。
- 部品の依存が循環していたら、組み立ての時点でエラーにする。
- 部品は純粋な関数なので、1回の計算の中では「部品ID＋入力のハッシュ」で結果を使い回してよい（エンジンの中で行う）。部品のファイルの一番外側に変わる状態（書き換えられる変数）を置かない（lint で禁止）。
- 組み立てた部品表（部品IDごとの実装・約束の版・改訂・中身の指紋）は、結果の見出し（下の7）に必ず残す。

### 3. 差し込み口（拡張点）

- 設計として固定する差し込み口は8つ。

| 差し込み口ID | 中身 | 正式公開の時 |
|---|---|---|
| `slot.expense.flow` | 支出の流れ（独自の支出の行を出す） | **開く** |
| `slot.protection.method` | 必要保障額の考え方 | **開く** |
| `slot.retirement.rules` | 退職給付の規程（勤め先の退職金規程など） | **開く** |
| `slot.income.flow` | 収入の流れ | 後の版で開く |
| `slot.lumpSum` | 一時金 | 後の版で開く |
| `slot.account` | 資産の器 | 後の版で開く |
| `slot.insurance.table` | 保険の数表の型 | 後の版で開く |
| `slot.withdrawal.order` | 取り崩しの順序 | 後の版で開く |

- 各差し込み口は、計算部品と同じく入出力の約束（JSON Schema と版）を持つ。開いていない差し込み口も約束は内部で定義しておき、公式部品はその形で作る（後で開くときに作り直さないため）。
- 開いていない差し込み口を宣言したカスタム部品は、読み込みの時点で拒む。
- 足した計算が出してよいのは、その差し込み口の出力だけ。出力の行は、差し込み口ごとに決めた科目の枝の下に限る（例: `slot.expense.flow` は `cf.expense` の下と、その下の `ext.<作成者>.<キー>`。0004）。
- **差し替え**（公式部品の置き換え）と**追加**（差し込み口への足し算）は別の仕組み。差し替えられるのは、公式部品のうち `replaceable: true` を付けた（一覧に載せた）ものだけ。

### 4. 部品の版は2つ

- **入出力の約束の版**（`contract`）: `MAJOR.MINOR`。
  - MAJOR は互換を壊す変更で上げる: 必須の入力の追加、欄の削除・改名、出力の意味・単位の変更。
  - MINOR は互換を保つ変更で上げる: 任意の入力の追加、任意の出力欄の追加。MINOR で足した出力欄を使う側は、その欄が無い場合の扱いを必ず持つ（古い MINOR に合わせて書かれた差し替えでも動くように）。
- **実装の改訂**（`revision`）: 不具合修正・制度改正のたびに1ずつ増やす整数。約束の版とは独立。取り下げはこの単位（部品ID＋改訂。0009・0017）。
- 結果の見出しでは、部品を `{"id": "pension.oldAge.basic", "contract": "2.1", "revision": 14, "hash": "sha256:…"}` の形で記録する。
- 差し替えと追加の宣言は、約束の版の MAJOR に対して行う。カスタム部品のマニフェストの書き方は 0016 で、例えば `{"type": "replace", "target": "retirement.benefit.rules", "contract": "1"}`、`{"type": "extend", "extensionPoint": "slot.expense.flow", "contract": "1"}` のように書く。
  - 公式の MAJOR が上がったら、その差し替えは自動では使わない。その案の計算を止めてFPに知らせ、「差し替えを直す／公式に戻す」を選ばせる（黙って公式に戻さない）。
  - 差し替えている公式部品の改訂が上がったときの知らせ方は 0016。
- **新旧の制度**は、同じ部品を書き換えるのではなく、「同じ系統の別ID＋有効期間」にする。
  - 例: 系統 `ideco.contributionLimit` に、`ideco.contributionLimit.until202611` と `ideco.contributionLimit.from202612` の2つの部品を置く。
  - どの月からどちらを使うかの切り替え表は制度データの側に持つ（0007）。部品は系統IDで `ctx.call` し、部品表が計算している月に合わせて実体を選ぶ。
  - 差し替えは実体のIDに対して行う。

### 5. 入出力の書式は JSON Schema

- エンジン全体の入力・出力、各計算部品・各差し込み口の入力・出力を、JSON Schema（2020-12）で定義する。スキーマは公開の約束の一部で、SDKフォルダに同梱する（0019）。
- スキーマの共通の決まり:
  - 金額は整数、率は10進の文字列（0002）。年月は `"YYYY-MM"`（0003）。IDは 0004 の書式。
  - エンジン全体の入力は `additionalProperties: false`（知らない欄を拒む。参照値の混入を防ぐ。0004）。
- 実行時の検査:
  - 製品でも常に検査する: エンジン全体の入力と出力、カスタム部品の入力と出力、差し込み口の出力。
  - CI とテストでだけ検査する: 公式部品どうしの呼び出しの入出力（製品では速さのため省く）。
- 検査器は、ビルドの時に公式のスキーマからコードを作っておいたもの（Ajv の standalone の出力など）を使う。実行環境ではコードを作れない（`eval`・`Function` を消している。0005）ので、実行時に検査器を生成しない。カスタム部品は公式のスキーマ（差し込み口・差し替え先の約束）に合わせるので、公式の検査器で足りる。
- **置き換え口**: 部品ごとに「与えられたらこの値を使う」入力欄を約束の中で定義する（例: ねんきん定期便の見込額、返済額の直接入力、手取りの直接入力）。置き換え口を使った値は、根拠に「入力値を使った」と出す。

### 6. 前提は年ごとの列で持てる型

- プランの前提条件（物価上昇率・運用利回り・昇給率など）は、型として「年ごとの列」で持つ。定数はその特別な場合（全部の年が同じ値）として表す: `{"default": "0.02", "byYear": {"2027": "0.03"}}`。
- 部品は前提を `ctx` 経由で「その年の値」として読む。定数か列かを部品は気にしない。
- 型の決まったストレステスト（退職直後の相場の下落など）は、この列を書き換えた想定として表す。

### 7. 結果は「値＋根拠の記録」

- エンジンの要求に、根拠の記録の細かさ `trace: "none" | "summary" | "full"` を持つ。

| 細かさ | 中身 |
|---|---|
| `none` | 数字だけ。ただし見出し（下）は必ず付ける |
| `summary` | 部品ごとに、使った計算式ID・制度の値（ID・値・データの版）・端数処理の規則IDの一覧 |
| `full` | 出力のお金の動き1件ごとに、計算式ID、使った入力（入力項目IDと物のIDと値）、制度の値（ID・値・出典・適用期間・データの版）、計算部品（ID・約束の版・改訂・指紋）、端数処理（規則ID・丸める前と後）、解決した時点（0003） |

- **見出し**（どの細かさでも必ず付ける）: エンジンの版と指紋、組み立てた部品表、使った制度データ・マスタデータの版、カスタム部品の指紋、計算基準日、計算方式の設定。
- `full` の記録は、同じ制度の値・同じ入力の記録を1回だけ持ち、お金の動きからはその記録を番号で指す形（重複を除いた有向グラフ）にする。
- 記録は自動で取る: 制度の値は `ctx.param`、丸めは `ctx.money` の関数、部品の呼び出しは `ctx.call` を通るので、エンジンがその場で記録する。部品が自分で書くのは計算式IDだけ（出力のお金の動きに `formula` を付ける。カスタム部品の計算式IDは `ext.<作成者>.` で始める）。
- 記録の形は実行時に検査する（公式もカスタムも）。計算式IDの無いお金の動きはエラー。
- **作る時機**:
  - スライダーを動かしている間・画面の通常の表示: `none`。
  - 数字をクリックしたとき: その数字を含む案×想定だけを `full` で計算し直し、その数字の記録を取り出して見せる。
  - 提案書のPDFを作るとき・顧客に見せた版の控えを作るとき: 対象の案の全想定を `full` で計算し、控えに圧縮して保存する（根拠の記録を保存するのは控えだけ。作業中のプランは必要なときに計算し直す。0009）。
  - 移行の照合・不具合報告の再現: `summary`（必要なら `full`）。
- 根拠の記録だけから計算し直して同じ値になることを、テストで確かめる。

## 理由

- 部品表を通して呼ぶのは、差し替えた部品が、それを呼ぶすべての公式部品に効くようにするため。直接の呼び出しを許すと、差し替えが一部にしか効かず、同じ世帯の中で新旧の計算が混じる。
- 差し込み口を8つ設計しておき、正式公開の時に3つだけ開くのは、約束を早く開きすぎると後で変えられなくなるため。FPの要望が多い支出・必要保障額・退職金規程から開き、残りは使われ方を見てから開く。設計だけ先にしておけば、公式部品の作り直しが要らない。
- 版を2つに分けるのは、「入出力の形が変わったか（差し替えが壊れるか）」と「中身が直ったか（取り下げ・再計算の対象か）」が別の問いだから。1つの版で表すと、制度改正のたびに差し替えが無効になってしまう。
- 新旧の制度を別IDにするのは、施行日の前後で同じ世帯の計算が切り替わる（過去の年は旧制度、将来の年は新制度）ことを、部品の中の分岐ではなくデータで表せるようにするため。
- JSON Schema にするのは、言語をまたいで（TypeScript・Rust・FPのAI）同じ定義を使え、実行時に機械で検査できるため。カスタム部品の正しさの最低限（形が合っていること）を、承認の前に機械で判定できる。
- 根拠の記録を `ctx` で自動で取るのは、部品ごとに記録を書かせると、書き忘れ・書き間違いが必ず起きるため。金額を `ctx` の関数でしか計算できない決まり（0002）と組み合わせると、記録の抜けが仕組みの上で起きにくい。
- 記録を細かさで切り替え、`full` をPDF・控えのときだけにするのは、試作で `full` が2〜6倍遅く、結果が17MBになったため。画面の操作中に毎回作ると目標の速さに入らない。

## 影響

- 部品表・差し込み口・2つの版を後から変えると、全FPのカスタム部品が壊れる。根拠の記録の形を変えると、根拠の表示と検証の作り直しになる。
- 守るべき決まり:
  - 部品は `ctx` 以外の方法で他の部品・制度の値・入力に触れない。
  - 公式部品の約束を変えるときは、MAJOR と MINOR の区別を守り、変更点を SDK の「版ごとの変更点」に書く。
  - 開いた差し込み口・差し替えを許した公式部品の約束は、試験版の規則（3か月前の予告。0001）でしか変えない。
- テストで確かめること:
  - **差し替えたことにしたテスト**: 公式部品の2〜3個をテスト用の部品に差し替えた状態のテストを常に流し、差し替えが呼び出し元すべてに効くこと、部品表が見出しに正しく残ることを確かめる。
  - 部品の依存の循環がエラーになること。
  - 約束の MAJOR が合わない差し替えで、計算が止まりFPに知らせること（黙って公式に戻らないこと）。
  - 開いていない差し込み口を宣言した部品が拒まれること。差し込み口の外の行を出す部品が拒まれること。
  - スキーマの検査: エンジン全体の入力が知らない欄を拒むこと、カスタム部品の出力の形の誤りがエラーになること。
  - 根拠の記録: `full` の記録から計算し直して同じ値になること。`none`・`summary`・`full` で数字が同じこと（一致テスト。0005）。
  - 新旧の制度の切り替え: 切り替え月の前後で、系統IDから正しい実体が選ばれること。

## 試作での確認

数値の表し方は 0002 の工夫版、Rust組込みの quickjs-ng、ミリ秒の中央値。

| 計算 | 根拠の記録 | クラウド（Xeon 4コア） | Apple M5 |
|---|---|---|---|
| 5案×4想定 | なし | 614 | 217 |
| 5案×4想定 | 要約 | 1,000 | 316 |
| 5案×4想定 | 全部 | 1,432 | 464 |
| 1案×4想定 | なし | 125 | 43.8 |
| 1案×4想定 | 全部 | 284 | 90.9 |

- 結果の JSON の大きさ: 5案×4想定で、なし 363KB、要約 569KB、全部 17.0MB。1案×4想定で、なし 73KB、全部 3.4MB。
- 使ったメモリ: 5案×4想定で、なし 約3MB、全部 約88MB。
- 「全部」は、エンジンによって2〜6倍遅くなった。画面側のエンジン（V8）でも5案×4想定の「全部」は71〜221ミリ秒で、0.1秒に入らないことがある。
- 「要約」が「なし」より約1.5倍遅いのは、試作の作りで記録のたびに一覧に足していたため。部品ごとに最初の1回だけ記録すれば「なし」に近づく見込み（未確認）。
- 根拠の記録の細かさを変えても、数字の結果のハッシュは変わらなかった（全エンジンで一致）。

## 追記

- 2026-10-08（requires の書き方）: 部品の `requires` も、パック（0007）と同じ範囲の書き方（例 `">=1 <2"`）にそろえる。`"1"` は `">=1 <2"` の省略形として認める。範囲の数は約束の版の MAJOR。
- 2026-10-08（根拠の記録の細かさ）: `full` の細かさは「部品の呼び出しごと」を標準にする。出力のお金の動き・年ごとの行は、それを作った部品の呼び出しの記録（`call` のノード。使った制度の値・入力・端数処理・時点と、内側の呼び出しを番号で指す）を指す。お金の動き1件ごとの値の依存は、必要になったら足す。「未確定」の `full` の形のうち細かさはこれで閉じる（圧縮と大きさの目安は残す）。
- 2026-10-08（ctx.at(month) の形）: 制度の値と制度の端数処理は、`ctx.at(month)` で「いま計算している月」に結び付けてから使う（`param`・`paramYen`・`paramRate`・`paramBrackets` などと `money`）。`ctx.money` を直接使えるのはエンジンの規約（`conv.*`）の丸めだけ。制度の端数処理の規則IDも制度の値なので、マニフェストの `params` に書く。`param` に渡せるのは、条件 `birthDate` のための `member` と、`basis: anchor` のための `anchorEvent`（名前つきイベントのID。種類が anchor と一致するかを確かめる）だけで、任意の日付は渡せない。
