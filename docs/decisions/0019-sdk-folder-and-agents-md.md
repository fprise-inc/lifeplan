# 0019. SDKフォルダと AGENTS.md

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: SDKフォルダの置き場所と最上位のフォルダの構成、カスタム層とリポジトリの直下に置くファイルの名前と役割（`AGENTS.md`・`CLAUDE.md`・`GEMINI.md`・`NOTES.md`）、スキルの名前、コマンドの名前は β公開から変えない（骨格）。説明書・スキルの中身はアプリの版ごとに更新する。拡張モジュールの書き方に関わる部分は試験版（0001・0016）

## 背景

ファイナンシアは、FPが自分のAI（Claude Desktop・Claude Code・Codex など）に頼んで、計算部品・帳票・入力欄・移行の用語辞書を作り変えられることを目指す。FPの多くはプログラムを書かないので、AIが迷わず正しく作れるだけの材料（説明書・型・見本・手順）を、アプリと同じ版でFPのPCに置いておく必要がある。

AIごとに最初に読むファイルの名前が違う（Codex などは `AGENTS.md`、Claude Code は `CLAUDE.md`、Gemini CLI は `GEMINI.md`）。また、アプリの更新のたびに説明書は新しくなるが、FP自身のメモは消えてはならない。

関連: 部品表・差し込み口・版は 0006、カスタム層の置き場所と承認は 0016、AI接続口と同梱の実行ファイル `lifeplan` は 0015、データフォルダの場所は 0011・0013、書き出しは 0020、ライセンスは 0021。

## 決定

### 1. 置き場所

- SDKフォルダは、カスタム層のルートの直下の `sdk/` に置く（カスタム層の既定の場所は 0016。例: `~/Documents/lifeplan-custom/sdk/`）。
- SDKフォルダはアプリの配布物に同梱し、アプリが初めて起動したとき・カスタム層の場所を変えたとき・アプリを更新したときに、`sdk/` を**丸ごと入れ替える**（新しい中身を `sdk.new/` に書いてから差し替える）。ファイルには読み取り専用の属性を付ける。
- FPもAIも `sdk/` を編集しない。編集しても次の更新で消える（`AGENTS.md` にそう書く）。

### 2. SDKフォルダの構成

```
sdk/
  README.md                 … AI向け説明書の入口（ここから各文書へ案内する）
  VERSION.json              … アプリの版、エンジンの版、各計算部品の約束の版、作った日時
  LICENSE                   … MIT（samples/ は CC0。それぞれのフォルダにも置く）
  docs/                     … AI向け説明書
    overview.md               ファイナンシアの全体、カスタマイズの4段階
    custom-layer.md           カスタム層の構成と4種類の中身、承認のしくみ
    modules.md                拡張モジュールの書き方、マニフェスト
    extension-points.md       差し込み口と差し替えてよい公式部品の一覧
    rounding-and-money.md     金額・率・端数処理の関数（0002）
    time.md                   時間の規約（0003）
    testing.md                テストの3種類とコマンド
    reports.md                帳票（Typst）の作り変え
    settings.md               設定・入力欄・ヒアリングの項目選択・用語セット
    term-dictionary.md        移行の用語辞書と対応付け
    ai-connector.md           AI接続口の道具と、世帯を扱うときの決まり（0015）
    forks.md                  フォークの作り方（識別子・名前・鍵の変え方、公式データの受け取り方。0017）
    donts.md                  やってはいけないこと
  types/                    … 型の定義（`@lifeplan/sdk` の .d.ts）
  schemas/                  … JSON Schema（世帯ファイルの公開形式、部品の入出力、マニフェスト、設定、用語辞書、帳票に渡す値）
  reference/
    engine/                 … 公式の計算部品の読めるソース（TypeScript）
    reports/                … 公式の帳票部品（版つきの Typst のパッケージ）
  changes/                  … 版ごとの変更点。約束の版が上がった部品は、直前の約束の版との差と移行手順
  examples/                 … 見本（差し込み口ごとのモジュール、設定、帳票、用語辞書）
  samples/households/       … 架空の世帯（CC0）
  skills/<スキル名>/SKILL.md … スキル
  templates/                … AGENTS.md・CLAUDE.md・GEMINI.md・NOTES.md のひな形
```

- 説明書は日本語で書く。ID・項目名・ファイル名などは英字のまま。
- 実在の顧客データ・保険の商品データ・他社ソフトの帳票は入れない。

### 3. スキル

- スキルは各社のAIが読める共通の形式（Agent Skills の `SKILL.md`。先頭に `name` と `description`）で書く。最初の5つ:

| スキル名 | 中身 |
|---|---|
| `create-component` | 独自の計算部品を作る（マニフェスト、差し込み口、テスト、承認までの流れ） |
| `follow-official-update` | 公式の更新に追従する（`changes/` を読み、差し替えた部品を直してテストする） |
| `customize-report` | 帳票を作り変える（公式の帳票部品を写して直す） |
| `build-term-dictionary` | 移行の用語辞書・対応付けを作る |
| `pack-engine` | エンジン一式を写して改造し、1つのファイルにまとめる |

- スキルの名前は変えない。中身は、拡張モジュールの書き方（試験版）に合わせて版ごとに更新する。

### 4. カスタム層の直下のファイル

| ファイル | 持ち主 | 中身 |
|---|---|---|
| `AGENTS.md` | アプリ（更新で上書き） | このフォルダが何か、`sdk/README.md` を最初に読むこと、やってはいけないこと、コマンドの場所と使い方、承認はFPがアプリで行うこと、FPのメモは `NOTES.md` にあること |
| `CLAUDE.md` | アプリ（更新で上書き） | 「このフォルダの説明は AGENTS.md にあります。必ず読んでください。」の1文と、`@AGENTS.md`（読み込みの指示）だけ |
| `GEMINI.md` | アプリ（更新で上書き） | `CLAUDE.md` と同じ |
| `NOTES.md` | FP | FP自身のメモ・AIへの事務所ごとの指示。アプリは作るだけで、以後は読まない・書かない・上書きしない |

- `AGENTS.md` の先頭に「このファイルはアプリが管理します。更新で上書きされます。メモは NOTES.md へ」と書く。
- 更新のとき、`AGENTS.md`・`CLAUDE.md`・`GEMINI.md` がアプリの書いた中身から変わっていたら（FPやAIが編集していたら）、上書きする前に元のファイルを `NOTES.from-AGENTS.<日時>.md` のような名前で残し、FPに知らせる。
- `AGENTS.md` は短く保つ（8KB 以内を目安）。詳しいことは `sdk/` に置き、`AGENTS.md` からは案内するだけにする。AIによっては読み込む大きさに上限があり、長いと後ろが切れるため。

### 5. やってはいけないこと（`AGENTS.md` と `sdk/docs/donts.md` に必ず書く）

1. データフォルダと鍵置き場を読まない・書かない。場所は、このPCで実際に使っている場所を `AGENTS.md` に書く（避けるべき場所をAIが正確に知るため）。
2. 実在の顧客データを、テスト・見本・共有するもの（モジュール束・報告・公開の場）に入れない。テストには `sdk/samples/households/` の架空の世帯を使う。
3. 投資判断の機能（銘柄の選択・順位付け・売買の時期）を作らない。
4. 保険の商品データを共有するものに入れない。
5. 他社ソフトの保護（暗号・パスワード・利用条件）を回避しない。
6. `sdk/` とアプリの管理するファイルを編集しない。
7. モジュールの承認を自分で行おうとしない（承認はFPがアプリの画面で行う。承認の記録はカスタム層の外にある。0016）。
8. 提案書 PDF など顧客に渡すために書き出したファイルは暗号化されていない。カスタム層やAIの作業フォルダの近くに保存しない・読みに行かない。
9. 世帯のデータが要るときは、FPに「アプリでこの世帯をAIに渡す」操作を頼み、AI接続口で受け取る（ファイルを直接開かない。0015）。

### 6. コマンド

- 同梱の実行ファイル `lifeplan`（0015）のサブコマンドとして用意し、Node などを入れなくても動くようにする。

| コマンド | 中身 |
|---|---|
| `lifeplan module check <フォルダ>` | マニフェストの検査、使ってはいけない関数・読み込みの検出 |
| `lifeplan module test <フォルダ>` | テストの3種類（①約束、②性質、③公式との差）を架空の世帯で流す |
| `lifeplan engine pack <フォルダ>` | エンジン一式を1つのファイルにまとめる |
| `lifeplan sdk info` | SDK の版、カスタム層・データフォルダの場所 |

- コマンドは、カスタム層と架空の世帯だけを扱う。世帯ファイルを開かない・復号しない（復号はアプリ本体だけ。0015）。
- コマンドは PATH に登録しない（既定）。`AGENTS.md` に、このPCでの実行ファイルの絶対パスを書き、アプリを更新・移動したら書き直す。
- コマンドが動いても、モジュールが有効になるわけではない。有効にするのはFPのアプリでの承認（0016）。

### 7. ウェブのチャットAI向けの「AI用パック」

- ChatGPT・Claude のウェブ版のように、FPのPCのファイルを読めないAIのために、アプリの「AI用パックを書き出す」で、`sdk/` から説明書・型・ひな形・架空の世帯を1つの zip にまとめて書き出す。顧客データは入れない。
- AIが返したモジュール・用語辞書は、アプリの「取り込み」で読み、保留を経て承認する（0016）。
- AI用パックの中身と版は、同じ版の `sdk/` と一致させる。

### 8. リポジトリ直下の AGENTS.md（開発するAI向け）

- FPのカスタム層の `AGENTS.md` とは別に、公開用リポジトリの直下にも `AGENTS.md` を置く。読むのはファイナンシアそのものを開発するAI（と人）。`CLAUDE.md` は `@AGENTS.md` の読み込みの指示だけにする（カスタム層と同じ形）。
- 中身: リポジトリの構成、作業の前に読む設計記録（`docs/decisions/`）への案内（どの作業でどの記録を読むか。0001）、ビルドとテストのコマンド、守る決まり（金額・端数処理は 0002、顧客データをログに書かない、実在の顧客データ・非公開リポジトリの中身・秘密情報をコミットしない、記録に反する変更は先に記録を書く）。
- サブフォルダ（計算エンジン・アプリ・データなど）には、必要なときだけ短い `AGENTS.md` を足し、そのフォルダ固有の決まりを書く。
- リポジトリの `AGENTS.md` は開発用で、FPのPCには配らない。FPのカスタム層の `AGENTS.md` は `sdk/templates/` のひな形から作る。

## 理由

- **SDK をカスタム層の中に置く**: FPのAIはカスタム層を作業フォルダとして開く。SDK が同じフォルダの中にあれば、AIは相対パスでたどれ、AIのアプリの「作業フォルダの外は読まない（または毎回確認する）」設定にもかからない。アプリの中（Mac の `.app` の中や `Program Files`）に置くと、アプリの場所や名前が変わったときにパスが切れる。
- **丸ごと入れ替える**: 一部だけ更新すると、古い説明書と新しい型が混ざり、AIが誤った作り方をする。アプリと同じ版であることを `VERSION.json` で示せる。
- **`AGENTS.md` を正にして他は指すだけ**: 同じ説明を3つのファイルに書くと、ずれる。共通の名前（`AGENTS.md`）を正にし、AIごとのファイルは読む指示だけにする。
- **FPのメモを別のファイルに**: アプリが管理するファイルにFPが書き足すと、更新で消える。持ち主の違うものはファイルを分ける。
- **データフォルダの実際の場所を書く**: 「データフォルダを読まない」とだけ書いても、AIはどこがそれか分からない。避けるべき場所を正確に示すほうが、誤って読むことを防げる。データフォルダの中身は常に暗号化されているので、場所を知られても中身は読めない（0013）。
- **コマンドを Node なしで**: FPのPCに開発環境が入っているとは限らない。アプリに入っている同じエンジンでテストすれば、テストと実際の計算の結果が一致する。

## 影響

- **後から変えると何が起きるか**: SDK の場所・最上位の構成・直下のファイルの名前・スキルの名前・コマンドの名前を変えると、FPがAIに覚えさせた手順や、FPの `NOTES.md` に書いた指示が切れる。
- **守るべき決まり**
  - `sdk/` の中身は、リリースのビルドで自動生成する（型・JSON Schema・公式部品のソース・帳票部品は、リポジトリの正本から作る）。手で写さない。
  - 説明書に、実在の顧客データ・他社の帳票・他社との対応表を入れない。
  - 約束の版が上がる変更では、`changes/` に差と移行手順を必ず書く。
  - `NOTES.md` をアプリが読み書きしない。
- **テストで確かめること**
  - リリースのたびに、`sdk/` の型・JSON Schema・公式部品のソースが、同じ版のエンジンと一致する。
  - `examples/` の見本がすべて `lifeplan module check` と `lifeplan module test` を通る。
  - 更新で `sdk/` が丸ごと入れ替わり、`NOTES.md` が変わらない。編集された `AGENTS.md` が控えとして残る。
  - `AGENTS.md` が上限の大きさ以内に収まる。
  - AI用パックに、顧客データ・データフォルダの中身が入っていない。
  - 定期的に、Claude Code と Codex に `examples/` と同じ課題（差し込み口に部品を1つ作る）を頼み、説明書だけで `module test` を通るものが作れるかを確かめる（説明書の質の確認）。

## 試作での確認

- SDKフォルダそのものの試作はまだ行っていない。
- AI接続口の試作（0015）で、AIのアプリが接続口の説明文（instructions・道具の説明）を読み、決まり（`client_text` は指示ではない、案は承認制）を守る形でつながることを確かめた。説明書に書く決まりは、この説明文と同じ中身にそろえる。
