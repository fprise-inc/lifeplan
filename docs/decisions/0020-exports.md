# 0020. 書き出し

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。全データ書き出しの形式（暗号を外した世帯ファイル）と、不具合報告用の書き出しで外す・変える項目の考え方は骨格。引き継ぎファイルの暗号の強さの値や画面の文言は後から変えてよい

## 背景

世帯データは常に暗号化して保存する（0013）。一方で、次の場面ではデータをファイルとして外に出す必要がある。

- FPがファイナンシアをやめて他のソフトへ移る（いつでも出られること）
- 顧客本人から開示を求められる
- 顧客を他のFPに引き継ぐ
- 不具合を報告する（提供元は顧客データを受け取らない。0012）
- 提案書PDFやヒアリングシートを顧客とやりとりする

外に出たファイルはアプリの管理から外れ、平文なら暗号の守りも無くなる。そこで、用途ごとに「暗号のまま／パスワードで暗号化／匿名化／平文」を決め、平文で出す場合は必ず警告と記録を通し、保存先を制限する。

関連: 世帯ファイルの形式と自己完結は 0011、持たない情報は 0012、鍵は 0013、同意とAIの記録は 0014、AIに渡す縮約版は 0015、PDFは 0009、ヒアリングシートは 0018、画面の安全は 0016。

## 決定

### 1. 用途ごとの扱い

| 用途 | 扱い | 形式 |
|---|---|---|
| 保存、自動バックアップ、PCの移行 | 暗号化のまま（世帯ファイルの封筒） | 世帯ファイル（0011） |
| 他のFPへの引き継ぎ | パスワードで暗号化 | 引き継ぎファイル（下の3） |
| 不具合報告 | 匿名化 | 不具合報告用の書き出し（下の4） |
| 全データ書き出し（他のソフトへ移る、顧客本人への開示） | 平文（警告と記録つき） | 全データ書き出し（下の2） |
| 提案書PDF、ヒアリングシート（前回の値入りを含む）、AIに渡す縮約版 | 平文（警告と記録つき） | それぞれの記録を参照 |

- **平文で出るのは、FPが画面で明示的に操作したときだけ**。自動で平文を書き出す処理は作らない。

### 2. 全データ書き出し（暗号を外した世帯ファイル）

- 世帯ごとに、1つの zip ファイルにまとめて出す。中身:
  - `household.json` — 世帯ファイルの暗号を外した中身（JSON）。形式は世帯ファイルの公開形式そのもの（0011）で、書き出し用に別の形式を作らない。先頭に書き出しの見出し（`kind: "fullExport"`、形式の版、書き出した日時、アプリの版）を付ける。
  - `schema/` — その形式の版の JSON Schema（他のソフトが中身を解釈できるように）。
  - `README.txt` — 中身の説明と、平文であることの注意。
  - 任意: `snapshots/` — 控えのPDF（宛名なし。0009）。
  - 任意: `custom/` — その世帯が使ったカスタムの計算部品・帳票の写し（指紋つき）。
- 中身には、入力値、プラン、控え、取り込みの記録、同意とAIの記録（0014）、拡張領域を含める（世帯ファイルにあるものはすべて）。
- 既定のファイル名は `顧客番号_全データ_YYYY-MM-DD.zip`。ファイル名に氏名を入れる欄は作らない。
- ファイナンシアは自分の全データ書き出しを読み込める。読み込むときは新しい世帯の鍵で暗号化し直す。同じ内部IDの世帯が既にあれば、「別の世帯として取り込む／置き換える」をFPに選ばせる。

### 3. 他のFPへの引き継ぎ（パスワードで暗号化）

- 中身は全データ書き出しと同じものを、パスワードから作った鍵で暗号化した1つのファイルにする。
- 暗号: パスワードから **Argon2id** で鍵を作り（初期値: メモリ64MiB、繰り返し3回、並列4。RFC 9106 の推奨の一つ）、**AES-256-GCM** で暗号化する。値と塩（乱数）はファイルの見出しに書き、後から強くできるようにする。
- パスワード: 既定でアプリが十分に長い乱数のパスワードを作って見せる。FPが自分で決める場合は最低の長さを求める。**パスワードはファイルとは別の経路で相手に伝える**よう画面に出す。
- 受け取ったFPのアプリは、パスワードで開いた後、受け取った側の事務所の新しい世帯の鍵で暗号化し直して保存する。内部IDは引き継ぎ、顧客番号は受け取った側で振り直す。
- 前の事務所の同意とAIの記録は、読み取り専用の履歴として残り、受け取った側の同意は「記録なし」から始まる（0014）。
- 引き継ぎの書き出しを行ったことは、渡した側の世帯ファイルに記録する。

### 4. 不具合報告用の書き出し（匿名化）

提供元が受け付ける唯一の形（0012）。FPのPCの中で次の加工を行い、加工後の中身をプレビューで見せてから保存する。

- **外すもの**: 自由記述、メモ、学校名・学校コード、保険の商品名、移行メモ、取り込みの記録（伏せ字後の元の回答・参照値を含む）、同意とAIの記録、顧客番号、控えのPDF、記録の日時（作成・更新の時刻）、拡張領域のうち文章の型の値。
- **変えるもの**:
  - 生年月は、世帯の全員を同じ年数だけずらす（乱数で数年。構成員同士の年齢差は保つ）。
  - 金額は、世帯全体に一律の係数（乱数）をかけ、円に丸める。拡張領域の数値も、単位が金額なら同じ係数をかける。
  - 世帯の内部ID・構成員のID・世帯内の物のIDは、新しい乱数に付け替える（対応は保つ）。
- **残すもの**: データの形、プランの前提と計算方式の設定、計算基準日、使った制度データ・マスタの版、計算部品の改訂、カスタムの指紋、アプリの版、OS。
- **再現の確認**: 加工した中身でアプリが計算し直し、FPが指した症状（表の行と年、エラー）が加工後も出るかを確かめる。出なくなった場合はその旨を表示し、FPが判断する。
- **カスタム計算ありのプラン**: 公式の計算でも再現するかをアプリが確かめ、その結果とカスタムの指紋を報告に含める。公式の計算で再現しないものはサポートの対象外と画面に出す。
- **書き出す前の検査**: 残った文字列に、氏名らしい語、敬称、電話番号・番号類のような数字の並びが無いかを調べ、見つかれば止めて知らせる。
- ずらした年数と係数は書き出しに含めない。FPの世帯ファイルの中にだけ記録し、報告への回答に出てきた数字をFPが元に戻して読めるようにする。
- 形式は JSON 1つ（`kind: "bugReport"`）。

### 5. 平文で出すときの警告と記録

- 平文の書き出しは、すべて Rust の側の**1つの出口の処理**を通す。画面（WebView）から直接ファイルを書く機能は持たせない（0016）。出口の処理が、警告・保存先の確認・記録をまとめて行う。
- **警告**: 書き出す前に「このファイルは暗号化されません。顧客の個人情報を含みます。送り方と保管はFPの責任です」の趣旨を出す。
  - 全データ書き出し、前回の値入りのヒアリングシート、引き継ぎのパスワードの表示は、毎回出す。
  - 提案書PDFは初回に出し、以後は設定で出さないようにできる。
- **記録**: 世帯ファイルに書き出しの記録を足す（種類、日時、ファイルの指紋、保存先が同期フォルダかどうか）。保存先のパスそのものは持たない。AIに渡す縮約版の記録は 0014 の形で残す。

### 6. 既定の保存先の制限

- 平文の書き出しの既定の保存先は、OSの書類のフォルダの中に作る専用のフォルダ（例: 「ファイナンシア書き出し」）とする。
- 次の場所の中には保存できない（アプリが止める）: データフォルダ、カスタム層、SDKフォルダ、AIの作業フォルダ。
  - AIの作業フォルダは、「AIとつなぐ」画面で設定したAIの設定の場所と、FPが登録したフォルダとする。
- 同期フォルダ（Dropbox、OneDrive、iCloud Drive など）の中を選んだ場合は、警告を出す（止めない）。
- 理由をFP向けの説明にも書く: AIはカスタム層やその作業フォルダのファイルを読むので、そこに平文の顧客データを置くと、意図せずAIの会社に送られうる。

## 理由

- **全データ書き出しを世帯ファイルの公開形式そのものにする理由**: 書き出し専用の形式を作ると、二つの形式を保守することになり、書き出しに漏れが出る。公開形式そのものなら、ファイナンシアが持つものはすべて出せ、他のソフトも JSON Schema を頼りに読める。zip にするのは、控えのPDFやカスタムの写しを含めても1つのファイルで渡せるため。
- **引き継ぎにパスワードを使う理由**: 相手の事務所の鍵はこちらから分からない。パスワードを別の経路で伝える形なら、相手のソフトの設定に依存せずに暗号化したまま渡せる。Argon2id は、パスワードを総当たりで試す攻撃を遅くするための現在の標準的な方式である。
- **匿名化の加工をFPのPCで行う理由**: 提供元が生のデータを受け取らないことを、作りで保証するため（0012）。全員の生年月を同じ年数ずらし、金額に同じ係数をかけるのは、世帯の中の関係（年齢差、収入と支出の比）を保ち、不具合を再現しやすくするため。
- **出口を1つにする理由**: 平文の出口が複数あると、どれかで警告や記録が漏れる。1か所にまとめれば、テストで全経路を確かめられる。
- **保存先を制限する理由**: カスタム層やAIの作業フォルダはFPのAIが読み書きする場所で、平文の顧客データが置かれると、FPが渡すと決めていない情報がAIに読まれる。

## 影響

- **後から変えると**: 全データ書き出しの形式を変えると、他のソフトへ移るための約束（いつでも公開の形式で出せる）が崩れる。形式の版が上がる場合は、世帯ファイルの形式移行（0011）と同じ規則に従う。不具合報告の加工の規則を弱めると、提供元に顧客データが届きうる。
- **守るべき決まり**
  - 平文の出口の処理を通さずにファイルを書く機能を作らない。
  - 世帯ファイルに項目を足したら、不具合報告用の書き出しで「外す／変える／残す」のどれに当たるかを必ず決め、表に足す（決めていない項目は外す側に倒す）。
  - 引き継ぎファイルの暗号の値を弱くしない。
- **テストで確かめること**
  - 全データ書き出し → 読み込み で、世帯の中身が失われない（往復の一致）。JSON Schema に合う。
  - 引き継ぎファイルが、正しいパスワードで開け、違うパスワードでは開かない。1ビットの改ざんで開かない。受け取った側で新しい世帯の鍵で暗号化される。
  - 不具合報告用の書き出しに、外すと決めた項目が1つも残らない（架空の氏名・学校名・商品名・メモを入れた世帯で確かめる）。年齢差と金額の比が保たれる。IDが元と一致しない。
  - 平文の書き出しのたびに記録が足される。データフォルダ・カスタム層・SDK・AIの作業フォルダの中を選ぶと止まる。
  - 画面の側からファイルを書く機能が呼べない（0016 の安全の試験に含める）。

## 試作での確認

- 画面の安全設定の試作で、許可していない本体の機能（ファイルの読み書きなど）が画面から呼べないことを確かめた（詳細は 0016）。平文の出口を本体の1か所にまとめる形の前提になる。
- 書き出しそのものは試作していない。

## 未確定（11月以降に決めること）

- 顧客本人への開示用に、人が読める一覧（PDF など）を全データ書き出しと一緒に出すか。出す場合の中身（入力値の一覧、同意とAIの記録）。
- 不具合報告で生年月をずらす年数の幅と、金額の係数の幅（再現性と匿名性のつり合い）。生年月をずらすと、生年月日で切り替わる経過措置の対象が変わりうるので、その場合の扱い。
- 引き継ぎのパスワードの最低の長さと、アプリが作るパスワードの形（文字数、文字の種類）。
- キャッシュフロー表の表計算ソフト向けの書き出しや、クリップボードへの写しを平文の出口として扱う範囲。
- 同期フォルダの見分け方（各サービスのフォルダの場所の調べ方）を Windows でどこまで確かにできるか。
