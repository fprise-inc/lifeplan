# 0021. ライセンスとリポジトリの分割

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。β公開で公開したものはライセンスを取り消せず、履歴も取り戻せないので、β公開の時点の形がそのまま残る

## 背景

ファイナンシアは中身をすべて公開するソフトで、β公開（2027年2月予定）で公開用のリポジトリと配布物を誰でも入手できるようにする。公開は取り消せない（一度公開したライセンスは撤回できず、公開した履歴は誰かが写しを持ちうる）。

一方で、開発には公開できないものも要る: 制度の原本の写し（再配布の条件が個別のもの）、非公開のテスト用サンプルとそこから作った期待値、署名鍵などの秘密情報。これらが公開用のリポジトリの履歴に一度でも入ると、取り除けない。

そこで、ライセンスの区分、リポジトリの分け方、公開用のリポジトリに入れないもの、それを機械で守る仕組みを、最初のコミットの時点から決める。

関連: 署名と配布は 0017、制度データの形式と出典は 0007、学費データは 0010、自動化と承認は 0022、SDKフォルダは 0019。

## 決定

### 1. ライセンスの区分

| 対象 | ライセンス | 置き方 |
|---|---|---|
| 提供元（FPライズ／FPRISE, INC.）が書いたコード | **MIT** | リポジトリ直下の `LICENSE`。対象が「提供元が書いたコード」であることを本文に明記する（最初のコミットで置き済み） |
| 提供元が作るデータ（架空のモデル世帯、学費の学校別表、投資信託の資産クラス付け、移行の用語辞書など） | **CC0 1.0**（権利を手放す宣言。誰でも出典の表示なしに、コピー・再配布・加工・商用利用ができる。無保証） | そのデータのフォルダに CC0 の `LICENSE` を置く |
| 公的データ（国税庁・厚生労働省・金融庁・文部科学省などの公表値） | 各提供元の利用条件（政府標準利用規約・公共データ利用規約など）に従う | 出典（URL・取得日・原本の指紋・短い引用）を値ごとに持ち（0007）、加工した旨を表示する。国が作ったように見せない。提案書PDFでは注意書きのページに出典名だけを載せる |
| 試験の問題から作ったテスト（公的な検定の計算問題など） | 各実施団体の条件（出典・加工の表示など）に従う | 公開用のリポジトリに置けるかは条件を確かめてから決める（未確定）。確かめるまでは非公開のリポジトリに置く |
| 許諾を得たデータ | 提供元の条件に従う | 他のデータと混ぜず、別のデータパックにする。CC0 にはしない。私学事業団の数値は公開側に置かず、公式版に同梱するだけ（0010 の追記） |
| 同梱フォント（BIZ UDゴシック） | SIL OFL 1.1 | ライセンス文を同梱する |
| 依存ライブラリ | 各ライセンス | 第三者ライセンスの一覧を自動で作る（下の2） |

- フォルダごとに `LICENSE` を置き、リポジトリ直下に「フォルダ→ライセンス」の対応表（`LICENSES.md`）を置く。
- 製品名・ロゴの使い方のお願い（改造版には製品名・ロゴを使わないでほしい。強制力はない）を、最初から公開用のリポジトリに置く。公式版とは、FPRISE, INC. の署名があるビルドのことと明記する（0017）。

### 2. 第三者ライセンスの一覧とCIでの検査

- **一覧の自動生成**: Rust の依存（cargo-about などで生成）と画面側の JavaScript の依存から、第三者ライセンスの一覧を自動で作る。Apache-2.0 の部品の NOTICE も含める。一覧は次に入れる:
  - アプリの「ライセンス」画面
  - 配布物に同梱するファイル（`THIRD_PARTY_LICENSES`）
  - SDKフォルダ（0019）
- **CIでの検査**: 依存のライセンスを毎回の変更で検査し（Rust は cargo-deny など）、許可の一覧にないものが入ったら止める。
  - **許可**: MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC、Zlib、Unicode-3.0（Unicode-DFS-2016）、Unlicense、CC0-1.0、0BSD、BSL-1.0、OFL-1.1（フォントだけ）。
  - **個別に許可**: MPL-2.0。部品の名前を一つずつ例外の一覧に載せ、**改変せずに使う**場合だけ許す。
  - **禁止**: GPL・LGPL・AGPL の全版、SSPL、非商用の条件のもの（CC BY-NC など）、ライセンスの表示が無いもの。
  - 複数から選べる部品（例: 「MIT か Apache-2.0 か LGPL」）は、許可の側を選び、選んだことを一覧に記録する。
- LGPL も禁止にするのは、アプリを1つの実行ファイルとして配る形と、利用者による差し替えの条件が合わないため（同じ理由で、AI接続口の試作では、LGPL の部品を含む実行環境を候補から外した）。

### 3. リポジトリの分割

| リポジトリ | 公開 | 中身 |
|---|---|---|
| `fprise-inc/lifeplan` | β公開まで非公開、β公開で公開 | アプリ、計算エンジン、制度データ（出典の情報まで）、公式の読み取り規則、ヒアリングシートの定義、AI接続口、監視の道具、設計記録、AI向け説明書、合成したモデル世帯とそのテスト |
| `fprise-inc/lifeplan-private` | ずっと非公開 | 制度・学費の原本の写し（各種のページ・Excel・PDF）、非公開のテスト用サンプルとそこから作った期待値、それを使うテスト、他のソフトの帳票との対応に関する資料、利用条件で公開できない検証用の答え |
| `fprise-inc/lifeplan-releases` | β公開まで非公開、β公開で公開 | 署名つきのアプリとデータパック、更新情報（手動ダウンロード用の写し。アプリが自動で取りに行くのは配信元。0017） |

- **依存の向き**: 非公開のリポジトリは公開用のリポジトリを参照してよいが、逆は禁止。公開用のリポジトリは、非公開のリポジトリが無くても、ビルドとテストが通ること。
- 非公開のテスト用サンプルを使うテストは、非公開のリポジトリのCIでだけ流す。結果の数値も公開用のリポジトリに書き写さない。
- 製品の企画・事業の資料は、どのリポジトリにも入れない。

### 4. 公開用のリポジトリに入れないもの

- 原本の写し（出典の情報と短い引用は入れてよい）
- 非公開のテスト用サンプル、そこから読み取った数値・期待値
- 署名鍵・APIキー・トークン・証明書・パスワード（`.gitignore` で主な鍵の形式を除外済み）
- 実在の顧客のデータ（架空・合成したものだけを入れる）
- 許諾の無い第三者の素材（画像・文書・フォントなど）
- 個人名（コミットの作者名を含め、公開してよい名前だけを使う）

### 5. 秘密情報の検出と、β公開の前の監査

- **最初のコミットから、秘密情報の検出をCIに入れる**: gitleaks で、毎回の送信とプルリクエストのたびに全履歴を調べる（`.github/workflows/secret-scan.yml`。最初のコミットで導入済み）。
  - 署名やデータパックの鍵の形式など、標準の規則で拾えないものは独自の規則を足す。
  - 開発者の手元でも、送信の前に同じ検査を流すことを勧める。
  - 公開した後は、GitHub の送信時の秘密情報の保護（push protection）も有効にする。
- **β公開の前に、全履歴を機械で監査する**: 次を調べる。
  - 秘密情報（gitleaks の全履歴の検査）
  - 第三者の素材（許可の一覧に無い PDF・Excel・画像・フォントなどのファイル）
  - 個人名（調べる名前の一覧は、公開用のリポジトリの外に置く）
  - 実在の顧客データらしいもの（氏名らしい語、電話番号・番号類のような数字の並び）
- 問題が見つかった場合は、履歴を書き換えて取り繕うのではなく、問題を除いた状態から**新しい履歴で公開する**。

### 6. 外部からの変更提案は受け付けない

- 外部からのプルリクエストは受け付けない。受け付けるのは誤りの報告だけ。
- `README.md` と `CONTRIBUTING.md` に「作り変えは各自のカスタム層・フォークで自己責任で行う。誤りの報告は報告フォームへ」と書く。届いたプルリクエストは、この説明を添えて閉じる。
- 公開用のリポジトリの GitHub の Issues と Discussions は使わない（顧客の数字や画面が公開の場に貼られるのを防ぐため）。誤りの報告は非公開のフォームで、匿名化した書き出し（0020）を使って受ける。
- 安全上の弱点の報告は `SECURITY.md` で案内し、GitHub の非公開の報告機能で受ける。
- 実データが誤って公開の場に貼られた場合の削除の手順（削除、GitHub への依頼、投稿者への連絡）を `SECURITY.md` と同じ場所に用意する。
- 外部からのコードを取り込まないので、貢献者のライセンス同意（CLA）は要らない。良い改善のアイデアは、提供元が自分で作り直して取り込む。

## 理由

- **コードをMIT、提供元のデータをCC0にする理由**: FPが自分のAIで自由に作り変え、他のソフトでも使えるようにするため。データは出典の表示を求めないほうが、FPの独自帳票や他のソフトで使いやすい。CC0 にしても、提案書や画面に提供元の名前は出ない。
- **公的データ・許諾データを個別にする理由**: 提供元が権利を持たないものを CC0 にはできない。混ぜると、後で一部だけ外すことができなくなるので、パックとフォルダを分ける。
- **CIでライセンスを止める理由**: 依存の依存まで人が見続けることはできない。GPL 系が一度入ると、MIT で配る前提が崩れる。
- **3つに分ける理由**: 公開できないものを、最初から別の場所に置けば、公開用のリポジトリの履歴に入りようがない。配布用を分けるのは、大きな配布物でコードの履歴を重くしないためと、手動ダウンロードの置き場をはっきりさせるため。
- **新しい履歴で公開する理由**: 履歴の書き換えは漏れが残りやすく、確かめにくい。問題を除いた状態から始めるほうが確実である。
- **Issues を使わない理由**: 公開の場で不具合を報告してもらうと、FPが顧客の数字や画面をそのまま貼るおそれがある。報告は匿名化の書き出しを通す形に一本化する。

## 影響

- **後から変えると**: β公開の後は、公開したもののライセンスを狭めることはできない（新しい版から変えることはできても、公開済みの版は MIT・CC0 のまま残る）。公開用のリポジトリに一度入ったものは、履歴から取り戻せない。
- **守るべき決まり**
  - 新しい依存を足すときは、CIのライセンス検査を通す。MPL-2.0 の部品を足すときは、例外の一覧に名前を足し、改変しないこと。
  - 新しいデータのフォルダを作るときは、`LICENSE` を置き、`LICENSES.md` に足す。
  - 非公開のテスト用サンプルから得た値を、公開用のリポジトリ（テスト・設計記録・コメントを含む）に書き写さない。
  - 公開用のリポジトリから、非公開のリポジトリを参照しない。
- **テストで確かめること**
  - CIで: ライセンスの検査、秘密情報の検査、すべてのデータのフォルダに `LICENSE` があること、第三者ライセンスの一覧が最新であること（依存が変わったのに一覧が変わっていなければ止める）。
  - 公開用のリポジトリだけを取り出した環境で、ビルドとテストが通ること。

## 試作での確認

- 画面の安全設定の試作で、Tauri の標準構成の間接的な依存まで（Mac・Windows 向け）を調べた。GPL・LGPL・AGPL は無く、MIT・Apache-2.0・BSD・ISC・Zlib・Unicode・Unlicense のほかに、**MPL-2.0 の部品が5つ**あった（ビルド時に HTML を処理する部品の cssparser・cssparser-macros・selectors・dtoa-short と、dirs 経由の option-ext）。MPL-2.0 は「そのファイルを改変したら、そのファイルを公開する」型で、改変せずに使う分には配布に支障はない。このため、MPL-2.0 を「部品ごとの例外として、改変しない場合だけ許す」扱いにした。実行形式で配るときに求められる、元のソースの入手先の案内は、第三者ライセンスの一覧に載せる。
- AI接続口の試作で、Rust と npm の依存196件に GPL・LGPL・AGPL だけのライセンスが無いことを確かめた。「MIT か Apache-2.0 か LGPL」から選べるものが3件あり、MIT を選べた。候補の一つだった実行環境は LGPL の部品を静的に含むため、候補から外した。

## 未確定（11月以降に決めること）

- 公的な検定の計算問題から作ったテストを、公開用のリポジトリに置けるか（各実施団体の条件を確かめる）。
- 画面側の JavaScript の依存の一覧を作る道具と、Rust 側の道具（cargo-about・cargo-deny を第一候補とする）の最終的な選定。
- フォルダごとの `LICENSE` に加えて、機械で検査できる対応の書き方（REUSE の形式など）を採るか。
- 届いたプルリクエストを自動で閉じる仕組みを入れるか（GitHub の設定で止められる範囲を確かめる）。
- 開発の途中で、公開用のリポジトリの既定のブランチの保護（承認の必須化など）をどこまでかけるか（0022 と合わせて決める）。

## 追記
