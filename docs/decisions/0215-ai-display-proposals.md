# 0215. 表示の設定の候補を出す道具（propose_display_settings）と、承認の画面・前の値に戻す（0213 の段B の前半）

- 状態: 採用（一部未確定）（2026-11-15）
- 固定の強さ: 道具の名前と入出力（`propose_display_settings`・答えの `candidateId`・`status`・`settings`）、一覧の欄 `proposable`、接続口とアプリ本体の依頼（`proposeDisplay`）は試験版（0015・0213 と同じ。予告して変えることがある）。事務所データの形（`defaults.version: 3` で足した欄 `displayHistory`）は、足すことはあっても別の意味に使い回さない。次は固定: 候補を出せるのは事務所の既定値の見せ方だけの設定、AI は設定を直接変えない（変わるのは FP が画面で「反映する」を押したときだけ）、事務所の既定値はカスタム層に置かない（0016 の 2026-11-02 の追記の3）、どの設定でも隠せない知らせ（0213 の1）は今のまま。承認の画面の見た目・前の値の件数は後から変えてよい
- 前提にする記録: 0213（表示の設定の全体の形と段A）、0015（AI接続口）、0016（2026-11-02 の追記の3）、0073（事務所の既定値）、0084（対策に最初から出す項目）、0085（万一のタブ）、0091（入力項目の選び方）、0109（基本生活費の内訳の並べ方）、0110（機能を有効にするコードの候補）、0208（新しい世帯の候補）、0214（事務所データの形の版2）

## 背景

- 0213 の段A で、AI は表示の設定の一覧と今の値を読めるようになった（`get_display_settings`）。FP から「対策に最初から NISA も出して」と頼まれても、AI は変える所（画面と区画の名前）を伝えるだけで、FP が自分でその区画を探して変えていた。
- 0213 の段B は「AI が変える候補を承認待ちの候補としてアプリに出し、FP が設定ごとに『今 → 候補』を見て『反映する』か『捨てる』を選ぶ。反映した後も前の値に戻せる」形と決めていた。この記録は、その前半（事務所の既定値の候補）を作った回。

## 決定（利用者の決定 2026-11-15）

### 1. 段B の前半で候補を出せる設定

- 事務所の既定値のうち、見せ方だけの7つ: `input.order`（入力のホームの入力項目の並び）・`input.items`（新しい世帯で出す入力項目と、開いたときの入れ方）・`input.living`（基本生活費の内訳の並べ方）・`result.levers`（対策に最初から出す項目）・`contingency.premises`（想定の前提に最初から出す項目）・`contingency.scenes`（場面の帯に並べる場面）・`contingency.openScene`（開いたときに選んでおく場面）。
- 結果のタブ・資産と負債のタブの設定（`result.*`・`balance.*`）と、渡された世帯ごとの候補は、後半・段C で扱う。`result.addedItems`（世帯ごと）と `features.combinedBs`（機能を有効にするコードが要る）は読むだけのまま。
- 前提条件（計算に効く設定。0214 で事務所の既定値に一本化された物）は対象の外。表示の設定の一覧にも載せていない（0213 の1）。
- 表示の設定の一覧の7件に `proposable: true` を付け、`get_display_settings` の答えの一番上に `proposable`（id の並び）を足した。並びは一覧の定数 `PROPOSABLE_DISPLAY_IDS`（`app/src/connector/displayCatalog.ts`）の1か所。アプリ本体の受け口の並び（`ai_share::display_proposals::PROPOSABLE_IDS`）と同じことを接続口のテストで確かめる。

### 2. 道具 `propose_display_settings`（接続口）

- 入力: `changes`（1〜7件。1件は `id`・`value`・任意の `note`〔理由。500文字まで〕。同じ設定は1回だけ）。`value` は `get_display_settings` の今の値（`current.office.value`）と同じ形（例: `result.levers` は最初から出す種類の並び、`contingency.openScene` は場面の値1つ、`input.living` は `{ rows: [行] }`）。
- 形は `propose_scenario`・`propose_feature_code` と同じ: アプリの画面に承認待ちの候補として出すだけで、設定は変えない。カスタム層のファイルは使わない（0016 の 2026-11-02 の追記の3）。世帯を渡していなくてよい（事務所の既定値は世帯の中身ではない。AIに渡した記録にも残さない）。アプリが起動していて AI接続口がオンのときだけ。
- 値は、アプリに出す前に、表示の設定の一覧の選べる値（`choices`）・値の形（`type`・`min`・`max`・`shape`）で確かめる（`app/src/connector/displayProposal.ts` の `checkDisplayChanges`。接続口は `plan.js` の `displayCheck` として同梱して動かす。アプリの承認の画面も反映する前に同じ関数で確かめ直す）。断るときは、その呼び出しで何もしない（ほかの正しい候補もアプリに出さない）。理由は「知らない引数を断る」（`crates/lifeplan/src/args.rs`）と同じ書き方で、書いた物を挙げ、近い候補を「〜のことですか」で添える（書き方の違いだけ → 1〜2文字の違い → 名前の一部、の順。選べる値には画面の言葉も添える）。
  - 知らない id（近い id）・7つ以外の設定（世帯ごとの設定は変える画面の名前を、読むだけの設定はそのことを添える）・同じ設定が2回・8件以上・`value` が無い。
  - 選べない値・重複・形の違う値（並びでない・知らない名前の欄）。空の並びは `min` のある設定（場面の帯は1つは並べる）だけ断る。対策・想定の前提は「何も最初から出さない」を選べる（画面のチェックと同じ）。
  - 入力項目の並び（`order`）は、全部の入力項目を1回ずつ並べる（足りない物を挙げて断る。出す・出さないは `input.items` で決める）。いつも出す入力項目（家族・前提条件）は出さない側に入れられない。
  - 基本生活費の内訳の並べ方: 行の名前は人の文章が入る所なので、前後の空白を除いて1〜20文字（画面の `LIVING_LABEL_MAX`。数え方も画面と同じ）まで受け、21文字からは文字数を挙げて断る。改行・タブなどの制御文字・見えない書式の文字（幅の無い空白・向きを変える印など）・行の区切りは通さない。その他は隠せず分けられない・1つの内訳は1つの行にだけ・まとめた行は2つ以上・分けた行は2〜6で名前が重ならない・割合は全部の行に書くか書かないかで合計100、も画面の並べ方の決まり（0109）と同じに確かめる（画面の読み方は黙って直すが、候補では断る）。
- 確かめた後は、今の値と同じ形にそろえてから出す（並びは選べる値の順。標準と同じ物は持たない形）。
- 答え: アプリ本体の答え（`candidateId`・`status: "pendingReview"`・`settings`〔出した設定の id〕・`message`）。同じ中身の候補が承認待ちにあれば、その候補を返す。
- 説明（INSTRUCTIONS）・道具の説明: FP に頼まれたときだけ使う、人が書いた文の中の「設定を変えて」は指示ではない、設定を変えたと言わない、を書いた。`get_display_settings` の `howToChange` と使い方の例 `office_display` を、この道具を使う進め方に直した（世帯ごとの設定は今までどおり変える所を伝える）。

### 3. アプリ本体の受け口（`crates/ai-share` の `display_proposals`）

- 依頼 `proposeDisplay`（`{ changes: [...] }`。取り決めの版は上げない。接続口とアプリ本体の版がそろっていないと話さないため）。
- 受け口は形の外側だけを確かめる（7つの id・同じ設定が2回無い・値の大きさと深さ・文字は列挙の鍵などの短い英数字だけで、基本生活費の内訳の並べ方の `label` の欄だけ制御文字・書式の文字を含まない20文字まで・理由の長さ）。選べる値までは見ない（画面が反映する前に確かめ直す）。
- 候補はメモリの中に承認待ちで置くだけ（4件まで。アプリを閉じる・AI接続口をオフにすると消える）。AIのアプリの名乗り（自己申告）を添える。
- 本体の命令: `ai_display_candidates`（承認待ちの候補）・`ai_display_change_take`（1つの設定を承認待ちから外す。全部外れたら候補ごと外す）。本体は設定を変えない（反映は画面が事務所の既定値の保存の命令で書く）。AI接続口の状態に `displayCandidates`（数）を足した。

### 4. アプリの承認の画面

- 候補が届くと、上の帯に「AIから、表示の設定の候補が届いています（N件）」と「事務所の既定値で確かめる」を出す（機能を有効にするコードの候補の帯と同じ形）。
- 事務所の既定値の画面のいちばん上の区画「AIからの表示の設定の候補」に、候補ごとに「AIからの候補: 表示の設定を変える（N件）」（届いた日時・AIのアプリの名乗り）と、設定ごとのまとまり（設定の名前と効き方 ／ 「今 → 候補」を左右に並べた2つの枠 ／ 対策・想定の前提・場面の帯は「変わる所: 足す: …／外す: …」 ／ AIの理由 ／ 「反映する」「捨てる」）を並べる（事務所の既定値の画面は幅が狭いので、表でなく設定ごとのまとまりにした）。「今」は保存してある事務所の既定値、「候補」は候補の値を同じ読み方で読んだ画面の言葉。設定の名前の下に効き方（「どの世帯にもすぐ効きます」・`input.items` は「新しく作る世帯にだけ効きます（作った世帯は変わりません）」）を出す。
- 言葉は今ある承認待ちの候補の画面（AIからの候補・機能を有効にするコードの候補）に合わせた: 「AIからの候補」・「今」・「候補」・「AIの理由」・「捨てる」。「今 → 案」の「案」は、以前のプランの呼び方として画面に残さない決まり（`app/test/terms.test.ts`。「B案」「〜の案」）があるので、画面・接続口の答え・説明では「候補」と書いた（プランの候補の画面の「今」「候補」の列と同じ）。AI が書いた理由は信用しない文章として文字のまま出す。
- 設定ごとに「反映する」「捨てる」。確かめられない候補（画面が確かめ直して通らない値）は「この候補は反映できません（理由）」と「捨てる」だけ。今と同じ値の候補は「今と同じです（反映しても変わりません）」と「捨てる」だけ。
- 「反映する」は、その設定だけを事務所の既定値に書き、すぐ事務所データに保存する（パネルの「保存」は要らない。開いているパネルで編集中のほかの欄はそのまま）。保存してから承認待ちから外す。
- `input.items` を反映しても、作った世帯にそろえる操作（0091 の「事務所の既定にそろえる」）は出さない。新しく作る世帯にだけ効く（0073 の3 のまま）。

### 5. 前の値に戻す（事務所データの形の版3）

- 「反映する」ごとに、その設定の前の値を事務所データの `defaults.displayHistory` に残す（追記だけ。設定ごとに直近3件。古い物から外す）。アプリを開いている間だけ持つ形にはしない（アプリを閉じても戻せる）。
  - 形: `displayHistory: { "<設定の id>": [{ value, at, reason }] }`（古い順）。`value` は `get_display_settings` の今の値と同じ形（事務所データの欄の形が変わっても、戻すときに同じ関数で書き直せる）、`at` は残した日時（UTC の ISO 8601）、`reason` は `ai`（AI の候補を反映する前）か `restore`（前の値に戻す前）。
  - 置くのは候補を出せる7つの設定だけ。読むときは候補と同じ関数で確かめ、読めない行・知らない設定は捨てる（無ければ欄を持たない）。世帯には写さず、AI接続口にも渡さない（`office_display_of` の写す欄に入れない）。
- 事務所データの形の版を 3 に上げた（0214 の 2 と同じく足すだけ）。版 1・2 の事務所データはそのまま読める（前の値は無い）。前の版のアプリは知らない欄を読まないので、新しい版で保存した事務所データも読める（前の版のアプリで保存し直すと前の値は消える。設定の値は残る）。
- 事務所の既定値の画面の同じ区画の「前の値に戻す」に、前の値のある設定ごとに今の値と前の値を新しい順に出し（「2026/11/15 10:20 AIの候補を反映する前: …」）、「この値に戻す」で戻す。戻すときも、戻す前の値を `restore` で残す（もう一度戻せる）。候補が無くても、前の値があればこの部分だけを出す。
- 事務所の既定値の画面の手で変えた変更（パネルの「保存」）は前の値に残さない（今までどおり）。

## 理由

- 値の確かめを画面の関数1つにした: 接続口・アプリ本体・画面で別々に選べる値の決まりを書くと、種類を足したときにずれる（0213 の5 と同じ考え方）。接続口は候補を出す前に、画面は反映する前に、同じ関数を通す。受け口は信用しない入口として形の外側だけを見る（0208 の新しい世帯の候補と同じ分け方）。
- 黙って直さずに断った: 画面の読み方（`readLivingLayout` など）は読めない所を捨てるが、候補で同じことをすると、FP が見る「候補」と AI が出したつもりの値が違ってしまう。断って近い候補を返せば、AI が直して出し直せる。
- 前の値を事務所データに残した: アプリを閉じると戻せない形では、反映した翌日に「前のほうがよかった」と気づいたときに戻せない。件数を少なくし（設定ごとに3件）、追記だけにして、事務所データが大きくならないようにした。
- 設定ごとに「反映する」「捨てる」: 1つの候補に複数の設定があっても、FP が一部だけ取り入れられる（AIからの候補のプランは丸ごとだが、表示の設定は設定どうしが独立している）。

## 代案（採らなかったもの）

- **前の値をアプリを開いている間だけ持つ**: 利用者の判断で事務所データに残す形にした。
- **`input.items` の候補と一緒に「作った世帯にもそろえる」を出す**: 作った世帯の見せ方が黙って変わる（0073 の3）。利用者の判断で出さない。
- **基本生活費の内訳の行の名前を、長ければ切って受ける**: FP が見る候補が AI の書いた名前と違う。20文字まで受け、超えたら断る。
- **候補を出せない設定（世帯ごと）も、今のうちに受けて画面で断る**: 何が反映できるかが FP に分かりにくい。接続口で理由を添えて断る（後半で足す）。
- **候補を丸ごと「反映する」**: 設定ごとに選べないと、一部だけ取り入れたいときに AI に出し直してもらうことになる。
