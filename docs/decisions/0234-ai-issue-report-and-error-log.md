# 0234. AI に不具合を調べてもらい報告の文をまとめる・画面のエラーの記録

- 状態: 採用（一部未確定）（2026-11-20）
- 固定の強さ: エラーの記録を残すのはこの PC のアプリのデータだけ・どこにも送らない・世帯の中身（名前・金額・生年月日・メモ）とファイルの場所（PC のユーザー名）と世帯を識別する値を残さない・AI が読めるのはアプリが起動していて AI接続がオンのときだけ（読むだけ）・報告の文を URL に載せない・AI からフォームを開かない・アプリは何も送らないは骨格（0087 の6・0015 の2 のとおり）。道具 `get_error_log`・`draft_issue_report` と頼み方 `report_issue` の名前と入出力は試験版。記録のファイルの形・件数の上限・文の削り方・画面の言葉は内部
- 前提にする記録: 0087 の6（要望・不具合の受付番号。フォームには受付番号・版・OS だけ）、0015（AI接続。起動中の道具の決まり・自動の通信先を増やさない）、0014（AIに渡した記録）、0199（使い方の例）、0213（世帯の中身でない読み取りは記録に残さない）、0227（画面の操作の手引き）

## 背景

- FP が「この世帯の計算がおかしい」「計算できない」と気づいても、入力のせいか計算の仕組みのせいかを自分で見分けるのは難しい。AI接続には、画面と同じ計算（calculate）・入力の確かめ（check_inputs）・数字の根拠（explain_value）があり、AI が調べられる材料はそろっている。
- 「要望・不具合を送る」（0087 の6）はフォームを開くだけで、何をどう書けば直す側が再現できるかの手がかりが無い。お客さまの世帯の値をそのまま書かれると、0087 の6 の「世帯の情報は書かない」に反する。
- 画面や本体で起きたエラーは、今は画面の帯に一度出るだけで、後から何が起きたかを確かめられない。
- 利用者の判断（2026-11-20）: AI に不具合を調べて報告の文をまとめてもらう頼み方を足す。画面のエラーの記録も今回入れる。

## 決定

### 1. 不具合を調べて報告の文をまとめる頼み方と道具

- 頼み方（MCP のプロンプト）`report_issue`「不具合を調べて報告をまとめる」。引数は `household`（share_id か見本の id。省くと渡されている世帯を確かめる）と `what`（何がおかしいか。省くと最初に FP に聞く）。進め方を文で渡す:
  1. `get_error_log` でエラーの記録に関係しそうな行を見る（読めなければ FP に「エラーの記録」を写して貼ってもらう）。
  2. `check_inputs` で入力の確かめを引く。3. `calculate`・`explain_value` で、おかしいと言われた行と年の数字と根拠を取り出す。
  4. 見立て: 「入力が原因（ここを直せば戻る）」か「計算の仕組みの不具合の疑い」か。推測で決めつけず、根拠の道具の答えを示す。足りなければ「まだ分からない」。入力が原因なら、直した場合に戻ることを `calculate` の `changes` で確かめる。
  5. 再現: 見本の世帯（`list_sample_households`・`get_sample_household`）に変更を足し、`calculate` の `input` で同じことが起きるかを確かめる。お客さまの名前・生年月日・実際の金額・世帯を識別する値は使わない。見本で再現できず実際の値が要るときは、そう書いて FP の判断に任せる。
  6. `draft_issue_report` で報告の文にする。7. FP に「要望・不具合を送る」で「フォームを開く」を押して貼るよう伝える。入力が原因なら、送らなくてもアプリで直せることを先に伝える。
- 道具 `draft_issue_report`（単体の群。アプリが起動していなくても使える。読むだけの扱い）: AI が渡した `summary`・`screen`・`row`・`when`・`expected`・`actual`・`diagnosis`（`input`・`calculation`・`unknown`）・`evidence`（1〜20件）・`fix`・`sample_household_id`・`reproduce_changes`・`reproduce_steps`・`reproduced`・`error_log_lines` を、決まった見出し（何が起きたか・場所・期待した値・実際の値・AI の見立て・根拠・直し方・再現の手順・見本での再現・エラーの記録）で並べ、アプリの版と、入れていない値の一文と、最後に FP の送り方（「要望・不具合を送る」→「フォームを開く」→ 貼る）を添えた `text` を返す。
  - 見本の id は見本の一覧で確かめ（無ければ断る）、題と id を手順の1行目に書く。見本を書かなければ「見本の世帯では再現できていません。実際の世帯の値が要るかは、FP が決めてください。」と書く。
  - 共有の ID（`s-` と16進）の形の値は伏せる。年・月・日のそろった日付（生年月日かもしれない）は注意（`cautions`）を添える（エラーの記録の行の日時は見ない）。名前は形で見分けられないので、説明と頼み方で書かないよう伝え、FP が `text` を見て確かめる。
  - 文を返すだけで、送らない・フォームを開かない・URL に載せない。フォームの URL に差し込むのは今までどおり受付番号・版・OS だけ（0087 の6 の骨格。報告の文を URL の欄に足す案は採らない）。
- 説明（INSTRUCTIONS）と「できること」の頼み方にも、不具合を調べるときの進め方を1つ足す。

### 2. エラーの記録（この PC の中だけ）

- **置き場所**: アプリのデータの場所の `errors/log.json`（開発用のビルドは `errors-dev/`、試験用のデータフォルダ `FINANCIA_DEV_STORE_DIR` があればその中の `errors/`）。お知らせの手元の状態（`notices/local.json`）と同じ置き方。どこにも送らない（自動の通信先を増やさない）。世帯ファイル・事務所データには書かないので、どちらの形式の版も変えない。記録のファイルは自分の形式名 `financia-error-log` と版 `1.0` を持ち、読めない・大きすぎる（512 KiB を超える）・形式の違うファイルは読まずに空から始める。
- **記録する所**（既存のエラーの扱いを調べて決めた）:
  | どこで | 何を | 種類 |
  |---|---|---|
  | 画面の想定外のエラー（`window` の `error`・`unhandledrejection`。`main.tsx`） | エラーの名前と文 | 画面のエラー |
  | 本体の命令の失敗（`engine/host.ts` の `invoke` を1か所で包む。画面の try/catch・保存の失敗・開けない世帯・前の世代での開き直しなど、本体に頼む所はすべてここを通る） | 命令の名前と返ったエラー（本体の命令は `E_…` の符号を返す） | 本体の命令の失敗 |
  | 計算できなかったとき（エンジンの失敗。結果の帯の「計算できませんでした」と、数字の根拠） | エラーの符号だけ（制度データに値が無いときは値の ID も。時期は世帯の生年月日などから決まるので残さない） | 計算できなかった |
  | 本体が想定外に止まったとき（Rust の panic。本体が自分で残す） | 削った文と、止まった所のファイルの名前と行だけ | 本体の想定外の停止 |
  - 画面の try/catch が自分で受けて文にしているエラー（保存の失敗の帯・開けない世帯の文など）は、もとは本体の命令の失敗なので、命令の所で1回だけ残す（画面の文は世帯の名前を含みうるので残さない）。記録そのものの命令（`error_log_*`）の失敗は残さない（繰り返さない）。
  - 本体がまだ用意できていない起動の途中のエラーは、画面が20件まで覚えておき、用意できたら渡す。
- **残すもの**: 日時（最初と最後）・回数・アプリの版・OS（おおまかな名前）・画面（上のタブの名前。起動の途中は「起動」、本体は「本体」）・操作（決まった言葉か「世帯の保存（store_save）」のような命令の名前）・種類・削った文・（止まったときだけ）止まった所。
- **残さないもの**: 世帯の中身（名前・金額・生年月日・メモ）・ファイルの場所（PC のユーザー名）・世帯を識別する値（内部 ID・共有の ID・顧客番号）・命令の引数。画面から本体へ渡す欄は種類・画面・操作・文の4つだけで（ほかの欄は断る）、日時・版・OS は本体が入れる。
- **文の削り方**（本体の `errlog.rs` の1か所。エラーの文に世帯の中身やパスが混ざりうるので、残す前に必ず通す）:
  1. 4,000 文字で切り、改行などの制御文字を空白にする。
  2. 引用符（' " ` “” ‘’ 「」 『』）の中は、短い英字の名前（プロパティの名前など。英字で始まる英数字と _ $ . の40文字まで）のほかは … に伏せる。閉じは一番後ろの閉じまで取る（JSON の切れ端のように入れ子になっていても間の言葉を残さない）。閉じていなければ、そこから後ろを伏せる。
  3. `/`・`\`・`://`・`file:` を含む語（ファイルの場所・URL）は <場所>、`@` を含む語は <メール> に伏せる。
  4. 日本語など ASCII の外の文字の並びは … に伏せる（お客さまの名前は日本語のことが多く、形で見分けられないため。何が起きたかは画面・操作・種類の決まった言葉で表す）。
  5. 数字を含む語（金額・日付・内部 ID・顧客番号・位置）は # に伏せる。エラーの符号（`E_` で始まる英大文字・数字・_）だけは残す。
  6. 300 文字で切る。空になったら「（文なし）」。
  - 画面・操作の言葉は、画面のコードの決まった言葉（型で決めた言葉か命令の名前）だけを渡す。本体は念のため、かな・漢字・英字と _ ・ （ ）のほかを落とし（数字は残らない）、`/`・`\`・`@` を含む言葉は「—」にし、40 文字で切る。
  - 残る限界: 引用符の外の ASCII の言葉（ローマ字の名前など）が、画面のコードの作った文に入っていれば残りうる。画面のコードはエラーの文に世帯の値を入れない（本体の命令は符号を返す）。FP は写す前に一覧で中身を見られる。
- **件数と忘れ方**: 同じ版・種類・画面・操作・文（削った後。数字だけ違う文は同じになる）のエラーは1件にまとめ、回数と最後の日時を進めて先頭へ（同じエラーが続いても件数を食わない）。上限は 100件で、最後に起きたのが古いものから忘れる。
- **FP が見る・写す・消す**: 「要望・不具合を送る」の下に「エラーの記録（N件）」を置く。新しい順の一覧（日時・画面・操作・種類・文・回数）、「記録を写す」（報告に貼る文。本体が記録から作り、OS のクリップボードに写す。画面からは文を受け取らない。写せないときはブラウザの仕組みで写し、それもだめなら文を出して選んでもらう）、「記録を消す」（「すべて消す」で確かめてから。AI が読んだ回数も消す）。日時はこの PC の時刻で出す（画面が時差を本体に知らせ、本体が写す文と AI に渡す文の日時に使う）。

### 3. AI が読む道具（`get_error_log`）

- アプリが起動していて AI接続（事務所全体の設定）がオンのときだけ読める（受け口が開いているときだけ。オフのときは受け口が無いので「アプリが起動していないか、AI接続がオフ」と断り、FP に「エラーの記録」を写して貼ってもらうよう案内する）。世帯を渡していなくてよい。読むだけで、消す・送る道具は無い。
- 返すのは新しい順に `limit` 件（既定30・100まで）の1件ごとの日時・回数・版・OS・画面・操作・種類・文と、報告に写せる1行（`line`。この PC の時刻）。
- 依頼 `getErrorLog`（ai-ipc。取り決めの版は変えない: 新しい依頼を足すだけで、古い接続口は送らない。接続口とアプリは同じ版でしかつながらない）。アプリは台帳に読む所（`set_error_log`）を入れ、無ければ断る。
- **記録**: エラーの記録は世帯の中身ではなく、どの世帯で起きたかも分からないので、世帯ごとの「AIに渡した記録」（0014）には残さない（0213 の事務所の既定値の読み取りと同じ考え）。代わりに、AI が読んだ回数と最後の日時をエラーの記録の中に残し、「エラーの記録」に「AI がこの記録を読んだのは N回です（最後は …）」と出す。

## 理由

- 報告の文を AI に組み立てさせても、送るのは FP がフォームで行えば、0087 の6 の骨格（アプリは送らない・フォームの URL に入るのは受付番号・版・OS だけ）を変えずに済む。決まった見出しにすると、直す側が再現の手順と見立ての根拠を毎回同じ所で読める。
- 再現を見本の世帯に変更を足す形にすると、お客さまの値を出さずに、直す側が同じ入力を作れる。見本で再現できないときに AI が実際の値を勝手に書かないよう、FP の判断に任せる。
- エラーの記録は、本体の命令の1か所（`invoke`）と画面の想定外のエラーの口で、ほとんどの失敗を拾える（画面の try/catch を1つずつ直さない）。文は世帯の中身が混ざりうるので、「形で見分けられない物（名前）は ASCII の外ごと伏せる」「数字は伏せる」の保守的な側を選んだ。調べるのに要るエラーの符号・英語のエラーの文・プロパティの名前は残る。
- 同じエラーをまとめると、計算できない入力のまま打ち続けたときでも、上限の100件がすぐに埋まらない。

## 代案（採らなかったもの）

- 報告の文をフォームの URL の欄に載せる・AI からフォームを開く: 0087 の6 の骨格（URL に入るのは受付番号・版・OS だけ）に反し、世帯の値が URL に残りうる。採らない。
- アプリがエラーの記録を配信元に自動で送る: 自動の通信先を増やさない決まり（0015・0017）に反する。採らない。
- 画面の文（帯の「計算できませんでした（…）」など）をそのまま残す: 制度データに値が無いときの時期など、世帯の生年月日から決まる値が入る。採らない（符号と値の ID だけ）。
- エラーの記録を世帯ファイルに置く: どの世帯で起きたかを結びつけることになり、世帯ファイルの形式の版も上がる。採らない。
- AI が読むたびに、開いている世帯の「AIに渡した記録」に残す: 記録は世帯の中身ではなく、どの世帯にも結びつかない。採らない（読んだ回数はエラーの記録の中に残す）。

## 影響

- 世帯ファイル・事務所データの形式は変えない（版も上げない）。AI接続の取り決めの版も変えない（依頼を足すだけ）。
- 画面から呼べる命令が4つ増える（`error_log_add`・`error_log_get`・`error_log_clear`・`error_log_copy`。capabilities にも足す。パスは受け取らない・返さない。写す命令は文を受け取らない）。
- AI接続の道具が2つ（`get_error_log`・`draft_issue_report`）、使い方の例が1つ（`report_issue`）増える。手引き（`docs/app-guide/01-households.md` の `app.notices`、`09-ai.md` の `ai.issueReport`）と `docs/ai-connector.md` に足した。

## 試験での確認

- 本体（`app/src-tauri/src/errlog.rs`）: ファイルの場所（Mac・Windows・file:）・日本語の名前・金額・生年月日・JSON の切れ端・内部 ID・共有の ID・顧客番号・メール・閉じていない引用符の後ろが残らない。英語のエラーの文・プロパティの名前・符号は残る。300文字で切る。同じエラーは1件にまとめて回数と最後の日時を進める・数字だけ違う文はまとまる・上限100件で古いものから忘れる・0件の文。画面から panic と知らない種類は足せない・4つのほかの欄は断る。壊れた・違う形式のファイルは空から。AI が読んだ回数。止まった所はファイルの名前と行だけ。写す文の日時はこの PC の時刻。
- 接続口（`crates/lifeplan/tests/mcp_connector.rs`・`issue.rs`）: アプリが起動していない（AI接続がオフも同じ）と読めず、写して貼る案内。読む所が無ければ断る。起動していれば新しい順に limit 件。知らない引数は断る（読まない）。報告の文の見出し・見本の id の確かめ・見本なしは FP の判断・共有の ID を伏せる・生年月日のような日付の注意（エラーの記録の日時では出さない）・長い文を切る・間違った見立て。頼み方が一覧に出て、書いた道具の名前がすべて今ある道具であること。
- 画面（`app/test/error-log.test.ts`）: 画面から渡すのは4つの欄だけ・起動の途中のエラーを後で渡す（20件まで）・記録に失敗しても止めない・本体の命令の失敗は命令の名前と文を残して投げ直し、引数（世帯の ID）は渡さない・記録の命令は記録しない。「エラーの記録」の0件・一覧の順・回数・AI が読んだ回数。

## 未確定

- 文の削り方で、引用符の外の ASCII の言葉も伏せるか（調べやすさとの釣り合い。β公開の前に、実際に残った文を見て決める）。
