# 0221. 明細の写真・スクショの文字を PC の中で読む試し（OS の文字認識で読める度合い。0034 の段階3の前段）

- 状態: 提案（2026-11-17。試しの結果。次の PR で読み手を作る前に、下の「決めてほしいこと」を決める）
- 固定の強さ: 次は 0034 の2 のとおり骨格: 写真・スクショ・画像だけの PDF の明細は外の AI・外のサービスに送らず、PC の中の OS の文字認識で読む（macOS は Vision、Windows は Windows.Media.Ocr を本体から呼ぶ）。本体の命令 `statement_ocr` の形（画像のバイト列を受け、`[{text, x, y, w, h, conf?}]`〔画像に対する 0〜1 の割合・左上が原点〕を返す）は試験版。測る道具（`statement/scripts/ocr-*.ts`）・架空の画像・測り方は内部（後から変えてよい）
- 前提にする記録: 0034（明細の取り込み。2 外に送らない・番号を消す、3 読み手と欄の表）、0016（画面から呼べる命令）、0021（依存のライセンス）

## 背景

- 0034 は段階3（スクショ・写真の文字認識）を後に回していた。文字の入っていない PDF は「段階3と案内する」で止めている（`S_PDF_NO_TEXT`）。
- 明細の写真・スクショを外の AI に送ると、カード番号・店の名前（通院先など）が外に出る。0034 の2 の方針（外に送らない）に合わせ、OS に入っている文字認識だけで足りるかを、画面に組み込む前に測ることにした。
- 読んだ文字の塊を `TextItem {x, y, width, size, text}` にすれば、文字の入った PDF と同じく `toLines()`（`statement/src/pdf/text.ts`）から先の流れに乗る、という前提を確かめる。

## この試しで作ったもの

1. **本体の命令 `statement_ocr`**（`app/src-tauri/src/statement.rs`。部品は `crates/statement-ocr`）: 画像（PNG・JPEG・BMP・TIFF・GIF・HEIC。10MB まで）のバイト列を受け、文字の塊を返す。ファイルを書かない・ネットにつながない。別のスレッドで読む。
   - macOS: Vision の `VNRecognizeTextRequest`（正確さを優先・言語の補正あり・日本語→英語の順）。部品は `objc2-vision`（Zlib OR Apache-2.0 OR MIT）。座標は Vision の左下原点を左上原点にそろえる。`conf` は Vision の確からしさ。
   - Windows: `Windows.Media.Ocr`（入っている文字認識のうち「ja」で始まる言語）。部品は `windows`（MIT OR Apache-2.0。Tauri が使っている版と同じ 0.62）。画像はメモリの中のストリームで読み、`MaxImageDimension` を超えれば縮める。1行の中の単語は、隙間が文字の高さの 0.9 倍以下ならつなぎ（両側が半角のときだけ空白をはさむ）、表の欄をまたいではつながない。`conf` は無い。
   - Linux など: `E_OCR_UNSUPPORTED`（読めません）。日本語の文字認識が入っていない Windows は `E_OCR_NO_LANGUAGE`。
   - 画面には組み込んでいない（許可 `allow-statement-ocr` だけ足した）。番号を消すのは、受け取った画面の部品（statement/）が読み手の中で行う（0034 の2 と同じ）。
2. **架空の明細の画像**（`statement/test/fixtures/ocr/`。作り方は `statement/scripts/ocr-images.ts`。Chrome の canvas で描いて崩す）: 店・カード会社・銀行の名前はすべて架空（0034 の追記 2026-11-01 の決まり。銀行は「ほしぞら銀行」）、番号はすべて 0 の並び、どの画像にも「見本（架空のデータ）」を入れた。
   - カードの明細の PC のスクショ（等倍・16件）、スマホのスクショ（3倍・1件が2行・10件）、銀行の入出金明細のスキャン（明朝・グレー・0.6度の傾き・ざらつき・JPEG・8件）、紙のカードの明細の写真（3度の傾き・ぼけ・明るさむら・JPEG・16件）、小さい字（字の高さ 9 画素・24件）、電気の請求書（1件）、携帯の請求書の写真（1.5度の傾き・3件）
   - 前処理を当てた画像: 拡大2倍・二値化（周りの平均と比較する方法）・傾き直し（暗い点の横の数え方で角度を推し量る。推し量った角度は描いた角度と 0.1 度まで一致）とその組み合わせ（9枚）
   - 正解（`truth.json`）: 件ごとの日付・店の名前・金額と、描いた文字の塊（文字が完全に読めたときの `toLines()` への入力）
3. **測り方**（`statement/scripts/ocr-measure.ts`。CI は `.github/workflows/statement-ocr.yml`。この部品・画像・道具が変わった PR と、手で起動したときだけ流す）:
   - **文字**: 正解の日付・金額・店の名前の文字が、読んだ文字の中にいくつあるか（NFKC・空白を除いてそろえる）。表の形に関係しない、文字認識そのものの読める度合い。
   - **表（今の組み立て）**: 読んだ文字の塊 → `toLines()` → PDF の読み手の後半（`linesToTable`。この PR で `pdfTextReader` から分けた。動きは変えない）→ `readStatement` の行を、正解の行と比較し、日付・金額・店の名前がすべて正しい行の割合を出す。「理想」は描いた文字の塊（文字が完全に読めたとき）を同じ流れに通した結果。
   - **表（組み立ての試し）**: 次の PR の読み手の候補として、(1) 文字の塊の並びから傾きを推し量って座標を回す、(2) 行は塊の上下の中心でまとめる、(3) 見出しの行の塊の位置で欄を決め、各行の塊を重なる欄に入れる（空の欄を詰めない）、を足した組み立て。src/ には入れていない（測る道具の中だけ）。

## 考察

1. **Mac（Vision）は足りる。** 文字としては、日付はどの画像も 100%、金額は 88〜100%、店の名前は小さい字（58%）を除いて 81〜100%。請求書は3つの値（発行元・金額・日付）がすべて読めた。弱いのは字の高さ 9 画素ほどの小さい字の濁点・半濁点（ぞ→そ、ぜ→ゼ）と似た漢字（電→犯）、3桁の小さな金額の取りこぼし、「PAYPAY*」の「*」。1枚 0.3〜1.8 秒。
2. **Windows（Windows.Media.Ocr）は、日本語のままでは足りない。** スクショ（PC・スマホ）と請求書はおおむね読める（PC のスクショは試しの組み立てで日付・金額 100%・店 81%）が、明朝の銀行のスキャン・斜めの写真・小さい字では、数字を日本語の字と取り違える（「1」→「」」「川」「ー」、「0」→「田」「当」、「6,200」→「6.28」）・桁の区切りの「,」を「.」と読むため、金額が 0〜47% になる。速さは 1枚 0.05〜0.2 秒で十分。
   - 数字は英語の文字認識の方がはるかに正しい（上の比較）。**日本語で店の名前を、英語で数字を読み（同じ画像を2回読む。どちらも PC の中）、日付・金額の欄だけ英語の結果を使う**と、写真・スキャンでも金額 9 割台まで届く見込み（金額の読み替えの決まり「数字.3桁 → 数字,3桁」も要る）。小さい字は英語でも半分ほどで、拡大しても良くならなかった。
3. **いちばんの壁は文字認識より組み立て（行と欄）。** 今の `toLines()`→`linesToTable` は、文字が完全でも、(1) 0.5 度ほどの傾きで右の欄が次の行に落ち、(2) 空の欄（銀行の出金・入金のどちらか）が詰まって列がずれ（理想でも 0%）、(3) 見出しの欄どうしが近いとつながって列の数が変わる。試しの組み立て（文字の塊の並びから傾きを推し量って座標を回す・行を塊の上下の中心でまとめる・見出しの塊の位置で欄を決める）で、Mac は PC のスクショ 94%・銀行のスキャン 88%・斜めの写真 81% まで上がった（今の組み立ては 88%・25%・0%）。どれも理想（文字が完全なとき）は 100%。
4. **前処理（画像を直す）の効き目**:
   - 傾き直し: 今の組み立てでは効く（斜めの写真 0%→81%）が、試しの組み立ての座標の傾き直しで同じ効き目が出る（94%）。画像を回す処理は要らない見込み。
   - 拡大2倍: Mac の小さい字の店の名前は 58%→88%（行 58%→75%）に上がったが、落ちた金額は戻らない。Windows は日付が上がる（58%→100%）が金額は 0%→8% にとどまる。小さい字だけ拡大して2回読むのは試す価値がある。
   - 二値化: どちらの OS でも悪くなった（Mac は銀行のスキャンの見出しの「摘要」「残高」を読み違えて店の列を失い 0%、斜めの写真の店 81%→38%）。OS の文字認識は自然な画像で学んでいるので、二値化はしない。
5. **形の違う明細は読み手で分ける。** スマホのスクショ（1件が2行: 店と金額、その下に日付）は、どちらの組み立てでも理想 0%（文字は 100% 読めている）。請求書（1枚に1〜数件）は表ではないので、見出しの言葉（ご請求金額・お支払期日・発行元）から値を拾う読み手が要る。
6. 番号: 読んだ文字は今の読み手の流れ（`maskCell` と `readStatement` の二重の消し方）を通るので、0034 の2 のとおり外へは出ない。画像のカード番号の行（「0000-XXXX-XXXX-0000」）は Windows では「OOOO-XXXX-…」と英字で読まれることがあり、番号の消し方（A の「数字と伏せ字が10字以上」）に当たらない形がありうる（次の PR で、文字認識の結果には英字の O・I・l を数字と見なして当てる決まりを足すか決める）。

## 決めてほしいこと（次の PR の前に）

おすすめ: **このまま進める。前処理（画像の加工）は足さず、組み立てを直す。Windows は「数字だけ英語で読み直す」を足し、写真・小さい字は案内で補う。**

1. 読み手の組み立てを、試しの形（座標の傾き直し・上下の中心で行・見出しの位置で欄）で作るか。文字の入った PDF の読み手（`pdfText`）にも同じ組み立てを使うか（PDF も空の欄で列がずれる。版を上げて取り込みの記録に残す）。
2. Windows で「日本語で読む＋英語で数字を読み直す」（1枚を2回読む。0.1〜0.4 秒）を入れるか。金額の「数字.3桁 → 数字,3桁」の読み替えを文字認識の結果にだけ当てるか。
3. Windows で日本語の文字認識が入っていないとき（`E_OCR_NO_LANGUAGE`）の案内（「設定 → 時刻と言語 → 言語 → 日本語 → オプション → 光学式文字認識」を足す）を出すか、英語だけで数字を読み、店の名前は FP が入れる形にするか。
4. 写真・スキャンの読み取りの品質の案内: 「スクショか、真上から明るく撮った写真で。小さい字は拡大してから」と画面に出すか。Windows で写真・小さい字を読むときに「読めた行を確かめてください」と強めに出すか（どちらの OS でも、読んだ行は今の取り込みの画面で FP が確かめて取り込む。0034 の9）。
5. スマホのスクショ（1件が2行）の読み手と、請求書（電気・携帯など1枚に1〜数件）の読み手を、次の PR に入れるか、その次にするか。請求書は、0034 の8 の口座の扱い（どの口座の明細として入れるか）と一緒に決める。
6. 文字認識の結果に、番号の消し方の決まりを英字の O・I・l も数字と見なして当てるか（上の考察の6）。
7. 架空の画像（約 3MB）をリポジトリに置き続けるか（測り直しには要る。作り直すと OS の字形で少し変わる）。

この PR でしていないこと: 画面への組み込み、読み手（statement/ の画像・画像だけの PDF）、請求書の口座、AI に聞く仕分け。
