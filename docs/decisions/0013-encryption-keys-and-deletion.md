# 0013. 暗号化・鍵・完全削除

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。鍵の3段、鍵置き場、復元キーの中身、完全削除の考え方は骨格。復元キーの見せ方（文字の並べ方）や画面の文言は後から変えてよい

## 背景

FPのPCには、多数の顧客世帯のデータが保存される。PCの紛失・盗難、同期サービスへの写し、バックアップの持ち出しのどれでも中身が読まれないよう、保存データは常に暗号化する。一方で、面談のたびにパスワードを打たせると使われなくなるので、普段はパスワードなしで開けるようにしたい。また、顧客から削除を求められたときに、バックアップを含めて確実に読めなくする「完全削除」が要る。

この3つ（常に暗号化・普段は入力不要・完全削除）を同時に満たす鍵の形を、最初の版で固定する。後から変えると、配布済みの全世帯ファイルの再暗号化が要る。

関連: 世帯ファイルの封筒は 0011、持たない情報は 0012、書き出しの暗号は 0020、AI接続口の許可は 0015。

## 決定

### 1. 保存データは常に暗号化する

- 暗号化するもの: 世帯ファイル、控えのPDF（宛名なし。0009）、事務所データ、鍵置き場、自動バックアップ、AIへの許可の台帳。
- 暗号化をOFFにする設定は作らない。平文で出るのは、FPが明示的に書き出したものだけ（0020）。
- 暗号の方式: **AES-256-GCM**（鍵は256ビット、ナンス（使い捨ての乱数）は保存のたびに96ビットの乱数）。方式の名前は封筒に書き、将来の方式の追加に備える（0011）。
- 改ざん検出の対象（付加データ）は、封筒の見出しのJSON全体とする（形式の版・世帯の内部ID・保存の世代番号・鍵のIDを含む。項目は 0011）。これにより、別の世帯のファイルとの入れ替えや、古い世代を新しい世代と偽って差し込むことを検出する。
- 復号はアプリ本体（Rust）だけが行う。鍵と復号した世帯データを、画面（WebView）の保存機能・ログ・一時ファイルに置かない（0016）。使い終わった鍵はメモリから消す。

### 2. 鍵の3段

```
OSの資格情報の保管庫
  └─ 事務所の親鍵（32バイト）
       └─ 鍵置き場ファイル（親鍵で暗号化）
            └─ 世帯ごとの鍵（32バイト、世帯ごとに別）
                 └─ 世帯ファイル・控えのPDF（世帯の鍵で暗号化）
```

- **事務所の親鍵**
  - 事務所データを最初に作ったときに乱数で作る。
  - 置き場所はOSの資格情報の保管庫: Mac はキーチェーン（ログインキーチェーン）、Windows は資格情報マネージャー（ユーザーのログインに結び付いた DPAPI で守られる）。
  - 項目の名前: サービス名はアプリの識別子 `com.fprise.lifeplan`、アカウント名は事務所ID。開発用のビルドは `com.fprise.lifeplan.dev` を使い、製品の鍵に触れない。フォーク（識別子を変えた版）は自分の識別子を使うので、公式版の鍵とぶつからない。
  - 親鍵には鍵IDを付け、鍵置き場に記録する（入れ替えに備える。下の6）。
  - 親鍵から、用途ごとの鍵を HKDF-SHA256 で導く（鍵置き場の暗号化用、許可の台帳の改ざん検出用など）。1つの鍵を複数の用途に直接使わない。
- **鍵置き場**（事務所データの一部。0011）
  - 中身: `{ 形式の版, 事務所ID, 親鍵の鍵ID, 確かめ値, 世帯の内部ID → { 世帯の鍵の鍵ID, 世帯の鍵 } }`。
  - ファイル全体を親鍵（から導いた鍵）で暗号化する。世帯の数や世帯IDも外から見えない。
  - 中の世帯の鍵は、「世帯の鍵であること＋世帯の内部ID」を改ざん検出の対象に入れて包む。別の世帯の欄と入れ替えても開かない。
  - 確かめ値（KCV）で、違う親鍵で開こうとしたことを、復号の失敗と区別して分かりやすく伝える。
- **世帯の鍵**
  - 世帯を作るときに乱数で作り、鍵置き場にだけ置く。世帯ファイルの中には入れない（入れると完全削除が成り立たなくなる。下の5）。
  - 世帯の鍵には、作るときに乱数の鍵ID（UUID 第4版。0004）を付け、鍵置き場に記録する。親鍵の鍵IDとは別のもの。
  - 封筒の「鍵のID」（`keyId`）は、この世帯の鍵の鍵IDで、どの世帯の鍵で暗号化したかを示す。封筒の項目の並びと名前は 0011 が正。

### 3. 復元キー

- 復元キーは**親鍵そのものを書き写せる形にしたもの**: 親鍵32バイト＋確かめ用4バイトを Base32 にした58文字を、4文字ずつ「-」で区切った**72文字**。
- 入力のときは、大文字・小文字、空白、区切りの有無を問わず、紛らわしい文字（0 と O など）を吸収する。確かめ用の4バイトが合わなければ「打ち間違いがあります」と出す（読み違いに気づかないまま進まない）。
- 初回に、復元キーの保管を強く勧める（印刷、またはパスワード管理のソフトへの保存）。保管するかどうかはFPが選ぶ。
  - 保管していない間は、起動時に定期的に促す。
  - **2台目のPCで使うとき、保存場所に同期フォルダを選ぶときは、復元キーの保管を必須にする**。
  - 「復元キーで実際に開けるか試す」機能を付ける（保管した控えが正しいかを、データを壊さずに確かめる）。
- 復元キーを使う場面: 親鍵が保管庫から消えた（OSの入れ直し、PCの故障・交換、保管庫の項目を誤って消した）、2台目のPCを設定する。復元キーを入れると、そのPCの保管庫に親鍵を入れ直す。
- 復元キーを保管せずに親鍵を失うと、全世帯とバックアップは誰にも読めなくなる（提供元にも戻せない）。画面と説明書でこの点を正確に伝える。

### 4. バックアップ・同期・2台目のPC

- **自動バックアップ**: 1日1回、暗号化したままの写しを作り、30世代持つ（世帯ファイル・事務所データ・鍵置き場）。
- **鍵置き場のバックアップは、アプリが決めた場所に、日ごとの世代で最大30日分だけ持ち、31日より古い世代は自動で消す**。作った世代は後から書き換えない（削除の処理に不具合があっても、全世代を一度に壊さないため）。
- 鍵置き場とその世代は、外のバックアップ・同期の対象から外す。
  - Mac: バックアップから除外する印（Time Machine の除外）を付ける。
  - Windows: 同期の対象になりやすい場所（OneDrive の既知のフォルダなど）の外、ユーザーごとのアプリのデータの場所に置く。
- **同期フォルダ**: 世帯ファイルは同期フォルダに置ける前提で作る（2台のPCでの同時編集は 0011 の親の改訂のIDで検出する）。2台で使う場合は、事務所データ（鍵置き場を含む）も同期フォルダに置くか、書き出して移し、どちらも復元キーで開く。
  - 鍵置き場を同期フォルダに置いた場合、同期サービスの版の履歴に古い鍵置き場が残る。このときの完全削除の範囲は下の5のとおり画面で案内する。
- 保存は「一時ファイルに書いて差し替える」方式で行う: 同じフォルダに一時ファイルを作る → 書く → ディスクへ同期 → 名前を差し替える → フォルダも同期する（Windows は上書きありの移動で差し替える。フォルダの同期は無い）。直前の世代を1つ残す。起動時に残った一時ファイルを片付ける。

### 5. 完全削除

- 世帯ごとに「完全削除」を最初の版から用意する（顧客からの削除の請求に応えるため。書き出しは 0020）。
- 完全削除で行うこと:
  1. 世帯ファイル、その直前の世代、控えのPDFを消す。
  2. 今の鍵置き場から、その世帯の鍵を消す。
  3. アプリが管理するその世帯のバックアップの写しを消す。
  4. 削除の記録（世帯の内部IDと日付だけ）を事務所データに残し、30日後に「完全削除が終わった」と画面で確かめられるようにする。
- 鍵置き場の古い世代には削除した世帯の鍵が残っているが、世代は30日で入れ替わるので、**アプリが管理する範囲では、最長30日で、どこにも読める鍵が無くなる**。画面には「削除しました。バックアップからも完全に読めなくなるのは30日後です」と出す。
- アプリの管理外にある写し（同期サービスの版の履歴、FPが自分で取ったバックアップ、Time Machine の古いスナップショットなど）は、アプリから消せない。削除の画面で、主な同期サービスでの消し方を案内する。説明では、この範囲を正確に書き、「すべて消えます」とは書かない。
- **特別な削除（親鍵の入れ替え）**: 30日を待たずに、またはアプリの管理外の写しも含めて読めなくしたい場合に備え、親鍵を新しくして全世帯の鍵を包み直し、古い親鍵を捨てる操作を設計に含める。世帯の鍵は変わらないので、世帯ファイルの再暗号化は要らない。ただし、古い親鍵（＝古い復元キー）の控えが残っていると古い鍵置き場の写しは開けるので、新しい復元キーの保管と古い控えの破棄が必要になる。この操作は親鍵が漏れた疑いのあるときにも使う。

### 6. 前提として案内するもの

- **OSのログインパスワードとディスクの暗号化（Mac は FileVault、Windows は BitLocker／デバイスの暗号化）**: 親鍵は同じPCにパスワードなしで置かれるので、これがないとPCの紛失時に鍵も一緒に渡る。初回に確かめ、満たしていなければ設定の方法を案内する。
  - 管理者の権限なしで調べられる範囲で状態を調べ、分からない場合はFPに確認を求める。満たしていなくても使用は止めない（判断はFP）。
  - これらを満たせば、PCをなくしても漏えいの報告が要らないと判断されうる（最終判断はFP）と説明する。
- **Windows Hello／PIN**: Windows で親鍵を使うときに Windows Hello／PIN を求める設定を選べる。既定はOFF。最初の版では「使う前の確認」として働き、暗号の強さそのものは変わらない（説明にもそう書く）。
- **同じPCで動くプログラムからは守りきれない**: 鍵は同じPC・同じユーザーの保管庫にあるので、同じユーザーで動く悪いプログラムや管理者が鍵を取り出すことは、OSの仕組み上、防ぎきれない（特に Windows）。そのため、データフォルダはカスタム層・SDK・AIの作業フォルダとは別の場所に固定し（中や、それらを含むフォルダは選べない）、AI向け説明書で鍵置き場とデータフォルダに触れないよう指示する。

## 理由

- **3段にする理由**: 親鍵だけで全世帯を暗号化すると、1世帯だけを読めなくする（完全削除）ことができない。世帯ごとの鍵を親鍵で包んで1か所（鍵置き場）にまとめると、「世帯ファイルとその鍵を消す」だけで、外に残った世帯ファイルの写しを読めなくできる。親鍵だけを保管庫に置くので、保管庫の項目は1つで済み、世帯が何千あっても保管庫を汚さない。
- **世帯の鍵を世帯ファイルに入れない理由**: 入れると、世帯ファイルのバックアップの写しごとに鍵が残り、親鍵で開けてしまう。
- **復元キーを親鍵そのものにする理由**: 2台目のPCが同じ親鍵を持てば、同期した鍵置き場をそのまま開ける。別の鍵で親鍵を包む形にしても、守れる範囲は変わらず、管理する物が増えるだけになる。
- **Base32・72文字にする理由**: 数字と英大文字だけで、印刷して書き写しても読み違いが起きにくい。確かめ用の4バイトで打ち間違いに気づける。英単語を並べる形も考えたが、日本の利用者には英単語のほうが書き写しにくい可能性がある。
- **鍵置き場の世代を30日で入れ替える理由**: 鍵置き場を失うと全世帯が読めなくなるので、バックアップを無くすことはできない。一方で古い写しが残る限り削除した世帯を開けてしまう。期限を決めて入れ替えることで、両方を満たす。
- **AES-256-GCM を選ぶ理由**: 改ざん検出を兼ね、Mac・Windows の両方で速く、Rust の実績ある実装（RustCrypto）がある。試作でも速さと改ざん検出を確かめた。

## 影響

- **後から変えると**: 鍵の段の数・鍵置き場の形を変えると、配布済みのすべての世帯ファイルと鍵置き場の移し替え（再暗号化）が要る。復元キーの中身（親鍵そのもの）を変えると、FPが保管済みの控えが使えなくなる。
- **守るべき決まり**
  - 世帯の鍵を世帯ファイル・ログ・書き出しに入れない。
  - 鍵置き場とその世代を、アプリの管理外のバックアップに置かない（同期フォルダに置くのはFPが2台で使うことを選んだ場合だけ）。
  - 鍵置き場のバックアップの世代を後から書き換えない。
  - 画面の側に鍵を渡さない。復号は Rust の側の1か所で行う。
  - 説明書・画面で、完全削除の範囲（最長30日、アプリの管理外の写しは対象外）を正確に書く。
- **テストで確かめること**
  - 3段をたどって開ける。1ビットの改ざん・別の世帯の鍵・違う親鍵では開かない。古い世代を新しい世代として差し込むと検出される。
  - 保管庫から親鍵を消した状態から、復元キーで戻せる。打ち間違い（1文字違い）を検出する。大文字・小文字・空白・紛らわしい文字を吸収する。
  - 完全削除の後、外に残った古い世帯ファイルの写しが、手元のどの鍵でも開かない。他の世帯は開ける。
  - 鍵置き場の古い世代が残っている間は開け、31日目以降は開けない（模擬の日付で）。
  - 一時ファイルへの書き込みの途中・差し替えの直前・直後でプログラムを強制終了しても、前の世代か新しい世代のどちらかが完全な形で残る。
  - 製品の識別子の保管庫の項目に、開発用ビルドが触れない。
  - 上のすべてを Mac と Windows の両方のCIで流す。

## 試作での確認

Mac（Apple シリコン）で、捨てる前提の試作を作り、24項目すべてが合格した。データはすべて架空で、試作で作ったキーチェーンの項目は試験の後に消したことを確かめた。

- 3段（キーチェーンの親鍵 → 鍵置き場 → 世帯ファイル）は素直に作れた。キーチェーンへの保存は約15ミリ秒、読み出しは約1.5ミリ秒。1MBの世帯ファイルの暗号化・復号は約8ミリ秒。
- 1ビットの改ざん、別の世帯の鍵、違う親鍵では開けなかった（AES-GCM の認証と確かめ値で検出）。
- 復元キー（72文字）で、キーチェーンから消した親鍵を戻せた。小文字・空白区切り・「O」を「0」と書いたものでも戻せ、1文字違うと確かめ用の4バイトが合わずにエラーになった。
- 世帯ファイルとその鍵を消すと、外に残った古いバックアップは読めなくなった。他の世帯は読めた。
- **弱点**: 削除する前の鍵置き場の写しが残っていると、古い世帯ファイルはまだ読めた（親鍵が同じため）。鍵置き場の世代を30日で入れ替えると、31日後には開ける鍵がアプリの中から無くなることを、模擬の日付で確かめた。これが4と5の決まりの根拠である。
- 一時ファイルに書いて差し替える保存では、途中で強制終了しても、前の世代か新しい世代のどちらかの完全な形で残った。比較として直接上書きすると、両方とも読めなくなった。
- 同じプログラムでの保存・読み出しでは、キーチェーンの確認ダイアログは一度も出なかった。
- Windows（資格情報マネージャー）向けは、コンパイルが通ることだけを確かめた。

## 未確定（11月以降に決めること）

- **署名した版でのキーチェーンの確認ダイアログ**: 署名なしで作り直したプログラムが、前のビルドが作った項目を読むときにダイアログが出る可能性がある（推測。試していない）。製品は署名を毎回同じにするので出ないはずだが、署名した版で、更新の前後に確かめる。
- **Windows の実機での確認**: 資格情報マネージャーへの保存、差し替え方式の保存の途中終了、Windows Hello の確認の出方。資格情報マネージャーの代わりに「DPAPI で親鍵を暗号化してファイルに置く」形にするかも、実機の結果で決める（どちらでも3段の形は同じ）。
- **電源が落ちた場合の保存**: Mac で通常の同期より強い同期（`F_FULLFSYNC`）を使うか。差し替え方式なので、最悪でも1つ前の世代に戻るだけである。
- **特別な削除（親鍵の入れ替え）の画面**を最初の版に入れるか、正式公開までに入れるか。形式（親鍵の鍵ID）は最初の版から持つ。
- Windows Hello を、確認だけでなく鍵の保護に結び付けるか。Mac で Touch ID の確認を選べるようにするか。
- 復元キーの別の見せ方（英単語や仮名の並び）を足すか。表し方の追加は中身を変えないので、βの声を見て決める。
- ディスクの暗号化の状態を、管理者の権限なしで Windows でどこまで調べられるか。

## 追記

- 2026-10-08（全体の整合）: 改ざん検出の対象を、封筒の記録（0011）に合わせて「見出しのJSON全体」とした。世帯の鍵に鍵IDを付けて鍵置き場に持つことと、それが封筒の `keyId` であることを明記した。

- 2026-10-19（事務所での共有。0023）: 共有をオンにした事務所では、鍵の3段の一番上の親鍵を、メンバーごとの X25519 の公開鍵で包んで共有フォルダの名簿に置く（秘密鍵は各PCの保管庫、アカウント名 `<事務所ID>.member`）。鍵置き場は1つのファイルにせず、世帯ごとの鍵の札（`keys/<親鍵の鍵ID>/<世帯ID>.lphk`）にする（同期の衝突で世帯の鍵を失わないため）。メンバーを外すときは、本記録の5の「特別な削除（親鍵の入れ替え）」と同じ操作に、世帯の鍵の入れ替え（次の保存から新しい鍵）を足して行う。共有の事務所の復元キーは共有の事務所の親鍵で、外すたびに変わる。完全削除は、共有フォルダのすべての時代の世帯の鍵の札も消す。共有オフの事務所の鍵の形は変えていない。
