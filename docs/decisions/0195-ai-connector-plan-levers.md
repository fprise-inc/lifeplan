# 0195. AI接続口でも、画面の結果のタブのプランと同じ「動かす項目」で計算する（list_plan_items・plan_changes）

- 状態: 採用（一部未確定）（2026-11-11）
- 固定の強さ: 道具の名前と入出力（`list_plan_items`、`calculate`・`explain_value` の `plan_changes`、答えの `planChanges`）は試験版（0015 と同じ。予告して変えることがある）。作り（画面のプランの部品を同梱して当てる・候補の当てはめを1か所にする・固めた実行環境のための組み込みの代わり）は内部
- 前提にする記録: 0005（計算の実行環境）、0014（AIに渡した記録）、0015（AI接続口。プランの候補）、0036（プランの差分）、0084（対策の項目）、0183（画面の関数を同梱する）、0184（計算の前の処理）

## 背景

- `calculate`・`explain_value` の `changes` は、計算の入力の欄を JSON Pointer で1つずつ直す書き方だった。画面の結果のタブの「動かす項目」（働く最後の年齢・年金の受け取り開始・NISA の積立・生活費など）は、1つ動かすと関係する欄も一緒に動く（働く最後の年齢なら、働き方の期間の終わり・生活費の「退職後」の段階の始まり・積立の終わり・定年後の働き方の期間）。AI が働き方の期間の終わりだけを動かすと、生活費の段階が動かず、画面で同じ年齢にしたときと違う数字になった。
- プランの候補（`propose_scenario`）は「対象（物・構成員の ID か前提）・入力項目ID・値」の書き方で、計算の書き方（JSON Pointer）と違った。AI が計算で確かめた物と、プランの候補に出す物を同じにできなかった。
- 利用者の判断（2026-11-10）: 画面のプランと同じ「動かす項目」で計算できるようにする。画面のプランの部品から画面の状態に依らない入口を切り出して同梱し、接続口に別の書き方を作らない（0183・0184 と同じやり方）。

## 決定

### 1. 動かせる項目の一覧 `list_plan_items`（単体の群。`share_id` のときは世帯を扱う群）

- 入力: 世帯は `calculate` と同じく見本の世帯（`sample_household_id`）・FP が渡した世帯（`share_id`）・AI が組み立てた入力（`input`）のどれか1つ。`group`（項目のまとまりで絞る）・`fields`（入力の数の欄から作った項目も返す）。
- 返すもの（項目ごと）: `target`（対象。物・構成員の ID か `"assumptions"`）・`item`（入力項目ID）・`label`（画面の名前）・`group`・`value`（今の値）・`valueText`（画面の文）・`kind` と `unit`（値の形: 年齢・金額・率・入れる/入れない・配分・金利の上昇・働き方と年収・整数・10進）・範囲（`min`・`max`・画面のスライダーの幅 `slider`・率の入れてよい範囲 `limitPercent`・働き方の選択肢 `options`）・`note`（スライダーの下の補足）・`proposable`（プランの候補に出せるか）。ほかに、まとまりごとの数 `groups`・返した数 `count`・全部の数 `total`・この書き方で選べないので出さなかった数 `unlisted`。
- 既定は、画面の対策・資産運用・貯まり方・よく使う項目だけ（見本の世帯で平均 6.5 件・約 2.6KB）。`fields: true` で、入力の数の欄から作った項目（画面の「＋ 動かす項目を追加」）も返す（平均 37.5 件・約 13KB）。
- 項目と範囲は画面と同じ関数（`plans/items.ts` の `buildCatalog`）で作る。見本の世帯では、画面で見本を開くときと同じく見本の目盛りと定年後の働き方を使う。
- 一覧に出すのは、その書き方（対象・入力項目ID）で当てはめ直すと、その項目自身に1つに決まる項目だけ（3）。同じ対象・同じ入力項目ID で場所だけが違う項目（資産運用の「毎月の積立額」と「積立をやめる年齢」、取り崩しの3項目、黒字の貯まり方の欄、教育の段階ごとの欄など）は、この書き方では選べないので出さない（未確定）。
- `proposable`: `propose_scenario` の確かめ（`crates/ai-share` の `proposal.rs`）は、対象を前提（`assumptions`）にできるのを前提条件の入力項目（`assumptions.〜`）だけにしている。対象が前提で入力項目が前提でない項目は false。

### 2. `calculate`・`explain_value` の `plan_changes`

- 書き方は `propose_scenario` の `changes` と同じ `[{target, item, value}]`（理由 `note` は要らない。50件まで）。`list_plan_items` の `target`・`item` と、`kind`・`unit` の形の値を渡す。
- 当てる順: 世帯 → `changes`（JSON Pointer）と `stress_test` → `plan_changes` → 計算の前の処理（0184）→ 計算。`changes` は欄の場所で当てるので先に、`plan_changes` は物の ID で当てるので後にした。今の `changes` はそのまま動く（両方を一緒に使える）。
- 当てはまらない変更（対象・入力項目ID が項目に当たらない・値の形が違う・範囲の外）が1つでもあれば、何も当てずに計算もせず、変更ごとの理由を返す（直し方が分かるように `list_plan_items` を案内する）。
- 当てたときは答えに `planChanges`（`note` と、変更ごとの `label`・`from`・`to`・`status`〔`applied`＝当てた・`same`＝今と同じ値〕）を添える。
- `explain_value` は、画面の根拠のパネルと同じく、根拠の記録「全部」で計算するのは計算の前の処理の後の要求、根拠の読み方に渡すのはプランを当てた後・計算の前の処理の前の要求。

### 3. 画面のプランの部品から切り出した入口

- 候補の当てはめを1か所にした: 画面の「AIからの候補」の当てはめ（`ai/model.ts` の `candidateRows`・`coerce`）を、画面の状態に依らない `app/src/workspace/plans/candidates.ts` に移した（`ai/model.ts` は同じ名前で出し直す）。画面の候補と接続口の計算が同じ関数で当てはめる。
  - 当てはまる項目の探し方（`matchItems`）を切り出し、一覧に出すかを決める `candidateTargetOf` を足した。項目のキーの読み替えは一覧ごとに1回だけ作る（一覧の全部の項目を当てはめ直すため）。
- 当てはめを直した（画面の「AIからの候補」も同じく変わる）:
  - 対策の固定の項目（働く最後の年齢・年金の受け取り開始・NISA の積立・毎月の生活費・FP顧問料）にも当てはまるようにした。前は入力の欄の項目だけに当てはめ、これらの候補は「動かせない項目」として取り込まなかった。
  - 対策の固定の項目を先に探し、当たらなければ入力の欄の項目を探す。同じ入力項目ID・同じ向き先の欄（本人の「今の勤め先の終わりの年齢」の欄など）より、結果の画面の対策を選ぶ（AI が「退職の年齢」を出すとき、ふつう働く最後の年齢を指すため）。その欄は候補の書き方では選べなくなった（入力の欄の画面からは今までどおり直せる）。
  - 対策の固定の項目の値を確かめる: 年齢は1歳ずつの整数で、画面のスライダーの下の端（働く最後の年齢は今の年齢の次・年金の受け取り開始は過ぎていない年齢）から上の端（今の値が外にあれば広げる）まで。金額は0以上の整数の円（スライダーの幅は目盛りなので確かめない）。今と同じ値は確かめない。
- 接続口の入口 `app/src/connector/plan.ts`: 世帯の要求から画面と同じく作業中の世帯（`fromRequest`）と動かす項目の一覧（`buildCatalog`）を作り、`listPlanItems` は一覧を返し、`applyPlan` は候補の当てはめ（`candidateRows`・`candidateValues`）で動かす項目の値にしてから、画面のプランと同じ `applyValues` で要求に当てる。帯・選んだプラン・保存していない変更などの画面の状態は読まない。事務所の推定の値は、計算の前の処理と同じく渡された世帯のときだけ入れてから当てる（働き方を選び直したときの年収の目安などが読む）。
- lint で、接続口の入口が読める作業の層を、`evidence`・`present`・`office/estimates` に加えて `catalog`・`roles`・`input/household`・`plans/candidates`・`plans/items`・`plans/plans` だけにした（画面の部品・本体の命令・画面の大枠は今までどおり読めない）。

### 4. 固めた実行環境で画面の部品を動かす: 別の JS と組み込みの代わり

- 入力の欄の定義まで読むので、まとめた JS は約 2.1MB になる。数字の根拠の読み方（`explain.js`）には入れず、別の JS `crates/lifeplan/dist/plan.js`（グローバル `FinanciaPlan`）にまとめる（`scripts/build-explain.ts` が両方を作る）。プランを当てるときと一覧を返すときだけ読み込む（読み込み約 0.1 秒・一覧約 0.1 秒。プランを当てない計算は今までと同じ）。
- 計算の固めた実行環境（0005 の3）には `structuredClone`・`TextEncoder`・`crypto`・`Intl` が無く、結果がエンジンや OS で変わる Math の関数（`round`・`pow` など）は呼ぶとエラーになる。画面の部品はこれらを使うので、`plan.js` の中だけで同じ名前を、OS に依らず画面と同じ答えになる実装に置き換える（`PLAN_INTRO`。グローバルの組み込みも、エンジンの実行環境の固め方も変えない）:
  - `Math.round`（仕様どおり）・`Math.pow`（指数が整数のときだけ。2乗を重ねる。住宅ローンの返済額の式。整数でない指数はエラー）・`structuredClone`（JSON の値と Map・Set）・`TextEncoder`（UTF-8）・`crypto.randomUUID`（呼ぶ順の番号。プランを当てる途中の差分の仮の ID だけで、要求には入らない）。
  - 数の `toLocaleString`: まとめるときに `x.toLocaleString(…)` の呼び出しを `__fxLocale(x, …)` に書き換え、Intl と同じ形（3桁ごとのコンマ・いちばん短い10進の形から最大 `maximumFractionDigits` 桁に四捨五入・後ろの0を落とす）にする。
  - 残りの使えない関数（`Math.sqrt`・`Math.log` など）はそのままエラー（プランを当てる道筋では使わない。使えば下のテストで止まる）。
- これは計算エンジン（0005 の正）ではなく、画面の部品を画面と同じ答えにするための物。エンジンの計算は今までどおり同じ固めた実行環境で、組み込みの代わりは入らない。

### 5. 世帯を扱う道具の決まりはそのまま

- `share_id` の世帯は、今までと同じく `calculate` の読み取り（`getShare` の `forCalc`）でアプリ本体に頼む（同意・期限・縮約・記録はアプリ本体だけ）。`list_plan_items` も同じ読み取りで、読んだ道具の名前 `list_plan_items` で「AIに渡した記録」に残る。
- 一覧と答えの物の ID は、AI に渡した世帯の ID（渡された世帯では共有の仮の ID）のまま。`propose_scenario` に同じ書き方で渡すと、アプリ本体が元の ID に戻して承認待ちに入れ、画面の「AIからの候補」が同じ当てはめでプランにする（3）。

### 6. テスト

- 画面の側（`app/test/connector-plan.test.ts`）:
  - 見本の世帯 54 件のどれでも、一覧の項目を今の値のまま当てはめると同じ項目に当たり「今と同じ値」で要求が変わらないこと、入力項目が縮約版で AI に渡る項目（許可リスト）であること。
  - 決まった変更（働く最後の年齢・年金の受け取り開始と生活費と NISA・配偶者の働き方と繰上返済と金利の上昇・入力の欄から作った項目・FP顧問料・定年後の働き方のある見本の働く最後の年齢）で、`applyPlan` の要求が、画面でつまみを動かしたとき（結果のタブの動かした値 → `applyValues`）と同じこと。働く最後の年齢で、生活費の段階と積立の終わりも動くこと。
  - 当てはまらない変更（範囲の外・値の形・知らない対象・動かせない入力項目）で何も当てないこと、画面の「AIからの候補」も対策の固定の項目に当たり範囲の外を取り込まないこと。
  - 見本: 決まった変更の画面の数字（年ごとの年間収支・金融資産と合計）と根拠（1つのマス）を `crates/lifeplan/tests/fixtures/plan/expected.json` に書く（`LIFEPLAN_UPDATE_FIXTURES=1` で作り直す）。
- 組み込みの代わり（`app/test/connector-plan-intro.test.ts`）: Node の組み込み（Intl を含む）と同じ答えを返すこと。
- 接続口の側（`crates/lifeplan/tests/mcp_connector.rs`）:
  - `plan_changes_match_the_screen`: 本物の接続口に MCP で `calculate`・`explain_value` を `plan_changes` つきで呼び、見本の画面の数字・根拠と同じこと。一覧の対象・入力項目ID、範囲の外の理由、JSON Pointer の `changes` が今までどおり動き一緒にも使えること。
  - `plan_items_for_a_shared_household`: 渡された世帯の一覧の対象が共有の仮の ID で、その書き方の計算が同じ入力と同じ数字、`propose_scenario` に渡すと元の ID に戻ること、記録に `list_plan_items` が残ること、取り消した共有では使えないこと。
  - `every_plan_item_matches_node`: 同梱した `plan.js` を接続口と同じ固めた実行環境（quickjs-ng）で動かし、見本の世帯 54 件の一覧と、全部の項目を1つずつ動かして当てた答え（約 1,400 件）が、同じ JS を Node で動かした答えと1文字も違わないこと（並べ替え・正規表現・数の文字などの実行環境の違いで答えが変わらない）。見本のファイルを持たないので、画面の欄の名前を直しても作り直しは要らない。Node が要る（CI の host にもある）。
- 道具の入力の形の見本（`fixtures/tools/list_plan_items.input-schema.json`・`explain_value.input-schema.json`）。

### 7. ビルドと CI

- `npm run build:explain` が `explain.js` と `plan.js` を作る。接続口の build.rs は両方が無ければ止まる。CI の `ai-explain` の成果物に `plan.js` も入れる。

## 理由

- 画面のプランの部品（動かす項目の一覧・当て方・合成の対策）をそのまま同梱すれば、関係する欄の動き方（働く最後の年齢と生活費の段階・積立の終わり・定年後の働き方など）が画面とずれない（直すのは1か所。0183・0184 と同じ考え）。
- 計算の書き方をプランの候補と同じにすれば、AI が計算で確かめた変更をそのままプランの候補に出せ、FP が画面で承認したプランの数字と AI が見た数字が同じになる。
- 候補の当てはめを1か所にすれば、画面の「AIからの候補」と接続口の計算で、同じ候補が同じ項目に当たる。

## 代案（採らなかったもの）

- **当て方を Rust で書き直す**: 対策の合成（働く最後の年齢・年金の受け取り開始・定年後の働き方）と入力の欄の書き方を二重に持つことになり、ずれる。
- **`changes` に動かす項目のキー（`lever:retireAge` など）を渡す書き方**: プランの候補と書き方が2つになる。キーは画面の内部の名前で、物の ID を含む（共有の仮の ID に戻す処理も要る）。
- **書き方に場所（`at`）か動かす項目のキーを足して、場所だけ違う項目も選べるようにする**: `propose_scenario` の取り決め（`crates/ai-share`）と画面の候補の形が変わる。今回は見送り、未確定に置く。
- **固めた実行環境を画面の部品のために緩める**（Math の関数を戻す・Intl を入れる）: 計算エンジンと同じ環境の約束（0005 の3）が崩れ、OS で答えが変わる関数が使えるようになる。
- **`explain.js` に入れる**: すべての計算で 2MB を読み込むことになる。

## 未確定

- **場所だけ違う項目**: 同じ対象・同じ入力項目ID で場所だけが違う項目は、この書き方では選べない（見本の世帯で平均約 46 件。資産運用の「毎月の積立額」「積立をやめる年齢」、取り崩しの3項目、黒字の貯まり方の欄、教育の段階ごとの欄など）。書き方に場所か項目のキーを足すか（`propose_scenario` も一緒に変える）。
- **定年後の働き方の条件**: 画面の側の値で、計算の入力の外にある（世帯ファイルの `postRetirement`）。渡された世帯では縮約版に入らないので、入力の働き方の期間から推し量る（保存した世帯を画面で開いたときの条件と違うと、働く最後の年齢を動かしたときの定年後の働き方が画面と違うことがある）。縮約版に足すか。
- **保存したプランを土台にする**: 渡るのは現状だけなので、`plan_changes` は現状に当てる。保存したプラン（プランA・プランB …）の上に重ねて試すことはできない（保存したプランを AI に渡すかの判断と一緒に）。
- **一覧の大きさ**: 入力の欄から作った項目まで返すと約 13KB（多い世帯で約 30KB）。まとまりごとに引く使い方で足りるか。
