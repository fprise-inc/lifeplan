# 0002. 金額・率・端数処理

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。データの中の金額・率の書き方は公開の約束（安定）の一部

## 背景

ライフプランの計算は、税・社会保険料・年金などを100年分、月ごとに積み上げる。制度の計算は「円未満切り捨て」「100円未満切り捨て」「50銭以下切り捨て・50銭超切り上げ」のように、条文で丸め方が決まっている。丸めの境目で1円ずれると、その差が年をまたいで積み重なり、結果が制度どおりの円単位にならない。

また、同じ計算をアプリ本体の実行環境・画面・CI（Node）の複数のエンジンで動かし、結果がビット単位で一致することを確かめる（0005）。エンジンやOSによって結果が変わる演算は使えない。

## 決定

### 1. 金額

- 金額は「通貨＋最小単位の整数」で持つ。円なら円、米ドルならセント。小数の金額は持たない。
- データ（世帯ファイル・入出力のJSON）での書き方:
  - 円の欄は、JSON の整数（円）をそのまま書く。欄が円であることは JSON Schema で宣言する（`"type": "integer"` と `"x-unit": "JPY"`）。
  - 外貨になりうる欄（外貨建保険など）だけは `{"amount": 12345, "currency": "USD"}` の形にする。`amount` は最小単位の整数、`currency` は ISO 4217 の通貨コード、最小単位の桁は ISO 4217 の minor unit に従う（JPY は0桁、USD は2桁）。
  - 値の範囲は ±(2^53−1)（JavaScript の安全な整数）。範囲を超える値はスキーマの検査でエラーにする。
- エンジンの中:
  - 金額は JavaScript の `number` の整数で持つ（型は `Yen` などの区別できる型にする）。
  - 金額どうしの足し算・引き算は演算子 `+` `-` で書いてよい（安全な整数どうしは正確）。
  - 掛け算・割り算・余りは演算子で書かず、下の3の関数を通す。金額×率の積が 2^53 を超えるときだけ、関数の中で `BigInt` に切り替えて計算し、丸めた後に `number` へ戻す。
  - 部品の出力を検査するとき（0006）、すべての金額が安全な整数であることを確かめる。
- 通貨の違う金額を足し引きすると、型の検査と実行時の両方でエラーにする。円への換算は `convert(amount, fxRate, roundingId)` だけで行い、為替レートはプランの前提条件の率（例: `"150.25"` 円／ドル）を使う。

### 2. 率

- 率は割合で持つ（9.85% は `0.0985`）。画面ではパーセントで表示する。
- データの中では10進の文字列で書く（例: `"0.0985"`）。書式は `^-?\d+(\.\d+)?$`、小数点以下は12桁まで、指数表記（`1e-3`）は使わない。JSON の数値で書くと読み込みの時点で誤差が入るため。
- エンジンの中では「整数×10のマイナス桁乗」（例: `0.0985` → 985 と 4桁）で正確に持つ。
- 率どうしの計算（足す・引く・掛ける・割る・累乗）の途中は、小数12桁で丸める。丸め方は銀行丸め（偶数への丸め）に固定する。
- 制度データの率も、プランの前提条件（物価上昇率・運用利回りなど）も、同じ型で扱う。

### 3. 端数処理は「規則ID」を受け取る関数だけ

- 金額を丸めることができるのは、次の関数だけにする（カスタム部品も同じ）。

| 関数 | 中身 |
|---|---|
| `mulRate(amount, rate, roundingId)` | 金額×率を丸める |
| `mulRatio(amount, num, den, roundingId)` | 金額×num÷den を丸める（按分・日割り・持分） |
| `divInt(amount, k, roundingId)` | 金額÷整数を丸める（月割りなど） |
| `round(amount, roundingId)` | 金額を指定の単位に丸める（100円未満切り捨てなど） |
| `allocate(total, weights, roundingId, remainderTo)` | 合計を保ったまま分ける（年額を支払月に分けるなど）。端数の寄せ先（`"first"`／`"last"`／位置）を指定する |
| `convert(amount, fxRate, roundingId)` | 外貨を円に換える |

- `roundingId`（端数処理の規則ID）は2種類ある。
  1. **制度の端数処理**: 法令で決まる丸め。制度データの値として持つ（ID の例: `incomeTax.taxAmount.rounding`、`healthInsurance.premium.rounding`）。中身は「方式」と「単位」と出典（条文）。制度データの形式は 0007 で、値の種類は `kind: rounding`（制度の端数処理）、単位は `unit: rounding`、値は `{"mode": "DOWN", "unit": 100}` の形にする。他の制度の値の `rounding` 欄（0007）は、この規則IDを指す。丸め方が改正で変わっても、データの更新で追従できる。
  2. **エンジンの規約**: 法令に定めがない丸め。エンジンの規約表に持つ（ID は `conv.` で始める。例: `conv.investment.return`、`conv.display.manYen`）。
- 方式は次の5つ。負の数は絶対値に対して丸め、符号を戻す（0に向かう丸め）。

| 方式 | 意味 |
|---|---|
| `DOWN` | 切り捨て |
| `UP` | 切り上げ |
| `HALF_UP` | 四捨五入 |
| `HALF_DOWN` | 五捨六入（社会保険料の「50銭以下切り捨て、50銭超切り上げ」） |
| `HALF_EVEN` | 銀行丸め |

- 単位は 1・10・100・1000・10000 円など、正の整数。
- 規則IDの付かない丸め（`Math.round`、`Math.floor` を金額に使う、`toFixed` で丸める）は禁止する。
- 丸めのたびに、使った規則IDを根拠の記録（0006）に残す。
- 表示のための丸め（万円表示など）は画面の側で行い、計算の値には戻さない。

### 4. 浮動小数点の数学関数を使わない

- エンジンと計算部品では次を使わない: `Math.pow`、`**` 演算子、`Math.exp`、`Math.expm1`、`Math.log`、`Math.log1p`、`Math.log2`、`Math.log10`、`Math.sqrt`、`Math.cbrt`、`Math.hypot`、三角関数、`Math.round`、`Math.fround`、`parseFloat`、`Number.prototype.toFixed`・`toPrecision`、小数を含む数値リテラル（`0.7` など）。
- `Math` で使ってよいのは、整数に対する `abs`・`min`・`max`・`sign`・`trunc`・`floor`・`ceil` だけ。
- 代わりに次を使う:
  - 複利 `(1+r)^n` は `ratePow(r, n)`（掛け算を n 回繰り返し、1回ごとに小数12桁・銀行丸め）。
  - 元利均等返済の返済額、現在価値への割り戻しなども、`ratePow` と率の割り算 `rateDiv`（小数12桁・銀行丸め）で書く。
  - 年率から月率は「年率÷12」に統一する（国内の住宅ローンの慣行と同じ）。べき根（12乗根など）が要る計算は作らない。
  - 率をコードに書くときは文字列から作る（`rate("0.007")`）。
- 禁止は2か所で守る。
  1. **lint**: ESLint の `no-restricted-properties`・`no-restricted-syntax` で上の関数・演算子・小数リテラルを禁止する。`Yen` 型に `*` `/` `%` を直接使うことは、型情報を使う自前の規則で禁止する。公式もカスタム部品も同じ設定を使う（SDKに同梱する。0019）。
  2. **実行環境**: アプリ本体の計算用の実行環境（0005）では、上の `Math` の関数を「呼ぶとエラーになる関数」に差し替えてから凍結する。
- 画面側のエンジン（0005 の二本立ての表示の先出し）は、画面の他の部品が `Math` を使うので差し替えない。lint と、CI の一致テスト（ハッシュの比較）で守る。

### 5. 10進ライブラリは製品のエンジンに入れない

- big.js・decimal.js などの10進ライブラリは、エンジンでは使わない（遅いため。試作の数字は下）。
- テストの参照実装（上の関数が正しく丸めているかを、無作為の入力で突き合わせる）には使ってよい。

## 理由

- 浮動小数点（`number` のまま小数で計算）は、`0.0985` のような率を正確に表せないので、四捨五入の境目で結果が変わり、100年分で円単位のずれになる。どのエンジンでも同じように間違えるので一致テストでは見つからない。
- 10進ライブラリは正確だが、内蔵の実行環境（JIT を持たない）では遅く、画面の操作に間に合わない。
- 「ふだんは整数、桁があふれる掛け算だけ BigInt、率は10進文字列から正確な値」という形なら、10進ライブラリと同じ円単位の結果を、浮動小数点に近い速さで出せる。
- `Math.pow` などはエンジンやOSの数学ライブラリによって最後の桁が変わる。四則演算・文字列化は規格で結果が決まっているので一致する。
- 丸めを規則IDつきの関数に限ると、(a) どの丸めがどの条文によるかを根拠として表示でき、(b) 丸めの取り違えをテストで見つけやすく、(c) 法令の丸めが変わってもデータの更新で直せる。
- 円の欄を JSON の整数のまま書くのは、データの大半が円で、ファイルを読みやすく小さく保てるため。外貨は欄を分けて混同を防ぐ。
- 負の数を0に向かって丸めるのは、制度の計算で負の値を丸める場面がほぼなく（還付額なども正の値として計算する）、符号で結果が非対称になるのを避けるため。負の値に固有の丸めが必要な制度が見つかったら、方式を足す（未確定）。

## 影響

- 後から変えると、全部品の計算とテストの期待値の作り直しになる。
- 守るべき決まり:
  - 金額の欄に小数を書かない。率の欄に数値を書かない（文字列で書く）。
  - 丸めは必ず規則IDつきの関数で。新しい丸めが要るときは、制度の端数処理なら制度データに、そうでなければ `conv.` の規約表に、先に規則を足す。
- テストで確かめること:
  - 丸め関数を、10進ライブラリによる参照実装と、無作為の入力（境目のちょうど0.5を含む）で突き合わせる。
  - 積が 2^53 を超える場合（BigInt の経路）を必ず通すテスト。
  - 金額の出力がすべて安全な整数で、`-0` や小数が混じらないこと。
  - lint の禁止が効いていること（禁止した関数を書いたファイルで lint が失敗するテスト）。
  - 実行環境で `Math.pow` などを呼ぶとエラーになること（脱出テストと一緒に流す。0016）。
  - 複数のエンジンで結果のハッシュが一致すること（0005）。

## 試作での確認

試作（合成した14部品・1200か月の計算。クラウドの仮想マシン Intel Xeon 2.1GHz 4コア／Linux と、Apple M5 10コア／macOS の両方）で確かめた。

- **浮動小数点はずれる**: 金額 58,040 個のうち 5,647 個が10進の方式と違った。最大923円、資産残高の最小値で最大474円のずれ。
- **10進で正確に計算する4方式（工夫版・BigInt 固定小数点・big.js・decimal.js）は、4つとも完全に同じ結果**だった。
- **速さ**（Rust組込みの quickjs-ng、5案×4想定＝20回、根拠の記録なし、ミリ秒の中央値）

| 数値の表し方 | クラウド | Apple M5 |
|---|---|---|
| 浮動小数点 | 478 | 168 |
| 工夫版（ふだん整数＋必要時 BigInt、率は10進文字列から） | 614 | 217 |
| BigInt 固定小数点 | 644 | 206 |
| decimal.js | 5,506 | 1,991 |
| big.js | 9,692 | 3,198 |

  工夫版は10進ライブラリより9〜16倍速かった。

- **数学関数のずれ**（2000個の入力のうち Node（V8）と最後の桁まで一致しなかった数。クラウド）: `Math.pow(1+r, n)` は Rust組込みの QuickJS で189、JavaScriptCore で1967、`Math.exp` は約189、三角関数は最大752。四則演算・文字列化は0。Mac ではずれ方が違い（`pow` は Mac では一致、クラウドではずれた）、OSの数学ライブラリに左右されることを確認した。
- 複利と元利均等返済を「掛け算の繰り返し＋小数12桁・銀行丸め」で書いた版は、すべてのエンジン・両方のOSで結果のハッシュが一致した。

## 未確定

- 率の途中の桁（小数12桁）で足りるか。為替レートの逆算や、非常に長い期間の複利で問題が出ないかを、本物の部品ができた段階（12月）で確かめる。
- 負の値に固有の丸め（負の無限大方向など）が必要な制度があるか。部品を作りながら洗い出し、必要なら方式を足す。
- 制度の端数処理の規則IDの一覧（所得税・住民税・社会保険料・年金・給付ごと）。所得税・社会保険料の部品を作る11月に、制度データの初期データとして作る。
- アプリ本体（Rust）の側で金額を扱う場面（書き出し・PDFへの差し込み）の型。計算はしないが、`i64` で受けて同じ範囲の検査をする案が有力。

## 追記

- 2026-10-08（全体の整合）: 制度の端数処理の値の種類を、制度データの形式（0007）の `kind: rounding` にそろえた（以前の「`kind: constant`」の書き方を改めた）。値の欄名は `mode`・`unit` で 0007 と同じ。「未確定」があるので状態を「採用（一部未確定）」に直した。
- 2026-10-08（端数処理の規則IDの一覧）: 「未確定」の制度の端数処理の規則IDの一覧のうち、所得税・住民税・社会保険料の分を決めた。制度の端数処理（制度データの `kind: rounding`。ID は対象の値IDに `.rounding` を付ける）: `incomeTax.employmentIncome.tableRounding`（別表第五の収入金額の4,000円未満切り捨て）、`incomeTax.taxableIncome.rounding`（課税所得金額の1,000円未満切り捨て）、`incomeTax.surtax.rounding`（復興特別所得税・防衛特別所得税の1円未満切り捨て）、`incomeTax.taxAmount.rounding`（所得税及び復興特別所得税の額の100円未満切り捨て）、`incomeTax.insuranceDeduction.rounding`（生命保険料控除・地震保険料控除の1円未満切り上げ）、`residentTax.taxableIncome.rounding`（課税総所得金額などの1,000円未満切り捨て）、`residentTax.incomeLevy.calc.rounding`（税率・調整控除の率を掛けた額の1円未満切り捨て）、`residentTax.incomeLevy.rounding`（所得割額の100円未満切り捨て。市町村民税・道府県民税それぞれ）、`socialInsurance.employeeShare.rounding`（健康保険料・介護保険料・子ども・子育て支援金・厚生年金保険料の被保険者負担分を給与から控除するときの50銭以下切り捨て・50銭超切り上げ＝`HALF_DOWN`）、`socialInsurance.standardBonus.rounding`（標準賞与額の1,000円未満切り捨て）、`employmentInsurance.employeeShare.rounding`（雇用保険料の被保険者負担分。`HALF_DOWN`）。エンジンの規約（`conv.`）に足したもの: `conv.salary.monthly`（給与の年額を月に・賞与を支給月に分ける。端数は最後の月）、`conv.salary.growth`（賃金上昇率で翌年の給与を出す）、`conv.socialInsurance.remuneration`（標準報酬月額の基にする報酬月額の平均）、`conv.tax.exact`（割り切れる計算）、`conv.tax.allocate`（年税額を支払月に分ける。端数は最後の月）。法令の端数の扱いを原本で確かめられなかった2つは、確かめるまでの仮の規約として `conv.tax.fractionalDeduction`（給与所得控除の10%の段・住民税の保険料控除の式の1円未満）と `conv.residentTax.installment`（住民税の年税額を納期に分ける。端数は最初の納期）を置いた。確かめたら制度の端数処理に置き換える。いずれも円未満は切り捨て（`DOWN`、単位1）。
- 2026-11-08（給与所得の端数を原本で確かめた。0167）: 仮の規約 `conv.tax.fractionalDeduction` のうち給与所得控除の分は、原本（所得税法別表第五の備考・国税庁の年末調整のしかた）では逆向きだった。給与等の金額が660万円以上の給与所得（算式で求める額）は**給与所得の1円未満を切り捨てる**（控除額の側は切り上げ）。制度の端数処理 `incomeTax.employmentIncome.rounding`（`DOWN`・単位1。確認済み）に置き換え、`tax.employmentIncome` は 収入×(1−率)−加算額 をこれで丸める。給与所得の表の最初の区分（最低保障額＋1,000円未満は0円）も制度データの区分の幅で表した。`conv.tax.fractionalDeduction` は、住民税の保険料控除の式・公的年金等控除・障害年金の所得の見積もりでまだ使う（公的年金等の雑所得の向きは、国税庁の速算表が画像で文で確かめられなかったので仮のまま。0167 の未確定）。
