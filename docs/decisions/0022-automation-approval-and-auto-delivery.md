# 0022. 自動化と承認・自動配信の範囲

- 状態: 採用（一部未確定）（2026-10-08）
- 固定の強さ: β公開から変えない（骨格）。とくに、自動配信用の鍵で受け付ける変更の種類と変化率の上限の仕組み、配信の目録の段階の欄、一時停止・巻き戻しの入口は、配った後から足せないので最初の版に入れる。自動配信の対象の一覧そのものは、決まった手順で広げられる

## 背景

制度の金額を返す公式のAPIは無く、金額は各省のPDF・Excel・HTMLから読むしかない。読み取りはAIと決まった手順で自動化するが、AIは読み違えることがある。誤った値をすべてのFPに配ると、すべての世帯の計算が狂う。

そこで、制度改正への追従は「見つける・変更案を作る・確かめるまでを自動、配るのは人の承認の後」を原則とする。ただし、機械で確かめきれる種類の更新だけは、人の承認なしに配れるようにしたい。その場合でも、誤りが通ったときの被害を、アプリの側の仕組みで小さく抑える。

アプリの側の仕組み（どの鍵で何を受け付けるか、段階配信、一時停止と巻き戻し）は、配布済みのアプリが理解できなければ働かない。後から足しても古いアプリには効かないので、最初の版から入れる。

関連: 署名鍵の体系と配信は 0017、制度データの形式は 0007、検証の層は計算エンジン・制度データの各記録、リポジトリは 0021。

## 決定

### 1. 変更案はボットの名義、承認は人

- 監視と変更案づくりは、リポジトリの定期実行（GitHub Actions）で動かす。
- 変更案（プルリクエスト）は、専用のボット（GitHub App）の名義で作る。人の名義では作らない。
- 変更案に必ず付けるもの:
  - 値・状態・適用期間のデータの差分
  - 出典（URL、取得日、原本の指紋、原本からの短い引用）。原本の写しは非公開のリポジトリに置く（0021）
  - 公式の計算例から作ったテスト
  - 別の会社のAIによる独立の読み取りの結果と、機械の確認（引用が原本にあるか、派生する値と合うか、期間の重なり・空白、前年からの変化率）の結果
  - 差分表用のモデル世帯（合成した50件）を新旧のデータで計算した差分表
- **作る人と承認する人を分ける**: ボットは自分の変更案を承認・合流できない。既定のブランチは保護し、合流には人の承認を必須にする。
- 人が承認した変更は、承認と同じ操作で人が署名する（データ用の鍵。鍵の体系は 0017）。
- 計算方法そのものが変わる改正は、自動配信の対象にしない。公開した「対応の規則」（施行日どおりに切り替える、合格の条件など）に照らして人が判断する。
- 承認待ちの変更は配らない。承認の前に施行日が来た場合は、アプリに黄色い帯で「反映待ち」と出す（承認が遅れても誤りは配らない）。

### 2. 自動配信の範囲

人の承認なしに、**48時間の確認期間の後に**自動で配るのは、次の2種類だけ。確認期間中は承認者に通知し、承認者はいつでも止められる。

1. **公式の表の値**: 機械で読める公式の表（健康保険の料率表、源泉徴収税額表など）。独立した2つの読み取りと公式の計算例がすべて一致したもの。
2. **値だけ変わる更新**: 年金額の改定一式、国民年金保険料、在職老齢年金の基準額、介護保険・子ども・子育て支援金・雇用保険の料率、高校の就学支援金の上限額など。**税の段階表と、計算方法の変更とセットになった更新は対象外**。

値だけ変わる更新は、次の**5つの関門をすべて通ったもの**だけを自動で配る。1つでも外れたら人の承認に回す。

1. 違う経路の2つの読み取りが一致する（決まった手順での読み取りと、別の会社のAIによる原本全文の読み取り。ページを要約する道具を通した読み取りは使わない）。
2. 派生する値の検算が合う。
3. 法律の計算式や事前の公表値からの予測と合う。
4. データの形（区分・系列の数、適用開始の月、本則と特例）が前の期間と同じ。
5. モデル世帯の差分が値の変化だけで説明でき、変化率が過去の幅に収まる。

**分野ごとの卒業試験**: 値だけ変わる更新は、分野ごとに、次の両方に合格してから自動配信に移す。それまでは人の承認で配る。

- わざと誤りを混ぜた変更案を、すべて止められる。
- 1シーズン（12〜4月）、人の承認と並行して動かし、判定の不一致が0件。

自動配信した分野で誤りが見つかったら、その分野は人の承認に戻す。自動配信の対象の種類は一覧にして公開する（一覧を広げても、利用者への約束の文言は変えずに済むように）。

### 3. 自動配信用の鍵で受け付けるもの

自動配信の分は、人の署名とは別の「自動配信用の鍵」で署名する。アプリは、この鍵で署名されたデータパックについて、次だけを受け付ける。

- **受け付ける**: 既にある制度の値ID（0004）に、**前の期間と同じ形**（型・区分・系列の数）の新しい適用期間を1つ足すこと（0007 の「新しい行を足す」形）。足す行の状態は `enacted` だけ（画面では「成立・未施行」か「施行中」になる。`proposed` の行は受け付けない。0007）。
- **受け付けない**: 新しい値ID、計算部品、既存の期間の値の書き換え、状態の変更（案→成立など）、データの形の変更、切り替え表の変更。
- **変化率の上限**: 値の種類ごとに、前の期間からの変化率の上限を持つ。上限を超える変更は、鍵が正しくても受け付けない。
- **受け付ける範囲そのもの（「自動配信の許可表」）は、人の鍵で署名して配る**: どの値の種類を自動配信の対象にするか、種類ごとの変化率の上限はいくつか、を1つの文書にまとめ、データ用の人の鍵で署名する。アプリは初期版を同梱する。自動配信用の鍵では許可表を変えられない（自動配信用の鍵が漏れても、自分の権限を広げられない）。
- 受け付けなかったパックは適用せず、理由をアプリの記録に残し、FP向けの画面に「受け付けなかった更新がある」と出す。

### 4. 配信の目録の段階の欄、一時停止と巻き戻し

**配信の目録**（各データパックに付く、署名された説明書き）に、最初の版から次の欄を持つ。

| 欄 | 中身 |
|---|---|
| `manifestVersion` | 目録の形式の版 |
| `packId`・`field`・`version` | パックのID、分野、版 |
| `signer` | 署名した鍵のIDと種類（`data`（データ用＝人の鍵）／`auto_delivery`（自動配信用）。名前は 0017 の鍵の種類と同じ） |
| `changes` | 変える値ID・期間の一覧 |
| `issuedAt`・`serial`・`expiresAt` | 発行日時、通し番号、有効期限（古い目録を見せ続ける攻撃を防ぐ） |
| `reviewWindowEndsAt` | 確認期間の終わり（自動配信の分） |
| `rollout` | 段階配信: 段階の番号と、適用してよい割合（0〜100） |
| `paused` | 一時停止の印 |
| `rollbackOf` | 巻き戻しの場合: 巻き戻す元のパックの版 |
| `critical` | アプリが理解しなければならない欄の名前の一覧 |

- **段階配信**: 各アプリはインストールのときに0〜99の乱数（配信の組）を作り、手元にだけ持つ（送信しない）。目録の `rollout` の割合より組が小さいアプリだけが適用する。割合を段階的に上げて全体に広げる。配信元は、誰がどの組かを知らない。
- **一時停止**: 自動配信用の鍵（と人の鍵）で、配信中のパックの広がりを止められる。まだ適用していないアプリは適用を待つ。
- **巻き戻し**: 自動配信用の鍵（と人の鍵）で、自動配信で足した新しい期間の値を外せる。外した後は、その値は連動の規則による推計（0007）に戻る。巻き戻した値を使っていたプランには、FP向けの画面で知らせる。
- **段階配信にしないもの**: 重大な誤り（年金や税が数%以上ずれ、結論が変わるもの）の修正と取り下げは、全体に一度に配る。取り下げ・最低版の一覧は、別の鍵（オフラインに二重に保管）で署名する（0017）。
- **理解できない目録は適用しない**: アプリは、知らない `manifestVersion` や、`critical` に知らない欄が入った目録のパックを適用しない（安全な側に倒す）。知らない欄でも `critical` に入っていなければ無視してよい。

### 5. ほかの自動化と人の承認の線

| 自動化 | 自動で行うこと | 人が行うこと |
|---|---|---|
| 依存部品の更新 | 小さな更新は、すべてのテストが通れば自動で取り込む | 大きな更新は、画面の自動テストの結果を見て判断する |
| 不具合報告 | AIが再現・分類（入力ミス／仕様どおり／不具合）・修正案の作成まで行う。重大度を数値の物差し（年金・税・手取り・資金が尽きる年の差）で提案する。AIは重大度を上げられるが、下げられない | 重大度の判断と、修正の承認。修正の自動取り込みはしない |
| データの取得の故障 | 取得が止まったら、自動で直しの変更案まで作る | 変更案の承認 |
| お知らせ | 事実だけの短い文を作り、承認の後に自動でアプリ内と紹介ページに載せる | 承認 |

- 自動で動くAIの処理には、上限を設け、超えたら止めて知らせる。

## 理由

- **作る人と承認する人を分ける理由**: 変更を作った者が自分で承認できると、誤りが確認なしに通る。ボットの名義にすると、どの変更が自動で作られたかが履歴で一目で分かる。
- **自動配信を2種類と5つの関門に限る理由**: 形が前と同じで値だけが変わる更新は、複数の独立した確かめ方で正しさを判定できる。計算方法の変更や、税の段階表のような形の変わりうるものは、機械の判定では見落としがありうる。
- **卒業試験を置く理由**: 関門が実際に誤りを止められるかを、配る前に確かめるため。わざと混ぜた誤りを止められなければ、関門は飾りになる。
- **自動配信用の鍵の権限を、アプリの側で縛る理由**: 自動の仕組みは、人の確認を通らない分、鍵が漏れたときや判定が誤ったときの被害が大きい。アプリが「既にある値IDへの、同じ形の新しい期間の、上限内の追加」しか受け付けなければ、最悪の場合でも被害はその範囲に収まる。許可表を人の鍵で署名するのは、自動配信用の鍵が自分の権限を広げられないようにするため。
- **段階配信を手元の乱数で行う理由**: 配信元が利用者を識別せずに済む（提供元は利用者の情報を集めない。0012）。
- **最初の版に入れる理由**: 段階の欄・一時停止・巻き戻しを理解しない古いアプリは、配られたものをすぐに全部適用してしまい、止められない。β公開の時点で配ったアプリが理解していなければ、後から足しても効かない。

## 影響

- **後から変えると**: 自動配信用の鍵で受け付ける範囲を広げる変更は、配布済みのアプリの判定を変えることになり、許可表の署名の仕組みを通さずには行えない。目録の欄を後から足しても、古いアプリは理解できず、段階配信・一時停止・巻き戻しが効かない。
- **守るべき決まり**
  - 自動配信の対象を広げるのは、卒業試験に合格した分野だけ。広げたら公開の一覧を更新する。
  - 自動配信用の鍵で、許可表・計算部品・新しい値ID・取り下げの一覧に署名しない（アプリも受け付けない）。
  - 目録に新しい必須の欄を足すときは、`critical` に載せ、`manifestVersion` を上げる。
  - 重大な誤りの修正と取り下げを、段階配信にしない。
- **テストで確かめること**
  - 自動配信用の鍵で署名した次のパックを、アプリが受け付けないこと: 新しい値ID、計算部品、既存の期間の書き換え、状態の変更、形の変更、変化率の上限を超える変更、許可表に無い種類の値。
  - 許可表を自動配信用の鍵で署名しても、アプリが受け付けないこと。
  - 段階配信: 組が割合より小さいアプリだけが適用すること。割合を上げると広がること。
  - 一時停止の後に、未適用のアプリが適用しないこと。巻き戻しの後に、値が連動の推計に戻り、影響するプランに知らせが出ること。
  - 知らない `critical` の欄を持つ目録を適用しないこと。期限切れ・通し番号の古い目録を適用しないこと。
  - 変更案の流れの側: わざと誤りを混ぜた変更案（桁の誤り、期間のずれ、区分の取り違えなど）を、関門がすべて止めること。
