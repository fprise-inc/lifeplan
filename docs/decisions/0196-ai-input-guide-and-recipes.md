# 0196. AI接続口の入力の形の案内・直し方の分かるエラー・場面の手本

- 状態: 採用（一部未確定）（2026-11-11）
- 固定の強さ: 道具の名前と入出力（`get_input_guide`・`get_input_recipe`、エラーの文の「直し方」）は試験版（0015 と同じ。予告して変えることがある）。作り（エンジンと同じスキーマを埋め込んで案内と確かめ直しに使う・手本は接続口の中で世帯に合わせて変更を作る）は内部
- 前提にする記録: 0003（時点の型）、0004（ID）、0005（計算の実行環境・エラーには ID だけを入れる）、0006 の5（入出力の検査）、0008（入力の形・値の箱）、0015（AI接続口）、0183（数字の根拠）、0184（計算の前の処理）

## 背景

- AI が接続口の `calculate` に渡す入力（エンジンへの要求の `input`）を一から組み立てると、何度も計算が止まった。試しでは、AI が架空の世帯を一から作って4回目でやっと通った。
- 止まった理由は3つ。
  1. 入力の形の手がかりが見本の世帯しか無い。スキーマ（`engine/schemas/engine.input.json`）は約208KB あり、そのままでは AI に渡せない。区分ごとに引く道具も無い。
  2. エラーが場所と記号だけ（`/input:required`・`/input/household/members/0/id:pattern` など）で、何が足りないか・どう直すかが書かれない。エンジンは誤りを1つずつしか返さない。エラーに値を入れない（0005）。
  3. 書かないと黙って計算に入らない欄がある。家の頭金・諸費用（`residences[].purchase`）や、子の教育費・生活費がそうで、場面ごとに一緒にそろえる欄が分からない。
- 目標は、セミナー用の架空の世帯を、AI が少ない回数で組み立てられること。

## 決定

### 1. 入力の形の案内（`get_input_guide`。単体で使える群）

- エンジンと同じスキーマ（`engine.input.json`・`common.json`）を、ビルドの時に接続口に埋め込む。スキーマが変われば案内も変わる。
- `section` を省くと、次を返す（約9KB）。
  - 形の決まり: ID は UUID 第4版、金額は値の箱、率は文字、前提は年ごとの列、時点の形、空でも配列で書く区分、書かなければ入らない物
  - 入力の一番上の欄
  - 主な区分の一覧（鍵・呼び名・場所・必須）
  - 計算できる最小の入力の例（`skeleton`）: 会社員と扶養のパートの夫婦・賃貸・預金・生活費。計算できることをテストで確かめる
  - 新しい UUID 8つ（`freshIds`）
- `section` に区分の鍵（`members`・`employmentPeriods`・`accounts`・`residences`・`debts`・`goals`・`livingExpenses`・`assumptions`・`contingencies` など）か、入力の中の場所（例 `/household/residences/purchase`。配列の番号は省いてよい）を渡すと、その物について次を返す（どれも16KB 未満）。
  - 欄を1行ずつ: 「名前*: 形 — 説明 [入力項目ID]」。必須の欄を先に並べる。形は「金額の箱」「時点」「選択 rent|own」「物（price*・downPayment*…）」などの短い呼び名で、呼び名の意味は `legend` に付ける
  - if/then の条件の文（例「type が regular|contract|partTime|civilServant のとき: healthInsurance・pensionCategory・employer・salary も必須」）と、oneOf の枝（関係の夫婦と親子など）
  - 見本の世帯から取った例（`exampleFrom`。3KB を超えたら世帯の ID だけ）と、同じ物を持つほかの見本の世帯
  - 区分ごとの注意（書かないと入らない物。人が書いた短い文）と、関係する手本
- 説明の文は、スキーマの `title`・`description` を短くした物（頭の設計記録の番号は外し、90字で切る）。

### 2. 直し方の分かるエラー（`calculate`・`explain_value`）

- エンジンが入力の形の誤り（`E_INPUT_SCHEMA`）を返したら、接続口は同じスキーマで入力（changes を当てた後）を確かめ直し、見つかった所を最大20件、エラーの文に「直し方」として足す。エンジンが言った場所を先に並べる。それぞれ次を書く。
  - 足りない欄の名前と形
  - 知らない欄と、使える欄
  - 選べる値
  - 正しい形（「UUID 第4版の文字…"self" などの名前は使えない」「値の箱 {"value": 円の整数, "state": "confirmed", "origin": {"kind": "manual"}}」「年ごとの列 {"default": "0.01"}」「時点 {"at": "YYYY-MM"}…」）
  - 条件つきの必須（「type が … のとき: …」）
  - oneOf のどの形に合わせるか
- 同じ形の説明は2回目から「（形は上と同じ）」と短くする。素朴な入力でも、1回の答えで約3KB に収まる。
- 確かめ直しはスキーマの決まりを読む小さな検査（`$ref`・type・properties・required・additionalProperties・enum・const・pattern・範囲・items・allOf・oneOf・anyOf・not・if/then・propertyNames）。判定はいつもエンジンが正で、確かめ直しは直し方の手がかりだけに使う。エンジンが通した入力を止めない。見本の世帯（54件）と骨組みで誤りを1つも出さないことを、テストで確かめる。
- 形は合っているのに、ほかのエラー（時点の指す先が無いなど）のときは、コードごとの目安を書く。UUID の形の値が世帯のどの物の `id` とも合わないときは、その場所も書く。
- `changes` を当てられなかったときにも、目安を足す（`/-` で末尾に足す・配列が無ければ配列ごと add・区分の名前は `get_input_guide`）。
- 答えに入力の値は写さない（場所・欄の名前・スキーマの中身だけ）。渡された世帯（`share_id`）の入力でも同じ。エンジンのエラーに値を入れない決まり（0005）と合わせる。

### 3. 場面の手本（`get_input_recipe`）

- 手本は6つ。どれも、関係する欄を一緒にそろえる。

  | 手本 | そろえる物 |
  |---|---|
  | `buyHome`（家を買う） | 今の住まいを前の月で住み終わり（持ち家なら評価額で売る）、入居のイベント、持ち家（購入の価格・頭金・諸費用・新築か・固定資産税・修繕費・名義・評価）、住宅ローン（金利・返済・団信・住宅ローン控除の住宅の情報。入居と住まいを指す） |
  | `newChild`（子が生まれる） | 子の構成員（大学を出た翌月の4月に独立）、親子の関係、教育の目標（公立・標準・私立の3つの進路。保育所は選ぶ）、子の分の生活費（独立の前の月まで、別の生活費の行で） |
  | `retire`（退職の年齢） | 画面の「働く最後の年齢」（`app/src/workspace/levers.ts` の `retireAt`）と同じ決まりで、働き方の期間を終える・延ばす（後の期間は外す）、ご本人なら退職の段階の生活費、退職の月に終わっていた積立の終わり。再雇用は入れない |
  | `prepayment`（繰上返済） | 負債の `prepayments` に、mode（必須）も入れて足す |
  | `startNisaIdeco`（NISA と iDeCo を始める） | その人の NISA・iDeCo の口座が無ければ残高0円で作る。積立・掛金を足す（終わりは空＝退職の月まで） |
  | `contingency`（万一の想定） | 死亡・障害・就業不能の想定（1件まで。今の想定があれば置き換え）。必要保障額の推移（`/protection`）も選べる |

- 世帯は `calculate` と同じく、見本の世帯（`sample_household_id`）・渡された世帯（`share_id`）・AI が組み立てた入力（`input`）のどれか1つ。接続口は世帯を読んで、その世帯の構成員・物の ID と配列の位置に合わせた `changes` を返す。形は今の `calculate` の JSON Pointer の add・replace・remove。
  - `share_id` は `calculate` と同じく、アプリ本体の計算に使う読み取りを通る（同意・期限・縮約・仮の ID）。読んだことは、道具の名前 `get_input_recipe` で「AIに渡した記録」に残る。
- `params` で時期・額・選び方を変えられる。省いた物は既定の値で、使った値は答えの `params` に出す。知らない `params` と形の違う値は、使える物を添えて断る。
- `apply: true` なら、changes を当てた後の `input` も返す。手本を重ねるときは、それを次の手本の `input` に渡す。別々に作った changes を並べると、配列の位置や「配列ごと add」がぶつかるため。
- 答えの `notes` に、何を入れたか・入れていない物（再雇用・出産での収入の変化・売却の税など）・確かめ方を書く。
- 当てられない世帯（負債が無いのに繰上返済、働き方の期間が無いのに退職）は、理由を返して断る。
- 既定の値は目安。
  - 家: 価格4,000万円・頭金1割・諸費用は新築5%（中古7%）・変動0.9%・35年・住宅の種類 ZEH（2028年以後に入居する新築の省エネ基準適合住宅は住宅ローン控除の対象外になるため）
  - 子: 生活費 月3万円
  - NISA 月3万円・iDeCo 月2万円
- テストで確かめること: 6つの手本を見本の世帯54件のすべてに当て、当てられる世帯では計算が通り、当てられない世帯では理由を返すこと。骨組みに5つの手本を重ねると、頭金・諸費用・教育費・児童手当・繰上返済・iDeCo・遺族年金の行が表に出ること。

### 4. 確かめた結果（一から世帯を作る流れ）

- 同じ架空の世帯（夫婦と3歳の子・賃貸・2028年に家を買う）を、道具の答えだけを手がかりにする AI に一から組み立てさせ、前の道具と比べた。どちらもソースコードと文書は見せていない。
  - 前の道具: `calculate` は6回目で通った（道具は16回）。ID の形、`housing` と `purchase` の足りない欄、`propertyType` の選べる値が分からず、見本の世帯と対応範囲の一覧から推し量った。
  - 新しい道具: `calculate` は1回目で通った（道具は10回。うち3回は答えを確かめる計算）。骨組みを写して直し、`newChild` と `buyHome` を `apply` で重ねた。
- そのとき出た残りの課題は、未確定に書く。

### 5. 画面と同じ「動かす項目」で計算する書き方との関係

- 手本の changes は、今の JSON Pointer の形で返す。`retire` は、画面の `retireAt` と同じ決まりを接続口の中で書き直したもの（画面の関数を同梱していない）。
- 画面の動かす項目と同じ書き方（対象・入力項目ID・値）が `calculate` に入ったら、次を決める。
  - 退職・NISA の積立・生活費のように、動かす項目があるものは、手本もその書き方で返せるようにするか
  - `retire` を、画面の関数を使う書き方に置き換えるか

## 理由

- 区分ごとに短く返せば、AI が要る所だけを読める（全体208KB を渡さない）。スキーマから作るので、入力の形が変わっても案内がずれない。
- エンジンの検査（ビルドの時に作った検査器・最初の誤りだけ・値を入れない）は変えない。直し方は、接続口の中で同じスキーマを読んで作る。エンジンの答えと速さに触れずに、1回で多くの直し方を返せる。
- 手本は、場面ごとの「一緒にそろえる欄」の知識。AI が見本から推し量るより確かで、書き忘れて黙って入らない物を減らす。世帯に合わせた changes にすれば、AI は ID と配列の位置を数えなくてよい。

## 影響

- 接続口の道具が2つ増える（単体で使える群。`get_input_recipe` の `share_id` だけ、世帯を扱う群と同じ扱い）。INSTRUCTIONS に、入力を組み立てるときは案内と手本を使うことを足した。
- 接続口の依存に `regex` を足した（スキーマの pattern を読むため。アプリ本体の `ai-share` と同じ版）。
- スキーマの欄を足す・変えると、案内と確かめ直しは自動で変わる。見本の世帯で偽の誤りを出さないテストが、確かめ直しの読み違いを捕まえる。
- 手本は人が書いた決まりなので、入力の形を変えたら（購入・ローン・教育・積立の欄）、手本のテストが落ちて見直しを促す。

## 未確定

- 計算の答えの `summary` には内訳が無く、`rows` に渡す行ID の一覧を先に知る手段も無い（試しの AI は、一度絞らない表を取って行ID を知った）。計算の答えを小さくする作業の側で、行の一覧を返すか。
- 知らせ（`N_NOT_ELIGIBLE` など）がコードだけ。知らせを文にする作業の側で直す。
- 欄の説明に、「その月を含むか」（働き方の期間の `to`）・「返済は借入の翌月から」などの数え方を足すか（スキーマの説明を直すか、区分の注意に足すか）。
- 手本を足すか: 配偶者を足す・転職・介護・車の買い替え・相続・贈与・再雇用。
- 子の生活費を別の行で足すのでなく、今の生活費の段階で増やす書き方も選べるようにするか。
- 画面と同じ「動かす項目」の書き方との関係（決定の5）。
