# 0087. お知らせの一覧（上の帯のベル）と、要望・不具合の受付番号

- 状態: 採用（一部未確定）（2026-10-30）
- 固定の強さ: **既読の印・受付番号を配信元に送らない（アプリは何も送り返さない）こと**、種類が4つで宣伝の種類を作らないこと、急ぎ具合の3段（重大・ふつう・参考）、配信元のお知らせの形式（封筒・一覧・1件の欄。`app/schemas/notices.json`）と読む口が1か所であること、受付番号の形（`R-` と、0・O・1・I・L を除いた英大文字・数字4文字）、要望のフォームの URL に差し込むのが受付番号・アプリの版・OS だけであることは骨格。一覧の見た目・文言・並び・種類の印の色・見出しの文は内部（後から変えてよい。変えたら追記に書く）
- 前提にする記録: 0012（識別と持たない情報）、0016（画面は外と話せない箱）、0017（配布・更新・署名・取り下げ）、0035 の8（開いたときの知らせ）

## 背景

- 上の帯の「通知」のベルは、本体が返す保存先・同期の通知（復元キーの保管・事務所の共有など）と、編集中の人、世帯の開いたときの知らせ（0035 の8）を並べる入れ物だった。0件のときはベル自体を出さず、世帯の知らせは押すと世帯ファイルから消していた（1回だけ見せる）。
- 配信元から「更新の中身・新しい機能・要望への対応」や「制度データ・学費などの更新・誤りの修正」を知らせる場所が無かった。0017 の3 に「お知らせ」の経路（データ用の鍵で署名した JSON）と配信先（`config/distribution.toml` の `notices`）は決めてあったが、形式と画面は未定だった。
- FP からの要望・不具合の知らせを受けて直したときに、その FP にだけ「あなたの要望に対応しました」と知らせたい。ただし、アプリは FP・PC・世帯を識別する値を送らない（0012・0017 の4）。

## 決定

### 1. ベルと一覧

- ベルは**常に出す**（0件でも）。数字は**未読の件数**（参考を除く）だけで、0なら数字を出さず、落ち着いた色にする。読み上げの名前は「お知らせ（未読 n件）」、0件なら「お知らせ」。
- 押すと帯の下に一覧を重ねて出す: 「未読」「すべて」の切り替え、種類の絞り込み、「すべて既読にする」、一覧の下に「要望・不具合を送る」。
- 1件を押すと詳しい中身: **何があったか（見出し）→ 何が変わったか（本文）→ 関係する世帯 → その画面を開くボタン**。開いたものは既読になり、**一覧に残る**（押しても消さない）。
- 並び: 重大を先に、次に今の状態の知らせ（世帯・事務所。日付なし）、配信元のお知らせは日付の新しい順。

### 2. 種類は4つ（宣伝の種類は作らない）

| 種類 | 鍵 | 中身 | どこから |
|---|---|---|---|
| ファイナンシアから | `app` | 更新の中身・新しい機能・要望への対応 | 配信元 |
| 制度・データの更新 | `data` | 制度データ・学費などの更新、誤りの修正 | 配信元 |
| 世帯 | `household` | 変換の段の知らせ（`smrBlank`・`outsideFamily`・`unresolvedDiffs` など。0035 の8） | 開いている世帯のファイル |
| 事務所 | `office` | 保存先・復元キー・事務所の共有の通知（本体の `storage_notices`）と、ほかの人が開いていること | 本体 |

- 一覧では種類の印（色と短い名前）を見せ、種類で絞れる。
- **宣伝には使わない**: 配信元の形式の `kind` は `app`・`data` の2つだけ。知らない種類の1件はアプリが捨てる（宣伝の種類を後から足しても、どのアプリにも出ない）。
- 今ある知らせの**文言と押したときに開く画面は変えない**（入れ物を変えるだけ）。一覧の見出し（何があったか）だけを足した（`header/status.ts` の `storageNoticeTitle`・`householdNoticeText` の `title`）。

### 3. 急ぎ具合は3段

| 段 | 鍵 | 動き |
|---|---|---|
| 重大 | `critical` | 未読の間、上の帯の札（「重大なお知らせ」）でも出す。押すと一覧でその1件を開く。件数に数える |
| ふつう | `normal` | 件数に数える |
| 参考 | `info` | 一覧に入るだけ（「未読」の一覧には出るが、件数に数えない） |

- 本体の通知の `level` は、`alert` → 重大、`warn` → ふつう、`info` → 参考に当てる（このため、参加の承認待ち・まだ移していない世帯・この PC の中の復元キーの保管は参考になり、件数に数えなくなった）。編集中の人・世帯の知らせはふつう。

### 4. 既読の印と受付番号は手元にだけ置く（何も送り返さない）

- 既読の印と覚えた受付番号は、**この PC のアプリのデータ**（`<アプリのデータの場所>/notices/local.json`。開発用のビルドは `notices-dev/`）にだけ置く。本体の命令 `notice_local_get`・`notice_local_put` で読み書きする（画面の保存の仕組みは使えない。0016 の1）。形は `{"read": {鍵: 既読にした日}, "receipts": [{"code", "on", "manual"?}]}`。既読の印は 2000 件・受付番号は 200 件を上限にし、古いものから忘れる。
- **既読かどうかを配信元に知らせない**。アプリは配信元に何も送らない（0017 の4 の「送るのは更新の判定に要る版・OS・CPU だけ」を変えない）。
- 世帯の知らせの既読も手元に置く（**世帯ファイルには書かない**）。理由: 事務所では複数の人が同じ世帯を開くので、既読は人ごと・PC ごとの手元が自然。世帯ファイルに書くと、1人が開いただけでほかの人には既読になってしまう。このため、世帯の知らせは押しても世帯ファイルから消さなくなった（0035 の8 の追記）。世帯ファイルの形式は変えない（0.38 のまま）。
- 既読の鍵: 配信元のお知らせは `feed:<ID>`、世帯の知らせは `household:<世帯の内部ID>:<知らせのID>`（同じ知らせの ID が別の世帯にもあるため）、事務所の知らせは `office:<種類>:<文>`（数が変わるなど文が変われば、また未読になる）。事務所の知らせは今の状態の知らせなので、本体が返さなくなれば一覧から消える。

### 5. 配信元のお知らせの形式と読む口

- 全員に同じ一覧を配る。形式は `app/schemas/notices.json`（JSON Schema）。
  - **封筒** `{"format": "financia-notices-envelope", "formatVersion": "1.0", "payload": "<一覧の JSON の文字列>", "signatures": [{"keyId", "alg": "ed25519", "sig"}]}`。署名は `payload` の UTF-8 のバイト列への切り離した Ed25519 の署名（0017 の5。お知らせは**データ用の鍵**）。正規化をせずに確かめられるよう、一覧は文字列のまま入れる。
  - **一覧** `{"format": "financia-notices", "formatVersion": "1.0", "issuedAt", "notices": [...]}`。`formatVersion` は MAJOR.MINOR（0001）。MINOR を上げた一覧は、古いアプリが知らない欄を無視して読む。MAJOR が違えば読まない。
  - **1件** `id`（変えない。既読の鍵）・`kind`（`app`／`data`）・`urgency`（`critical`／`normal`／`info`）・`date`（YYYY-MM-DD）・`title`（何があったか）・`body`（何が変わったか）・任意の `appVersions`（`min`・`max`。どちらも含む）・任意の `receipts`（受付番号の並び。6）・任意の `screen`（関係する画面: `plans`・`work`・`family`・`storage`・`office`・`households`・`recovery`）。形の合わない1件・知らない種類・急ぎ具合・画面の1件は捨て、ほかは読む。
- **読む口は本体の `notices_feed` の1か所**（`app/src-tauri/src/notices.rs`）。封筒を確かめ（知らない鍵の署名・署名なしは拒否。どれか1つがデータ用の鍵の現用・次期で確かめられれば受け付ける）、確かめた一覧の文字列だけを画面に渡す。画面（`notices/center.ts` の `parseFeed`）は1件ずつ形を確かめて出す。
- 今は鍵が無く（`config/distribution.toml` の `[keys] data` が空）、更新の仕組み（通信）も入れていないので、**製品のビルドは何も渡さない**。開発用のビルドと開発用のサーバーだけ、環境変数 `FINANCIA_DEV_NOTICES` に書いた手元のファイル（見本は `app/schemas/notices.dev-sample.json`。署名なし）を読む。署名なしを受け付けるのは開発用のビルドだけ（0017 の「開発用の抜け道を本番に入れない」）。
- 更新の仕組みを入れる回で: 配信先 `endpoints.notices` から封筒を受け取って保存し、`notices_feed` がそれを読む。鍵は build.rs が `[keys] data` から作り、`verify_ed25519` に Ed25519 の確認を入れる（今はここに来ない）。

### 6. 要望・不具合の受付番号

- 「要望・不具合を送る」を、FP のメニュー（「ファイナンシアへ」）とお知らせの一覧の下に置く。開くと受付番号（でたらめに作る短い番号。例 `R-7K2Q`。`R-` と、**0・O・1・I・L を除いた**英大文字・数字の31文字から4文字。暗号の乱数で、剰余の偏りが出ないように選ぶ）を大きく出す。
- 「フォームを開く」を押すと、その番号を手元に覚え（日付つき）、**既定のブラウザで要望のフォームを開く**。フォームの URL は `config/distribution.toml` の `[feedback] form` の1か所に、差し込む印 `{受付番号}`・`{版}`・`{OS}` つきのひな形で置く（今は**仮の値**）。差し込むのは**受付番号・アプリの版・OS（おおまかな名前）だけ**で、世帯の情報・FP や PC を識別する値は入れない。画面は本体に受付番号だけを渡し（`feedback_form_open`）、本体がひな形に版と OS を差し込んで開く（画面から任意の URL は開けない。https だけ）。
- **アプリ自身は送らない**。ブラウザでフォームを開くのは FP の操作で、アプリの自動の通信ではない（0017 の4 の自動の通信先は増えない）。
- フォームが差し込みに対応していないときのために、番号は「写す」で写せる（本体の `feedback_copy`。受付番号の形のものだけ写す）。
- 配信元のお知らせに受付番号の並びがあり、**手元に覚えた番号と合うものだけ**を「あなたの要望に対応しました」として出す（合った番号を添える）。**受付番号を持つお知らせは、合わない PC には一覧にも出さない**。
- 別の PC で入れ直したとき・別の PC で送ったとき用に、受付番号を手で入れる欄を置く（小文字・全角・`R-` なしも読む。使わない文字・長さ違いは理由を出す）。覚えた番号の一覧（日付つき・この PC で送ったか手で入れたか）も見られる。
- 宛先のフォームは config の値だけで差し替えられ、フォークは自分のフォームにできる（0017 の2）。`npm run check:distribution` が、ひな形が config の外に書かれていないことを確かめる。

## 理由

- **既読を手元だけに**: 既読を集めると、どの FP がいつ何を読んだかが配信元に残る。お知らせの役目は「届けること」で、読んだかを知る必要は無い。0012 の「FP・PC を識別する値を送らない」とも合う。
- **受付番号をでたらめに作って手元で照らす**: 配信元は番号と要望の中身だけを知り、どの PC の番号かは知らない。全員に同じ一覧を配っても、合う PC にだけ出せる。4文字（約92万通り）は、同時に対応中の要望の数に対して重なる心配が小さく、電話やメールでも読み上げられる長さ。
- **紛らわしい文字を除く**: 手で写す・読み上げることがあるため。
- **フォームのひな形に3つだけ差し込む**: 受付番号を FP が書き写す手間と誤りを減らしつつ、渡す値を目で確かめられる範囲に留める。
- **世帯の知らせを世帯ファイルに書かない**: 形式を変えずに済み、人ごとの既読にできる。

## 代案（採らなかったもの）

- 既読を世帯ファイルに書く: 事務所の共有で1人が読むと全員に既読になる。形式の MINOR も上がる。
- 要望をアプリから送る: 自動の通信先が増え、送る中身の確かめが要る（0017 の4）。
- メールの下書き（mailto）: 宛先・本文の扱いがメールのアプリごとに違い、受付の整理がしにくい。フォームにした（2026-10-30）。

## 影響

- **守るべき決まり**
  - 既読・受付番号・一覧を開いたことを、どこにも送らない。
  - 配信元のお知らせに宣伝の種類を足さない。足しても読まれない形を保つ（知らない種類は捨てる）。
  - 署名なしの封筒を受け付けるのは開発用のビルドだけ。
  - フォームのひな形に差し込める印は `{受付番号}`・`{版}`・`{OS}` だけ（prepare-assets と build.rs が検査する）。
- **テストで確かめること**（`app/test/notice-center.test.ts`・`app/test/header.test.ts`・`notices.rs` のテスト）
  - 既読にしたものが「すべて」に残り、手元の状態を読み直しても残る。参考を件数に数えない。0件のベルに数字が出ない。
  - 受付番号の合うお知らせだけが出て、合わない受付番号つきのお知らせは一覧にも出ない。版の範囲の外は出ない。
  - 受付番号の文字（0・O・1・I・L を使わない）と形、手で入れた番号の読み方。
  - フォームの URL に受付番号・版・OS 以外が入らない。
  - 封筒: 署名なしは開発用だけ、知らない鍵・正しくない署名・形式違いを拒否する。

## 後で足すもの（4月の正式公開の分）

- **制度改正で結果が変わる世帯を数える知らせ**: 種類「制度・データの更新」（`data`）の手元の知らせとして足す（配信元のお知らせの `id` を手がかりに、手元で世帯を計算し直して数える。関係する世帯は一覧で見せる）。数えた結果は手元だけに置く。
- **ヒアリングシートの受け取りフォルダ**: 種類「事務所」（`office`）の手元の知らせとして足す（受け取った件数。押すと取り込みの画面）。
