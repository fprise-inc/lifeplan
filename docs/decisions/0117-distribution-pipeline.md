## 背景

- 0017 で、識別子・署名の名義・配布元の設定の1か所化・更新の4経路・自動通信の相手・4種類の鍵（現用＋次期）・段階配信の欄・取り下げと最低版を骨格として決めた。0022 で、配信の目録の欄（段階・一時停止・巻き戻し・`critical`）と自動配信用の鍵の範囲を決めた。
- 残っていたのは、それを実際に回す段取り: 鍵をどこに置き、どう入れ替え、失くしたらどうするか。目録の正確な形。Mac の署名と公証、Windows の署名の方式、CI でのビルドと署名。Tauri の updater（公開鍵を1本しか設定できない）で2本の鍵を確かめる方法（0017 の未確定）。
- 利用者の判断: ストアに出さず Web から配る。Windows は管理者権限のいらないインストーラーと企業向けの MSI、Mac は Intel・Apple シリコン。β公開に間に合わせる。

## 決定

### 1. 全体の流れ

```
提供元                                           配信元（配布元の設定の host）             アプリ（Rust 側だけで確かめる）
アプリ本体: CI でビルド → Tauri の鍵で署名 ───→ /v1/app/latest.json と配布物            ①取り下げの一覧 → 鍵の束から外す
            目録を tauri signer sign で署名 ──→ /v1/app/catalog.json                     ②アプリの目録 → 段階・一時停止・最低版
制度・マスタ: 承認 → データ用の鍵で署名 ──────→ /v1/packs/index.json とパック               → 当てるなら、確かめた鍵で Tauri の updater
            自動配信 → 自動配信用の鍵で署名 ──→ （同じ index.json の別の項目）              ③パックの目録 → 範囲・確認期間・段階 → 要約を確かめて当てる
お知らせ: データ用の鍵で署名 ───────────────→ /v1/notices/notices.json                    ④お知らせ（0087）
取り下げ: 取り下げ用の鍵（オフライン）で署名 ──→ /v1/revocations/revocations.json
コードを止める: コードを止めるだけの鍵で署名 ──→ /v1/revocations/feature-codes.json（追記の2）
```

- 確かめる順番は、取り下げの一覧が先（漏れた鍵を外してから、ほかの目録を確かめる）。
- 確かめる部品は `crates/distribution`（ネットにつながない。バイト列と手元の状態と今の時刻を受け取り、受け付けるか・当てるか・待つかだけを返す）。取りに行く・保存する・帯を出すのはアプリ本体（この記録の段取りの「未確定」）。
- 受け付けない理由は符号（`E_DIST_FORMAT`・`E_DIST_UNSUPPORTED`・`E_DIST_KEY`・`E_DIST_SIGNATURE`・`E_DIST_SIGNER_MISMATCH`・`E_DIST_OLDER`・`E_DIST_EXPIRED`・`E_DIST_SCOPE`・`E_DIST_DIGEST`）だけで返し、中身や鍵を文に入れない。

### 2. 鍵の体系と保管・入れ替え・失くしたとき

鍵は、0017 の5 の4種類と、OS のコード署名の2つ。

| 鍵 | 形 | 作る道具 | 秘密鍵の置き場所（ふだん） | オフラインの控え | 使う人・場所 |
|---|---|---|---|---|---|
| アプリ更新用（現用） | minisign（Tauri の updater） | `tauri signer generate` | CI の秘密の値（`TAURI_SIGNING_PRIVATE_KEY`。必須の承認を付けた環境に置く） | 暗号化した USB メモリ2本（別の場所）＋パスワードは紙とパスワード管理 | CI のリリースのビルド |
| アプリ更新用（次期） | 同上 | 同上 | オフラインの控えだけ（入れ替えるまで CI に入れない） | 同上 | 入れ替えのときだけ |
| データ用（現用・次期） | Ed25519（「鍵の名前:公開鍵」） | `dist-keys keygen data …` | 承認する人の PC（リポジトリの外。暗号化したディスクの中） | 同上 | 人が承認した制度・マスタのパック、お知らせ、自動配信の許可表 |
| 自動配信用（現用・次期） | Ed25519 | `dist-keys keygen auto_delivery …` | CI の秘密の値（既定のブランチだけが使える、アプリ更新用とは別の環境） | 同上 | 決まった関門を通った自動の更新（0022） |
| 取り下げ用（現用・次期） | Ed25519 | `dist-keys keygen revocation …` | オフラインの控えだけ（ネットにつないだ場所に置かない） | 同上 | 取り下げの一覧の発行（期限があるので、少なくとも期限の前に出し直す）。機能を有効にするコードの取り下げも（追記 2026-11-04） |
| 機能を有効にするコード（現用・次期。追記 2026-11-04） | Ed25519 | `feature-code keygen --kid …`（0110 の6） | 発行する人の PC（リポジトリの外 `~/.lifeplan-issuer/`。暗号化したディスクの中） | 同上 | コードの発行（`feature-code issue`・`batch`）。ほかの物には署名しない |
| 機能を有効にするコードを止めるだけ（現用・次期。追記の2） | Ed25519 | `dist-keys keygen feature_code_revocation …` | 現用は CI の秘密の値（`FEATURE_CODE_REVOCATION_KEY`。GitHub の環境 `feature-code-revocation`。既定のブランチだけ）と発行する人の PC。次期はオフラインの控えだけ | 同上 | コードを止めるだけの一覧（`/v1/revocations/feature-codes.json`）。ほかの物には署名できない |
| Mac の Developer ID | Apple の証明書（.p12） | Apple のアカウントの所有者だけが作れる | CI の秘密の値（`APPLE_CERTIFICATE`） | .p12 とパスワードを同じ USB に | CI の Mac のビルド |
| Windows の署名 | 秘密鍵は持たない（Azure Artifact Signing の中） | 申し込み・本人確認の後に Azure が発行 | CI には署名の役割だけを持つアプリの登録の値（`AZURE_*`） | アプリの登録の作り直し方を書いておく | CI の Windows のビルド |

- **秘密鍵はリポジトリ・クラウドの開発環境・CI の公開ログに置かない**（0017・0021）。CI の秘密の値に置くのは、CI が使うもの（アプリ更新用の現用・自動配信用の現用・コードを止めるだけの鍵の現用〔追記の2〕・OS の署名）だけ。データ用・取り下げ用・各次期は CI に入れない。
- アプリ更新用の現用を CI に置くと決めた: リリースのビルドは CI で行い、Tauri はビルドの中で更新のファイルに署名する。手元で署名し直す運用は、1人で回すには手順が多く、誤りやすい。漏れたときの被害は、役割の分離（データ・取り下げには使えない）・次期の鍵への入れ替え・取り下げの一覧で抑える。
- 鍵の名前は、作った年と通し文字（例: `data-2026a`、次期は `data-2026b`）。アプリ更新用は鍵の番号（16桁の16進）が名前になる。
- 同じ公開鍵を2つの役割に使わない（`npm run check:distribution` と部品が止める）。

**入れ替え（ふだん）**

1. 公開の前に、4種類とも現用と次期の2本を作り、公開鍵を配布元の設定の `[keys]` に並べる（β公開のアプリから2本とも入る）。
2. 入れ替えるときは、次期の鍵で署名を始める（配布済みのアプリは次期も持っているので、そのまま受け取る。アプリ本体の更新は、確かめられた鍵を Tauri の updater に渡すので実行中に切り替わる。3 を見る）。
3. 次の版のアプリで `[keys]` を「元の次期を現用に、新しい次期を足す」に直す。元の現用は、取り下げの一覧に載せるか、そのまま使わずに置く。
4. 入れ替えの目安は、漏れの心配が無ければ2年ごと（データ用・自動配信用）。アプリ更新用と取り下げ用は、事故が無ければ入れ替えない。

**漏れた・失くしたとき**

| 起きたこと | すること |
|---|---|
| どれかの現用が漏れた | 取り下げの一覧の `revoked.keys` にその鍵の名前を載せて出す（アプリは鍵の束から外す）。次期で署名を始め、次の版で新しい次期を足す |
| どれかの現用を失くした（漏れていない） | 次期で署名を始める。次の版で新しい次期を足す |
| アプリ更新用を2本とも失くした | 配布済みのアプリへ自動で更新を届けられない。お知らせ（データ用）で手動の入れ直しを案内し、取り下げの一覧の `minAppVersion` で古い版の計算と出力を止め、新しい鍵の版をダウンロードで配る。これを避けるためにオフラインの控えを2か所に持つ |
| 取り下げ用の1本が漏れた | もう1本で一覧を出し続ける。取り下げ用の鍵は一覧では外せない（漏れた鍵で、もう1本を外して乗っ取るのを防ぐ）ので、アプリ本体の更新で入れ替える |
| 取り下げ用を2本とも失くした | 新しい取り下げ用の鍵を入れたアプリ本体の更新を配る（アプリ更新用の鍵で）。それまで取り下げを出せない |
| データ用・自動配信用を2本とも失くした | アプリ本体の更新で新しい鍵を入れる。それまでパックとお知らせは止まる（アプリは手元のパックで使い続けられる） |
| Mac の証明書を失くした・期限が来る | アカウントの所有者が作り直す（配布済みのアプリの更新は Tauri の鍵で確かめるので影響しない） |
| Windows の署名が使えなくなった | 5 の代わりの方式に移る。発行元の名前が変わると SmartScreen の評判は最初からになる |

### 3. 更新の目録の形

3つとも「封筒（署名）＋中身の JSON の文字列」。中身は署名を確かめた後に読み、中身の `format` を必ず確かめる（同じ鍵で署名する別の種類の中身と取り違えない）。形式の版の MAJOR が違うもの、`critical` に知らない欄があるものは当てない（知らない欄は `critical` に無ければ無視する。0022 の4）。時刻は UTC の `YYYY-MM-DDTHH:MM:SSZ`。

**(1) アプリ本体の目録 `catalog.json`**（配布元の設定の `[endpoints] app_catalog`）

```json
{
  "format": "financia-app-catalog-envelope", "formatVersion": "1.0",
  "payload": "{\"format\":\"financia-app-catalog\",\"catalogVersion\":\"1.0\",\"serial\":7,\"issuedAt\":\"…\",\"expiresAt\":\"…\",\"version\":\"1.2.0\",\"rollout\":{\"stage\":1,\"percent\":10},\"paused\":false,\"noDefer\":false,\"critical\":[]}",
  "signature": "<payload のバイト列への tauri signer sign の署名（.sig の中身）>"
}
```

- 署名はアプリ更新用の鍵（minisign の形）。配布物と同じ道具・同じ鍵で署名する。署名の中の鍵の番号で、現用か次期かが分かる。
- アプリは、確かめられた鍵の公開鍵を Tauri の updater に渡し（`updater_builder().pubkey(..)`）、目録の `version` だけを受け付ける（`version_comparator`）。これで **Tauri の updater に1本しか設定できない公開鍵の制約を越えて、現用と次期のどちらで署名した更新も受け取れる**（0017 の未確定を、この形で決めた）。
- `latest.json`（`[endpoints] app`）は Tauri の形のまま（版・各 OS の URL と署名）。全部の OS を1つのファイルに書くので、アプリは問い合わせに版・OS・CPU の種類を付けない（Tauri の差し込み `{{target}}` などは使わない）。
- `rollout`（段階。0〜99 の配信の組が `percent` より小さいアプリだけ）・`paused`（一時停止）・`serial`（増える一方）・`expiresAt`（過ぎたら受け付けない）。
- `noDefer`: FP が最大14日遅らせる設定（0017 の7）を無視する更新（世帯ファイルの形式が変わる更新など）。取り下げの一覧の最低版より古いアプリは、段階の順番を待たずに受け取り、遅らせられない（一時停止は守る）。
- **巻き戻し**: アプリは古い版に戻さない。問題のある版は `paused` で止め、前の中身を新しい版の番号で配る。

**(2) パックの配信の目録 `index.json`**（`[endpoints] packs`）

- 入れ物 `{"format":"financia-pack-index","formatVersion":"1.0","entries":[封筒, …]}` には署名しない。中の封筒（`financia-pack-catalog-envelope`）を1つずつ、データ用か自動配信用の鍵で確かめる（0017 の6: 項目ごとの署名）。
- 中身の欄（0022 の4 の欄に、ファイルの指し方を足した）: `format`（`financia-pack-catalog`）・`catalogVersion`・`packId`・`field`・`version`・`signer`（`keyId` と `role`。`data` か `auto_delivery`）・`file`（`path`〔配信元の中の相対の場所。ほかのホスト・`..` は不可〕・`sha256`・`size`）・`changes`（`valueId`・`kind`・`from`）・`issuedAt`・`serial`・`expiresAt`・`reviewWindowEndsAt`・`rollout`・`paused`・`rollbackOf`・`critical`。
- `signer` に書いた鍵と、実際に確かめられた鍵が違えば受け付けない（自動配信用の鍵で「data」と偽るのを止める）。取り下げ用・アプリ更新用の鍵では署名できない。
- `changes[].kind` は `addPeriod`（新しい期間を足す）・`removePeriod`（巻き戻しで外す）・`addValue`・`modifyPeriod`・`changeStatus`。**自動配信用の鍵では `addPeriod` だけ（巻き戻しの目録では `removePeriod` も）を受け付け、`reviewWindowEndsAt`（確認期間の終わり）が無ければ受け付けず、その時刻まで当てない**。パックの中身が本当にその変更だけか（既にある値IDに同じ形の期間を1つ足すだけか・変化率の上限内か）は、パックを当てる部品が手元のパックと比べて確かめる（0022 の3。段取りの「未確定」）。
- 版は手元より新しいものだけ。巻き戻しも新しい版で配り、`rollbackOf` に外す元の版を書く（元の版は配る版より前でなければならない）。
- 取ってきたパックのファイルは、`sha256` と `size` が合うものだけを使う。

**(3) 取り下げの一覧 `revocations.json`**（`[endpoints] revocations`）

- 封筒は `fprise-lifeplan-revocations-envelope`、中身は 0017 の7 の形のまま（`format`・`formatVersion`・`serial`・`issuedAt`・`expiresAt`・`minAppVersion`・`revoked`〔`regulationValues`・`componentRevisions`・`packs`・`appVersions`・`keys`〕・`notice`）。取り下げ用の鍵だけで確かめる。知らない欄は無視する（追記の2）。
- 機能を有効にするコードは、コードを止めるだけの鍵で署名した別の小さな一覧（`fprise-lifeplan-feature-code-revocations`。追記の2）でも止める。
- 期限切れの一覧も受け付けて、載っている取り下げは当て続ける（取り下げは安全な側のもの）。そのうえで、期限切れか、有効な一覧を30日を超えて取れていなければ黄色い帯（0017 の7）。
- `minAppVersion` より古いアプリ・`appVersions` に載った版は、閲覧だけ（計算と PDF の出力は更新してから）。

**封筒の形**: データ用・自動配信用・取り下げ用の封筒は、お知らせの一覧（0087。`app/schemas/notices.json`）と同じ形（`format`・`formatVersion`・`payload`・`signatures[]`〔`keyId`・`alg`=`ed25519`・`sig`〕）にそろえた。署名するのは `payload` のバイト列（お知らせと同じ）。封筒の形の名前は「中身の形の名前＋`-envelope`」。アプリ本体の目録だけは、Tauri の道具で署名するので `signature` 1つの形。

### 4. Mac の署名と公証の流れ

1. Apple Developer Program（法人の登録。発行元の名前は配布元の設定の `publisher`）の**アカウントの所有者**が、Developer ID Application の証明書を作る（所有者しか作れない）。キーチェーンから .p12 に書き出し、base64 にして CI の秘密の値 `APPLE_CERTIFICATE`、書き出しのパスワードを `APPLE_CERTIFICATE_PASSWORD` に置く。
2. 公証の鍵は App Store Connect の API キー（チームのキー。役割は「Developer」で足りる）。発行者 ID を `APPLE_API_ISSUER`、キーの ID を `APPLE_API_KEY`、.p8 の中身を `APPLE_API_KEY_P8` に置く（.p8 は1回しかダウンロードできない）。Apple ID とアプリ用パスワードの方式は使わない（人の Apple ID に結びつくため）。
3. 配布元の設定の `[signing] mac_signing_identity` に「Developer ID Application: <発行元の名前> (<チームID>)」を書く（秘密ではない）。
4. CI（`app/scripts/bundle.ts`）が、証明書と名前がそろっていれば署名の名前を Tauri の設定に上書きし（hardened runtime は有効）、API キーがそろっていれば .p8 を一時ファイルに書いて `APPLE_API_KEY_PATH` で渡す。Tauri が一時のキーチェーンへの取り込み・署名・公証・公証の結果の貼り付け（staple）をする。対象は Intel・Apple シリコン両対応の1つのビルド（`universal-apple-darwin`）。
5. 同梱する実行ファイル（AI接続口。0015）も同じ名前で署名される（Tauri が中の実行ファイルも署名する。署名した版で確かめる）。

- `.github/workflows/app-bundle.yml`（手で起動するかリリースのとき）は、秘密の値を環境変数として渡し、`app/scripts/bundle.ts` を呼ぶ。`bundle.ts` は `app/scripts/signing.ts` の `signingPlan` で段取りを決める:

### 8. Tauri の updater とのつなぎ方（入れる回の形）

```rust
// 取り下げの一覧で鍵の束から外してから、アプリの目録を確かめる（どちらも crates/distribution）
let ring = revocations::apply_to_ring(&ring, &rev);
let cat = app_catalog::verify(&catalog_bytes, &ring, saved.app_serial, now)?;
if let UpdatePlan::Offer { version, tauri_pubkey, required } =
    app_catalog::plan(&cat, &current, cohort, rev.min_app_version.as_ref())
{
    let updater = app.updater_builder()
        .pubkey(tauri_pubkey)                       // 確かめられた鍵（現用か次期）
        .endpoints(vec![LATEST_JSON_URL.parse()?])? // 配布元の設定の [endpoints] app
        .version_comparator(move |cur, rel| rel.version > cur && rel.version.to_string() == version)
        .build()?;
    // 裏でダウンロードし、終了時か「今すぐ再起動」で当てる（0017 の7。Windows は passive）
}
```

- updater の命令は画面に出さない（`capabilities` に `updater:*` を足さない。0016: 画面から呼べるのはアプリが定義した命令だけ）。
- 通信は本体の HTTP の部品の決まり（https・転送に従わない・許可したホストだけ。0017 の4）に合わせる（Tauri の updater が転送に従うかを、入れる回に確かめる）。
- `[keys] app_update` が空のビルド（開発・鍵の無いフォーク）は updater を登録しない。

## 理由

- **目録を先に確かめて鍵を選ぶ**: Tauri の updater の設定は公開鍵1本だが、実行中に `pubkey()` で差し替えられる。Tauri の署名には鍵の番号が入っているので、同じ鍵で署名した目録を先に確かめれば、どちらの鍵を渡せばよいかが分かる。updater を2回試す方法より、段階・一時停止・有効期限・通し番号も同じ場所で扱える。
- **目録をアプリ更新用の鍵（Tauri の形）で署名する**: リリースのときに使う道具と鍵が1つで済む（1人で回す前提）。Ed25519 の別の鍵にすると、アプリ本体の経路の鍵が2種類になり、入れ替えも2倍になる。
- **封筒の形をお知らせにそろえる**: 確かめる部品を1つにでき（お知らせの読む口も、鍵を入れる回にこの部品へ寄せられる）、発行の道具も1つで済む。署名の対象を `payload` のバイト列のままにしたのは、お知らせの形（0087）を変えないため。取り違えは中身の `format` の確認と、鍵の役割の分離で防ぐ。
- **期限切れの取り下げの一覧も当て続ける**: 期限は「新しい一覧が届いているか」の目安で、届かないことを理由に取り下げを外すと、古い一覧を見せ続ける攻撃より悪い（取り下げそのものを無効にできる）。
- **取り下げ用の鍵を一覧で外せない**: 外せると、漏れた1本でもう1本を外し、取り下げの経路を乗っ取れる。取り下げ用はオフラインで保管し、漏れる心配が最も小さい。
- **Windows は Azure Artifact Signing**: 5 の表のとおり。費用・CI との相性・証明書の更新の手間で最も軽い。日本の法人が対象になったことを、今の一次情報で確かめた。
- **MSI を最初から出す**: 企業の PC では MSI でしか入れられないことがある。Tauri は同じ設定で作れ、署名の段取りも同じ。

## 影響

- **後から変えると**: 目録の欄・封筒の形・`critical` の扱い・鍵の選び方は、配ったアプリが理解するもので、後から変えると古いアプリに効かない（0017・0022 と同じ）。目録に必須の欄を足すときは `critical` に載せ、形式の版を上げる。
- **守るべき決まり**
  - 秘密鍵・証明書・パスワードをリポジトリに置かない（テストの鍵は、テストの中で決まった種から作る使い捨てのものだけ。`crates/distribution/tests/data/` は使い捨ての鍵の公開鍵と署名だけで、秘密鍵は置かない）。
  - アプリ本体の目録と配布物は、同じ鍵で署名する。
  - 自動配信用の鍵で、許可表・取り下げの一覧・アプリ本体の目録に署名しない（部品が受け付けない）。
  - 重大な誤りの修正と取り下げは段階配信にしない（`percent` を 100 で出す。0022）。
  - 取り下げの一覧は、期限（初期値90日）の前に出し直す（取り下げ用の鍵はオフラインなので、人の作業になる）。
- **テストで確かめていること**（`crates/distribution/tests/distribution.rs`・`app/test/distribution-signing.test.ts`）
  - 本物の Tauri の道具で作った使い捨ての鍵の公開鍵と署名を読め、確かめられる（中身・注記の書き換え、別の鍵を拒否する）。
  - 4種類とも現用・次期のどちらでも受け付け、知らない鍵・役割の違う鍵・取り下げた鍵・書き換えを拒否する。1つの役割に3本は書けない。同じ公開鍵を2つの役割に使えない。
  - アプリの目録: 通し番号の古いもの・期限切れ・形式の版の MAJOR の違い・`critical` の知らない欄を拒否し、段階（組と割合）・一時停止・最低版（順番を待たずに受け取る）・`noDefer` で正しく決める。古い版へ戻さない。
  - パックの目録: 署名者の食い違い・取り下げ用の鍵・自動配信用の鍵の範囲の外（`addValue`・`modifyPeriod`・`changeStatus`・巻き戻しでない `removePeriod`・空・確認期間なし）・古い通し番号と版・期限切れ・ほかのホストを指す場所を拒否し、確認期間・段階・一時停止で待つ。ファイルの要約の食い違いを拒否する。
  - 取り下げの一覧: 取り下げ用の鍵だけで受け付け、通し番号の古いものを拒否し、最低版・取り下げた版・鍵の外し方・新しさ（30日・期限切れ）を正しく決める。取り下げ用の鍵は外れない。
  - CI の段取り: 秘密の値が無ければどの OS も署名せずにビルドし、空の秘密の値を渡さない。そろえば Mac は署名と公証、Windows は Azure Artifact Signing、更新のファイルは署名する。説明に秘密の値が入らない。

## 試作での確認

- 確かめる部品とテストは、ネットにつながずに動く（`cargo test -p distribution`）。本物の Tauri の道具（`tauri signer generate`・`sign`、2.12.1）で作った使い捨ての鍵で、署名の読み方が合うことを確かめた（要約してから署名する形 `ED`）。
- 署名した CI のビルド・公証・Windows の署名・配信元からの更新は、まだ確かめていない（証明書・鍵・配信元が無いため）。`bundle.ts --plan` で、秘密の値が無いときの段取りだけを確かめた。

  - **背景**: 上の追記で、コードの取り下げを取り下げの一覧（オフラインの取り下げ用の鍵）に入れた。利用者の判断で、返金などでコードを止めるたびにオフラインの鍵を出すのは手間なので、コードを止めるだけの手軽な鍵（CI の秘密の値などオンラインに置ける）を別に持つことにした。守りの決まりは「その鍵が漏れても、できるのはコードを止めることだけ（鍵・アプリの版・データパックの取り下げや、ほかの鍵の取り外しはできない）」。
  - **決めたこと**
    1. **鍵の束の6つ目の役割 `feature_code_revocation`**（`distribution::keys::Role::FeatureCodeRevocation`）。書き方は「鍵の名前:公開鍵」、現用＋次期の2本まで、ほかの役割と同じ公開鍵は使えない、開発用は `[dev_keys]`（`dev-fr1`）。作るのは `dist-keys keygen feature_code_revocation …`。**取り下げの一覧の `revoked.keys` で外せる**（漏れたら、オフラインの取り下げ用の鍵で外す。取り下げ用の鍵だけが外れない決まりは変えない）。2 の表に行を足した。
    2. **置き場所は、取り下げの一覧とは別の小さな一覧**（`/v1/revocations/feature-codes.json`、配布元の設定の `[endpoints] feature_code_revocations`。部品は `distribution::feature_code_revocations`）。封筒は 3 の形（`fprise-lifeplan-feature-code-revocations-envelope`）、中身は `format`（`fprise-lifeplan-feature-code-revocations`）・`formatVersion`（`1.0`）・`serial`・`issuedAt`・`expiresAt`・`featureCodes` だけ。確かめるのはこの役割の鍵だけ。この鍵では取り下げの一覧・パックの目録・お知らせ・アプリの目録に署名できない（それぞれの部品が役割で断る）。中身に鍵・版などを書いても読まない（知らない欄）。**アプリの取りに行く先は配信元（`updates.fprise.com`）のまま**で、依頼が2つになる（外部送信の一覧〔0012 の5〕の行を直した）。
    3. **止めるのは2つの一覧の和**（`feature_code_revocations::stopped_ids`）。取り下げの一覧の `revoked.featureCodes` は残す（オフラインの鍵で止めた番号は、手軽な鍵では戻せない）。アプリは先に取り下げの一覧を当て、そこで取り下げた鍵を外した束で小さな一覧を確かめる（外した鍵で署名した小さな一覧は、保存したものも使わない）。通し番号・有効期限（既定90日）・期限切れでも当て続けること・取れない／受け付けない一覧は無視して最後のもののままにすることは、取り下げの一覧と同じ（通し番号は別に数える）。画面の確かめの様子は2つをまとめ、2つとも取れたときだけ「確かめた」。
    4. **この鍵で止めたコードを、この鍵で戻せる**（小さな一覧は「今止めている番号の全部」で、外せば次に確かめたときに戻る）。
    5. **取り下げの一覧も小さな一覧も、知らない欄を無視する**（0110 の未確定「知らない欄があると一覧ごと受け付けない作りのままでよいか」を閉じた。`deny_unknown_fields` を外した）。前の版のアプリが知らないと危ない取り下げを足すときは、同じ一覧の `minAppVersion` で前の版の計算と出力を止める。読み方を変えるときは形式の版の MAJOR を上げ、`/v2/` に分ける（`/v1/` には最後の 1.x の一覧を出し続ける）。封筒（3。お知らせ・パックと共通）は `deny_unknown_fields` のまま（形を変えるときは封筒の形式の版で）。
    6. **道具**: `feature-code revocations new|open|add|remove|show` は、ふだんは小さな一覧の下書き（`~/.lifeplan-issuer/feature-code-revocations-draft.json`）を直す（`--draft` に取り下げの一覧の下書きを渡せば、その `revoked.featureCodes` を直す）。`open` は配信元の一覧を、配布元の設定の `[keys] feature_code_revocation` の鍵で確かめて下書きにする（CI と、手元で続きから直すとき）。署名は `dist-keys revocations sign <秘密鍵> <下書き> <一覧>` で、下書きの種類と鍵の役割が合わなければ止める。設定の1行の読み方は `distribution::config` に移し、本体の build.rs と道具が同じものを使う。
    7. **CI で止める**: `.github/workflows/feature-code-revocations.yml`（手で起動。止める番号・戻す番号を渡す。GitHub の環境 `feature-code-revocation` の秘密の値 `FEATURE_CODE_REVOCATION_KEY`。配信元の今の一覧を取って確かめ、番号を直し、署名して成果物に残す。配信元へ置く段は、配信元が決まってから足す）。手順は `docs/feature-codes-operations.md` の 3。
  - **理由**
    - **別の小さな一覧にした**: 同じ一覧に2つの署名の部分を持たせると、手軽な鍵の側を出し直すたびに、オフラインの鍵で署名した部分を壊さずに組み直す段が要り、2つの署名する人（CI と人）が1つのファイルを取り合う。取り下げの一覧の形（3 (3)・0017 の7）も変わり、前の版のアプリは知らない欄で一覧ごと受け付けなくなる。別の一覧なら、それぞれが自分のファイルだけを出し直せ、取り下げの一覧の形は変わらない。依頼が1つ増えるが、相手と送る中身は同じ。
    - **戻せるようにした**: 返金の取り消しや番号の打ち間違いを、オフラインの鍵を出さずに直せることが「手軽さ」の目的に合う。止めた番号を戻せないようにする（アプリが今までに見た番号を全部覚える）と、打ち間違いがオフラインの鍵でしか直せず、アプリの手元の状態も増える。漏れたときに戻されるのは、この鍵で止めた返金などのコードの機能だけで、新しいコードは出せず（発行の鍵は別）、データも消えない。戻されたくない番号は取り下げの一覧に写せばよい（`docs/feature-codes-operations.md` の 5）。
    - **知らない欄を無視する**: 一覧ごと受け付けないと、β の後に欄を1つ足しただけで、前の版のアプリには新しい一覧の取り下げが1つも効かなくなる（最後に受け付けた古い一覧のまま）。取り下げは安全な側のもので、知っている分だけでも当てる方が守りが強い。
  - **影響**: 配布元の設定に `[endpoints] feature_code_revocations` と `[keys]`・`[dev_keys]` の `feature_code_revocation` を足した。本体は2つの一覧を続けて取りに行き、この PC のアプリのデータ（`feature-codes/revocations.json`）に2つとも置く（`codeList`・`lastCodeList` を足した。前の保存の形はそのまま読める）。世帯ファイル・事務所データの形式の版、計算エンジン・計算の結果は変わらない。本番の鍵は作っていない（提供元が公開前に作る。手で作る鍵が2本〔現用・次期〕増え、現用を GitHub の環境に置く作業が増えた）。
